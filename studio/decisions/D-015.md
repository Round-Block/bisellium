How an opus branch reaches the trunk is a **setting**, not something the
studio decides for its users. Different teams want different flows; a
studio that hardcodes one is locked in, against the project's own
first decision (conventions first, any toolchain can produce the state).

The Patron's own flow, and the reference default:

- push to origin, then pull latest
- a new opus branch rebases onto the current trunk before work lands
- conflicts are cleared on the branch
- a PR carries it to the trunk
- the QA agent (`censor`, the single review gate per D-014) reviews the PR

Other officinae may want fast-forward only, a merge commit, or no PR at
all. The manifest carries the choice; `bisellium merge` reads it.

Consequences worth naming before anyone builds this:

- **Rebase invalidates evidence, and nothing currently catches it.**
  Rebasing opus B onto a trunk that now contains opus A changes B's source
  tree, so B's `tree:` certificates no longer describe what ships.

  This entry originally claimed `check` would catch that "for free" and
  that `merge` therefore need not re-run gates. **That is false**, caught
  by round-3 review of PR #2 on 2026-09-19. `probatio.certifies.stale` is
  scoped to ACTIVE opera (`check.ts`), on the deliberate reasoning that a
  done item's certificate is history — and `mergeOpusBranch` refuses
  unless the opus is `done`. The rule can never fire for any opus that
  merge accepts. Verified: flipping W-026 to `done` takes the finding from
  3 to 0.

  So the open question stands and needs an answer: either `merge` re-runs
  the gates itself, or it refuses when the certificates do not match the
  post-rebase tree. It cannot lean on a rule that does not apply to it.
- ~~**`process.*` rules must read the setting.** A rule that flags "no PR"
  or "not rebased" is wrong for an officina configured the other way.~~
  Struck 2026-09-19: no `process.*` rule reads or assumes a merge strategy
  — the ids are `process.cascade`, `.review_tier`, `.tdd`, `.checkpoint`,
  none branching-aware. Nothing is wrong for a differently-configured
  officina, so this clause was vacuous. It stays struck rather than erased
  because it was cited as a known gap in PR #2.
- **Scope spans two opera.** The rebase half is W-026 (branching and
  merge coordination). The PR half has no home yet: W-026's brief defers
  "GitHub PR creation (manual or patron-as-agent, W-028)" to W-028, but
  W-028's own brief never picked it up — it contains no mention of PR or
  GitHub at all. An opus must be opened for it. (This entry originally
  asserted W-028 owned it, inferred from W-026's deferral without reading
  W-028's brief; corrected 2026-09-19 after a review caught it.)
- `gh` is authenticated in this environment, so PR creation is available
  rather than hypothetical.

The same principle extends to harness settings (Claude Code hooks,
subagents, commands): surfaced as configuration the user can see and
change, not baked in. A settings screen is on the backlog for that.
