**A check rule for red provenance: `bisellium red` records a working-tree
identity, and a rule verifies it — superseding the tree-ancestry proposal.**

The censor has now ruled on red ordering four times in prose (W-046's
stash, W-046's re-record, W-067's bundled reds, W-071's stub-after-
implement), and "process enforcement is a check rule or a hook, never a
memory or prose" forbids a fifth. Two mechanisms have been proposed:

1. **Tree ancestry** (raised at W-067's round): a red's `tree:` hash must
   name an ancestor of the commit introducing it. **Measured insufficient
   at its first live test**: W-071's five stub-after-implement reds pass
   it cleanly — `dirty:<spec-gate-HEAD>` is byte-identical whether the
   working tree held prescribed skeletons or stubbed-out finished code.
   The header names the committed HEAD, never the working tree's content.

2. **Working-tree identity** (raised at W-071's round, this petitio):
   `bisellium red` additionally records a content identity of the working
   tree over the opus's declared files (a hash of the tracked-file diff,
   or per-file content hashes). A later rule — or the censor,
   mechanically — can then verify the recorded state actually matches the
   brief's prescribed red state (skeletons, a named parent overlay, a
   mutation of a specific site), making skeleton-first and
   stub-after-implement distinguishable BY ARTIFACT rather than by the
   builder's candour.

The ask: adopt mechanism 2 as an opus (the `red` command change plus the
verifying rule), and record mechanism 1 as considered-and-refuted with
W-071 as the counterexample. D-024's kill condition already names this
mechanism — granting this petitio is what retires that waiver class.
