## Intent

Decree family: red-tree-order

Red order: one at a time

The decree: **a brief that carries the line above opts in to D-036's one-at-a-time order. For such a brief, `bisellium red <id> --behaviour <n>` first runs every earlier behaviour's recorded red command on the same clean tree and refuses unless each passes; `bisellium check` blocks an active opus's red whose tree equals an earlier behaviour's red tree; `next` orders test, red, log commit and implementation one behaviour at a time; in an officina that declares `brief_behaviour_limit` (the real studio does), `ready` refuses a new brief without the line. A red never certifies a repository other than the one its command ran in, and a Git identity it records in the studio's own repository (any of its worktrees) is hashed with the officina's exclusions, and an opted-in red's HEAD must be reachable from `opus/<id>` when recorded, so its `# tree:` names a commit on the branch the host replay walks; an unrelated repository is hashed with no exclusions, as today.**

Evidence of the class:

- W-161 (L-085, `ci/W-161-review-1.log` #2): reds 04 and 05 certified one pre-implementation tree although behaviours 3 and 4 had to be built first.
- W-167: reds 1–5 were recorded on the bare test commit (all `tree:a6f528…`, the source tree of the original test commit `d953417`), because `next`'s reds order says "phase 1, reds only, implementation absent" (`next.ts` `dispatch`, line 810). Two re-recording attempts then hit the facts below.
- W-167 fact (a): a red recorded with `--cwd` in a temporary worktree and `--studio` in another one hashes with no exclusions (`hashRepo` excludes only when the studio lies inside the hashed root), so its `# tree:` matches no branch commit and the host falls back to the commit that introduced the log (W-134).
- W-167 fact (b): those logs were committed at the branch tip, so the fallback replays them on the finished code, they pass, and the mint refuses. The only remedy was rewriting unpushed history, which the permission classifier blocks as audit tampering.
- `next` prints `--repo .`, and `--repo` overrides the hashed repository, so a red run in one worktree can certify another (W-021 B2 again).

Where the proof lives. `red` is the only place that runs the prerequisite rows, at record time, on the tree it certifies. `check` verifies only what logs prove without running anything. The host replay (`scripts/run-builder-host.mjs` ~665–780) stays unchanged: it already replays each target red at the commit whose source tree (excluding the studio, `.bisellium` and `source_excludes`) equals the log's `# tree:`, and after a rebase at the parent of the unique studio-only commit that introduced the log. Behaviour 1 makes `# tree:` equal that commit's source tree in every worktree of the studio's repository; behaviour 4's order (log committed alone, before the implementation), when followed, makes the rebase fallback land on the red's own tree. Re-running prerequisites in the host is the upgrade if a wrong-tree red ever passes both `red` and `check`.

Grandfathering. Only a brief carrying the line has a prerequisite contract. No historical brief carries it, so no historical log gains a finding, and W-167 (now merged) gains none. `ready` adds the requirement only on entry, and only where `brief_behaviour_limit` is declared, so opera already past `ready` are never re-admitted against it. W-166's own brief carries the line: from red 3 on, the `red` under construction proves its own prerequisites.

Threat model (D-045): mistakes, not adversaries. `red` can show that the named commands exited 0 having passed at least one test, on one clean tree unchanged outside the exclusions, as `git status` reports it (files Git ignores are not seen). It cannot show that a test asserts the intended semantics, that a header was not edited by hand, or that a test did not change and restore the tree.

## Interfaces

// The repository a red certifies: the Git root containing execCwd. A --repo that is a Git work tree must be that

`hashRepo(repoDir)` applies `[<studio relative to its own Git root>, ".bisellium", ...source_excludes]` whenever `repoDir` and the studio belong to one repository: the same `git rev-parse --path-format=absolute --git-common-dir`, canonicalised. A linked worktree of the studio's repository therefore hashes exactly as the host's `sourceCommits` map does. An unrelated repository keeps today's empty exclusion list.

For every red, before any command runs, `runRed` refuses (exit 2) a `readSourceExcludes` error; today a scalar is spread into one-character exclusions. After the target runs, a `spawnError` (the executable was never started, e.g. a misspelt name) exits 2 and writes nothing; today it is recorded as exit 1. A command that starts and then fails for an environment reason (a missing module) is outside this guarantee and keeps today's handling: `next` counts a module-load red as missing and the host replay's poison list refuses it.

For an opted-in brief, `runRed` behaves as below; without the line it behaves as today.

1. Read `opera/<id>.md` and its `spec:` brief through `readContainedRegularFile`.
2. Run `readRedOrder` on the brief.
3. Require a clean `tree:` identity, the command's cwd equal to that repository's canonical root, its `HEAD` an ancestor of or equal to `refs/heads/opus/<id>` there (`git merge-base --is-ancestor HEAD refs/heads/opus/<id>` exits 0; an absent branch refuses), and every target argument non-empty and free of whitespace. The host replay runs `# command:` split on whitespace at the checkout root, so this is the shape it can already replay; every opted-in log therefore re-splits to the argv it ran.
4. For each behaviour `k` from 1 to `n-1`, read `ci/reds/<id>/<kk>.log` and split its `# command:` on whitespace, as the host replay does.
5. Run each command at the same root, in order. Each must satisfy `prerequisitePassed`.
6. Run the target. It must exit non-zero, and `hashRepo` must still return the step 3 identity. That identity covers committed source plus `git status` outside the exclusions, so a change the target leaves outside them to a tracked file, or a new untracked file Git does not ignore, is refused; a file Git ignores (`.gitignore`, `info/exclude`) is not seen, a stated limit; a change under the studio, `.bisellium` or `source_excludes` is not seen, by design.
7. Write the log, unchanged in shape.

Progress goes to stderr. Stdout keeps its one recorded line.

`next`'s reds order, with `k` the lowest missing behaviour (`studioRel` as today):

```text
dispatch <sella> (phase 1, one behaviour at a time, D-036), in .worktrees/<id>, from behaviour <k> through <n>, for each in turn:
1. commit the behaviour's test, its rows failing;
2. from .worktrees/<id>: bisellium red <id> --behaviour <b> --sella <sella> --studio <studioRel> -- <cmd…>
3. commit the red log alone (studio files only), before any implementation;
4. implement the behaviour until its rows and every earlier behaviour's rows pass, and commit.
If red refuses, finish the earlier behaviour it names; never re-record a red at the tip.
A red recorded on the wrong tree is re-recorded with --cwd in a detached worktree at the commit it belongs on, after the branch's last rebase, and its log committed at the tip; never rewrite history.
```

With no missing behaviour and a red finding, the order's first line names the finding (`why`) and the order keeps only its last two lines.

### Input domain

In both cases it writes nothing. `check` emits one `opus.red_evidence` block. `ready` exits 1 with the record and event log byte-identical. `next` adds no read: its reads are today's (rows below, with their existing rejectors and stated limits), and W-166 changes only the order text it names at `reds`.

## Out of scope

- Re-running prerequisites in the host replay, or changing W-134's rebase fallback. After a rebase a corrected log's tree no longer matches, so a correction is re-recorded after the branch's last rebase (stated in the order).
- Inferring prerequisites from prose such as "after behaviour 1"; a subset of earlier behaviours as prerequisites.

## Defaults for the Patron to veto

1. One line in the brief, `Red order: one at a time`, switches the rule on. Old briefs without it are history and are never re-read against it.
2. A behaviour's prerequisites are all earlier behaviours, run with the commands their own reds recorded.
3. A prerequisite must pass at least one test; a command that runs no test does not count.
4. `--repo` may confirm the repository the command runs in, never choose another.
5. `check` blocks only what the logs prove alone: a red on the same tree as an earlier behaviour's red.
6. `next` keeps one builder dispatch, which works through the behaviours in order.
7. New opera need the line at `ready` where the officina declares `brief_behaviour_limit` (the real studio does). A brief signed but not yet ready (W-068) needs the line and a new signature.
8. A wrong red is fixed by re-recording it at the right commit in a side worktree, after the last rebase, never by rewriting history.
