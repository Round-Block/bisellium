## Intent

W-348 gave a `kind: ui` opus its own spec pair (`ui_spec_signer`, `ui_spec_reviewer` in `bisellium.yml`) and left one gap as a stated limit: next chooses the pair from records that are not the ones its spec evidence lives in. Two reviews named the gap.

- `ci/W-348-spec-2.log` blocker 1: after the branch, the spec is signed in the opus worktree and `verdict --studio .worktrees/<id>/studio` trusts the worktree's manifest, but next takes the pair from the main checkout's manifest. A pairing change on the branch lets next order one signer while verdict holds another to the ledger.
- `ci/W-348-spec-4.log` blocker 1: an absent, unreadable, malformed or non-mapping record collapses to "no record" (`recordOf`), and next then falls back to the trunk's record, so it can order the wrong signer. No row went through `gather`.

On master c4a0dbac every read of kind or pairing for the spec rungs, and the record each reads, is:

- `gather` (`next.ts:739`–`:743`): `design`, the signer every later reader uses, is chosen from `(branchRecord ?? trunkRecord).kind` and the **main checkout's** manifest. Before the branch `branchRecord` is undefined, so the kind is the **trunk's** (committed master), not the main checkout's record where the spec is signed. After the branch an unreadable branch record falls back to the trunk's.
- `deriveNext` (`:944`, `:959`): `readSpecReviewer(f.manifest, { ...(branchRecord ?? trunkRecord), state: trunk state })`. The same two fallbacks, and the main checkout's manifest after the branch.
- the fast lane (`:968`–`:969`): the trunk's record, plus the branch's once it exists. Before the branch the main checkout's record is not read.
- the worktree's ui-lead test and the pending ui-lead test (`:997`, `:1028`): `f.branchRecord.kind`. With a usable worktree that record is the worktree's, so these already read the owner.
- `reviewedSpec` (`:374`): `recordOf(src, id).kind` of the source being judged. That is the owner, except when `ci/` cannot be listed and the committed branch is judged instead of the worktree.
- `uiSpecProblems` (`:797`), W-338's ui-lead input check: before the branch, `branchRecord ?? trunkRecord`, so the trunk's. It stays so (Limits).
- consumers of `f.design`: replay red attribution (`:1281`), `signedAfter` for the class loop (`:1442`), the default dispatch sella (`:1571`), the replayed red's sella and its commit (`:2062`, `:2069`), the signed and re-signed spec commits (`:2109`, `:2173`), and ready attribution's fallback (`:2475`).

Other reads of kind are outside the spec rungs and unchanged: `automatedGates` (`:524`, certificates), the done rung's UI verify (`:1241`), the build review's UI input (`:798`, `:799`, `:2281`) and `uiRulingWait` (`:1253`).

The design names one **spec owner** per gather. Before `opus/<id>` exists it is the main checkout: its `opera/<id>.md` and its `bisellium.yml`, the files that `verdict --studio studio` reads. After the branch it is the usable opus worktree: its record and its manifest, the files that `verdict --studio .worktrees/<id>/studio` reads. Without a usable worktree it is the committed `opus/<id>`: its record and manifest read through `git show`. The spec rung reads the kind and the pairing only from the owner. The signer that `gather` gives every later reader is the spec rung's own `readSpecReviewer` selection over the owner. The owner's record is read strictly: absent, unreadable, malformed, without front matter, or not a mapping is an error. So is an owner manifest that cannot be read, does not parse or is not a mapping, after the branch. Next then holds at spec, naming the record and the owner, and orders nothing. It never reads the trunk's record or the main checkout's manifest in their place. A readable record with no `kind` keeps the default pair, as any other non-`ui` kind does.

verdict is unchanged: it already reads the record and manifest of the `--studio` it is given, and every spec order next names carries the owner's studio. When the worktree is unusable, next orders no spec write (W-206), so no verdict is ordered against the committed branch.

Revision 2 (`ci/W-355-spec-2.log` #1): owning the manifest is not enough if next accepts a manifest the ordered verdict refuses. The spec verdict reads the design collegium through `readDesignMagister` (`verdict.ts:426`): no `design` row means the architect, exactly one row must name a nonblank magister, and anything else exits 2. On master `readSpecReviewer` returns a valid UI pair before it looks at that row, and without `spec_reviewer` it takes the first row's magister. A duplicate or blank design row in the worktree thus had next order a signer whose verdict then refused. `readSpecReviewer` now applies `readDesignMagister` itself, exported from `verdict.ts`, before it returns either pair.

Threat model: mistakes, not adversaries (D-045).

## Interfaces

**`readSpecOwner(src, id, where, manifest)`** (next, new) returns `{ where, record, manifest }` or `{ error }`:

1. `src.read("opera/<id>.md")` (the contained `fsSrc` for a checkout, `git show` for the committed branch) returns nothing: `opera/<id>.md in <where> is absent or unreadable; …`.
2. `parseFrontMatter` throws (no front matter, YAML that does not parse): `… is malformed (<first line of the parser's message>); …`.
3. The front matter is not a mapping: `… is not a mapping; …`.
4. `manifest()` errors: `<that error>; the spec's seat pairing is read only from the checkout that owns its evidence, <where> (W-355)`.

Every record error ends `the spec's kind and seat pairing are read only from the checkout that owns its evidence (W-355)`. `<where>` is `the main checkout (<studio>)`, `.worktrees/<id>/<studio>` or `opus/<id>`.

**The owner** (`gather`): before the branch (`tip` undefined), `readSpecOwner(fsSrc(<studio>), …, () => ({ manifest }))`, with the main checkout's manifest read as today. With a usable worktree, the worktree's `fsSrc` and `readWorktreeManifest(<worktree studio>)` (reused: an unreadable, unparsable or non-mapping file is an error). Otherwise the committed branch's `gitSrc` and `branchManifest`. `branchManifest` (new) reads `bisellium.yml` through the same source and parses it with `yaml`; absent, unparsable or non-mapping is an error.

**The signer** (`gather`): `design` is `readSpecReviewer(owner.manifest, { ...owner.record, state: <trunk state> }).signer`. When the owner or that read errors, it is the design magister, as before; the spec rung then holds before any reader of `design` runs.

**`readSpecReviewer(manifest, record)`** (next, extended): it calls `readDesignMagister(manifest)` once. On a `kind: ui` record with a valid UI pair, an error from it is returned before the UI pair. On the default pair without `spec_reviewer`, it is returned instead of the signer. With `spec_reviewer`, the existing seat and design-row checks run first, and the error is then returned as `bisellium.yml#spec_reviewer: <error>`. A manifest that is not a mapping keeps its existing early return (the architect, no reviewer). Every other return is unchanged.

**The spec rung** (`deriveNext`): after the greenlight rung, `if ("error" in f.specOwner) return hold("spec", f.specOwner.error)`. `readSpecReviewer` reads the owner's manifest and record with the trunk's state, as before. The fast lane's records are `[trunkRecord, owner.record]`: every one must be a native non-`ui` kind, as before. Before the branch that now includes the main checkout's record. The worktree's ui-lead tests and `reviewedSpec`'s ui-lead skip read the owner's kind. The rung runs on every pass, so an unreadable owner record holds every later step at spec until it is restored. Once the trunk record is done, `afterDone` comes first and is unaffected.

Promise owner: before the branch, the spec's kind comes from the main checkout's record and its pair from the main checkout's manifest; after it, both come from the opus worktree, or from the committed branch when there is no usable worktree. The signer `next` orders, the reviewer and model it orders, the fast lane's kind and the worktree's ui-lead classification all read that owner, pinned by `W-355-b1` "the main checkout's kind: ui orders the UI signer", `W-355-b1` "a main-checkout record with no kind keeps the design magister", `W-355-b2` "the worktree's pair orders its UI signer", `W-355-b2` "the main checkout's pair does not reach the branch" and `W-355-b2` "the committed branch's pair wants a UI signature" — limit: the gate state still comes from the trunk record, unchanged, and the readers of `design` after the spec rung (red attribution, `signedAfter`, commits) take it by construction from the same `readSpecReviewer` call. Those readers are unpinned here.

Promise agree: the signer and reviewer `next` orders are the seats `verdict --studio <the order's studio>` treats as signer and reviewer. Both read the same studio's record and manifest, through `readUiSpecPairing` and `readDesignMagister`. A design collegium that the verdict refuses holds `next` at spec on either pair instead of ordering a signer, pinned by `W-355-b2` "the worktree verdict accepts the UI signer", `W-355-b2` "the worktree verdict accepts the design magister", `W-355-b4` "the UI pair: a duplicate design row holds", `W-355-b4` "the default pair: a blank design magister holds" and `W-355-b4` "the engineering pair: a blank design magister holds" — limit: `next` is stricter than `verdict` on `spec_reviewer`'s seat (W-162), so it may hold where a verdict would be accepted, never the reverse; `verdict` is unchanged and reused (D-076 E); its own ledger rule is pinned by `W-348-b3` and `W-306-b1`, not here.

Promise fail-closed: an invalid owner record or post-branch owner manifest holds at spec with no order or command, as pinned by `W-355-b3` "a record absent holds", "a record malformed holds", "a record without front matter holds", "a record not a mapping holds", "an unreadable record holds" (each in the main checkout and in the worktree), "a malformed worktree manifest holds", "a non-mapping worktree manifest holds", "the committed branch's absent record holds" and "the committed branch's malformed manifest holds" — limit: before the branch, the unchanged main-manifest reader remains a stated limit: a read or parse failure, and a parseable non-mapping value, can stop next before the spec rung, so no no-setting-ladder behaviour is promised. Absent and unreadable share one message, because the reused readers (`readContainedRegularFile` under `fsSrc`, `git show` under `gitSrc`) do not tell them apart.

Limits, stated:

- Unchanged code the promises lean on is stated, not guaranteed (D-076 E): `parseFrontMatter` and the `yaml` parser; `readContainedRegularFile` and `fsSrc`; `git show` and `gitSrc`; `readManifest`, `readWorktreeManifest`, `readSpecReviewer`, `readUiSpecPairing`, `readTip`, `opusWorktree`; the strict sequence readers (`readSpecSignature`, `readSpecReview`, `signedSpec`, `reviewedSpec`'s grammar); and `runVerdict`.
- When the worktree is usable but its `ci/` cannot be listed, the committed branch's spec is judged (W-206) while the kind and pairing come from the worktree. The two can differ only when an uncommitted worktree edit changes the kind or the pair; the rung's existing uncommitted-work holds then decide.
- `uiSpecProblems`, W-338's ui-lead input check, keeps its record: before the branch the trunk's, after it the worktree's (the owner's). A `kind` changed in the main checkout and not yet committed is therefore read for the pair and the fast lane but not for the ui-lead input until it is committed. Reading the main checkout's record there flips `W-275-b3` (`next-ladder.test.ts`), whose done-rung fixture marks the record `kind: ui` in the main checkout after cleanup with no ui-lead input; the prototype tried it and kept the record.
- The build review's UI reads (`uiReviewProblems`, `uiReviewInput`, the review perform's `branchRecord` kind) and the certificate's gate set keep their records; they are not spec rungs.
