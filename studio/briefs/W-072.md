# W-072 — the vendor-spend sentinel: `npm test` fails if any test invokes a real vendor binary

Spec of record, signed by the architect, 2026-09-25. **Revision 2**, after
Sol's red-team pass: AMEND-FIRST, 5 lands / 4 held. Sol has attacked
revision 1; it has not reviewed revision 2, and this remains the
architect's document alone. The amendment log is at the end; every land is

**Rev 2 renumbered the behaviours.** Old → new: 1→1, 2→2, 3→6, 4→7, 5→8,
6→10, 7→11, with 3, 4, 5 and 9 new. Any red recorded against revision 1's

## Intent

`npm test` spawns roughly sixty node processes. Several of them reach
production code whose default argument is a **real vendor CLI**:

| Site | Call | Cost |
|---|---|---|
| `packages/shim/src/harness/claude-code.ts:132` | `spawnSync("claude", args)` | **a turn — real money** |
| `packages/shim/src/harness/codex.ts:227` | `spawn("codex", args)` | **a turn — real money** |
| `packages/shim/src/harness/catalog.ts:46` | `execFile("codex", ["debug","models"])` | $0, but real vendor contact |
| `packages/shim/src/harness/catalog.ts:75` | `execFile(bin, ["--version"])`, both vendors | $0 |
| `claude-code.ts:177`, `codex.ts:279` | `--version` | $0 |
| `packages/providers/src/index.ts:181` | `spawn(bin, args)` — manifest-supplied | unknown |

Nothing mechanical keeps a test away from any of them. What keeps the suite
honest today is **convention**: `apps/server/test/server.test.ts:69`
comments that `listModels` "defaults to must not be called" and every test
routes through a `baseOpts` helper that injects a stub;
`packages/cli/src/tick.test.ts:76` spreads a `NO_PROBE` object for the same
reason. I checked every call site on this tree and the convention is
currently held — no `startServer(` bypasses `baseOpts`, no `runTick(`
omits `NO_PROBE`. **That is the strongest possible argument for this opus,
not against it:** the suite is one forgotten spread away from billing the
Patron, and the thing standing in the way is a comment.

The censor has already watched it fail. `apps/server/src/http.ts:830` reads
`createListingCache(opts.listModels ?? codexListModels)`, and the W-065
censor rounds verified that a test forgetting the injection shells out to
the real `codex`. That verification was done by PATH-shadowing the vendor
binaries — the prototype this opus makes permanent.

CLAUDE.md's standing rule is that mechanical work is a script you write, run
and keep. A comment saying "must not be called" is the prose form of a
guard. This opus is the kept script.

## Placement: test infrastructure at the spawn boundary, inside the `tests` probatio

The coordinator asked for an argument rather than an assumption. Three
candidates:

**A check rule — no.** `check` reads a tree at rest. This guard's subject is
a *runtime event*: did a process get spawned during a test run. A snapshot
cannot see it. The precedent is explicit and recent: D-021 refused a check
rule for the one-writer discipline on the same grounds — *"The violation is
about which ref a write landed on, and a tree snapshot cannot see that."*
Same shape, same answer. The standing rule "process enforcement is a check
rule or a **hook**" is satisfied by the other arm: a PATH shadow is a hook
at the process-spawn boundary, which is where the wallet is.

**A new probatio — no, and unnecessary.** `studio/bisellium.yml:24` declares
`tests` as `command: "npm test -s"`. Put the sentinel inside `npm test` and
**every opus's `tests` gate already certifies it**, against the tree hash it
already certifies, with no manifest edit, no new gate to plumb through six
readers, and no new officina record kind (a stated constraint). A separate
probatio would also be per-opus, and this property is per-run.

**Plain test infrastructure — yes.** It rides the command every gate, CI job
and `bisellium ci` invocation already runs.

## Mechanism: PATH shadow, adjudicated out of band

Five parts. Part 2 is what makes it work at all; parts 4 and 5 are what
revision 1 got wrong.

### 1. The shadow

`test/bin/claude` and `test/bin/codex`, checked in, mode 755, executable
`.mjs` with a `#!/usr/bin/env node` shebang (the house precedent is
`packages/shim/test/fake-harness.mjs` and `scripts/*.mjs`). The runner
prepends `test/bin` to `PATH`. Any process in the suite that resolves the
bare name `claude` or `codex` gets ours.

**Why PATH and not a `--import` preload that patches `child_process`.** A
preload is not inherited by the ~60 child processes unless smuggled through
`NODE_OPTIONS`; `shell: true` invocations route around the Node API; and a
worker re-importing `child_process` escapes the patch. Wrapping six
functions (`spawn`, `spawnSync`, `execFile`, `execFileSync`, `exec`,
`execSync`) for the whole suite is also the kind of invasive cleverness that
corrupts every test at 3am when it is wrong. PATH is boring and reviewable.
The `NODE_OPTIONS=--import` variant is the **documented upgrade path** if the
static pin in behaviour 10 ever proves insufficient — it would cover
arbitrary `opts.env.PATH` and absolute paths, at the cost of patching the
process API for every test in the repo. Not now.

**No nested `npm run` — measured, and this is land 1.** Revision 1 had the
runner call `npm run -s test:suite`. That breaks the shadow's precedence,
and by more than Sol claimed. npm prepends `node_modules/.bin` **for every
ancestor directory** ahead of whatever PATH the caller supplied:

```
caller sets PATH=/SENTINEL:…
  npm run -s outer  → PATH[0..2] = [".../npmpath/node_modules/.bin",
                                    "/tmp/claude-1000/node_modules/.bin",
                                    "/tmp/node_modules/.bin"]
  npm run -s inner  → same; /SENTINEL is not in the top three at all
  sh -c '…'         → PATH[0..2] = [".../npmpath/sentinel", …]  ← survives
```

So a `node_modules/.bin/claude` anywhere up the tree would win. **The runner
therefore executes the suite through `sh -c` directly**, never through a
nested `npm run`, and builds PATH as
`<repo>/test/bin : <inherited PATH>` — the inherited PATH already carries
`node_modules/.bin` from the outer `npm test`, so tooling that needs it
still resolves, one position behind the sentinel. Behaviour 5 pins the
ordering so a future convenience refactor back to `npm run` fails loudly.

**Why the shadow reaches a locked-down spawn — and the one place it does
not.** W-049 projects every vendor spawn's environment onto a ten-name
allowlist (`packages/shim/src/harness/env.ts:21`) in which `PATH` is the
first entry, copied verbatim. So an *inherited* PATH survives `harnessEnv`
and lands where it must (behaviour 7 pins it; if a future amendment drops
`PATH` the sentinel silently dies and that assertion says so).

But `harnessEnv` copies **the caller's** PATH, not the runner's — and land 7
is that tests legitimately supply their own. `packages/cli/src/harness-env.test.ts:112`
builds `PATH: ${binDir}:${dirname(process.execPath)}:/usr/bin:/bin`, which
excludes `test/bin` entirely and *includes* two system directories where a
real vendor may live. Today that site is safe because `binDir` holds a stub
that resolves first. It is safe by aim, not by construction.

**So the claim narrows, honestly: the shadow guarantees inherited-PATH
vendor calls.** A test that builds its own PATH is outside the runtime
guard, and is covered instead by behaviour 10(c)'s static pin — every
test-supplied PATH must either contain the shadow dir or contain no system
binary directory. That pin is checkable, and it converts land 7 from a
silent hole into a named boundary with an assertion on it. No PATH-based
mechanism can do better: a caller that constructs an environment can always
exclude any directory, which is why the alternative is the `NODE_OPTIONS`
patch above and not a cleverer PATH.

### 2. The adjudication — a file, not an exit code

**This is the crux, and it is why the naive version of this opus does not
work.** The shim cannot simply exit non-zero, because the vendor call sites
are built to survive vendor failure:

- `codexListModels` **rejects** on any failure, and `createListingCache`'s
  existing `catch` handles the rejection (`harness/catalog.ts:36-43`).
- `harnessVersions` maps *any* error to `undefined` **by design** —
  "A vendor that is absent, fails or times out yields `undefined` for that
  key" (`catalog.ts:69-71`).

A non-zero exit from the shim is therefore swallowed, the test goes green,
and the sentinel has achieved nothing but a slower suite. Scanning the
child's stderr for a marker fails for the same reason: `execFile` captures
stderr into a callback that never prints it.

So the shim writes a **violation line to a file**, and the runner adjudicates
after the suite finishes. A `catch` can swallow an exit code; it cannot
unwrite a file.

**The file is `<repo>/.bisellium/vendor-violations.log`.** That path is
chosen, not incidental: `.bisellium/` is already in `.gitignore`, and
`verify`'s exclusion set already lists `.bisellium` — so the file cannot
dirty the source tree, cannot mint a `dirty:` certificate, and needs no new
ignore rule. The shim locates it from its own `import.meta.url`, needing no
environment variable at all, which matters because `harnessEnv` would strip
any custom variable before the shim could read it. `appendFileSync` in
`O_APPEND` mode is atomic for lines this short, so parallel test processes
within one run cannot interleave a partial record.

**One run at a time, enforced by a lock (land 9).** A fixed log path plus a
"delete the stale log first" step is a cross-run race: two concurrent
`npm test` runs in one checkout share the file, and either runner can delete
violations the other has already written, before the other adjudicates. The
fix is an exclusive lock held for the whole guarded run —
`.bisellium/vendor-sentinel.lock`, created with `open(…, "wx")`, carrying the
holder's pid and start time, released in a `finally`.

A second runner finding the lock held **refuses and exits non-zero**: two
concurrent suites in one checkout already contend for temp fixtures and git
state, so serialising them loses nothing anyone wants. A lock whose recorded
pid no longer exists is taken over rather than being a permanent wedge after
a `SIGKILL`.

```
// ponytail: one lock per checkout, so two runs serialise instead of
// interleaving. Upgrade path if parallel suites ever matter: run-scoped
// log paths, which need the shim to learn its run id — and it cannot be
// told through the environment, because harnessEnv strips everything
// outside its ten names.
```

Each line carries the binary, the argv, the cwd, and the **calling
process's command** read from `/proc/<ppid>/cmdline` — so the failure says
*which test did it* rather than merely that something did.

```
// ponytail: /proc is Linux-only; CLAUDE.md pins this repo to WSL. On a
// platform without /proc the line still appears with the caller unnamed —
// never omitted, never fatal. Upgrade path: ps(1) if a non-Linux adopter
// ever needs the attribution.
```

### 3. Opting in to a real vendor, on purpose

The probe battery (`bisellium probe`) and the W-046-class attended smokes
must stay runnable. **The opt-in is that the shadow is installed by the
`test` script and by nothing else.** An attended run invokes the command
directly and never sees `test/bin` on its PATH.

There is deliberately **no `BISELLIUM_ALLOW_VENDOR` escape hatch**, and the
reason is measured rather than aesthetic: `harnessEnv`'s allowlist has no
room for a custom name, so such a variable would be stripped on exactly the
spawn paths that matter and the hatch would be unreliable where it counted.
An opt-in that works only sometimes is worse than none.

### 4. Fail closed, and prove activation rather than assert it

Revision 1 let the runner "announce inactivity and run the suite anyway" when
it could not install the shadow. **Land 8: that is fail-open, and it permits
exactly the spend this opus promises to fail.** A wallet guard whose
degraded mode is "no guard, but loudly" is not a guard; the announcement
scrolls past in sixty invocations of output and the suite goes green.

The runner's preflight, all of it before the suite is spawned, any failure
exiting non-zero **without running the suite at all**:

1. `mkdir -p .bisellium` and confirm it is writable. `.bisellium/` is
   gitignored and therefore **need not exist after a fresh clone** — rev 1
   assumed it did and only deleted a stale log.
2. Both `test/bin/claude` and `test/bin/codex` exist and pass
   `accessSync(X_OK)`. A shim git checked out without its exec bit is a shim
   that never fires.
3. **The activation self-test.** Execute `test/bin/claude --version` by
   absolute path, confirm a violation line appeared, then clear it. This
   proves the shim fires *on this machine, in this checkout, right now* —
   evidence produced, not assumed — at a cost of one node startup and no
   vendor contact whatsoever.
4. Acquire the lock (above).

**No platform exemption and no escape hatch.** A platform that cannot run the
sentinel cannot run `npm test`. CLAUDE.md pins this repo to WSL, so the
exemption would buy nothing real and would reintroduce the fail-open hole it
was meant to describe. An adopter on an unsupported platform gets a clear
refusal naming the reason, which is a better outcome than a suite that
silently stops protecting them. Silence inside an expected-good path is a
class this officina has already paid for (retro-22: "an expected-red CI job
hides real anomalies inside it").

### 5. The dynamic binary: closed by an injection pin, not by shadowing `npx`

Land 4 says my revision-1 "deliberately open hole" must close, and it is
right that *"unreachable today" is load-bearing luck* which contradicts an
opus whose purpose is removing injection-by-convention. Sol's amendment was
to restructure `quotaAxiSource` into `{bin, args}` and **shadow its launcher,
"including `npx` if retained"**.

**Measurement says `npx` cannot be shadowed.** `scripts/lint-fix.test.mjs:40`
executes the real `scripts/lint-fix.mjs`, and that script spawns
`execFileSync("npx", ["eslint", ".", "--fix"])` (`lint-fix.mjs:13`);
`scripts/format-all.mjs:11` does the same with `prettier`. Shadowing `npx`
would break the existing suite. Sol's own conditional — "if retained" —
resolves against retaining it.

**And the harm is a different class than this opus's.** `npx --yes quota-axi`
fetches third-party code from the registry; it is not a metered vendor turn.
The tree already classifies it exactly that way: `claude-code.ts:21` records
that `providers` was cut from the talk profile's allowed tools because "its
default source spawns `npx --yes quota-axi`, a network fetch plus third-party
code neither talk nor tick needs". That is the censor's carried C4 class
(`gate×network-dependent-probatio`), which this brief argues out of scope —
and having just refused to widen into L-030, widening into C4 would be
inconsistent.

So land 4 closes at the **seam** rather than the launcher: behaviour 10(d)
pins that every `quotaAxiSource(` in a test passes an explicit `command`, with
a positive control proving the pin rejects a defaulted call. That removes the
forgotten-injection accident — the actual class — without shadowing a
general-purpose tool the suite needs or reshaping another package's API.

Residual, named rather than hidden: a **different** dynamically-resolved
binary, in a seam nobody has written yet, escapes both the shadow and every
pin. The structural fix is Sol's `{bin, args}` restructuring, filed as the
successor in Out of scope. This opus does not perform surgery on
`packages/providers` to guard a call that no test makes.

## Interfaces

```jsonc
// package.json
"test":       "node scripts/no-vendor.mjs",
"test:suite": "<the existing chain, plus the one new test invocation>"
```

`test` takes **no arguments**: the runner reads `scripts["test:suite"]` out
of `package.json` and executes that string through `sh -c`, which is what
`npm run` would have done anyway, minus npm's PATH re-prepending. One copy of
the chain, no nested npm, and the runner owns PATH precedence absolutely.

The chain is moved, not rewritten — but rev 1's claim that it is
**byte-identical is withdrawn** (land 1): registering
`scripts/no-vendor.test.mjs` appends one invocation to it. The honest claim
is that every pre-existing invocation is unchanged, character for character,
and exactly one is added at the end.

`scripts/ci-workflow.test.mjs`'s parity guard is safe, and rev 1 described it
wrongly. Sol read it: it substring-checks for `npm test` and then
exact-matches the workflow's ordered `run:` strings against `CI_STEPS`
(`package.json:16`, `ci-workflow.test.mjs:65,144`). It **never reads the
package script body**, so splitting `test` from `test:suite` cannot trip it.
That was my revision-1 target 1, and it is answered — the "keys on step
names" phrasing was a guess, and the substring check is the fact.

`scripts/no-vendor.mjs`:

1. Preflight, fail closed — the four steps in "Fail closed" above.
2. Build `PATH = <repo>/test/bin : <inherited PATH>`.
3. `sh -c "<test:suite>"` with `stdio: "inherit"`, so the suite's output is
   untouched and a developer sees exactly what they see today.
4. Release the lock, then adjudicate: if the log is non-empty, print
   **every** line and exit non-zero; otherwise exit with the suite's own
   code.

Step 4's last clause is not a detail: a sentinel that masks a genuine test
failure by replacing its exit code has broken the suite it guards.

## Behaviours to test

All fixtures under `$TMPDIR`. Tests live in `scripts/no-vendor.test.mjs`,
matching the existing `scripts/*.test.mjs` house shape, registered in
`package.json`'s chain.

**The absolute prohibition, restated because it is this opus's own trap: no
test here may spawn the bare string `claude` or `codex`.** A test for a
vendor-spend guard that spends is the one unacceptable outcome, and the
obvious way to write behaviour 4 is exactly that mistake. Every behaviour
below reaches the property another way: the shim by absolute path, the
runner by a pre-seeded file, the end-to-end path by a **fake vendor name**.

1. **The shim records, refuses, and appends.** Invoke `test/bin/claude` **by
   absolute path** (never via PATH) with arbitrary argv: exit code is
   non-zero; one line is appended to `.bisellium/vendor-violations.log`
   naming the binary, the argv and the cwd; the shim spawns nothing itself
   (assert no child process — a shim that execs the real binary to "pass
   through" would be the whole defect). Then invoke `test/bin/codex` by
   absolute path: two lines, the first byte-identical to what it was.
2. **The violation names its caller.** The line carries the parent process's
   command from `/proc/<ppid>/cmdline`. With `/proc` unreadable (simulate by
   pointing the lookup at a path that does not exist), the line is still
   written, still non-zero, with the caller recorded as unknown — degraded,
   never dropped and never fatal. Sol held this target and confirmed the
   attribution is usable: this repo's chain runs tests directly as
   `node --import tsx <file>` with no `node --test` controller, so the shim's
   parent is the test process itself and its cmdline ends in the test
   filename. Noisy, recognisable, not decorative.
3. **Preflight fails closed, and the suite never starts** (land 8). Four
   rows, each asserting a non-zero exit **and** that the inner command never
   ran — prove the latter with a marker file the inner command would have
   created, whose absence is the assertion: `test/bin/claude` missing;
   `test/bin/codex` present but not executable (`chmod -x`);
   `.bisellium` unwritable; the lock already held by a live pid. No platform
   is exempt and no environment variable overrides any of it.
4. **Activation is proved, not assumed.** With everything installed, the
   preflight's self-test executes the shim by absolute path, observes the
   violation line, clears it, and proceeds — so the suite starts with an
   empty log, and a shim that silently fails to fire makes the runner exit
   before spending anything. Assert the log is empty at suite start and that
   the self-test spawned no vendor.
5. **PATH precedence inside the suite** (land 1, the measured one). Running
   through the runner, the inner command observes `<repo>/test/bin` as
   `PATH[0]`, and the inherited `node_modules/.bin` still present behind it.
   Then the regression pin: an inner command that itself invokes
   `npm run -s <fixture-script>` observes `node_modules/.bin` ahead of the
   sentinel — asserted as the *reason* the runner must never use a nested
   `npm run`, so a future refactor back to one fails here with the
   explanation attached.
6. **The runner's verdict table.** Four rows, one block, asserting exit code
   and output, with no vendor name involved anywhere: suite exits 0 and no
   log → runner exits 0; suite exits 1 and no log → runner exits **1**, the
   inner code passed through unmasked; suite exits 0 with a pre-seeded
   two-line log → runner exits non-zero and prints **both** lines; a stale
   log present before a clean run → runner exits 0, because a violation from
   yesterday must not fail today.
7. **The shadow composes end to end, with a fake vendor.** A temp dir holds
   a shim named `bisellium-fake-vendor`; an inner script spawns that **bare
   name**; the runner, pointed at the temp dir as its shadow dir, exits
   non-zero and names it. Assert in the same block that
   `harnessEnv({ PATH: "x", FOO: "y" }).PATH === "x"` — the inherited-PATH
   passthrough the runtime guard rests on. Proves shadow plus adjudication
   compose, with zero possibility of vendor contact.
8. **A swallowed failure is still caught.** The behaviour that justifies the
   file over an exit code. The inner script spawns the shadowed fake name
   inside a `try/catch` that discards the error and exits **0**, exactly as
   `createListingCache` and `harnessVersions` do. The runner still exits
   non-zero. Without this behaviour the design is unjustified; with it, the
   file is not a preference.
9. **The lock serialises runs and never wedges** (land 9). A second runner
   started while the lock is held by a live pid exits non-zero, does not run
   its suite, and **does not delete the first run's log** — the race asserted
   directly by seeding a violation, starting the second runner, and checking
   the line survives. A lock whose recorded pid no longer exists is taken
   over and the run proceeds. The lock is released on both the passing and
   the failing path.
10. **The static pins**, four scans reusing `usage.test.ts`'s file-walking
    idiom. **Each pin gets a positive control** — a synthetic violating input
    that it must reject — because a scan that cannot fail is decoration:
    - **(a)** every `spawn`/`spawnSync`/`execFile` of a vendor binary under
      `packages/`, `apps/`, `adapters/` uses a **bare name** present in the
      shadow dir, so nothing routes around PATH by absolute path and a third
      vendor binary fails here instead of escaping silently.
    - **(b)** no test file in this opus spawns the bare string `claude` or
      `codex` — the $0 prohibition made mechanical rather than prose.
    - **(c)** every test-supplied `PATH` in the repo either contains the
      shadow dir or contains no system binary directory
      (`/usr/bin`, `/bin`, `/usr/local/bin`, `/opt/homebrew/bin`, `$HOME`).
      This is land 7's boundary. `packages/cli/src/harness-env.test.ts:112`
      fails it today and is fixed by appending the shadow dir to its
      synthetic `PATH` — which does not weaken that test, since it asserts
      the value is copied **verbatim**, whatever it is.
    - **(d)** every `quotaAxiSource(` call in a test file passes an explicit
      `command` (land 4's boundary — see below).
    Pin (a) reds honestly: it reads the shadow set from `test/bin/`, which
    does not exist yet, so the set is empty and the two real vendor spawns
    are uncovered. Pin (c) reds on the `harness-env.test.ts` site.
11. **The log cannot dirty the tree.** After a violation is recorded,
    `git status --porcelain` in the repo is byte-identical to before, and
    `.bisellium` is in the exclusion set `verify` computes. A sentinel that
    makes every certificate `dirty:` would cost more than it saves.

### Reds

One red per behaviour, assertion-level, no two sharing an output
(engineering lex §2, `opus.red_evidence`, P-005), via
`bisellium red W-072 --behaviour <n> --sella <id> --studio studio -- <cmd>`.

Behaviours 1-5 and 7 red because `test/bin/` and `scripts/no-vendor.mjs` do
not exist — but **assert, do not crash**: each block checks for the missing
file and reports a failed assertion, so the log records an assertion-level
red rather than an ENOENT stack trace, which `opus.red_content` would flag
as a module-load failure. Behaviour 6 reds on its own logic as described.

No red may be produced by running `npm test` as a whole; each is the
targeted block. And no red may involve a real vendor binary — a red log
proving the sentinel works by spending money would be self-defeating
evidence.

## Acceptance

1. `npm test` green; `typecheck`, `lint`, `format:check` clean.
2. **Zero violations on the current tree.** `npm test` reports no vendor
   contact, which establishes the regression baseline. Sol's independent
   inventory confirms this is achievable and says why: five direct
   `codexListModels()` calls, all under a temp-only or temp-first PATH
   (`probe.test.ts:622`); every `probeBattery` and `runTick` test supplies
   listing/version seams; vendor profile tests use stub or deliberately
   nonexistent PATHs; every direct server test goes through `baseOpts`; and
   `runServe` builds the lazy real listing default but its tests never
   request `/api/models` (`server.test.ts:48`). If a violation nonetheless
   appears, it is a real bug found on the first honest run: fix it here if it
   is an injection one-liner of the `opts.listModels ?? codexListModels`
   shape, file it if larger. The acceptance is never "disable the check".
3. The sentinel costs **$0** and makes no vendor contact, in the suite and in
   its own tests — demonstrated by behaviour 6(b) plus the absence of
   `claude`/`codex` as spawn targets anywhere in this opus's diff.
4. A deliberately violating fixture fails `npm test`. Run it by hand with
   the fake vendor name, keep the output.
5. `bisellium ci` and the CI `gates` job both still pass, proving the
   `test` → `test:suite` split did not break the parity the drift guard
   asserts.

## House constraints

## For Sol

Sol keeps the slot; this is not a UI opus, so D-022's `ui-lead` exception
does not apply.

**Revision 1's six targets are spent.** Sol attacked all six: targets 1, 4
and 6's neighbourhood produced lands that changed the mechanism; targets 2,
3 and 5 held and are closed, with the holding reasons folded in where each
belongs (behaviour 2 carries the `/proc` finding, Out of scope carries the
`test:attended` reasoning, and "a caught violation exits immediately" answers
the deferred-adjudication worry — the shim writes and exits, so no vendor
timeout is incurred). Sol also found two defects revision 1 never pointed
at: fail-open activation (land 8) and the cross-run log race (land 9). **Do
not re-litigate a held target.** The targets below are revision 2's own new
surface, and three of them exist only because rev 2 added machinery.

1. **The `sh -c` execution of `test:suite` is now the riskiest line.** Rev 1's
   risk was the nested `npm run`; rev 2 removed it and took on a different
   one. The runner reads a string out of `package.json` and hands it to
   `sh -c`. `npm run` does the same, but not *identically*: npm sets
   lifecycle variables (`npm_lifecycle_event`, `npm_package_*`,
   `npm_config_*`), uses `script-shell` if configured, and on some platforms
   picks a different shell. Sol verified no current reader depends on npm
   lifecycle variables — **verify that again against the chain as executed,
   not as read**, because the chain contains `(cd apps/web && …)` subshells
   and a `node scripts/*.mjs` step that could plausibly read
   `npm_package_version`. If any step needs npm's environment, the runner
   must synthesise it or go back to a nested `npm run` with a different
   precedence fix.
2. **Whether the preflight self-test is worth its cost, or is a liability.**
   Behaviour 4 has the runner execute a shim on every single `npm test` to
   prove activation. I think that is the difference between asserting and
   proving. But it also means every test run writes to `.bisellium/` and
   deletes from it before doing anything, and a filesystem that is slow,
   full or read-only now fails the suite *before* the suite. Is proving
   activation worth adding a new way for `npm test` to fail?
3. **Fail-closed on every platform.** I removed rev 1's inactivity
   announcement entirely: no platform exemption, no hatch. A Windows adopter
   therefore cannot run `npm test` at all. I justify it with CLAUDE.md
   pinning this repo to WSL — but `docs/ADOPTION.md` addresses adopters who
   are not this repo, and `providers/src/index.ts:181` already carries a
   `shell: process.platform === "win32"` branch, so someone once cared. Is
   fail-closed-everywhere right, or does the honest version fail closed on
   Linux and refuse to *install* on win32 with a filed follow-on?
4. **Pin 10(c) is the weakest of the four, and it edits another opus's
   test.** "Contains no system binary directory" is a denylist of five
   paths, and a denylist is the shape that rots. A test-supplied PATH built
   from `process.env.PATH` at runtime, or from a variable, defeats the scan
   entirely. And the fix it forces on `harness-env.test.ts:112` appends the
   shadow dir to a fixture whose whole point is a *synthetic* env — I argue
   verbatim-copy makes that safe, but I did not run W-049's test with the
   longer value. Break either half.
5. **The lock's take-over rule.** A lock whose recorded pid is gone is taken
   over. Pid reuse is real: on a busy machine the pid in a stale lock can
   belong to an unrelated live process, in which case the second runner
   refuses forever and `npm test` is wedged until someone reads the error.
   Is pid-liveness the right staleness test, or should it be an age bound, a
   `flock(2)`, or nothing at all (always refuse, never take over)?
6. **Whether land 4's close is a close or a relabelling.** I declined to
   shadow `npx` on measurement (`lint-fix.mjs:13` needs it) and declined to
   restructure `quotaAxiSource`, closing instead with pin 10(d): tests must
   inject `command`. That removes the accident but leaves the *production*
   default reachable, and the pin is a scan over test files — exactly the
   "injection by convention" this opus exists to abolish, now enforced by a
   grep instead of a comment. Is a pinned convention meaningfully better
   than a commented one, or have I renamed the problem? This is the target I
   would attack hardest.
