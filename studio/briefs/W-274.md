## Intent

A build-review round is run by hand today, in two scripts the orchestrator copies per opus. `~/.bisellium-evidence/W-306-review/r1-run.sh` runs `next` for the ticket, `review-packet.sh`, writes the prompt as a heredoc, runs `codex exec -m gpt-5.6-sol … -s read-only` and prints the verdict; the orchestrator reads it and runs `~/.bisellium-evidence/record-review.sh` with the outcome, which runs `next`, `verdict`, `next`, `review` and one commit. Later rounds copy a third script that resumes the Codex session (`W-293-review/r2-run.sh`). That is about ten hand steps and three orchestrator turns per round. D-071 C makes the round one `next` perform; D-075 measures it in cycle minutes (5 to 10 per opus, plus the orchestrator's turns).

W-274's title is larger than one opus. This brief is part 1: the smallest slice that removes the most hand steps. After it, `npm run -s bisellium -- next <id> --perform --expect review --budget 400000 --studio studio --repo .` runs one build-review round end to end: the packet, the prompt from a template file, Codex `gpt-5.6-sol` through the harness adapter, then the verdict and review records with the ticket, and one commit on `opus/<id>`. Any failed step holds with nothing recorded after it.

Threat model: mistakes, not adversaries (D-045).

## Interfaces

`next --perform` performs the `review` rung when it is named, in either of its two readings; `--budget` is required as for every dispatch order (`gateDispatch`). Before either reading, `performReview` holds when the branch record's `kind` is `ui`, then when the worktree is not usable or has a tracked change (`dirtyHold`).

The perform runs inside the step marker like the others, and performReview converts every returned refusal and thrown step error into next: <id> review held, why: <reason>, exit 1.

**The censor's order (round `n`).** In order:

1. The round is at least 1.
2. The packet: `packetBase` first proves the containment of `<repo>/.bisellium/reviews/<id>/`: `<repo>/.bisellium` (real path) is a real directory (`requireRealDirectory`), `parsePacketArgs` (W-215's real-path check) refuses it at or under either studio tree (the main checkout's and the worktree's), neither studio's real path is inside it, and `ensureRealDirectory` creates or checks each level below it only inside a real one. Only then is `r<n>/` removed if present, then built by `buildPacket` (`scripts/review-packet.mjs`, W-215, unchanged) with phase `build`, the censor, the worktree's studio and the worktree as the repo. It holds `facts.txt` and, for a later round of a sessioned sequence, `delta.diff` and `prompt.md` from `prompts/later-round.md`. After step 3 the perform creates `r<n>/` and writes `<id>.diff` (`git diff refs/heads/master...HEAD` in the worktree) and `prompt.md`, each exclusively (`wx`); after the call it proves `r<n>/` a real directory again and writes `verdict.md` the same way.
3. The prompt: a later round of a sessioned sequence takes the packet's `prompt.md`. Otherwise `prompts/build-review.md` is read from the worktree's studio by `readContainedRegularFile`, as `buildPacket` reads `later-round.md`, and `fillSlots` fills its six slots in one pass: `<ID>`, `<ROUND>`, `<WORKTREE>` (the worktree path), `<PACKET>` (the packet path), `<REVIEWED_HEAD>` (the opus tip) and `<FOCUS>`. A missing slot holds (`prompts/build-review.md lacks the slot <S>`). `<FOCUS>` is four fixed lines: the brief's numbered behaviours, the flips its Acceptance names and no other, the source diff against Files owned, and each red failing by assertion (Defaults 2).
4. Codex, through the adapter (`codexProfile` in `@bisellium/shim`): `start` for a new session, `resume` with the previous log's session for a later round. The call passes model `gpt-5.6-sol` (`REVIEWER_MODEL`), reasoning effort `high`, `timeoutMs` 25 minutes (`REVIEW_TIMEOUT_MS`), the worktree as the working directory and the prompt on stdin; the adapter adds its read-only policy flags. One step-log line is written before the call and one after it.
5. The reply is refused, with nothing recorded, unless Codex closes normally with code 0; a signal is failure, as are a non-zero exit, an invalid or changed session, or a last nonblank line other than exactly VERDICT: PASS or VERDICT: FAIL.
   The hold names the cause: `codex exited <n>` (3 a usage limit; `(timed out after <ms> ms)` for a call the adapter killed; `(signal <name>)` for any other signal close), `codex reported no session id` (`SESSION_ID`), `codex resumed <a> but reported session <b>`, or the reply's last line (`replyOutcome`: the last line that is not blank, with only a CRLF's CR removed, no other whitespace normalized).
6. `runVerdict` records the reply in-process: round `n`, the censor, outcome `passed` or `failed` from that line, model `gpt-5.6-sol`, the session, `--from` the packet's `verdict.md`, the worktree's studio. Its refusal holds as `verdict refused: <its first line>`.

A recorded verdict the gate does not cite yet is finished without another Codex call only when its log records exactly one model header equal to gpt-5.6-sol, exactly one SESSION_ID-valid session header, and, for a later round, that session equals the preceding sequence's sole valid session header when present; otherwise performReview holds.

**That second reading** is what a ticketed studio names for round `n` with actor `producer`; steps 1 to 6 are skipped. The preceding sequence's session is the one round `n-1`'s log records, when it records one.

**Then, in both readings:** the facts are read again, round `n`'s log through the strict build-round reader (`f.buildRounds`), and its model and session are checked as the second reading requires (`parseVerdictLog` on the worktree's copy; in the first reading the perform wrote them). Its recorded outcome is the one `review` records (verdict may have reconciled the reply, W-126). The ticket is refreshed from the new derivation, `runReview` records `--pass` or `--fail` with `--evidence ci/<id>-review-<n>.log`, and one commit in the worktree carries exactly the log and the record: `chore(studio): <id> review round <n> <outcome>`, with a `Co-Authored-By: <censor> (bisellium next)` trailer. The output adds `review: round <n> <outcome>`, `log: ci/<id>-review-<n>.log` and `branch: opus/<id>`, then `next-step:` as every perform does.

**Waiting.** The perform runs in the foreground of `next`, as `merge --poll-ms` does; the orchestrator launches it in its own background call and waits for its exit (D-071 D). `REVIEW_TIMEOUT_MS` (1,500 s) is under `STEP_SILENCE_SECONDS.review` (1,800 s), so the marker of a live round never reads stalled; a call past 25 minutes is killed by the adapter and held. Test seam: `BISELLIUM_TEST_REVIEW_TIMEOUT_MS`, a positive integer, honoured only with `BISELLIUM_TEST_CLOCK=1`; any other value is ignored.

**The adapter seam** (`HarnessProfile`, documented reason): the codex profile's fixed 120 s timeout would kill every review, and every hand round ran at reasoning effort `high` (`r1-run.sh`, `r2-run.sh`). Both options are optional; absent, each profile behaves as today. Only the codex profile reads `reasoningEffort`. One behaviour of the codex profile changes for every caller, `talk` included: a close by signal is a failure (exit 1, the signal in `raw`), where a parsed reply used to count as exit 0.

Limits, stated:

- A review refusal after verdict leaves only the log uncommitted, and a ticketed re-run finishes it without Codex. A failed commit or crash after review leaves the log and record uncommitted; pr holds on the dirty record, and committing the two is a hand step.
- A recorded log the second reading refuses (another model, no valid session, another session than the sequence's) stays uncommitted, and every re-run holds on it the same way: the orchestrator records it by hand (`next`, then `bisellium review`, then a commit) or removes it, and the next perform runs the round anew.
- `facts.txt`'s `next` block exits 2: `buildPacket` runs `next` with the worktree as `--repo`. Today's later-round packets show the same (`W-293-review/packets/r2/facts.txt`); this part does not change `review-packet.mjs`.
- A verdict `verdict` refuses for its shape is not reissued by the same session (lex §9 step 2): the perform holds, and a re-run makes a new call.
- The template is read from the opus branch, so an opus may change its own review prompt; `studio/prompts/` is code-owned, so such a change is the Patron's to review.

### Input domain

A rejection fails closed: the perform holds, exit 1, the step marker is released, and nothing is recorded after the failed step (no log before step 6, no gate, no commit). A test row whose own read fails throws, which fails the row.

## Behaviours to test

Each row builds the file's `world()` at the `build` stage (a current receipt, no review), sets `step_tickets: required` (`ticketed`), commits fixture templates under `studio/prompts/` on the opus branch (studio files, so the source tree and the receipt stay current), and puts a stub `codex` first on `PATH`. The stub logs each call's argv and stdin under `$HOME` and answers from `$HOME/codex-reply.json` with a `thread.started` and an `agent_message` event. The real `codex` never runs.

1. **`next <id> --perform --expect review` runs round 1 end to end through the codex adapter, or holds with nothing recorded.** In `W-274-b1`: a PASS reply exits 0 with `next: W-900 review performed`, `review: round 1 passed` and `next-step: pr`. The stub was called once, with `exec` (not `resume`), `-m gpt-5.6-sol`, `-c model_reasoning_effort=high`, `-c sandbox_mode=read-only` and `-` last, and its stdin is the template with every slot filled. A FAIL reply with a blocker citing `brief:1` is recorded failed, and `next-step` is `build`. Each of these holds with exit 1, `next: W-900 review held` and its exact `why:`, with no log, no gate, no commit and the step marker released: no template, a template without `<FOCUS>`, a tracked change in the worktree (no Codex call for these three), Codex exiting 1, a usage limit (exit 3), a call past `BISELLIUM_TEST_REVIEW_TIMEOUT_MS=300`, no session id, no `VERDICT:` last line, and a reply `verdict` refuses (no `## Findings`).
