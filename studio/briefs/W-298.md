## Intent

A sella with a question for the Patron has no command: `talk`'s `PETITIO:` line and the cascade retro write petitiones only as a side effect of something else, and P-004, P-008 and P-009 were written by hand (W-038's brief), which CLAUDE.md forbids. A question also holds nothing: the ladder goes on naming the next step while the Patron has not answered. D-080 D rules the scope: W-038's verb plus a `next` hold; no `evidence` key and no lex clause sending every question through it.

**The design.** Two pieces.

1. **The verb.** `bisellium petitio --from <sella> --subject <text> [--opus <id>] <body…>` writes `petitiones/P-<n>.md` through the shared allocator, addressed to the manifest's patron, `state: needs_you`, with `opened` and `subject` stamped. It refuses, exit 2 with nothing written, whatever `check` would block and it can see.
2. **The hold.** `next` reads the main checkout's `petitiones/`. A record naming the opus with `state: needs_you` turns the rung the ladder would name into `held`, `actor: patron`, exit 1, the why naming the petitio, its subject and how to answer, and `underlying:` the rung's own why, the shape `gateDispatch` already prints for its holds. The step stays the step: a held opus still says where it is. It carries no order, so no ticket and no silence read: an opus waiting on the Patron is not a stalled agent. `answer --petitio` (the Inbox's route) resolves the record and the hold is gone at the next read.

**Choices, and why.**

- **`next` wraps the ladder; it does not change it.** `petitioHold(deriveNext(f), f)` sits where `gateDispatch(deriveNext(f), …)` already does, as `derivedStep`, and every `deriveNext` call in `next.ts`'s paths moves to it (report mode, `--perform`, `--chain`, `--all`, each ticket refresh). `deriveNext` stays pure and its name stays: tests build hand-made `Facts` for it (`next-spec.test.ts`, `ladder-followon.test.ts`) and `next-branch.test.ts:814` reads its source span, and none of them flips.
- **One place of truth: the main checkout's files.** That is where `next` must run (it refuses a linked worktree), where the verb writes, and where the Inbox served from that checkout answers. Reading the opus worktree too would hold on a copy `answer` never edits, and a stale `needs_you` there would hold until merge. So the verb **refuses a linked worktree** rather than file where `next` cannot see it, which would be a silent no-hold, and refuses too when git cannot tell: only git's own "not a git repository (or any of the parent directories)" reads as outside git, since a linked worktree whose admin directory is gone fails differently. Reading master's tree as well was rejected: it adds a `git show` per record per opus to `next --all`, and the checkout has the record anyway once it syncs (Limits).
- **Fail closed, as W-185's class asks.** A record that cannot be read may name this opus, so it holds every opus, on the producer, naming the file. A record of this opus with an unknown state holds too. `check` already blocks every one of those forms, so an honest officina never sees it.
- **A done opus is not held.** Its retro and checkpoint go on, and it reads no petitio at all. A question about finished work still reaches the Inbox.
- **The verb checks what it reads, and `next` what it prints.** `readManifest` only parses, so `manifestProblem` refuses a manifest whose `patron` or `sellae` would crash or mislead it. On an open record of this opus, `openPetitiones` holds on the producer for an `id` that is not its filename (the why would send the Patron to another file), a blank `subject`, or a `to` that is wrong for its state. A resolved record's other fields are not read: they reach no output. `next` does not check the manifest as the verb does: a `sellae` that is not a list fails `next` rather than holding (Limits, W-507).
- **`state: awaiting_reply` holds on the sella asked.** After `answer --ask-back` the Patron is waiting for that sella; naming the Patron would be false.
- **`--opus` stays optional,** as W-038 signed and as `docs/ADOPTION.md` has it: a question about scope, budget or a lex names no opus and holds nothing. Without it the sella would be back to writing the file by hand.
- **`--to`, `--state` and W-038's Patron-as-sender are dropped.** D-080 D scopes this to questions to the Patron: each flag would add a state the verb has no caller for and a `petitio.direction` refusal to carry.

## Interfaces

```
usage: bisellium petitio --from <sella> --subject <text> [--opus <id>] [--studio <dir>] [--now <iso>] <body…>
```

- Prints `<id>: <subject>`, exit 0. Every refusal prints to stderr, exit 2.
- The record, keys in this order, values JSON-quoted as `talk`'s `openPetitio` writes them: `id`, `from` (the seat's id, for an instance too), `to`, `state: needs_you`, `opened`, `subject`, `opus` only when given; then the body.
- `runPetitio(args: string[], opts?: WriteOptions): WriteResult` (new export of `@bisellium/commands/writes.js`, reached through the `packages/cli/src/writes.ts` shim).
- `next`'s output grammar is unchanged: `next: <opus> <step> held`, `actor: patron` or the asked sella or `producer`, `why:`, `underlying:`, `health:`, exit 1.
- Why, for one question: `P-024 asks the Patron: <subject>; answer in the Inbox, or: bisellium answer --petitio P-024 <reply…> --studio <studio>`. For an ask-back: `P-024: the Patron asked back; <sella> replies`. An open record that fails its fields holds on the producer: `petitiones/P-024.md: <what is wrong>`. Several are joined by `; ` in numeric id order, with the Patron as actor if any asks, and one command naming the first that asks. A record with no subject names its id alone.
- `openPetitiones(studioAbs, id, manifest)`, `petitioHold(d, f)`, `derivedStep(f)`: internal to `next.ts`. `deriveNext` is unchanged and stays exported.
- Unchanged: `runAnswer`, `createNextRecord`, `checkStudio`, the `petitio.*` rules, the snapshot's petitio row, `POST /api/answer`, the Inbox.

The prototype (`prototype.mbox`) is four patches over master debcb104, built by `series.sh` from the stage scripts: `test(W-298): row b1, red`, `feat(W-298): behaviour 1`, `test(W-298): row b2, red`, `feat(W-298): behaviour 2`.
