# W-032 — PR gate: opening a pull request goes through the CLI and can be refused

## Intent

D-015 made the pull request a lifecycle step. Nothing enforces it.

Observed 2026-09-19: W-030 went `bisellium new` → brief → builder → open PR
with `state: backlog` and `probationes: {}`. No spec, tests, lint or types
certificate existed. Round-1 review caught it and called absent
certificates worse than the stale ones it had failed an earlier PR for.

Four layers all missed it, and the AAR is the spec for this opus:

1. The officina enforces gates at `done` — `closeChecks` refuses an opus
   whose gates have not passed. The PR sits upstream of `close`, so the
   guard is downstream of where the work stopped.
2. The PR is a gate point introduced the same day. Every existing rule was
   written around `done`.
3. **PR creation bypasses the CLI entirely.** `close` can refuse because it
   is a bisellium command. `gh pr create` cannot, because bisellium is not
   involved.
4. `check` has no rule for "an opus has work in flight but no gates" — the
   only backlog rule is a depth cap.

D-015's `pr.required: true` already makes `bisellium merge` stop short of
landing, "leaving the seam for W-028". W-028's brief never picked that up.
This opus is that seam.

## Interfaces

`bisellium pr <opus> --studio <dir> --repo <dir> [--title <text>] [--body <path>]`

Refuses, before touching any remote, when:

- the opus is not in a state a PR may be opened from
- any gate the manifest declares has not passed
- a gate's `certifies: tree:<hash>` does not match the opus branch's source
  tree — the same comparison `merge` makes, reusing `sourceTreeHash`, not a
  second implementation

On success it opens the PR and records its reference on the opus.

**Provider shape.** A GitHub pull request is GitHub-specific, and this
project's first decision is that the officina state is files and any
toolchain can produce them. Follow how `talk` handles harness profiles
rather than hardcoding `gh`: the gate logic is provider-neutral, the
creation step is behind an adapter, and an officina with no provider
configured still gets the refusal.

## Behaviours to test

1. Refuses when a declared gate has not passed, and touches no remote
2. Refuses when a gate's certificate does not match the branch's tree
3. Refuses from a state a PR may not be opened from
4. Opens the PR and records its reference when every check passes
5. The refusal cannot be walked past by running the command again — a
   refused run leaves no state that makes the next run succeed
6. With no provider configured, the gate still refuses, and a passing opus
   reports what it would have opened rather than failing obscurely
7. `process.pr_bypass` (advise): an opus whose branch exists on a remote
   but which records no PR reference — the `gh pr create` path this
   command cannot intercept

## Acceptance

An ungated opus cannot reach a pull request through the CLI, and one that
reaches it another way is visible to `check`.

## Out of scope

- Merging the PR. That is `bisellium merge` under `pr.required`.
- Reviewing it. That is the `censor` gate per D-014.
- Anything that assumes GitHub beyond the adapter.

## Note on behaviour 5

Take it seriously rather than asserting it. Round-4 review of W-026 found
`merge`'s stale-certificate refusal could be defeated by running the
command a second time: the first run rebased without rolling back, so the
second found nothing to rebase, skipped the block containing the check,
and landed. The error message's own instruction to "retry the merge" was
sufficient to defeat it. Any refusal this command makes must hold on every
run, not only the first.
