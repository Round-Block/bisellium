## Intent

The opus title: retire `scripts/open-pr.sh` and `scripts/merge-gate.sh` and drop
the W-124 parity pins that freeze them; `fetchTrunk` against a checked-out
`master`; the checkpoint rung's bare-heading regex; the done-rung remedy text; a
dirty-red ordering hint. Six items, each small. If any item grows past what is
written here, the builder stops and escalates (Stop conditions).

1. **Retirement.** W-114 (PR 163) ran the `pr`, `merge`, `cleanup` and `done`
   rungs live through `bisellium next --perform`; the verb has outlived the
   scripts it absorbed. Both scripts are deleted with `git rm` (the only
   mechanism; nothing is rewritten by hand), and the behaviour-3 parity loop in
   `next.test.ts`, which runs each script beside the verb and so freezes the
   scripts byte-identical, becomes a verb-only terminal-state table. Everything
   the verb does stays asserted; only the script half goes.
2. **`fetchTrunk` from a checked-out master.** Git refuses `git fetch origin
   master:master` whenever `master` is checked out in any worktree, even when
   already current (measured below). The `pr` and `merge` rungs both call it, so
   from the normal configuration (the main checkout on `master`) they are held
   for ever; W-114 detached HEAD to get past it. The Patron has ruled that the
   verb may fast-forward the main checkout's checked-out `master`; the contract
   below bounds that mutation to the reviewed merge commit.
3. **Checkpoint heading.** `afterDone` matches `^#{1,6} Where things stand$`
   exactly, but the handoff convention is a dated heading (`## Where things stand
   (2026-10-02 late night)`). The named section is then never found and the rung
   says "does not name it" for an opus the handoff names (found live closing
   W-124).
4. **The landing remedy text.** `SCRIPTS_LAND` in `next.ts` is the `command:` the
   verb prints when a spec signed on `spec/<id>` or a done committed on
   `chore/done-<id>` must still land. It names the scripts. The `pr` rung opens
   only `opus/<id>` heads, so no verb lands these two branches; the remedy must
   say the plain `gh` and `git` path, and must leave HEAD on `master` before it
   pulls (a `git pull --ff-only` from the chore branch after a squash-merge exits
   128, probed).
5. **The spec-log ordering (decided: a doc note, no code).** Since D-021 refuses a
   spec verdict written off the opus branch once the branch exists, the architect's
   spec verdict must be written on `spec/<id>` before `opus/<id>` is created, and it
   rides the spec PR. The spec rung already handles this: it reads the committed
   trunk, and when the evidence is only on `spec/<id>` it names the landing
   (`specBranch` fact). No wording or validation in `next.ts` changes beyond item 4's
   text; one sentence in `docs/ARCHITECTURE.md` records the order. Smallest honest
   fix.
6. **Dirty-red hint.** `bisellium red` records `# tree: dirty:<hash>` when the
   working tree is dirty, and `next` and the producer replay both treat that red as
   missing. Recording reds before committing the tests cost a round-trip in W-114.
   The verb now says so at write time (Interfaces: warn, not refuse).

## Interfaces

### The fetchTrunk contract (`packages/cli/src/integrate.ts`)

New signature: `fetchTrunk(repo, target?: string): { ok: true } | { ok: false; reason: string }`.
`target` is the **reviewed merge commit**. `landed()` passes `pr.mergeOid` (already
well formed and identity-checked by the PR read) as the literal; `openPr()` passes
nothing, so the `pr` rung can never move a checkout. All reads fail closed: an
unreadable ref, an oid that fails `wellFormedOid`, a spawn error or an unexpected exit
status is a hold with a one-line reason and nothing mutated. Hold reasons go through
the existing `clean`/`firstLine` sanitising.

1. If `target` is given it must pass `wellFormedOid` (rejects non-hex, uppercase,
   all-zero, a leading dash), else hold.
2. `git fetch -q origin master:master`. Exit 0 returns ok (existing fast path; no
   worktree holds `master`).
3. On failure, find the worktree whose branch is `refs/heads/master` (`listWorktrees`).
   None: hold with the existing `git fetch origin master:master failed: ...` text.
4. A holder exists. Run `git fetch -q origin +refs/heads/master:refs/remotes/origin/master`
   (the remote-tracking ref only; the checked-out branch is never a fetch target).
   Failure holds with `git fetch origin master failed: <why>`.
5. Read `L = rev-parse --verify refs/heads/master^{commit}` and `O = rev-parse --verify
   refs/remotes/origin/master^{commit}` (both `wellFormedOid`); with a target also `T =
   rev-parse --verify <target>^{commit}`. Unreadable holds.
6. **Contained is ok.** With a target: `merge-base --is-ancestor T L` exit 0 returns ok
   (the reviewed merge is already in local `master`; nothing is moved, whichever
   worktree holds `master`). Without a target: `L === O` returns ok.
7. If the holder's real path differs from `repo`'s real path (`realpathSync` applied
   to **both** sides; `listWorktrees` paths are not canonicalised), hold with the
   existing text (`master is checked out at <path>, so it cannot be fetched into; run
   there: git -C <path> pull --ff-only origin master`). This verb never writes into
   another worktree.
8. **No target (the `pr` rung): never moves anything.** Classify with
   `merge-base --is-ancestor`: `L` behind `O` holds with the step-7 text naming `repo`
   and the pull to run; `O` behind `L` holds with a reason containing `ahead`; neither
   holds with a reason containing `diverged`; any other status holds.
9. **Target (the `merge` rung): the bounded fast-forward.** Require `T` an ancestor of
   `O` (else hold, reason containing `not on origin/master`) and `L` an ancestor of `T`
   (else hold, reason containing `diverged`). Then, each failing closed with a hold:
   1. `git status --porcelain --untracked-files=no` in `repo` is empty (reason contains
      `uncommitted`).
   2. **No incoming path may overwrite an untracked or ignored entry.** Take the paths
      added between `L` and `T`: `git diff --no-renames --name-only -z --diff-filter=A
      L T`. Hold (reason contains `untracked or ignored`, naming the first path, clipped)
      if any such path exists on disk (`lstat`), has an ancestor that exists on disk as a
      non-directory, or is itself an ancestor of an entry in `git ls-files -o -i
      --exclude-standard -z` (an ignored directory that an incoming file would replace).
      Plain untracked files are refused by git itself and also surface here.
   3. Immediately before the merge, `git symbolic-ref -q HEAD` equals
      `refs/heads/master` (else hold, reason containing `HEAD`). The merge acts on the
      branch that was checked, not on whatever was switched to meanwhile.
   4. `git -c submodule.recurse=false merge -q --ff-only <T>` in `repo`, with `T` the
      **literal reviewed oid**, never `origin/master` and never the origin tip read in
      step 5. Re-read `refs/heads/master`; return ok only if it equals `T`. A non-zero
      exit, a spawn error (including the 120 s timeout) or a mismatch holds with
      `<why>; the working tree may be partly updated: git -C <repo> status`.

Origin may be ahead of `T`: `master` then stops at `T`, and a later `git pull` takes the
rest. No `--force`, no `reset`, no `checkout`, no `switch`, no `restore`, no `clean`, no
`--update-head-ok`, no `pull`, no stash. Repo hooks and filter drivers run as for `git
pull` (residual 4).

### The checkpoint heading (`packages/cli/src/next.ts`, `afterDone`)

Replace the regex with `/^(#{1,6})[ \t]+Where things stand(?:[ \t]+\([^\n)]*\))?[ \t]*$/m`:
the heading text, then optionally one parenthesised group with no `)` or newline inside,
then end of line. Still anchored at both ends; nothing else changes (the section runs to
the next heading of the same or a higher level; the id must appear inside it, by the
existing substring test, residual 7).

### The landing remedy (`packages/cli/src/next.ts`)

`SCRIPTS_LAND` is replaced by a function `landing(head, title)` returning

`git push origin <head>, then gh pr create --base master --head <head> --title <JSON title> --body-file <body-file>, then gh pr merge <pr-number> --squash --auto once its checks pass, then git switch master && git pull --ff-only origin master`

The `git switch master` is mandatory: after a squash-merge the pull cannot fast-forward
from the landing branch. The spec-on-branch rung calls it with `spec/<id>` and
`spec(<id>): signed`; the chore-done rung with `chore/done-<id>` and `chore(studio): mark
<id> done`, keeping its existing leading `git switch chore/done-<id> &&`. The `why`
strings are unchanged. The rungs stay named-only (the verb performs `pr` for `opus/<id>`
heads only; extending it to these heads is out of scope).

### The dirty-red warning (`packages/commands/src/lifecycle.ts`, `runRed`)

After the log is written and the existing `recorded` line printed, if `treeHeader`
starts with `dirty:`, print one line to **stderr**:

`red: warning: the working tree is dirty, so this red records a dirty: tree identity that the producer replay refuses; commit the tests first, then re-record`

**Warn, do not refuse.** Reasons: (a) `dirty:` is a defined, documented identity
(`ADOPTION.md`, `verify --allow-dirty`), and a red recorded in a scratch tree for
exploration is legitimate; refusing changes a verb's exit contract for every caller and
every existing fixture. (b) The failure was an ordering trap, not a wrong record, and
the verb can say it at the moment it knows. (c) The consumer already fails closed
(`next` and `opus.red_evidence` treat a `dirty:` red as missing), so a warning cannot
let a bad red through. (d) **Unconditional**, not only for `builder_runtime: isolated`
opera: a `dirty:` red is unreplayable for every opus, and reading the opus record
(which lives on the opus branch) would add a read path for no gain. Exit code, stdout,
the log bytes and every other message are unchanged. Nothing is printed when the tree is
clean, when the identity is `unknown` or `none`, or when the command exited 0 (nothing
recorded). No check rule.

## Stated residuals (accepted, with reason)

1. **The main checkout moves, to the reviewed commit only.** The Patron has ruled that
   `fetchTrunk` may fast-forward the working files of a clean checked-out `master`. The
   guard set: the reviewed merge commit as a literal (never the origin tip), clean tracked
   tree, no untracked or ignored overwrite, HEAD checked immediately before the merge,
   fast-forward only, own worktree only, and the `pr` rung never moves a checkout. A
   squash-merged PR's commit is still branch-protection-reviewed content, not
   cryptographically bound to the censor's review; that is the existing trust in `gh`.
2. **Case-insensitive filesystems and out-of-index state.** The added-path guard compares
   exact paths; a case-only collision on a case-insensitive filesystem, or an untracked
   path outside the repo's own index rules, is not modelled (WSL/ext4 and CI are
   case-sensitive).
3. **Behaviour 2 pins text.** It cannot prove the table is executed; the executing proof
   is `next.test.ts` green at acceptance.
4. **Hooks and filter drivers.** A repository `post-merge` hook and any configured
   checkout filter (for example git-lfs smudge, which reads `.lfsconfig` from the incoming
   tree) run on the fast-forward with the verb's environment, as they do for `git pull`.
5. **A failed fast-forward can leave a partly updated tree** (a read-only subdirectory or
   a timeout after some files were written). The hold says so and names `git -C <repo>
   status`; the next call then holds `uncommitted`. Behaviour 5(j) exercises the text with
   an `index.lock`, which works under any uid; the real partial write was reproduced with
   a read-only directory and is not asserted (a root-owned test run cannot cause it).
6. **The HEAD check narrows the switch race, it does not close it.** Between the
   `symbolic-ref` and the `merge` a branch switch can still land; `--ff-only` refuses a
   HEAD that is not an ancestor of the target and the post-merge re-read of `master` holds
   on a mismatch. Not testable deterministically.
7. **`section.includes(id)` is a substring test** in `afterDone` (pre-existing): a done
   `W-12` reads checkpoint-complete when the section names `W-124`. Not in this opus's six
   items; a boundary match with a `W-90`/`W-900` row is a follow-on.
8. **The ff rewrites the verb's own source** in the main checkout mid-run (lazy imports
   could in principle see mixed code). Accepted: `fetchTrunk` runs near the end of the
   `merge` rung and the process does not re-import afterwards.
9. **The warning is unconditional**, not limited to isolated-runtime opera (reason in
   Interfaces). A deliberate `dirty:` red in a scratch tree prints a line it does not
   need.
10. **Hand-built `Facts`** (behaviours 6-7) couple the test to the fields `deriveNext`
    reads on those two paths; a change to those paths updates the casts. The alternative
    is the full world in `next.test.ts`, which costs minutes per row.
11. **`done` and `spec` landings remain manual.** The remedy text names the commands; the
    verb does not run them.
12. **Historical citations.** `studio/briefs/W-124.md`, `studio/ci/*`, dated dossier pages
    and the handoff keep naming the scripts; they are history, not instructions.
13. **Operator copies outside the repo** still name the scripts: the user memory note
    `feedback-done-means-master-fetched.md`, the `~/.bisellium-evidence/open-pr.sh` and
    `merge-gate.sh` copies, and `docs/SESSION-HANDOFF.md:127`. Not the builder's; the
    producer updates them in the checkpoint.
