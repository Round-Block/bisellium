## Intent

Today `next` judges the spec on master alone, and D-021 refuses spec verdicts in the main checkout while `opus/<id>` exists. An amended brief on the branch is never re-reviewed, and with step tickets on no spec verdict can be recorded there. W-267's re-spec needed the Patron to rename the branch twice. Part 1 moves the in-flight spec to the branch:

- once `opus/<id>` exists, `next` judges the spec on the branch and orders the architect and the spec reviewer there;
- `next --perform --expect spec` commits the re-signed brief and its rounds on the branch;
- a build review of an older brief no longer opens the PR.

Later parts, each with its own signed brief: part 2 commits the first spec on the opus branch too and retires `spec/<id>` (W-256, W-191, W-194, the reused-name `identifyPr` case); part 3 closes an opus in one records PR (W-214, W-257, W-192); part 4 is W-214's architecture-page gate at done.

Threat model: mistakes, not adversaries (D-045).

## Interfaces

While `refs/heads/opus/<id>` is absent, the `spec` rung is unchanged (master, `spec/<id>`, the main checkout).

Once it exists in a studio that sets `spec_reviewer` (`readSpecReviewer` on the master record returns a reviewer; without one the rung is unchanged, since `signedSpec` pins no brief):

- `deriveNext` judges `specEvidence` on `f.branch` (the registered worktree when usable, else the branch ref) instead of master.
- A spec that has not passed, with a usable worktree, gets `specOrder`'s architect or reviewer order at the branch's next round. Its `boot:`, packet, dispute and `verdict` lines name `--studio .worktrees/<id>/<studio>`, and a resumed reviewer session is read from the branch's logs. Without a usable worktree, or with a worktree `ci/` that cannot be listed, `next` holds at `spec` and orders nothing.
- `MAIN_ACTIONS` loses `verdict-spec`, so its ticket binds the worktree studio, HEAD and brief blob whenever the worktree is usable (which needs `opus/<id>`).
- With a passed spec and a usable worktree, `next` reads the worktree's `git status` (untracked included). An edited brief or a new `ci/<id>-spec-<n>.log` is spec work: `spec` is named for `next --perform --expect spec`. Any other entry touching the brief or a spec log (a rename, a removal, an edit of a committed log) holds at `spec`, and so does a new spec log whose `# brief:` is not `briefs/<id>.md blob:<40 hex>` or that passes neither `readSpecSignature` nor `readSpecReview` against that value. Which blob it names is not checked: a brief revised before the commit was never in Git. The perform, `performOpusSpecCommit`, commits the brief, the new logs and the opus record if changed, as one `spec(<id>)` commit in the worktree on `opus/<id>`. It creates no `spec/<id>`, opens no PR and leaves master where it was.
- `parseBuildReviewLog` returns `brief` when the log carries one `# brief:`. A build round is current when its `# tree:` is the current SOURCE tree and, if it carries a pin, the pin equals what `verdict` would write now: `<the branch record's spec> blob:<sha1 of that file on the branch>`. A round with no pin is judged by tree alone (`verdict` writes none for a `kind: ui` build verdict, `verdict.ts:616`). A failed round of an older brief at the current tree orders `review`, not a build fix.

Limit: the packet's `next` fact, run with the worktree studio, prints `unknown opus`; the subject and round sequence the packet gives the reviewer are the branch's.

### Input domain

Every rejection fails closed: `next` holds or names the spec or review work, and no branch moves. Its usual pending-ticket refresh and `.bisellium` step-health writes still happen.

| Record | Valid domain | Rejected by |
|---|---|---|
| The spec once `opus/<id>` exists, with a reviewer | the brief and `ci/<id>-spec-<n>.log` files on the branch | `reviewedSpec` (existing): an edited or unsigned brief orders the architect; a malformed log above the newest signature holds |
| The opus worktree while branch-side spec work is pending | registered, not prunable, on `opus/<id>`, its `ci/` listable or absent | `deriveNext` (existing, extended): otherwise `spec` holds and no spec order is named; after the spec passes, the later rungs' worktree handling is unchanged |
| The spec verdict's ticket | `verdict-spec`, the round, the worktree studio, its HEAD and brief blob | `requireTicket` (existing): a mismatch exits 2 before `verdict` writes |
| The worktree's changes beside a passed spec | `git status` succeeds; the brief edited, spec logs only added, each new log a signature or spec review whose `# brief:` has the pin's shape and that passes its reader against that value, and the opus record | `deriveNext` (extended): a failed `git status`, any other entry touching the brief or a spec log, or an invalid new log holds at `spec`; `performOpusSpecCommit` (new): any other changed path holds before anything is staged, and a failed `git add` or `git commit` holds with the branch unmoved |
| A build round's brief pin | at most one `# brief:` header; current when it equals `<the branch record's spec> blob:<sha1 of that file on the branch>` | `parseBuildReviewLog` (existing, extended): two or more hold at `review`; `deriveNext`: a pin that differs, or whose branch-record `spec` or brief cannot be read, is not current and orders `review`; a round with no pin is judged by tree alone |
