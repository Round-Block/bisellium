## Intent

D-103 adds Dracula Cyan `#8BE9FD`, Pink `#FF79C6`, Purple `#BD93F9` and Yellow `#F1FA8C` to the one dark console palette. This draft proposes role tokens rather than new semantic states: `--accent-cyan` for content and evidence links, `--accent-pink` for browser text selection, `--accent-purple` for display and section headings, and `--accent-yellow` for the Board's project-name text. Cyan gives links the familiar coolest/highest-clarity accent; purple strengthens the heading hierarchy without competing with status; pink makes the transient browser selection conspicuous; yellow gives every project name the same stable text accent without colour-hashing projects.

The exact placement is deliberately narrow. Purple colours the nine existing display/section selectors listed in Interfaces, excluding phase headings, posture words, notices and other state-bearing copy. Cyan colours the Board drawer’s content/evidence links; the existing Officina link rule receives the same token but currently renders nowhere. Visited evidence remains the same cyan, so the accent does not reveal a state. Pink colours only `::selection`, paired with surface text. Yellow colours the disabled Board project selector and its option text identically for every project and condition.

`ok`, `amber` and `bad` remain the only status colours. Their meanings and shape cues do not change. Navigation current-page selection, focus, waiting, gate, loading, error, liveness and completion states do not take an accent. DIRECTION.md section 3's ceiling changes from “semantic colours” to “status colours”: accents do not count toward the at-most-three status-colour ceiling, but an accent never marks a state.

`W-366-b1` parses every new value from `tokens.css` and computes WCAG 2.2 relative luminance and contrast. It requires each accent as text to reach 4.5:1 on both `--surface` and `--wash`, and checks surface text on the pink selection fill at 4.5:1. `W-366-b2` enumerates every accent consumer in the console stylesheet, pins the role map, recognises the current status/state selector forms, and rejects an overlap. W-361's contrast and `bad` rows and W-339's whole-source colour rule remain green.

Threat model: palette drift and accidental reuse of an accent as a state cue, not adversaries (D-045).

For each RGB channel `W-366-b1` divides the byte by 255, applies `c / 12.92` at or below 0.04045 and `((c + 0.055) / 1.055) ** 2.4` otherwise, then uses `0.2126R + 0.7152G + 0.0722B`. Contrast is `(lighter + 0.05) / (darker + 0.05)`. It computes, rather than copies, eight accent-on-surface/wash text assertions and the surface-on-pink selection assertion. The observed accent ratios on surface/wash are Cyan 10.29/8.52, Pink 5.97/4.94, Purple 5.90/4.89 and Yellow 12.74/10.55; surface text on Pink is 5.97. The ratios are evidence, never the oracle.

`W-366-b2` removes CSS comments, recognises flat rule blocks, normalises selector whitespace, and enumerates declarations containing exactly `var(--accent-cyan)`, `var(--accent-pink)`, `var(--accent-purple)` or `var(--accent-yellow)`. It requires only the four roles above. Its current status-class vocabulary is `shell__status`, `screen-notice`, `token-prompt`, the ok/bad gate marks, amber burn fill, attention/count/posture/empty/loading Officina forms, attention/stale Inbox forms, Seats confirmation error, Board notice/WIP/card/liveness forms, drawer banner/gate status and Officina completion fill. Its application-state forms are `:hover`, `:active`, `:focus`, `:focus-visible`, `:disabled`, `:checked`, `[aria-selected]`, `[open]` and modifiers ending active, attention, amber, bad, ok, focused, loading, error, pending, stale, open, closed or selected. The same cyan declaration covers evidence-link base and `:visited`, so visited is not distinguished by colour; `::selection` is the explicitly ruled editing affordance.

Promise exact-accents: the one root palette and DIRECTION.md section 3 name all four D-103 values and role tokens exactly — limit: operating-system forced colours, browser extensions, user stylesheets and display calibration are outside repository control.

Promise computed-contrast: each accent is computed from `tokens.css` at 4.5:1 or better as text on surface and wash, and surface text on the pink selection fill also reaches 4.5:1 — limit: arbitrary nested backgrounds, alpha compositing, native disabled-control opacity and user-agent select chrome are not classified.

Promise role-placement: every current `--accent-*` stylesheet consumer is one of the heading, link, text-selection or project-name selectors in the table — limit: the lexical flat-rule reader does not interpret nested/generated CSS or runtime custom-property injection.

Promise no-accent-state: no recognised status selector consumes an accent and no recognised application-state form uses an accent to distinguish state; visited and unvisited evidence links use the same cyan — limit: the recognised forms are exactly the vocabulary enumerated above; every other class/pseudo/attribute form is outside this lexical classifier.

Promise status-contract: ok, amber and bad keep their W-361 meanings and shape cues, `bad` remains gate-only and never text, and the three-colour ceiling names status colours only. The existing amber waiting rule remains intact. Waiting-age styles are unchanged, but Inbox renders no age numeral; this existing omission is outside W-366. — limit: unchanged component data, rendering and screen-reader treatment are reused, not guaranteed (D-076 E).

Promise one-palette: there is no toggle, stored preference, alternate palette or JavaScript theme path in this change — limit: unchanged application and browser preference code is not guaranteed (D-076 E); the owned diff contains no JavaScript or storage file.

Promise source-colour-stays-green: W-339's whole-source row remains green because the new values exist only in `tokens.css` and consumers use custom properties — limit: W-339's existing lexical grammar and inline-style boundary are reused unchanged, not widened (D-076 E).
