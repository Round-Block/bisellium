## Intent

Lex §9.0 and §9.3 (production) say each red needs its own `next` ticket, and a fix round's builder runs `next` before each `red`. In a fix phase `next` names the fix check, a fix order or the review, never `red`, so a fix round cannot record a red: W-451 is blocked on it today, and W-461's fix shipped with a dry-run log instead (Fable audit 10-29).

**When `next` issues a red ticket in a fix phase.** When the review gate's round failed, the round is of the current brief, and one of its standing blockers cites a red log of this opus, `ci/reds/<id>/<nn>.log`, whose log on the branch is not recorded after that round's log. Not "whenever a test commit follows the failed verdict": a test commit is not a form `next` can classify, and a red no finding cites is not false evidence (D-084). A regression test a fix round adds for a new failure (W-461's kind) needs a second red log per behaviour and certify reading it; that is out of scope here (Defaults 2).

**Which round: only one of the current brief.** A present `# brief:` must exactly equal the current `spec:` pin. With no `# brief:`, the ticket fallback is current only when `opera/<id>.md#spec` is exactly `briefs/<id>.md` and its one canonical ticket's `brief` equals that pin's blob; a custom spec pointer, absent identity or any disagreement follows the existing review path. (A blocker's `<nn>` is a behaviour number of the brief the round judged. A kind: ui build round carries no `# brief:`, and a ticket hashes `briefs/<id>.md` whatever `spec:` names, so only on the default path does the ticket name the judged brief; W-451 is a ui opus whose `spec:` is `briefs/W-451.md`. The custom pointer's re-red is W-475.)

**Which behaviour.** Each cited behaviour in 1..n (the brief's numbered behaviours) whose log is absent, not a usable red, or recorded at or before the round's `# at:`; the lowest first, one at a time (W-166, D-036): the order is the `reds` step, phase `fix`, actor builder, and its ticket is `red round <k>`. When every cited red is recorded after the round's log, the ladder goes on as before (Promise sequence).

**Replace, not add.** The new red replaces `ci/reds/<id>/<nn>.log`; the old bytes stay in git history. `red` already writes the one log per behaviour, `next`'s reds rung, `opus.red_*` and `ladder.ticket` read that name, and the review reads `ci/reds/<id>/` as before. Certify's replay (`scripts/run-builder-host.mjs`, reached from `scripts/ci-certify.mjs`) reads only `<nn>.log`, so **certify needs no change: no split landing, no code-owned file**. A second fix-round log name would be invisible to certify (it reads only `^\d\d\.log$`) and so would need certify changed and landed first (W-323): that is why this brief replaces. At derivation time `next` trusts the worktree filesystem copy: untracked or tracked-but-uncommitted bytes are visible, and an unreadable copy is stale. Certify later trusts committed branch history, so the readers may disagree until the exact replacement bytes are committed; performed fix or review work refuses a dirty or stray-`ci/` worktree. Once committed, certify replays the named tree or, after rebase, the source-neutral commit that introduced those bytes.

**Where the red is recorded: a restage on the branch.** The tree the red must run at, the fixed test over the source without the behaviour, is on no commit of the branch (W-451's red stage 416ad88f holds the unfixed test), and certify replays only a commit on the branch: its rebase is linear, so a side commit or a merge would not carry. So the order tells the builder to commit a restage at the tip (the behaviour's implementation removed, its fixed test and every other behaviour's code kept), run `next`, record the red, commit the log alone, then `git revert` the restage. The tip's source tree is the fixed tree again, the history is only appended to, and certify replays the restage commit. **`--cwd`:** the ticket binds the studio's checkout HEAD, where the log is written, and the brief's blob; never the tree the command runs at. A red with `--cwd <dir>` is bound to its tree by `red`'s own checks (a clean `tree:` identity, `<dir>`'s HEAD an ancestor of `opus/<id>`, run from that repository's root) and by certify's replay of that tree; W-468 changes neither and orders the restage instead, since no commit carries the tree a historical `--cwd` red would need.

**Red first, then the census (D-086 D).** The re-red order comes before the fix check, and before any fix order: the fix check judges the tree and the paths a finding names, so it runs once the cited red is recorded again and sees the replaced log; the restage and its revert leave the tip's source tree as the fix left it, so the check is judged at the fixed tree. For W-451 this reads: `next` names `reds`, phase fix, ticket `red round 3`; the builder (test already fixed at 1afb27bd) commits the restage, runs `next`, records the red, commits it and reverts; `next` then names the fix check.

The change is inside `next` only: `red`, the ticket store, `review`, `verdict` and certify are unchanged.

## Defaults for the Patron

1. **When a code review fails because a recorded "red" test run is wrong, the next step now tells the builder to record that red again, before anything else.** The builder fixes the test, temporarily removes the feature in a new commit, records the failing run, then restores the feature with a revert commit. Nothing is rewritten, and the merge check replays the new run as it is. This unblocks the Home screen task (W-451). Agree?
2. **A new regression test written during a fix still gets no recorded red in this task.** Recording it needs a second red file per behaviour, and the merge check (a file only you merge) would have to read it first. I propose it as a separate follow-up task. Agree?
3. **The red is ordered again only when the review's blocking finding names the red's file** (`ci/reds/<id>/<nn>.log`). A finding that only describes the red in words does not trigger it. Agree?
4. **The red is ordered again only when the failed review judged the current version of the task's brief.** If the brief was revised since (its behaviours may be numbered differently), the review is simply run again, as today. Agree?
