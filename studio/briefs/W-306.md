## Intent

D-070 C asks for a cause fix (D-039 high). This opus makes that sweep a refusal in the writer instead of prose.

After this opus, the verdict writer refuses a spec-phase verdict by the design collegium's magister (this studio's `architect`) whose brief names a CLI verb in inline code, unless the signature names one ledger file whose lines cover each such brief line and each verb on it. A brief line is a promise line when it holds an inline-code span whose whole text is one of the CLI's verbs, as the usage text lists them (`ready`, `check`, `next` and the other 36 on master). Ten of the eleven lines W-264's rounds 2 and 4 failed are promise lines by this rule (`w264-lines.out`). What it checks, and what it cannot: it checks that the ledger exists and that its lines cover every (promise line, verb) pair with a code citation and a status. It cannot check that the cited line really guarantees the promise: W-264's round-2 sweep covered brief:54, 59, 63 and 65 for `next` and round 4 still failed them on `gateDispatch`. That judgment stays with the Codex spec review.

Threat model: mistakes, not adversaries (D-045).

## Interfaces

`runVerdict` gains two refusals. When `--phase` is `spec` and the opus is not `kind: ui`, right after reading `briefs/<id>.md` it calls `readDesignMagister(manifest)`, whatever the sella: a problem is printed as `<id>: <problem>` and the writer exits 2. When `--sella` equals the magister it returns, it calls `promiseLedgerProblems(brief, transcript, briefRel)`: each problem is printed as `<id>: promise ledger: <problem>`, one per line, and the writer exits 2. That is after the flag, ownership, findings-shape and body-cap refusals it already makes, and before the session checks, the ticket claim and the write.

`promiseLedgerProblems`:

1. Promise lines are brief lines containing an inline-code span whose trimmed text is in VERBS. usageVerbs(USAGE) (new) requires every nonblank usage line to contain exactly one complete command token matching [a-z][a-z-]* immediately after bisellium, returns a problem that makes runVerdict exit 2 otherwise, and VERBS is those tokens; a conforming new verb joins without another edit. No promise line requires no ledger. The Input domain includes USAGE with usageVerbs as rejector.
2. The citation: contentLines(transcript) locates the sole accepted level-2 Findings heading, and exactly one trimmed raw line before its reported source line starts Promise ledger:; promiseLedgerProblems rejects none or several and exits 2.
3. The path after the colon, trimmed, is absolute, or starts `~/` and is absolute once `~` is the home directory; else `"<path>" is not an absolute or ~/ path`. It must be a regular file of at most 256 KiB that reads; else `<path> is not a readable regular file`.
4. Coverage: a ledger line counts only when it contains full citation tokens brief:<n> and <file>:<positive-integer-line> other than brief:, whose positive integer is not followed by a word, /, ~ or - character, nor by . followed by a token character; prefix forms including brief:3x, brief:3.5, brief:3-5, NX:20x, NX:20.5 and NX:20/notes never count. promiseLedgerProblems emits one problem for every uncovered pair in brief-line then verb order and exits 2.

How the prototype reads them. A line of the usage text names its command as `bisellium <token>` once, not after a word, `.`, `/` or `-` character, the token running to the next space and matching `^[a-z][a-z-]*$`; else `usage line <n> does not name exactly one command "bisellium <[a-z][a-z-]*>"`. A citation token is `<name>:<line>`: `<name>` is a run of word, `.`, `/`, `~` and `-` characters not preceded by one, `<line>` a positive integer not followed by a word, `/`, `~` or `-` character, nor by `.` followed by a token character (`CITATION_TOKEN`); a `<file>` token's name holds a letter and is not `brief`, and a range such as `VP:12-14` is no citation, so a ledger cites a line on its own. A counting line also names the verb and holds or scoped as whole words by the same boundaries (`wholeWord`): not after a token character, and ending as a citation's line number ends, so `next.ts` or `src/next` does not name `next`. The problem texts: no citation, ``<briefRel> names a CLI verb in code on lines <n, …>; cite the promise ledger on one line above "## Findings": "Promise ledger: <absolute path>"``; several, ``<k> "Promise ledger:" lines above "## Findings"; one only``; an uncovered pair, ``brief:<n> names `<v>`, and no ledger line cites brief:<n> with <v>, a <file>:<line> and holds or scoped``. `readDesignMagister`'s: `bisellium.yml#collegia must be a list`, `bisellium.yml#collegia declares the design collegium <k> times; exactly one row names the magister`, and `bisellium.yml#collegia: the design row's magister must be a nonblank string`.

The form the architect writes, as this brief's own ledger does: `brief:<n>, <caller>, "<promise>": <file>:<line> — holds` (or `scoped`, with what was narrowed). One line may cover several callers of one brief line.

The `docs/ADOPTION.md` paragraph states the rule above and its limits:

- A caller named outside inline code, as a full command (`bisellium next W-1`), or by function name (`gateDispatch`) makes no promise line; nor does a sentence that names no verb (W-264's brief:19).
- The ledger's reasoning is not checked, only its coverage; the word test for `check` is also met by an incidental "check".
- The log names the ledger and does not copy or fingerprint it, so an edit after signing is not seen.
- Only new signatures are judged. `next` reads signatures as before (`readSpecSignature`, `signedSpec`), so a log written before this lands, or not by `verdict`, is not re-read by this check. The census (`census.out`) finds 246 architect signatures under `studio/ci/`; 239 have promise lines and none cites a ledger, so all 239 would be refused if re-judged.
- A reviewer's spec verdict, a build or handoff verdict, and a UI opus's spec input need no ledger. A design collegium row that `readDesignMagister` refuses refuses every non-UI spec verdict, the reviewer's included.

### Input domain
