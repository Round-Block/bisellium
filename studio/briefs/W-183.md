## Intent

Decree family: host-heavy-job-capacity

Lanes on one machine run their full `npm test`, `verify` and receipt mints at the same moment. W-183 caps how many run at once with `BISELLIUM_HEAVY_JOB_SLOTS` slots (an environment variable, default 1). A slot is a kernel file lock. A process waiting for one stays alive and prints a heartbeat, so waiting never becomes a failure. Four entry points take a slot:

1. `npm test`. The `test` script becomes `node scripts/heavy-job.mjs --kind test -- node scripts/no-vendor.mjs`.
2. `bisellium ci`, around its `npm test` step only. Its `GATE_TIMEOUT_MS` clock then starts after the wait, and the wrapped `npm test` inside reuses the lease.
3. `bisellium verify`, after the manifest is read and before the source tree is hashed. Its `npm test -s` probatio reuses the lease.
4. `bisellium run`'s host path (`runBuilderCommand`), after the producer lease and before the receipt start and the 60-minute host-runner clock.

Nested work reuses the holder's lease: the `BISELLIUM_HEAVY_JOB` variable passes through `filterEnv`, which drops only `TOKEN|SECRET|KEY|PASSWORD|CREDENTIAL`. Every call of `takeHeavySlot` or `runInHeavySlot` first checks `BISELLIUM_HEAVY_JOB_SLOTS` with `readHeavyJobSlots`, and refuses a bad value before it reuses a lease or tries a slot. A reused lease then prints nothing. No entry point reads a file to learn the capacity, so the `gates` job's `record-reads.mjs` preload sees no new read. A tracked `next` step whose newest output line is the waiting line reports `waiting`, exit 0.

The queue lives in `<os.tmpdir()>/bisellium-heavy-<uid>`. Agent sessions share `TMPDIR=/tmp/claude-1000`, so every agent lane on this machine shares one queue. A shell outside the sandbox uses `/tmp` and gets a separate queue. A bwrap cell (the mint's red replays and producer gate) has a private `/tmp`, and with it a private queue. That is why a mint's inner `ci --opus` never waits on the outer receipt slot. The threat model is mistakes, not adversaries (D-045).

Promise host-cap: among processes with the same `os.tmpdir()` and uid, at most N heavy jobs hold a slot at once, where N is the largest `BISELLIUM_HEAVY_JOB_SLOTS` value among them (processes started with different values each admit by their own) — limit: a process with another temp directory (the Patron's own shell, a bwrap cell, a GitHub runner) has its own queue. Only the four entry points are capped. A reused lease is trusted to be nested (D-045): it is reused only while its slot is held, but a held slot of an unrelated process is also accepted. For the three in-process owners (`ci`, `verify`, `run`) the slot is held by a helper child. If that owner alone is SIGKILLed, the slot frees while children it already started (`ci`'s `npm test`, which reuses the lease and holds no lock of its own) may run on uncapped until they end. If the helper child itself is killed, the slot frees while the owner's work continues; the owner prints `heavy-job: slot lost kind=<kind> slot=<k>` and its result is unaffected. A process-group kill (^C, a timeout's group kill) ends both together. The wrapper (`npm test`) has no such gap: its lock is on a file its own command holds open.

Promise wait-not-fail: a process that finds every slot busy prints `heavy-job: waiting kind=<kind> slots=<n>` to stderr at once and every 30 s, retries every second, and never exits because of occupancy. The clocks that can fail it (`ci`'s step timeout, verify's gate timeouts, `run`'s 60-minute host timeout) start after it has a slot — limit: there is no order between waiters, no maximum wait and no expiry. A holder that is alive but hung holds its slot until it ends, and a waiter killed by a signal is dead. `bisellium verify` waits even when a later check (a dirty tree) would refuse it.

Promise freed-on-death: a slot is a kernel `flock` lock on `<root>/slot-<k>`, freed when the last process holding that open file ends, with no PID read. The wrapper runs its command as `flock -n -E 75 <slot> sh -c 'echo held >&3; exec "$@"' heavy-job <cmd…>`, so the command inherits the locked file. For an in-process owner the holder is `flock -n -E 75 <slot> -c 'echo held >&3; exec cat'`, whose stdin is a pipe from the owner; when the owner exits, `cat` gets EOF — limit: the in-process gaps under host-cap; descendants of the wrapped command that keep the inherited descriptor extend the hold until they end; Node creates the helper's stdin pipe close-on-exec, so no grandchild of an in-process owner keeps it open. `flock` (util-linux) must be on `PATH`, which is Linux only; without it the entry point refuses with its refusal code: exit 2, or 1 for `runBuilderCommand`.

Promise outcome-kept: once a slot is held, each command's pass or fail and its timeouts are unchanged, and a reused lease adds no output, so verify's test-gate log is unchanged — limit: when a slot is taken, the output gains `heavy-job:` lines on stderr. The wrapper reports a command killed by signal N as exit 128+N (`flock`'s convention), where a caller may have seen a signal before. It is non-zero either way, and nothing turns a real failure, flake or timeout into a pass.

Promise visible-wait: `next` reports a tracked step as `waiting` exactly when the process is alive, its output is within the step's silence budget, and the newest output line is the waiting line — limit: `next` reads only the tracked output file, so the line reaches it only when that file captures stderr. The 30 s heartbeat is below every `STEP_SILENCE_SECONDS` budget (minimum 120 s).

No test row, CI step, probatio or receipt check is removed or weakened (production lex §11).

## Interfaces

```ts
export function readHeavyJobSlots(env: NodeJS.ProcessEnv): { slots: number } | { error: string }; // BISELLIUM_HEAVY_JOB_SLOTS: unset -> 1; else ^[1-9][0-9]?$ and <= 64
export function heavyQueueRoot(): { root: string } | { error: string };                     // <os.tmpdir()>/bisellium-heavy-<uid>, 0700
export const HEAVY_WAITING: RegExp; // ^heavy-job: waiting kind=(test|verify|receipt) slots=[1-9][0-9]*$
export function takeHeavySlot(o: { kind: "test" | "verify" | "receipt"; pollMs?: number }):
  Promise<{ ok: true; inherited: boolean; release(): void } | { ok: false; error: string }>;
export function runInHeavySlot(o: { kind: "test"; pollMs?: number }, cmd: string[]):
  Promise<{ ok: true; exitCode: number } | { ok: false; error: string }>;
```

`takeHeavySlot` behaves as follows:

- **Capacity first.** `readHeavyJobSlots(process.env)`. An error returns an error before anything else, including lease reuse.

- **Inherited lease.** If `process.env.BISELLIUM_HEAVY_JOB` is `<root>/slot-<k>` with `1 ≤ k ≤ 64`, whatever this reader's own capacity, and `flock -n <it> true` exits 1 (held), it returns `inherited: true` with a no-op `release`, reading no manifest and printing nothing. Otherwise the variable is ignored.
- **Acquiring.** It tries `slot-1` with an unref'd holder child `flock -n -E 75 <slot> -c 'echo held >&3; exec cat'` (fd 3 a pipe), then `slot-2` to `slot-<slots>`. On `held` it sets `BISELLIUM_HEAVY_JOB` to that slot, prints `heavy-job: running kind=<kind> slot=<k>`, and returns. `release()` ends the holder's stdin and deletes the variable. If the holder exits after `held`, it prints `heavy-job: slot lost kind=<kind> slot=<k>`; the promise has already resolved, and nothing else changes.
- **Waiting.** Exit 75 means busy. When every slot is busy it prints the waiting line (at once, then every 30 s) and retries after `pollMs` (default 1000).
- **Errors.** Before `held`, any other holder outcome (spawn error, an exit other than 75, a signal) returns an error.

All lines go to stderr.

`scripts/heavy-job.mjs --kind test -- <cmd…>` calls `runInHeavySlot`. That checks the capacity first, as `takeHeavySlot` does: a bad value exits 2 before the command, a lease or any slot. With a reused lease it then spawns `<cmd…>` directly. Otherwise it runs the same slot loop, and each try is `flock -n -E 75 <slot> sh -c 'echo held >&3; exec "$@"' heavy-job <cmd…>`, with stdio inherited, fd 3 a pipe and `BISELLIUM_HEAVY_JOB=<slot>` in the child's environment. `held` on fd 3 means acquired. Exit 75 with no `held` means busy. Any other end before `held` is an error. After `held`, the exit is the command's (128+N for a signal), and the wrapper exits with it.

`runCi`, `runVerify` and `runBuilderCommand` call `takeHeavySlot` with kind `test`, `verify` and `receipt` respectively. Any refusal, including a bad capacity, returns their refusal code: 2 for `runCi` and `runVerify`, 1 for `runBuilderCommand`.

In `next`, report mode prints `next: <id> <step> waiting`, `health: waiting for a heavy-job slot (pid <p>, writer <w>, last output <s>s ago)` and `last-output: …`, and exits 0. `--perform` and `--track` treat the step as running, as today.

The right number depends on where bisellium runs, and a cloud host differs from a laptop.
2. **Scope of "machine-wide":** is one queue per temp directory enough? All agent sessions on this machine share one queue. Your own terminal outside the sandbox would get a separate one, and so would GitHub runners and bwrap cells. Or should your terminal share the agents' queue? That needs a fixed path that both your shell and the sandbox can write.
3. **Lock tool:** may W-183 rely on util-linux `flock`? It is installed on WSL and GitHub's Ubuntu runners. It is the one mechanism found that still works when each sandboxed command has its own process namespace, and it frees the slot when the holder dies.
4. **Order:** is "no fixed order between waiters, each retrying every second" acceptable? With a few lanes that is fine. Strict first-come order would need a heavier design.
5. **Receipt slot:** should the receipt's slot cover the whole `bisellium run`? The ladder runs `-- true`, so in practice that is just the mint. The alternative is to take it only after the builder command, which means changing the host runner.
6. **Waiting forever:** while the holder is alive, should a waiter wait with no limit, printing a heartbeat every 30 seconds, rather than failing after some maximum?
