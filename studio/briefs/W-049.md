# W-049 — harness env is scrubbed: no ambient base-URL or auth override reaches a spawned session

Spec of record, signed by the architect, 2026-09-24. The finding is W-044's
round-2 review (`studio/ci/W-044-review-2.log`, "Attended live smoke"). It
absorbs W-044's round-3/4 residue (`studio/ci/W-044-review-3.log` Judgment
3, `studio/ci/W-044-review-4.log` A1/A2), as `docs/SESSION-HANDOFF.md`
directs. This is a security opus, so Sol red-teams this brief (D-020) as
input, not authority. The `ready` gate is signed on `opus/W-049` after
`bisellium branch` (D-021). Greenlight is the Patron's (2026-09-24).

## Intent

`talk` sets its subprocess env to `filterEnv(process.env)`
(`packages/commands/src/talk.ts:311`), and `tick`'s unattended daily and
`serve`'s `POST /api/talk` use the same `performTalk`. `filterEnv`
(`packages/shim/src/redact.ts`) is a name-pattern denylist. It drops a
name matching `TOKEN|SECRET|KEY|PASSWORD|CREDENTIAL` unless an allowlist
regex `^(PATH|HOME|NODE_.*|LANG|TZ)$` lets it back in. Everything else
passes.

Measured on this machine on 2026-09-24, from inside a Claude Code session.
Only names were printed, never values. `filterEnv` **drops**
`ANTHROPIC_AUTH_TOKEN` and `CLAUDE_CODE_MESSAGING_TOKEN`. It **passes**:

- **Endpoint and auth overrides:** `ANTHROPIC_BASE_URL`, `ANTHROPIC_MODEL`,
  `USE_STAGING_OAUTH`, `USE_LOCAL_OAUTH` and `CLAUDE_CODE_OAUTH_SCOPES`.
- **Host-session links:** `CLAUDECODE`, `CLAUDE_CODE_ENTRYPOINT`,
  `CLAUDE_CODE_SESSION_ID`, `CLAUDE_CODE_HOST_SESSION_ID`,
  `CLAUDE_CODE_CHILD_SESSION`, `CLAUDE_CODE_SDK_HAS_HOST_AUTH_REFRESH` and
  `CLAUDE_CODE_MESSAGING_SOCKET`. The messaging token that pairs with the
  socket is dropped.
- **Through the `NODE_.*` allowlist:** `NODE_OPTIONS`,
  `NODE_EXTRA_CA_CERTS` and `NODE_TLS_REJECT_UNAUTHORIZED`. None was set
  here, but the regex admits them.

So the child loses the token that went with the base URL but keeps the base
URL. It then sends the credential it does have, the Patron's stored login,
to whatever endpoint is ambient. That is the round-2 finding exactly.

The host-link half explains the inconsistency seen in cascades. Some links
survive the filter and their tokens do not, so a child's auth path depends
on which parent launched it.

The code has three spawn paths, and they are not uniform:

- `start`/`resume` get the filtered env from talk.
- `claudeCodeProfile.available()` and `codexProfile.available()` spawn
  `--version` with no `env` option, so they inherit **everything**.
- `codexProfile` passes whatever it is handed.

This opus makes one rule hold at every vendor spawn bisellium makes, and
puts it where every caller goes through: the profile. W-044 put the
permission boundary in the same place for the same reason.

## Threat model

- **Defended: a polluted ambient env.** Examples are a sourced vendor env
  in a shell rc (the tokenharbor history), a parent agent host's session
  vars, and a stale override the operator forgot. The harm is that the
  Patron's stored vendor login reaches a non-vendor endpoint, or a session
  runs on a model or provider the manifest never named. The harness must
  not depend on the operator's shell hygiene.
- **Not defended: a hostile author of the env.** Whoever sets the parent's
  `PATH` chooses which binary answers to `claude`. Whoever sets `HOME`
  chooses which login is used. Both are on the allowlist because nothing
  runs without them. A wrapper `claude` on `PATH` can re-inject any
  override, and no env filter can stop that. Pinning the vendor binary is
  the next step if this threat is ever in scope (Out of scope).

## The ruling

### Allowlist, not denylist

The child env is the **projection of the parent env onto a fixed set of
exact names**. Names are matched with case-sensitive set membership. There
is no regex, prefix, suffix or case folding. Everything else is dropped,
including every variable a vendor has not invented yet.

Two precedents decide this:

- **W-044.** That opus replaced an admit-all rule (`Bash(bisellium *)`)
  with an enumerated allowlist, and made a verb that doesn't exist yet
  denied by default (its behaviour 3). Env is the same shape of problem.
- **The measurement above.** `filterEnv` is a denylist by pattern plus an
  allowlist by pattern. On one machine, on one day, it had already missed
  five endpoint/auth overrides and six host-session links, and its pattern
  allowlist admits the TLS-trust overrides. A denylist of
  `ANTHROPIC_*`/`OPENAI_*` names would miss the next `CLAUDE_CODE_*` or
  `USE_*_OAUTH` the vendor ships, so it goes stale.

### The list, and why each name is on it

A name is on the list only if it has a named consumer. Evidence for the
list came from an offline probe, not a model turn. The probe started a real
`claude` 2.1.280 in `-p --restricted --permission-mode dontAsk` with its
base URL set to a dead localhost port, and killed it at `system/init`, so no
request left the machine. It reached `init` with policy applied under
`{PATH, HOME}` alone and under the full list below. No `ANTHROPIC_*` or
`CLAUDE_*` name is needed to boot. `init` comes before any auth request, so
the probe proves boot, not login. Login is proved by the attended smoke
(Acceptance).

| Name | Consumer |
|---|---|
| `PATH` | Node resolves the vendor binary against the child env's `PATH`. The node launchers' `#!/usr/bin/env node` needs it too. It seeds the vendor Bash tool's shell. |
| `HOME` | The vendor's stored login and config (`~/.claude`, `~/.claude.json`, `~/.codex`). |
| `SHELL` | The vendor Bash tool picks its shell from it. That shell runs the admitted verbs. |
| `TMPDIR` | Vendor temp files. Under the bubblewrap sandbox it is the only writable temp dir. |
| `HTTPS_PROXY`, `https_proxy`, `HTTP_PROXY`, `http_proxy`, `NO_PROXY`, `no_proxy` | Transport. Under the sandbox all egress goes through its filtering proxy, and without these a talked turn cannot connect. |

These 10 names are the whole list. It is written out literally in both the
code and the test.

**Why proxies pass and base URLs don't.** A base URL changes the TLS
endpoint itself, so the vendor client hands the credential to that host by
design. A proxy relays a tunnel whose TLS endpoint is still the vendor's
host, verified against the trust store. The credential leaves TLS only if
the verifier trusts an interceptor. The env route to that is closed:
`NODE_EXTRA_CA_CERTS`, `NODE_TLS_REJECT_UNAUTHORIZED`, `SSL_CERT_FILE` and
`NODE_OPTIONS` are all off the list.

**Accepted with eyes open:**

- **Metadata.** A proxy, polluted or not, sees the destination host, the
  timing and the volume of every turn. It can also refuse or delay them.
  This is traffic analysis and denial of service, not credential
  disclosure.
- **Machine-trusted interception.** A TLS-inspecting CA installed in the
  **system** trust store (a corporate middlebox) can read the credential.
  That trust belongs to the machine owner, like managed settings, and no
  env filter reaches it. An inspecting proxy whose CA is *not* in the
  system store makes talk fail TLS, which is fail-closed.
- **`NO_PROXY`/`no_proxy` bypass.** These can only exempt hosts from the
  proxy, meaning a direct connection to the same vendor host with the same
  TLS checks. They cannot change the endpoint. Under the sandbox a direct
  connection is refused, which is fail-closed. They stay on the list
  because without them a sandboxed or corporate operator cannot exempt
  local hosts.

`ALL_PROXY` is off the list: the vendor documents the three proxy names
above and not this one.

**Deliberately off the list, with the reason:**

- `LANG`, `LC_*` and `TZ`: no consumer in a `-p` turn. The vendor's shell
  snapshot sets the Bash tool's locale itself.
- `USER` and `LOGNAME`: the probe booted without them. The one claimed
  consumer, macOS keychain lookup, is unverified, and bisellium runs in
  WSL.
- `CLAUDE_CONFIG_DIR` and `CODEX_HOME`: these choose which login is used,
  so they are auth overrides. A non-default config home becomes an explicit
  opt-in if one is ever needed.
- `TERM`: headless.
- Everything `ANTHROPIC_*`, `OPENAI_*`, `CLAUDE*` and `USE_*_OAUTH`.

**The harness sets no variables of its own.** Talk sets none today. The
admitted verbs take `--sella`/`--studio` as flags, and `--restricted` drops
the hooks that read `BISELLIUM_SELLA`. Adding one later is an edit to this
list and to its test.

### Scope: every vendor spawn a harness profile makes

There are **six entry paths over four spawn expressions**:

- **claude.** `claudeCodeProfile.start` and `.resume` share `runClaude`'s
  `spawnSync("claude", …)` (`claude-code.ts:105`). `.available()` has its
  own `spawnSync("claude", ["--version"], …)` (`claude-code.ts:142`).
- **codex.** `codexProfile.start` and `.resume` share `runCodex`'s
  `spawn("codex", …)` (`codex.ts:138`). `.available()` has its own
  `spawn("codex", ["--version"])` (`codex.ts:190`).

Each of the four expressions builds its child env with the one function,
and the tests reach all six entry paths (behaviours 1–3). No second env
path exists. The shim's other subprocesses are the `fake` script and the
git/worktree helpers, and none of them is a vendor binary. Doing this in the profile, not in `performTalk`, covers every
caller by construction:

- talk start and resume.
- tick's unattended dailies (`talkOnce`).
- `serve`'s `POST /api/talk`.
- Any future caller of a profile, including W-046's cascade driver.

`available()` is in scope even though it only asks for a version. It is a
spawn of the vendor binary, and "inconsistent by spawn path" is the defect.

**Codex:** it is **in scope** wherever bisellium spawns it. That means
`talk --harness codex`, which uses the same profile seam. It is **not in
scope** where the orchestrator's shell runs `codex exec` directly: that is
not bisellium code. Those spawns belong to W-046, along with codex's
config-file override channel (see Out of scope).

**`run`:** out of scope, with a reason. `run -- <cmd>` is the operator's
arbitrary command, run in the operator's env and attributed to a sella.
Bisellium doesn't choose the binary, and the child is usually `npm` or
`git`. It is not a harness session. Scrubbing it to this list would break
builds without protecting anything. `bisellium run -- claude` gets exactly
what `claude` gets in the operator's shell. A sella session that bisellium
launches goes through a profile, and therefore through this rule.

### Where `talk`'s `filterEnv` fits

`talk.ts` keeps `filterEnv` unchanged. The `fake` profile reads
`BISELLIUM_FAKE_MODE` from `opts.env` in-process, and `talk.test.ts`
depends on that. For a vendor profile, `filterEnv`'s output is only the
parent env the allowlist then projects, so it is harmless and it is not the
boundary. `redact.ts` does not change. `filterEnv` stays `verify`/`ci`'s
probatio filter (Out of scope).

## Interfaces

- **No exported surface changes.** A new internal module,
  `packages/shim/src/harness/env.ts`, exports `harnessEnv(parent:
  NodeJS.ProcessEnv): NodeJS.ProcessEnv`, which returns a **new** object.
  That object holds every listed name whose parent value is not
  `undefined`, with the value copied verbatim, and nothing else. It never
  mutates `parent`. These are the contract, and behaviours 1–4 test them.
- **Design constraints, checked by review, not by tests.** The list is a
  module-local frozen array. `harnessEnv` is not re-exported from
  `harness/index.ts` or the shim index. The tests are black-box over what a
  stub vendor binary receives, so neither constraint is observable to them.
  They keep the list from becoming something a caller can configure, and
  they keep the tests off an import that doesn't exist at HEAD, so every
  red stays assertion-level (engineering lex §2, W-044's pattern). The
  censor checks both by reading the code. A violation is a review finding,
  not a behaviour failure.
- **Seam contract change** (`HarnessStartOpts.env` /
  `HarnessResumeOpts.env`, `packages/shim/src/harness/types.ts`):
  - Before: "the env the child gets".
  - After: "the parent env a vendor profile projects through the harness
    allowlist". The `fake` test double still reads test flags from it
    in-process.
  - Documented reason: this opus. Write it as the field's doc comment.
  - No production caller passes a variable the child needs. The only
    callers that did are two tests, `STUB_SCENARIO` and `TALK_STUB_LOG`,
    and both migrate here (Test hardening).
- **Header comments.** Rewrite the `claude-code.ts` and `codex.ts` header
  comments to state the env rule.

## Behaviours to test

All four live in a new `packages/cli/src/harness-env.test.ts`. It imports
only exports that exist at HEAD: `claudeCodeProfile` and `codexProfile`
from `@bisellium/shim`, `runTalk` from `./talk.js` and `runTick` from
`./tick.js`. All imports are static, so no module loads while `process.env`
is swapped. Its `BISELLIUM_ONLY_BEHAVIOUR` harness is copied from
`lifecycle.test.ts`, and block N is behaviour N.

**Stubs.** The test writes node stubs named `claude` and `codex` into a
temp bin dir:

- **Logging.** On every invocation, `--version` included, a stub appends
  one JSON line to a log file. The line holds `{bin, kind:
  "version"|"turn", args, env}`, where `env` is the stub's whole
  `process.env`. The log path is **a literal in the stub's source text**,
  never read from env, because an env-carried path would itself be
  scrubbed.
- **Replies.** A stub never executes what it is handed. It exits 0 on
  `--version`. Otherwise it prints a normal envelope: JSON with
  `session_id: "sess-w049"` for claude, and JSONL with a session event and
  one `agent_message` for codex.

**The parent env is synthetic, always** (`SYNTH`):

- **Why.** Red logs are committed, so no real ambient value may reach a
  stub or a log.
- **Allowlisted names.** `SYNTH` holds every allowlisted name except
  `http_proxy`, which is left out so the no-invention property is tested.
  Each has a sentinel value:
  - `PATH` = `<binDir>:<dirname(process.execPath)>:/usr/bin:/bin`.
  - `HOME` and `TMPDIR` are test-made temp dirs.
  - `SHELL` = `/bin/sh`.
  - The proxies are `http://proxy.w049.invalid:3128`.
- **The guard set.** `SYNTH` also holds every name in the set below, with
  sentinel values:
  - Endpoint overrides: `ANTHROPIC_BASE_URL`, `ANTHROPIC_BEDROCK_BASE_URL`,
    `ANTHROPIC_VERTEX_BASE_URL`, `OPENAI_BASE_URL`, `USE_STAGING_OAUTH`,
    `USE_LOCAL_OAUTH`.
  - Credentials and provider switches: `ANTHROPIC_AUTH_TOKEN`,
    `ANTHROPIC_API_KEY`, `CLAUDE_CODE_OAUTH_TOKEN`,
    `CLAUDE_CODE_OAUTH_SCOPES`, `CLAUDE_CODE_USE_BEDROCK`,
    `CLAUDE_CODE_USE_VERTEX`, `OPENAI_API_KEY`, `ANTHROPIC_MODEL`.
  - Config-home redirects: `CLAUDE_CONFIG_DIR`, `CODEX_HOME`.
  - Host-session links: `CLAUDECODE`, `CLAUDE_CODE_ENTRYPOINT`,
    `CLAUDE_CODE_SESSION_ID`, `CLAUDE_CODE_HOST_SESSION_ID`,
    `CLAUDE_CODE_SDK_HAS_HOST_AUTH_REFRESH`, `CLAUDE_CODE_MESSAGING_SOCKET`.
  - Trust and runtime injection: `NODE_OPTIONS`, `NODE_EXTRA_CA_CERTS`,
    `NODE_TLS_REJECT_UNAUTHORIZED`, `SSL_CERT_FILE`, `ALL_PROXY`.
  - Near-misses: `PATH_ZZ`, `ZZ_HOME`, `HTTPS_PROXY_ZZ`, `Path`, `home`,
    `LANG`, `LC_ALL`. These kill prefix, suffix, regex and case-folding
    implementations, and a re-added locale rule.
  - Test plumbing: `TALK_STUB_LOG`, `STUB_SCENARIO`, `BISELLIUM_FAKE_MODE`.
    No test-only channel may survive.
  - A future var: `ZZ_FUTURE_VENDOR_BASE_URL`.
- **Direct profile calls** pass `SYNTH` as `opts.env`.
- **Calls that read `process.env`** are `available()`, `runTalk` and
  `runTick`. For these the test copies the real `process.env`, deletes
  every key, assigns `SYNTH` and restores the original in `finally`.
- **Output.** Assertion details print env **names only**, sorted, never a
  value.

**The property** checked on every logged invocation: the stub's env name
set **equals** the allowlist ∩ the parent's name set, and each surviving
value is **identical** to the parent's. Identical `PATH` also means the
scrub cannot make the 127 residue worse. Guard assertions keep this from
passing vacuously:

- `SYNTH` contains the whole guard set.
- Every call adds exactly the records the spawn map below requires.
- `http_proxy` is absent from `SYNTH` and from every child env.

This is the guard, not a deny list. The property is set equality.

**The spawn map is exact, never aggregate.** Checking that each call site
logged "at least one" record would let a duplicated `start`, an omitted
`resume` or an extra vendor launch pass. That is W-044's
first-occurrence/single-instance class. So:

- The test takes the log's length immediately before each call, and
  partitions the records that call added.
- Every direct profile call must add **exactly one** record, with the
  right `bin` and `kind` and the right argv form:
  - claude `start`: no `--resume`.
  - claude `resume`: `--resume` followed by the id the test passed.
  - codex `start`: argv begins `exec` and has no `resume`.
  - codex `resume`: argv begins `exec resume` followed by the id the test
    passed.
  - Each `available()`: `kind: "version"`, argv exactly `["--version"]`.
- The property is then asserted on that one record, and on no other.

At HEAD all of this counting and form checking passes. Only the env
assertions fail. So each red is the env property, and a count mismatch
after the fix points at a regression in the spawn map.

1. **The claude profile's session spawns hand `claude` exactly the
   allowlist projection.** `claudeCodeProfile.start` and `.resume` are
   called directly with `opts.env = SYNTH`, and the property holds on both
   logged turns. `SYNTH` deep-equals a copy taken before the call, so the
   parent was not mutated.
   - At HEAD this fails: `opts.env` is passed through verbatim, and the log
     lists every guard name.
2. **The claude availability probe hands `claude --version` exactly the
   allowlist projection.** `claudeCodeProfile.available()` runs under the
   `process.env` swap. It returns `true`, the property holds on the logged
   `version` invocation, and `process.env` still deep-equals `SYNTH` after
   the call.
   - At HEAD this fails: `available()` sets no `env`, so it inherits the
     whole swapped `process.env`.
3. **The codex profile, all three spawns.** `codexProfile.start` and
   `.resume` are called with `opts.env = SYNTH`, and `.available()` runs
   under the swap. The property holds on all three logged invocations,
   and the parent is unmutated.
   - At HEAD this fails on all three.
4. **Both talk entry points, and the unattended path, carry the scrub.**
   - **Setup.** Use a temp copy of `examples/sample-studio`, whose magistri
     default to `claude-code`, under the `process.env` swap.
   - **Runs.** `runTalk --model-only` runs twice (a start, then a resume).
     `runTick` then runs with no `opts.talk`, so it takes the real
     `talkOnce` seam, as in `talk-boundary.test.ts` behaviour 4.
   - **Partitions.** The log is partitioned per phase, and each partition
     is asserted exactly:
     - First `runTalk`: exactly `[version, turn]`, and the turn is a claude
       `start`.
     - Second `runTalk`: exactly `[version, turn]`, and the turn is a
       claude `resume` of `sess-w049`.
     - `runTick`: exactly one `[version, turn]` pair per due magister, in
       that alternation, with the turn count equal to the dailies written.
       A magister whose session file exists resumes `sess-w049`; every
       other magister starts.
   - **Checks.** The property holds on **every** record in every
     partition. The tick still writes one daily acta per due magister.
   - At HEAD this fails. Talk's `filterEnv` output still carries
     `ANTHROPIC_BASE_URL`, `ANTHROPIC_MODEL`, the host links, the near-misses
     and `NODE_*`, and the probes carry everything. The dailies are written
     anyway: the defect is silent, which is the point.

## Test hardening (the absorbed W-044 residue, not behaviours)

These change existing tests. At HEAD's shim they pass, so none has a red,
and none is numbered. Numbering one would force either a fabricated red or
a mutation result filed as a red. The second is the provenance fault W-044
round 3 caught (F3). Their evidence is the censor's mutation run, below.
W-044 is `done`. This brief is the recorded handoff of
`talk-boundary.test.ts` and `harness.test.ts` to W-049, for exactly these
edits.

- **Stub plumbing leaves the env (forced by this opus).**
  - `talk-boundary.test.ts`'s stub reads its log path from `TALK_STUB_LOG`.
    Move the path into the stub's source text.
  - `harness.test.ts`'s stubs read `STUB_SCENARIO`. Write one stub per
    scenario into its own bin dir, and select the scenario with `PATH`,
    which is allowlisted.
  - Nothing else about either stub changes. In particular,
    `talk-boundary`'s stub still does not log `--version`, so its counts
    stand.
- **A1: taken.** `checkPolicy`'s start branch also asserts where the file
  is, beyond the current `endsWith("/system-prompt.md")`:
  - `basename(file)` is `system-prompt.md`.
  - `basename(dirname(file))` matches `^bisellium-sysprompt-[A-Za-z0-9]{6}$`.
  - `dirname(dirname(file))` equals `os.tmpdir()` as the test process sees
    it.

  This kills W-044's M24 (a fixed `/tmp/system-prompt.md`) and M25 (a
  relative `x/system-prompt.md`). Deletion after the call is already
  asserted in `harness.test.ts` ("temp file deleted after the call"), so
  nothing is added for it.
- **A2: taken.** The `talk-boundary` stub prints a fixed
  `session_id: "sess-stub"`. Behaviour 4 then asserts every resume argv's
  session id literally: `argv[2] === "sess-stub"`. This replaces the
  shape-only check for that slot, and the header comment that calls the id
  unpredictable is corrected. This kills a profile or talk path that
  resumes against any id other than the one the harness returned.
- **The 127 allow-half: re-cut, with one share kept here.**
  - **Evidence for this spec.** The vendor Bash tool runs commands under a
    shell snapshot (`~/.claude/shell-snapshots/snapshot-zsh-*.sh`). The
    snapshot contains its own `export PATH=<captured value>`: one line was
    inspected here, with the value redacted.
  - **What that means.** The PATH a harness hands the process is not shown
    to be the PATH the Bash tool resolves `bisellium` against. A
    stub-based test of the spawn env would go green while the real session
    still exits 127. That is vacuous evidence, the kind this repo refuses.
  - **Why fixing it isn't scrubbing.** The fix adds reach: a PATH entry
    that resolves `bisellium`. Every entry prepended to a session's PATH
    shadows resolution for every command that session runs. In this repo
    that entry would be `node_modules/.bin`, which holds every dependency's
    bins. It needs its own threat review, not a rider on this one.
  - **The cheaper fix.** It may be install-side: `bisellium` on the
    operator's login PATH.
  - **W-049's share.** `PATH` passes verbatim, which behaviours 1–4 pin, so
    the scrub cannot make 127 worse. The attended smoke records the
    allow-half as a baseline.
  - **File as a new opus:** "a talked session can run the admitted verbs:
    `bisellium` resolves in the vendor's Bash tool". Until it lands, the
    boot bundle's "run `bisellium`" instruction is broken in talked
    sessions. That was already true, and it is now written down.

## Order of work, and where each red comes from

The leak is live at HEAD. Work from the opus worktree root. Before
trusting any run, check `readlink -f node_modules/@bisellium/shim`. If it
resolves to the main checkout, you are measuring the wrong file.

- **Step 1: reds.** Write `harness-env.test.ts` and add it to
  `package.json`'s `test` script, and nothing else. Record each red:

      BISELLIUM_ONLY_BEHAVIOUR=<n> npm run -s bisellium -- red W-049 --behaviour <n> --repo . --studio studio -- node --import tsx packages/cli/src/harness-env.test.ts .

  Use n = 1 to 4, and confirm the four logs differ. Then check each log
  twice:
  - **Values.** A fixed-string grep for every sentinel **value** in
    `SYNTH` must return **no matches**. So must a grep for the values of
    the real `ANTHROPIC_*`, `CLAUDE_*` and proxy variables in your own
    shell. Pipe that to `grep -c` and never print a value.
  - **Names.** Every failing assertion's detail is a sorted list of
    variable **names** and nothing else.

  Commit the test and reds.
- **Step 2: test hardening.** Rework the two stubs and apply A1/A2. Then
  run `talk-boundary.test.ts` and `harness.test.ts` against the
  **unchanged** shim: both must be green. Land this as its own commit
  **before any production file changes**. That commit is how the censor
  shows that the rework neither weakened nor broke either suite.
- **Step 3: implementation.** Add `harness/env.ts`, the four spawn expressions,
  the `types.ts` doc comment, the header comments and `docs/ADOPTION.md`.
  Behaviours 1–4 go green along with the full suite.

If any other existing test breaks at step 3, stop and report. It means a
caller relied on a variable crossing the spawn, which is exactly what this
opus removes.

**Evidence is name-level, never a live exploit.** Do not run a listening
endpoint to capture what a child sends. Do not run a real vendor CLI with
a live override before the fix. Do not print or log a real env value
anywhere, including debugging output that could end up in a red.

## Out of scope

- **Which binary answers to `claude`/`codex`.** `PATH` decides, and a
  wrapper can re-inject env (Threat model). Pinning an absolute vendor path
  is its own opus if this threat is ever wanted.
- **Re-pollution inside the vendor Bash tool.** The shell snapshot
  re-sources the operator's rc for the Bash tool's subprocesses. This opus
  governs the vendor process's own env, which is what the vendor's API
  client uses. The admitted verbs (`context`, `query`, `check`) make no
  vendor calls. The snapshot belongs to the vendor.
- **Settings-borne env.** A `settings.json` `env` block or an
  `apiKeyHelper` is already ignored by W-044's `--restricted`. Managed
  settings belong to the machine owner.
- **Codex spawned outside bisellium, and codex's config file.** A
  `~/.codex/config.toml` `model_provider`/`base_url` is an override channel
  no env filter reaches. Both go to **W-046**, whose `-c` policy overrides
  are the place for them. Its brief should carry the condition: every
  codex spawn goes through `codexProfile`.
- **Vendor-mediated subagent spawns** (the Agent tool's builders and
  censors). Part of the "inconsistent by spawn path" evidence came from
  those spawns. The vendor makes them, not bisellium, and this opus does
  not govern them. The Patron fixed the root cause operator-side.
- **`run`, `verify`/`ci` and `providers`.**
  - `run` is the operator's command in the operator's env (The ruling).
  - Probatio commands keep `filterEnv`. Its `NODE_.*` rule admits
    `NODE_OPTIONS`/`NODE_TLS_REJECT_UNAUTHORIZED` to repo test commands.
    Those already run arbitrary repo code, so no credential-redirect path
    is added. Reopen this only if a probatio ever talks to a vendor.
  - `providers`' `npx quota-axi` spawn is an operator act, as W-044 ruled.
- **The `fake` profile.** It is a test double that spawns a repo script,
  with no vendor and no network. It keeps its env contract.
- **The 127 / PATH fix.** It gets a new opus (Test hardening, "The 127
  allow-half").
- **Windows env names** (`SYSTEMROOT`, `USERPROFILE`, …). Bisellium runs
  in WSL.
