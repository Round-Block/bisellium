### Defect 1 as filed is contradicted by the contract

The filing says `waived` "is first-class everywhere else" and that
`check.ts` "accepts it at three sites". The W-026 round-6 and round-7
reviews (`ci/W-026-review-6.log` B6.1, `ci/W-026-review-7.log` A7.3) cite
`check.ts:487/495/509`. Line 488, between them, says:

```

```

`docs/ADOPTION.md` §Lifecycle (fixed) says: "`waived` needs a `reason` and
is **never allowed on an automated gate**." The fixture
`examples/fixtures/bad-waived-automated` pins it, with EXPECT =
`probatio.waived.automated`, `probatio.waived.reason`. The lab11 record
(`tests: { status: waived, waived_by: patron, note: … }`) trips **both**
block rules, and it could only ever be reached by a hand edit.

So `done` refusing a waived automated gate is the contract working
correctly. The filed behaviour 1 ("`done` accepts an automated gate
recorded as `waived`") is **not built**. Reversing it would be a contract
change: the ADOPTION prose, a block rule, a fixture, and `verify`'s
"waived gates are untouched" clause would all move together. That is the
Patron's call (see "Patron decision point").

### What is actually wrong

The drift runs the other way: the code honours waivers the contract
forbids, and nothing can write a waiver the contract allows.

1. **`done` and `check` accept a waived agent gate.** The contract says
   `done` "needs all non-human gates passed and any recorded human gate
   passed or waived". But `lifecycle.ts:223` accepts `waived` on every
   `kind: agent` gate, and so does `check.ts`'s `notPassed` (`:495`). That
   includes `review`, D-014's single review gate, and `spec`, the
   architect's gate. Today a hand-written `review: { status: waived,
   reason: x }` takes an opus to `done` without a censor ever running, and
   `check` stays clean. That breaks engineering lex §1 ("with … a lead
   review") and §7 ("every `done` item carries … review note path").
2. **`done` honours any waived human gate, whatever its shape.** A bare
   `{ status: waived }` passes, even though `check` blocks it
   (`probatio.waived.reason`). So `done` writes a state that `check` then
   blocks.
3. **Nothing writes a waiver.** The only CLI writers of a gate's `status`
   are `verify` (automated gates), `ready` (`spec`) and `review` (the
   review gate). Every `waived` in existence was typed by hand, which
   CLAUDE.md forbids. The greenlit behaviour 3 ("reaches `done` through the
   CLI end to end, with no hand-edited front matter") cannot be met by any
   waiver today.

## Rulings

### Which gates are waivable: `kind: human` only

What binds this ruling:

- **`docs/ADOPTION.md` §Lifecycle.** Non-human gates must be *passed* for
  `done`, and `waived` is never allowed on an automated gate.
- **D-014.** `censor` is the single review gate. A waivable `review` gate
  would be a second path around it.
- **Engineering lex §1 and §7.** A `done` item carries a lead review.
- **`spec`.** `ready` is its only writer, and D-020's Sol red-team happens
  before it is signed. A waived `spec` means an opus built with no spec of
  record. (On active opera, `state.building.spec` already blocks a
  non-passed `spec`. The only hole is the jump to `done`, which this opus
  closes.)
- **`@bisellium/schema`** (`index.ts:58`): "human: the patron decides". A
  Patron waiving a gate whose owner is the Patron is the one coherent
  reading of "Patron waiver".

Consequence, stated plainly: the real officina (`studio/bisellium.yml`)
declares no human gate, so **nothing in `studio/` is waivable**, before or
after this opus. The sample studio's `patron` gate is the working example.

### What a waiver is, as a record

Only `bisellium waive` writes this entry, into the gate's existing node
(merge, not replace, through `editOpusFrontMatter`):

```yaml
probationes:
  patron:                      # a kind: human gate
    status: waived
    reason: "docs-only opus; the Patron's call is recorded in D-900"
    waived_by: D-900           # a decision id, same role as halt's halted_by
    sella: guest               # who ran the command
    at: 2026-09-24T12:00:00.000Z
```

A waiver is **honourable** when all of the following hold:

- the gate is `kind: human`;
- `reason` is a string with non-whitespace content;
- `waived_by` is a string, and `safeItemPath(<studio>/decisions, waived_by)`
  resolves to a file that exists;
- that decision's front-matter `by` equals `manifest.patron ?? "patron"`.

Why a decision anchor, and why `by`: the CLI cannot authenticate a human,
and neither can `halt`. `halt` carries its authority as a mandatory
`--decision` (W-042), and a waiver removes a gate, which weighs at least as
much as a halt. Checking `by` makes the word "Patron" mean something
mechanically. It is **not** authentication: anyone can hand-write a
decision that says `by: patron`. What the check buys is that the claim is
a named, reviewable file in a PR under `master_protection`, rather than an
unexplained status flip.

### How the trace reads, permanently

A waiver is never a pass, and it never turns into one:

- `done` writes only `state`. The waived gate keeps `status: waived`,
  `reason` and `waived_by` for as long as the record exists. The web gate
  ladder already renders `waived` at half height (`gateLadder.ts:27`).
- `done`'s stdout names every gate it honoured as a waiver:
  `W-x: done (waived: patron by D-900)`.
- `waive` emits `workflow.gate_evaluated` with `workflow.gate.status =
  waived` and `workflow.gate.evidence = decisions/<id>.md`. Both attribute
  names already exist, and no new `workflow.*` name is added.
- Nothing overwrites a waiver. `verify` runs only automated gates, `review`
  writes only the review gate, and `ready` writes only `spec`. None of those
  is waivable. `waive` itself refuses an already-waived gate.

## `done`'s gate predicate

This table is the whole contract for `runDone`'s loop. Cells not marked
"changed" are today's behaviour and must stay byte-for-byte the same
(including exit code 1 for a gate refusal). "Unrecorded" means the gate id
is absent from the opus's `probationes`.

| kind | unrecorded | pending / failed / stale | passed | waived, honourable | waived, not honourable |
|---|---|---|---|---|---|
| automated | refuse | refuse | pass iff `certifies` starts `tree:` | refuse, **changed message** | refuse, **changed message** |
| agent | refuse | refuse | pass | **refuse (changed)** | **refuse (changed)** |
| human | not demanded | refuse | pass | pass, **named on stdout (changed)** | **refuse (changed)** |

Refusal output keeps its first line prefix, `<id>: gates not passed:`, and
lists each refused gate id. For each refused gate recorded `waived`, the
output adds the reason:

- automated: names `probatio.waived.automated`, says no CLI verb writes that
  record, and gives the remedy: revert the out-of-band write with git, then
  run `bisellium verify`. That remedy terminates. After the revert the gate
  is no longer waived, so `verify` runs it. "Run verify" on its own does not
  terminate, because `verify` never touches a waived gate. That was W-026
  B6.1's loop.
- agent: names `probatio.waived.agent`.
- human, not honourable: names the specific failed condition. That is
  `reason` if the reason is missing or blank, `waived_by` if the decision id
  is missing or not a string, and otherwise the decision id together with
  `not found` or with the patron id it failed to match.

`done` does not honour `since` exemptions. That is today's behaviour and
it is unchanged.

## Interfaces

```
usage: bisellium waive <opus> --gate <id> --reason <text> --decision <id> [--sella <id>] [--studio <dir>] [--now <iso>]
```

`export function runWaive(args: string[], opts: WriteOptions = {}): WriteResult`
goes in `packages/commands/src/lifecycle.ts` as §6, with `WAIVE_USAGE`
equal to the line above.

Guard order. Every refusal exits 2 and writes nothing: no front matter, no
event.

1. Flags: `--gate`, `--reason` and `--decision` are all required, and
   `--reason` must have non-whitespace content. Otherwise print usage.
2. `--now` is ISO; `openStudio`.
3. The opus exists (`safeItemPath` under `opera/`). Otherwise `unknown opus`.
4. `recordOwnerRefusal(root, opusId)`, immediately after step 3, as in
   `ready`/`done`/`halt`.
5. The state is `building`, `verifying` or `review`. Anything else refuses
   with `<opus> is not building, verifying or review (state: <s>)`, the
   same wording as `done`.
6. `--gate` is declared in the manifest. Otherwise the message says `not
   declared`.
7. The gate kind is not `automated` (message names
   `probatio.waived.automated`) and not `agent` (message names
   `probatio.waived.agent`).
8. The gate's recorded status is unrecorded, `pending` or `stale`. A
   `passed` or `failed` gate is a verdict, and replacing one is W-040's
   append-only territory, so it refuses with a message containing
   `already <status>`. `waived` refuses with `already waived`.
9. The `--decision` check is the same predicate `done` uses (next
   paragraph). Its message names the decision id, plus `not found` or the
   patron id.

Then write the five keys shown above, emit one event, and print
`<opus>: <gate> waived by <decision>`.

**One predicate, two callers.** `runWaive` step 9 and `runDone`'s human
branch call the same module-private function in `lifecycle.ts`:

```ts
function patronDecisionProblem(root: string, manifest: Manifest, decisionId: unknown): string | undefined
```

It returns `undefined` when the decision is honourable, and a problem
string otherwise. A decision id reaches a filesystem read, so it goes
through `safeItemPath` (engineering lex §2, D-008), never a raw `join`.
The function never throws. If `decisionId` is not a non-empty string, if
the decision's front matter cannot be read or parsed, or if its `by` is
missing or not a string, the result is a problem string that names the
decision id (or `waived_by` when there is no usable id).

**Check rule.** One line in `check.ts`, directly after `:488`, with the
same shape and the same "every state" scope:

```ts
if (probatioKind.get(gid) === "agent") add("probatio.waived.agent", "block", where, `agent gate "${gid}" cannot be waived`);
```

Register it in `packages/cli/src/rules/ids.ts`. `notPassed` is **not**
edited, because the new rule already blocks the record and editing
`notPassed` as well would report the same defect twice. Migration: `grep`
on 2026-09-24 finds no waived agent gate in `studio/opera/` or
`examples/`. The only one anywhere is the `qa` line in
`lifecycle.test.ts`'s `passingLines` fixture, which this opus changes (see
Files owned).

## Out of scope

- **Waivable automated gates.** See the section above.
- **A CLI writer for a human gate's `passed`/`failed` verdict.** None
  exists today, which is the same gap as item 3 of "What is actually wrong"
  but for a verdict. `studio/` has no human gate, so there is no demand.
  Open it when a human gate is declared in `studio/`.
- **Un-waiving, amending a waiver, or waiving over a verdict.** These are
  W-040's append-only correction territory. `waive` refuses them.
- **Making `verify` re-run a waived automated gate.** That would be a
  cleaner end to the lab11 loop, but it changes `verify`'s documented
  contract. `done`'s message now names a remedy that terminates instead.
  Note for W-040's spec: its line "every automated gate is re-produced by
  re-running `verify`" is false for a waived one.
- **A check rule for waiver shape beyond `reason`.** Examples are a missing
  `waived_by`, or a decision not signed by the Patron. `check` cannot
  authenticate a decision any more than it can authenticate a hand-written
  `passed`. The anchor is enforced at the one writer (`waive`) and the one
  state writer (`done`), which is D-021's pattern ("No check rule").
- **Editing `check.ts`'s `notPassed`.** The new block rule already covers
  it (see Interfaces).
- **`done` honouring `since` exemptions.** That is today's behaviour and it
  is unchanged.
- **D-021's list of guarded writers.** `waive` joins that list in practice
  (behaviour 7). The decision text is not edited here.
- **New `workflow.*` attribute names**, and any change to lifecycle state
  ids.
- **W-040** (gate correction) and **W-032** (PR gate). Both are adjacent
  and both are separate.
