# W-034 — done: honour a waived gate, and refuse when run against the wrong ref

## Intent

Two defects in `bisellium done` (`packages/commands/src/lifecycle.ts`),
both found while reviewing W-026 and both explicitly out of that opus's
scope. They matter more now than they did before D-015: `done`'s gate is
the sole writer of `state: done` in the codebase, and round 7 of W-026
established that `merge`'s entire fail-open guarantee rests on it.

## 1. A Patron waiver cannot be honoured

`waived` is first-class everywhere else. `check.ts` accepts it at three
sites, the gate ladder renders it, and `verify.ts` explicitly never
touches a waived gate — that is the point of waiving one.

But `done` refuses an automated gate that is `waived`, so an opus carrying
a Patron waiver can never reach `done` through the CLI. The only routes
are to un-waive a Patron decision or to hand-edit front matter, which
CLAUDE.md forbids.

This surfaced twice: as W-026's round-6 lab11, where the absence rule
produced the same non-terminating refusal at the merge layer, and again in
round 7 once that rule was removed and the defect was seen to live in
`done` all along.

## 2. `done` succeeds against the wrong ref, then strands the operator

Under D-015 an opus's record exists on both the trunk and its branch, and
`done` writes whichever checkout it is run from.

Observed on W-026's own PR (round 7, A7.2): `bisellium done W-026` run on
master **succeeds**, because master's copy reads `state: building` with
`tree:`-prefixed gates — gates certifying a tree from several commits ago.
It dirties the trunk, including `studio/.bisellium/events.jsonl`, and the
subsequent `git checkout opus/W-026` aborts on the uncommitted change.

Git names the escape, so this is not a loop, but the operator has written
a lifecycle transition to a ref where it means nothing and has to unpick
it. `merge` reads `state` from the branch ref (W-026, B6.3), so a trunk
`done` does not even satisfy the merge it was run for.

## Relationship to W-033

W-033 asks the general question — which copy of an opus record is
authoritative, and how does a command know. Defect 2 is an instance of it
and may be answered wholesale there.

**Do not build defect 2 before W-033 is decided.** Defect 1 is
independent of that question and can proceed on its own.

## Behaviours to test

1. `done` accepts an automated gate recorded as `waived`
2. `done` still refuses an automated gate that is absent, `failed`, or
   carries only a `dirty:` certificate
3. A waived gate reaches `done` through the CLI end to end, with no
   hand-edited front matter

(Behaviours for defect 2 to be added once W-033 settles the provenance
question.)

## Out of scope

- `merge`'s own reads. W-026 owns those and round 7 judged the sequence
  converging.
- The provenance decision itself — that is W-033.

## Note

Round 7 verified `done`'s guard directly against five record shapes and
found only one hole: an *arbitrary* `tree:` hash passes, which `merge`'s
own comparison then catches. The guard is otherwise sound, so defect 1 is
a narrow exemption rather than a rewrite.
