## Intent

The Inbox is a decision desk, so typing, selection, in-flight work and failure must never change the addressed record by surprise. This brief closes the six truth and safety defects named by W-344 and D-090 A without adding a record form. Window shortcuts ignore `input`, `textarea`, `select` and contenteditable targets. A synchronous lock is taken before the answer request begins, so a second button press or key event in the same render is refused locally. Text drafts are stored by petitio id, so moving away and back preserves each draft without allowing one petition's text to submit against another.

Every failed `/api/inbox` read replaces the current view with `EMPTY`, settles loading and exposes the existing failure state. This includes a failed refresh after a successful answer: an earlier petition is never retained under an error notice. W-341's existing initial-read truth row remains green and its source matcher migrates to this stronger invariant.

At 899px and below, the split Inbox stacks instead of hiding the detail pane. The petition list is capped at 40 percent of viewport height and the answer pane follows in the normal scrolling flow. Petition selectors, the text field and all three actions measure at least 44×44px. Petition selectors are roving-tab buttons with a visible 2px verdigris focus ring; `j`/`k` move DOM focus and scroll the selected row into view through a fourteen-item list, while Tab proceeds from the selected petition to the text field, Approve, Decline and Follow up. W-341's two unreachable phone exceptions are removed, and those axe rows plus phone write-error run.

The Patron ruled **Approve**, **Decline** and **Follow up**. Defer and Delegate are removed. Approve and Decline send `<verb>: <trimmed text>` through `/api/answer`; the existing answer command appends that reply and resolves the petition. Follow up sends the trimmed text without a verdict prefix and `{ askBack: true }`. The handler maps that flag to `bisellium answer --ask-back`: it appends the Patron's text, records `ask_back: true` in the Patron timeline, changes `needs_you` to `awaiting_reply`, and flips direction from the Patron back to the original asker. The petition stays open but leaves the Patron's current Inbox until the sella replies. No new server or CLI form is invented.

Before submission, visible copy distinguishes the resolved verdicts from the open Follow up effect. All three controls require text after trimming; empty and whitespace-only values are refused. Success identifies the petition and whether it was resolved or remains open awaiting the asker's reply. That confirmation uses `--ink-2`, takes the list's existing `--sp-4` horizontal inset, lives independently of the detail selection, survives a successful or failed refresh and is sent to the shell's existing polite live region. If refresh removes the selected petition, selection clamps to a remaining row so its text field and actions stay reachable. The Inbox badge counts the petitiones in the latest successful `/api/inbox` read that need the Patron now, so the same refresh changes it from two to one when Follow up moves P-2 to `awaiting_reply`; a failed read leaves the last confirmed badge count unchanged.

The Inbox half of W-280 is absorbed here: failed reads show no records. W-280 retains only its `newItem` half. W-350's screenshot baselines remain untouched. W-339's colour rule, W-341's states matrix and axe contract, and W-361's contrast rows remain unchanged in meaning and green in their focused checks.

Threat model: accidental or duplicate Patron writes, stale/misdirected reasons, false records after read failure and misleading action labels; not hostile scripts or adversarial content (D-045).
