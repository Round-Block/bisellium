# W-057 — the server does not expose stack traces: GHAS alert 3 closed

Spec of record, signed by the architect, 2026-09-25. **Signed by the
architect alone.** No censor has read it.

Small, and security-scoped: one helper changes, one interpolation is dropped,
and the acceptance is an external alert flipping to fixed.

## Intent

GHAS alert 3, `js/stack-trace-exposure`, medium, **open**, flagged at
`apps/server/src/http.ts:108` — the `res.end(text)` inside `sendJson`.

The subtlety worth stating first, because it is why this has stayed open: the
code **already** withholds the stack. `serverError` (`:120-124`) reads

```ts
/** Never leaks a stack — the message only (spec: "500 never leaks a stack"). */
function serverError(res: ServerResponse, e: unknown): void {
  if (res.headersSent) return;
  sendJson(res, 500, { error: e instanceof Error ? e.message : String(e) });
}
```

That comment is true about `.stack` and **false about the alert**. CodeQL's
taint model treats an exception-derived **message** as stack-derived
information, so the flow `catch (e) → e.message → sendJson → res.end` is the
reported flow and dropping `.stack` never touched it. A reviewer reading the
comment concludes the alert is a false positive; it is not.

It is also not merely a model quirk. `route()`'s catch
(`:867`) receives **any** unexpected throw from any handler, and those
messages carry real server detail — an `ENOENT` names an absolute path, a git
failure names a ref, a YAML error names a line in a file the client cannot
see. The alert is pointing at a genuine disclosure channel that happens to be
untested: **nothing in `apps/server/test/server.test.ts` asserts on a 500 body
at all** (measured).

## The class, not the instance

One line is flagged; four response flows carry exception-derived strings.
Measured across `http.ts`, which is the **only** HTTP responder in the tree
(`index.ts` and `store.ts` write no responses):

| site | status | carries | in the class? |
|---|---|---|---|
| `:123` `serverError` | 500 | `e.message` / `String(e)` from **any** throw | **yes — the flagged flow** |
| `:163` `readJsonBody` | — | wraps `JSON.parse`'s message into a new `Error` | **yes**, and it feeds `:184` |
| `:184` `readJsonBodyOr400` | 400 | `e.message` / `String(e)` | **yes** |
| `:181` | 413 | `e.message` of our own `PayloadTooLargeError` | constant in fact, same shape |
| `:117` `notFound` | 404 | a caller-supplied noun | no — not exception-derived |
| `:499` | 503 | a string literal | no — **and it is the model** |
| `:830` poll failure | — | `e.message` to **stderr** | no — that is the correct destination |

`:499` already does the right thing: `sendJson(res, 503, { error: "too many
/api/live clients" })`. This opus makes 500 look like that.

## Design

**1. The 500 body becomes a constant plus a correlation id.**

```ts
{ error: "internal error", ref: "<uuid>" }
```

`randomUUID` comes from `node:crypto`, which `http.ts` **already imports**
(`:33`, for `randomBytes`/`timingSafeEqual`) — an extended import, not a new
dependency. Full uuid rather than a truncation: an 8-character id reads nicer
in a log and invites a collision argument nobody needs to have.

**2. The real error goes to the server log, with the same `ref`.** Message
**and stack**, to `process.stderr`, matching `:830`'s existing precedent for
server diagnostics:

```
bisellium serve: 500 <ref> <message>
<stack>
```

The stack is *why* the log exists. Withholding it from the client and
discarding it entirely would trade a security finding for an operability
one — an operator with the `ref` from a console screenshot must be able to
find the throw.

**3. The interpolated parse message is dropped** (`:163`):
`` `invalid JSON body: ${(e as Error).message}` `` becomes the constant
`"invalid JSON body"`. Not because a V8 parse message is sensitive — it
describes the client's own input — but because it is the only remaining path
by which an arbitrary exception's text reaches a response body. Dropping it
makes the invariant below **total over the file** rather than true of the 500
alone, and a total invariant is testable by inspection.

The cost, named: a client sending malformed JSON loses "Unexpected token } at
position 42". The only client is this repo's own console, and the status plus
the request is enough to debug it.

**4. The invariant.** After this opus: **no response body produced by
`http.ts` contains a string derived from a caught exception.** Every `error`
value in a response is a literal written in the source or a caller-supplied
noun. That is the sentence behaviour 3 pins and the reason the alert cannot
come back through a sibling flow.

**5. What does not change.** Statuses, shapes, and the 4xx/503 contract. 400
still answers a malformed body, 413 an oversized one, 404 an unknown thing,
503 a full SSE pool; every one still returns `{ error: <string> }`. The two
existing tests that touch these assert status and `typeof body.error ===
"string"` (`server.test.ts:438-439`, `:411`) and both keep passing unchanged —
verified by reading them, which is why this opus needs no fixture edits.

## Behaviours to test

1. **A 500 body carries nothing from the exception.** Inject a `checkStudio`
   that throws `new Error("ENOENT: open '/home/secret/studio/bisellium.yml'")`
   — the existing `StartServerOptions` seam, used by `GET /api/health`
   (`:631`), which reaches `route()`'s catch at `:867`. Then: status 500;
   `body.error === "internal error"` exactly; `body.ref` is a non-empty
   string; and the serialised body contains **neither** `ENOENT` **nor**
   `/home/secret` **nor** the word `Error`. Assert on the raw response text,
   not the parsed object, so a nested field cannot smuggle it.
2. **The exception reaches the log, correlated.** The same request writes to
   `process.stderr` a line containing the **same `ref`** as the body, the
   original message, and a stack. Correlation is the whole point: assert the
   `ref` from the body appears in the captured stderr, not merely that
   something was logged.
3. **The invariant, as a source pin.** Every `sendJson(res, <status>, …)` and
   `sendText` call in `http.ts` passes an `error` value that is a string
   literal or a template of literals and caller-supplied nouns — **no
   identifier derived from a `catch` binding**. Positive control: a synthetic
   copy of the file with `e.message` restored into `serverError` must fail the
   pin. Without the control the scan is decoration.
4. **The 4xx and 503 contract is unchanged.** Four rows: a non-object JSON
   body → 400; malformed JSON → 400 with `error === "invalid JSON body"`
   (the constant, no position text); an oversized body → 413 with a string
   `error`; an unknown route → 404. The two pre-existing assertions at
   `server.test.ts:411` and `:438-439` must still pass **untouched** — if the
   diff edits either, the change was wider than specified.
5. **Two 500s get two different `ref`s.** Two requests, two ids, both present
   in the log. Pins that `ref` is generated per response rather than a
   constant placeholder that would correlate nothing.

Reds via `bisellium red W-057 --behaviour <n> --sella <id> --studio studio --
<cmd>`, one per behaviour, assertion-level, no two sharing an output
(engineering lex §2). Behaviours 1, 2 and 5 red against today's tree because
`serverError` sends the message and writes no log; 3 reds because the pin does
not exist; 4 **passes** today — it is a regression guard for the contract this
opus must not break, so bundle its red with behaviour 1's rather than
manufacturing one, and say so in the evidence log.

## Sequence

- **W-070 (tailnet exposure) explicitly waits on this.** That ordering is the
  reason this opus is worth its size now rather than later: W-070 publishes
  the console beyond localhost, and a stack-trace channel is worth far more to
  an attacker who can reach it. The ranking acta
  (`acta/2026-09-25-ranking.md`) already puts W-057 ahead of W-070 for this
  reason; landing them the other way round would be the expensive order.
- **The merge gate's alert-3 exclusion becomes obsolete.** The orchestrator's
  gate scripts carry an exclusion so that alert 3 does not block a merge.
  Once `fixed_at` is set, that exclusion is dead code that would silently
  swallow a *future* stack-trace alert. It lives in the orchestrator's own
  scripts, not in this repo — I grepped `.github/` and `scripts/` and there is
  no alert allowlist committed here — so **removing it is the coordinator's
  action, named here so it is not forgotten.**

## House constraints

TypeScript strict + `noUncheckedIndexedAccess`; ESM `.js` import specifiers;
Node ≥ 25; `packages/cli/src/check.ts`'s house style. No new dependency —
`randomUUID` extends the existing `node:crypto` import.

## Out of scope

- **Structured logging.** One stderr line matching `:830`'s existing shape.
  A logger is a separate decision.
- **Returning `ref` on 4xx.** Client mistakes need no correlation id; the
  client has the request.
- **Rate-limiting or auditing 500s.** Different opus, different argument.
- **The other GHAS alerts.** This opus closes alert 3 and asserts no
  `js/stack-trace-exposure` replaces it. Any other rule's alerts are theirs.
- **Changing what CodeQL scans.** No in-repo config exists and none is added;
  suppressing an alert by configuration would be the opposite of this opus.
