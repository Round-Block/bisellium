# W-057 — the server does not expose stack traces: GHAS alert 3 closed

Spec of record, signed by the architect, 2026-09-25. **Revision 4** — the
census is confirmed complete by Sol's final pass (exactly 17 construction
sites, the 19-member union covers every resulting value, and deleting
`notFound` closes the string hatch); this revision fixes the two remaining
wording-and-coverage nits and nothing else. Revision 3, after two
Sol passes. The closure pass closed lands 1 and 5 and left land 3 open on a
fair charge: I had sized the union **from the flows I was fixing rather than
from the file**, and left `notFound(res, what: string)` as an unrestricted
string hatch. Revision 3 enumerates every error response body by measurement
and closes the hatch. Sol has not reviewed revision 3.

Small, and security-scoped: one helper changes, one interpolation is dropped,
and the acceptance is an external alert flipping to fixed.

## Intent

GHAS alert 3, `js/stack-trace-exposure`, medium, **open**, flagged at
`apps/server/src/http.ts:108` — the `res.end(text)` inside `sendJson`.

The subtlety worth stating first, because it is why this has stayed open: the
code **already** withholds the stack. `serverError` (`:120-124`) reads

```ts
/** Never leaks a stack — the message only (spec: "500 never leaks a stack"). */
function serverError(res: ServerResponse, e: unknown): void {
  if (res.headersSent) return;
  sendJson(res, 500, { error: e instanceof Error ? e.message : String(e) });
}
```

That comment is true about `.stack` and **false about the alert**. CodeQL's
taint model treats an exception-derived **message** as stack-derived
information, so the flow `catch (e) → e.message → sendJson → res.end` is the
reported flow and dropping `.stack` never touched it. A reviewer reading the
comment concludes the alert is a false positive; it is not.

It is also not merely a model quirk. `route()`'s catch
(`:867`) receives **any** unexpected throw from any handler, and those
messages carry real server detail — an `ENOENT` names an absolute path, a git
failure names a ref, a YAML error names a line in a file the client cannot
see. The alert is pointing at a genuine disclosure channel that happens to be
untested: **nothing in `apps/server/test/server.test.ts` asserts on a 500 body
at all** (measured).

## The class, not the instance

One line is flagged. There are **two response sinks** that can serialise an
arbitrary caught value, plus one transformation that feeds one of them.
Revision 1 called this "four response flows", which conflated a transformation
with a sink and understated what reaches `:184` — land 1. Measured across
`http.ts`, the **only** HTTP responder in the tree (`index.ts` and `store.ts`
write no responses):

| site | kind | status | carries |
|---|---|---|---|
| `:123` `serverError` | **sink** | 500 | `e.message` / `String(e)` from **any** throw in `route()` — the flagged flow |
| `:184` `readJsonBodyOr400` | **sink** | 400 | `e.message` / `String(e)` of **any** rejection that is not `PayloadTooLargeError` |
| `:163` | transformation | — | wraps `JSON.parse`'s message into a new `Error`; reaches `:184` |
| `:181` | guarded | 413 | `e.message` of `PayloadTooLargeError`, narrowed by `instanceof` — a constant **by the narrowing**, not by luck |
| `:117` `notFound` | — | 404 | a caller-supplied route noun, never a caught value |
| `:499` | — | 503 | a string literal — **the model this opus copies** |
| `:830`, `:865` | — | — | `e.message` to **stderr**, the correct destination |
| `:764` | — | — | calls `readJsonBody` and **discards** the error (`.catch(() => ({}))`) — correctly not a sink |

**`:184` is the finding revision 1 missed.** Its `catch` does not only receive
the two `Error`s `readJsonBody` constructs. The last line of that function is

```ts
    req.on("error", reject);
```

— `:166`, which rejects with the **raw request-stream error, unwrapped**. So a
socket-level failure (`aborted`, `ECONNRESET`, a TLS or proxy error under a
future W-070 deployment) has its message serialised into a 400 body. Whether it
is delivered depends on socket state, which is not a guarantee either way; the
flow exists in code and that is what the taint model reports and what an
attacker would probe.

`:499` already does the right thing: `sendJson(res, 503, { error: "too many
/api/live clients" })`. This opus makes 500 look like that.

## Design

**1. The 500 body becomes a constant plus a correlation id.**

```ts
{ error: "internal error", ref: "<uuid>" }
```

`randomUUID` comes from `node:crypto`, which `http.ts` **already imports**
(`:33`, for `randomBytes`/`timingSafeEqual`) — an extended import, not a new
dependency. Full uuid rather than a truncation: an 8-character id reads nicer
in a log and invites a collision argument nobody needs to have.

**The `ref` is the only correlator available, verified** (Sol's held 2). The
server's two log writers carry no wall-clock time: `:830` writes
`bisellium serve: poll failed: <msg>` and `:865` writes
`<method> <url> <status> <ms>` — a duration, not a timestamp. So an operator
handed a 500 cannot correlate it by time even with full stderr access, and
revision 1's own For Sol target questioning whether `ref` earns its place is
answered: it does, and the reason is a gap in the logs rather than a
preference.

**2. The real error goes to the server log, with the same `ref`.** Message
**and stack**, to `process.stderr`, matching `:830`'s existing precedent for
server diagnostics:

```
bisellium serve: 500 <ref> <message>
<stack>
```

The stack is *why* the log exists. Withholding it from the client and
discarding it entirely would trade a security finding for an operability
one — an operator with the `ref` from a console screenshot must be able to
find the throw.

**3. The interpolated parse message is dropped** (`:163`):
`` `invalid JSON body: ${(e as Error).message}` `` becomes the constant
`"invalid JSON body"`. Not because a V8 parse message is sensitive — it
describes the client's own input — but because it is the only remaining path
by which an arbitrary exception's text reaches a response body. Dropping it
makes the invariant below **total over the file** rather than true of the 500
alone, and a total invariant is testable by inspection.

The cost, named: a client sending malformed JSON loses "Unexpected token } at
position 42". The only client is this repo's own console, and the status plus
the request is enough to debug it.

**4. The invariant is enforced at the response boundary by the compiler, not
by a grep** (land 3). Revision 1 proposed a source pin asserting that no
`catch` binding reaches a `sendJson` argument. Sol is right that this is not an
invariant: assigning `const msg = e.message` two lines earlier defeats it, and
a brand whose constructor takes a `string` just relocates the hatch.

So the error body gets **one choke point with a closed input set**. Sizing that
set required enumerating the file rather than the fix — the census is below and
it is the substance of revision 3.

### Every error response body in `http.ts`, measured

Seventeen call sites. No `res.writeHead` with a 4xx/5xx status exists outside
these helpers (verified), so this is the whole surface:

| site | status | value today | kind |
|---|---|---|---|
| `:123` `serverError` | 500 | exception-derived | **sink** |
| `:184` | 400 | exception-derived | **sink** |
| `:181` | 413 | `e.message`, `instanceof`-narrowed | constant by narrowing |
| `:117` `notFound` | 404 | `` `unknown ${what}` `` | **template — the hatch** |
| `:581` | **401/403/415** | one of three literals | literal, **variable status** |
| `:441` | 403 | `"forbidden"` | literal |
| `:451`, `:671`, `:801` | 404 | `"not found"` | literal ×3 |
| `:499` | 503 | `"too many /api/live clients"` | literal |
| `:652` | 400 | `"item cannot be combined with since"` | literal |
| `:686` | 400 | `"petitio and reply are required strings"` | literal |
| `:701` | 400 | `"opus is required"` | literal |
| `:717` | 400 | `"period, collegium and tokens are required"` | literal |
| `:733` | 400 | `"opus, sella and next are required"` | literal |
| `:749` | 400 | `"sella and message are required"` | literal |
| `:786` | 400 | `"either {sella, model} or {munus, tier} are required"` | literal |

**Thirteen distinct literals already in use.** Revision 2 proposed a
five-member union, which would not have compiled against the file — Sol's
charge, and it is correct. With the four this opus introduces or promotes
(`"internal error"`, `"invalid JSON body"`, and `"request body must be a JSON
object"` / `"request body too large"` promoted from messages to codes) plus the
two the hatch becomes, the union is **nineteen members**:

```ts
/** Every `error` value any response may carry. A caught value cannot be a
 *  member, so `sendError` cannot be handed one — enforced by tsc. */
type ErrorCode =
  | "internal error" | "invalid JSON body" | "request body must be a JSON object"
  | "request body too large" | "forbidden" | "not found"
  | "too many /api/live clients" | "missing or invalid X-Bisellium-Token"
  | "cross-origin writes are refused" | "Content-Type must be application/json"
  | "item cannot be combined with since" | "petitio and reply are required strings"
  | "opus is required" | "period, collegium and tokens are required"
  | "opus, sella and next are required" | "sella and message are required"
  | "either {sella, model} or {munus, tier} are required"
  | "unknown opus" | "unknown sella";

function sendError(res: ServerResponse, status: number, code: ErrorCode, ref?: string): void {
  sendJson(res, status, ref === undefined ? { error: code } : { error: code, ref });
}
```

**The member count is deliberately not asserted.** Five was already
insufficient; nineteen will be insufficient the next time a route validates an
argument. Pinning the count would make every new error response a test edit and
teach people to widen the union carelessly to get past it. What behaviour 3
asserts instead is the property that actually matters — **closedness** — as a
compile-time negative:

```ts
// @ts-expect-error — an arbitrary string must not be assignable to ErrorCode.
const _errorCodeIsClosed: ErrorCode = "arbitrary" as string;
```

`@ts-expect-error` fails the build when the expected error **does not** occur,
so widening `ErrorCode` with `| string` breaks `typecheck` on this line. That is
the semantic assertion, it is plain TypeScript, and it survives the union
growing to fifty members.

### `notFound`'s hatch is closed by deleting `notFound`

`notFound(res, what: string)` took an unrestricted string and interpolated it,
which is a hatch regardless of who calls it today. It has exactly **two** call
sites (measured): `notFound(res, "opus")` at `:609` and `notFound(res, "sella")`
at `:637`. Route nouns are a closed set of two.

Rather than add a `RouteNoun` union and keep a helper that still builds a string
by interpolation, **delete `notFound`** and have both sites call
`sendError(res, 404, "unknown opus")` and `sendError(res, 404, "unknown sella")`.
The emitted bodies are **byte-identical to today's** — `unknown opus`,
`unknown sella` — so no client observes a change, one helper disappears, and no
error body anywhere is built by interpolation. That is the whole hatch, removed
rather than typed.

### The pin must be status-agnostic

Revision 2's pin grepped `sendJson(res, <4xx|5xx literal>`, which **would have
missed `:581` entirely** because its status is a variable (`authStatus`, one of
401/403/415 from `checkWriteAuth` at `:363-367`). That is the same
sized-from-the-fix error in the pin itself. The pin is therefore:
**no `sendJson` or `sendText` call in `http.ts` passes an object containing an
`error` key, with exactly one structurally identified exception: the call inside
`sendError`'s own body.** Status-agnostic, so a variable status cannot hide a
site.

That exception is not a loophole and it has to be named, because `sendError` is
itself `sendJson(res, status, { error: code, … })` — a pin phrased without it
would forbid the choke point it exists to protect. "Structurally identified"
means the scan recognises it by *position* — the single call lexically inside
`sendError`'s declaration — never by matching on the text of the argument, which
a second site could imitate. The alternative Sol offered, serialising below
`sendJson` so that no `sendJson` call carries an `error` object at all, is
cleaner in the abstract but duplicates `writeHead` and `JSON.stringify` in a
second place to win a phrasing argument; one named positional exception is the
smaller change.

**5. What does not change.** Statuses, shapes, and the 4xx/503 contract. 400
still answers a malformed body, 413 an oversized one, 404 an unknown thing,
503 a full SSE pool; every one still returns `{ error: <string> }`. The two
existing tests that touch these assert status and `typeof body.error ===
"string"` (`server.test.ts:438-439`, `:411`) and both keep passing unchanged —
verified by reading them, which is why this opus needs no fixture edits.

## Behaviours to test

1. **A 500 body carries nothing from the exception.** Inject a `checkStudio`
   that throws `new Error("ENOENT: open '/home/secret/studio/bisellium.yml'")`
   — the existing `StartServerOptions` seam, used by `GET /api/health`
   (`:631`), which reaches `route()`'s catch at `:867`. Then: status 500;
   `body.error === "internal error"` exactly; `body.ref` is a non-empty
   string; and the serialised body contains **neither** `ENOENT` **nor**
   `/home/secret` **nor** the word `Error`. Assert on the raw response text,
   not the parsed object, so a nested field cannot smuggle it.

2. **The exception reaches the log, correlated by `ref`.** The same request
   writes to `process.stderr` a line containing the **same `ref`** as the body,
   the original message, and a stack. Assert the `ref` from the body appears in
   captured stderr — correlation is the whole point, and per the design note it
   is the *only* correlator, since neither `:830` nor `:865` logs a timestamp.

3. **The choke point exists, is closed, and cannot be widened.** Three halves,
   and the first two are compile-time:
   - **`ErrorCode` is closed**, asserted semantically rather than by counting
     members: the `@ts-expect-error` line above must *keep* erroring, so
     widening the union with `| string` fails `typecheck`. Sol's ruling, and it
     is the assertion that survives the union growing. **Do not assert the
     member count** — five was already insufficient and nineteen will be.
   - **`npm run -s typecheck` fails** on a synthetic edit passing an
     exception-derived value to `sendError`: `sendError(res, 500, e.message)`
     and the aliased `const msg = e.message; sendError(res, 500, msg)`. Both are
     compile errors, aliased or not, which is what a grep could never achieve.
   - **A status-agnostic source pin**: no `sendJson` or `sendText` call in
     `http.ts` passes an object containing an `error` key, **except the one
     inside `sendError`'s own body**, identified by position rather than by the
     shape of its argument. Status-agnostic deliberately, because revision 2's
     literal-status grep would have missed `:581`, whose status is a variable.
     The pin's job is narrow: not "no tainted value reaches a response", which
     the type guarantees, but "nobody routed around the type". Positive
     control: a second `sendJson(res, 400, { error: … })` added anywhere outside
     `sendError` must fail the pin.

4. **Malformed JSON answers the constant.** A POST with `{` as its body gets
   status 400 and `error === "invalid JSON body"` **exactly** — no position
   text, no V8 wording. This has its own honest red (land 5): today the same
   request yields `invalid JSON body: Unexpected token ...`, so an exact-equality
   assertion fails before the fix. Revision 1 bundled this red with behaviour
   1's on the grounds that it "passes today", which was simply wrong — and
   bundling would have violated the one-red-per-behaviour contract this brief
   inherits (`W-072.md`'s reds section).

5. **Two 500s get two different `ref`s.** Two requests, two ids, both present
   in the log. Pins that `ref` is generated per response rather than a constant
   placeholder that would correlate nothing.

6. **A request-stream error is not narrated to the client** (land 1). Induce a
   rejection on the `:166` path — destroy or error the request stream mid-body
   — and assert the response is **not** a 400 carrying the stream error's
   message. It reaches the 500 path: `error === "internal error"`, a `ref`, and
   the stream error's own message in the log. If the socket is no longer
   writable the assertion is on the **log** alone, which is the honest
   outcome and must be stated in the test rather than skipped: the property is
   "the message never becomes a response body", and an undeliverable response
   satisfies it.

7. **Every one of the seventeen error bodies is byte-identical to today's.**
   The regression guard for a change that rewrites seventeen call sites, so it
   must exercise seventeen — revision 3 claimed byte-identity across all of
   them and tested five (Sol's finding, and he named the eleven I had missed).
   Assert on the **raw response text**, not on `parsed.error === "…"`: parsed
   equality cannot detect an added field, and `sendError` now has an optional
   `ref` that must appear on the 500 and **nowhere else**.

   | site | request that reaches it | expected raw body |
   |---|---|---|
   | `:441` | a forbidden read | `{"error":"forbidden"}` |
   | `:451` | the route's not-found branch | `{"error":"not found"}` |
   | `:671` | `/api/opus/:id` for an absent id | `{"error":"not found"}` |
   | `:801` | an unrouted path | `{"error":"not found"}` |
   | `:609` | `/api/opus/:id` with an unknown opus | `{"error":"unknown opus"}` |
   | `:637` | a sella route with an unknown sella | `{"error":"unknown sella"}` |
   | `:499` | the 51st `/api/live` client | `{"error":"too many /api/live clients"}` |
   | `:581` ×3 | a write POST with no token / bad Origin / wrong Content-Type | `{"error":"missing or invalid X-Bisellium-Token"}`, `{"error":"cross-origin writes are refused"}`, `{"error":"Content-Type must be application/json"}`, at 401 / 403 / 415 |
   | `:652` | `?item=` together with `?since=` | `{"error":"item cannot be combined with since"}` |
   | `:686` | `POST /api/answer` `{}` | `{"error":"petitio and reply are required strings"}` |
   | `:701` | `POST /api/greenlight` `{}` | `{"error":"opus is required"}` |
   | `:717` | `POST /api/budget` `{}` | `{"error":"period, collegium and tokens are required"}` |
   | `:733` | `POST /api/handoff` `{}` | `{"error":"opus, sella and next are required"}` |
   | `:749` | `POST /api/talk` `{}` | `{"error":"sella and message are required"}` |
   | `:786` | `POST /api/delegate` `{}` | `{"error":"either {sella, model} or {munus, tier} are required"}` |
   | `:181` | an oversized body | `{"error":"request body too large"}` |
   | `:184` | a non-object JSON body | `{"error":"request body must be a JSON object"}` |

   Nineteen rows for seventeen sites, because `:581` answers three. Each row
   asserts the raw text **and** the status; the two pre-existing assertions at
   `server.test.ts:411` and `:438-439` must still pass **untouched** — if the
   diff edits either, the change was wider than specified. Any row whose
   request is awkward to induce (`:441`, `:451` and `:499` in particular) is
   still owed a row: if a path cannot be reached from a test, say so in the
   evidence rather than dropping it silently, because an unreachable error body
   is its own finding.

Reds via `bisellium red W-057 --behaviour <n> --sella <id> --studio studio --
<cmd>`, one per behaviour, assertion-level, **no two sharing an output**
(engineering lex §2). Every behaviour above reds on its own against today's
tree: 1, 2, 5 and 6 because `serverError` sends the message and writes no log;
3 because neither `ErrorCode` nor the pin exists; 4 because the message carries

## Sequence

- **W-070 (tailnet exposure) explicitly waits on this.** That ordering is the
  reason this opus is worth its size now rather than later: W-070 publishes
  the console beyond localhost, and a stack-trace channel is worth far more to
  an attacker who can reach it. The ranking acta
  (`acta/2026-09-25-ranking.md`) already puts W-057 ahead of W-070 for this
  reason; landing them the other way round would be the expensive order.
- **The merge gate's alert-3 exclusion becomes obsolete.** The orchestrator's
  gate scripts carry an exclusion so that alert 3 does not block a merge.
  Once `fixed_at` is set, that exclusion is dead code that would silently
  swallow a *future* stack-trace alert. It lives in the orchestrator's own
  scripts, not in this repo — I grepped `.github/` and `scripts/` and there is
  no alert allowlist committed here — so **removing it is the coordinator's
  action, named here so it is not forgotten.**

## House constraints

TypeScript strict + `noUncheckedIndexedAccess`; ESM `.js` import specifiers;

## Out of scope

- **Structured logging.** One stderr line matching `:830`'s existing shape.
  A logger is a separate decision.
- **Returning `ref` on 4xx.** Client mistakes need no correlation id; the
  client has the request.
- **Rate-limiting or auditing 500s.** Different opus, different argument.
- **The other GHAS alerts.** This opus closes alert 3 and asserts no
  `js/stack-trace-exposure` replaces it. Any other rule's alerts are theirs.
- **Changing what CodeQL scans.** No in-repo config exists and none is added;
  suppressing an alert by configuration would be the opposite of this opus.
