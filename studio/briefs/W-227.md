## Intent

Three things went wrong at W-528's close (2026-11-07/08), and this opus fixes each at its cause.

**1. Cleanup stopped on a folder that holds nothing.** `next W-528 --perform --expect cleanup` was held with `worktree: held (/home/edckt/agents/bisellium/.worktrees/W-528 exists but is not the registered worktree for opus/W-528; left untouched)`, raised in `packages/cli/src/integrate.ts` `cleanup`, step (1), when git lists no worktree at the path but the folder exists. The hold returns before the branch steps, so the merged local branch was never deleted and `next` kept naming cleanup.

**2. What makes that folder (item 2 of the brief, settled before the design).** The Claude Code sandbox does, on every sandboxed command, for as long as the session lives. Evidence, from dry probes run in this session's sandbox (nothing was deleted by hand):

- *It is a mount point.* Inside a sandboxed command, `/proc/self/mountinfo` shows `.worktrees/W-528` and `.git/worktrees/W-528` as read-only bind mounts of an empty `/tmp/claude-empty-*` folder (`probe-stub-2.out`). Four more `.git/worktrees/<name>` stubs (W-508, W-508-re1106, W-508-spec, W-509-spec) are mounted the same way.
- *It is made for each command and taken down after.* In two probes 4 seconds apart its birth time is each command's own start (`08:08:36.43` and `08:08:40.79` SGT, `probe-stub-2.out`, `probe-stub-3.out`), mode `drwx------`, empty. So the folder the Patron or a later command sees is a new one each time.
- *It can hold stubs.* While another sandboxed command of the same session is still running (here this spec's own background test run), the folder persists between commands and the next command's sandbox makes its deny paths inside it: `.git`, `.mcp.json` and a `.claude/` folder of zero-byte, mode-0444 files (`settings.json`, `settings.local.json`, `hooks`, `skills`, `.cc-writes`, …), each one a read-only mount (`probe-stub-1.out`).
- *An rmdir of it fails with EBUSY.* Not tried by hand: git's own automatic `gc` after a commit in this spec's series ran `worktree prune` and printed `error: failed to delete '/home/edckt/agents/bisellium/.git/worktrees/W-528': Device or resource busy`, and the same for the other four stubs (`stages-b1-first.log`).
- *Why W-528.* The session's deny list names `.worktrees/W-528/.claude/settings.json`, `settings.local.json`, `skills`, `hooks` and `.cc-writes`, and no other of the 84 registered worktrees has a deny mount (`probe-stub-2.out`). The main thread `cd`'d into it once: `2026-11-07T16:05:33Z cd ~/agents/bisellium/.worktrees/W-528 && git show 8787cf58 --stat …` in session c849576a; the session that found the stub, 7eb150ce, is the same Claude Code process after a `/clear` (its first line follows c849576a's last by 15 ms), so the deny entry outlived the clear (`cd-evidence.out`). The first cleanup refusal that night, `git worktree remove … Device or resource busy`, is the same cause one step earlier: the deny mounts sat inside the then-registered worktree.

So: an rmdir from inside the session that holds the folder fails, and the folder comes back on its next command. The design must still finish the branch steps, and it does (behaviour 2). Once that session ends, nothing remakes the folder; a stub left on disk by a crash is what the plain rmdir (behaviour 1) clears.

**3. The guard sync did not fast-forward master after #1086.** The whole cause is two parts (`sync-evidence.out`):

- *No sync was asked for.* `patronStop` (`integrate.ts`, the merge rung's hold before the main checkout moves) writes the sync request only when `denied.length > 0`, the paths the sandbox denies (W-362), and for an incoming Patron path it never computes `denied`. On 11-07 #1082 (W-526) brought only `packages/` paths: the hold printed `sync: requested` and the PostToolUse sync printed `sync: master dc029c7d067e -> 41383abaaa52` at 14:22Z. #1086 (W-528) brought `.github/workflows/ci.yml`, a Patron path: its hold (`W-528-build/merge2.out`, 17:11Z) has no `sync:` line, and no sync ran until the next SessionStart. W-369's brief named this gap in its Out of scope: "a request from that hold is a later opus". This is that opus.
- *Then the SessionStart sync refused, rightly.* At 23:43Z it found the agent clone's tracked change ` M docs/design/dossier/progress-body.html` (written 22:19Z) and refused, as W-369 rules. That refusal is correct and stays: it was the second cause, not the first, and a clean tree would still have waited hours for a SessionStart.

The fix is small and in the same file: the hold asks for the sync whenever this checkout holds master, a Patron path included (behaviour 3). The sync is the Patron's own installed guard, unsandboxed, and fast-forwards only to the commit it fetches into the Patron's clone; a code-owned path reaches origin/master only through the Patron's approval as code owner, so the CLI still never writes a Patron path itself. The `patron:` line stays first, for when no sync runs.

**4. The guard's `cd` rule earns its place.** Item 2 shows that a main-thread `cd` into a worktree folder is what put that folder in the session's sandbox deny list, and that the entry lasts for the life of the process, across `/clear`. Both of W-528's cleanup refusals follow from that one `cd`. The guard (`bisellium hook-event guard`, PreToolUse) now refuses it for the main thread. A subagent's `cd` stays allowed: a subagent's shell starts over in the project folder on each call, and none of the worktrees subagents have entered (W-528-spec, W-528-series and the rest) has a deny mount.
