# W-033 — officina bookkeeping provenance: branch vs trunk copies diverge

## Intent

The officina's state is files inside the repo. Under D-015's branch-and-PR
flow every branch therefore carries its own copy of `studio/opera/*.md`,
and every command that reads or writes bookkeeping does so against
whichever checkout it happens to be standing in. Nothing declares which
copy is authoritative for which field.

This produced three distinct blocking findings in a single day
(2026-09-19), in three unrelated opera, found by three separate reviews:

1. **W-026, round 5.** `mergeOpusBranch` read the opus record off the
   filesystem while hashing the branch ref. With `studio/` inside the repo
   those are two files. It failed **open** — merging from the trunk, where
   the record predated any gate run, found no certificate and landed
   uncertified work — and failed **closed** on the PR that introduced it,
   refusing on a stale certificate that existed only in master's copy.
   Fixed there by reading the record from the branch ref.

2. **W-030, round 2.** The round-1 review verdict was written to master's
   copy at 16:08:28; greenlight/ready/verify ran on the branch at
   16:10:31. Neither saw the other. `git merge-tree` reports a genuine
   conflict in `studio/opera/W-030.md`: branch-wins erases the verdict,
   master-wins erases the four certificates.

3. **W-031, round 1.** Same shape — the reviewer's `bisellium review`
   write landed on master's copy, which still reads `state: backlog`,
   while the gates live on the branch.

Each was patched where it was found. The class was not addressed, and
patching per-opus does not scale: every command that touches `opera/`
front matter has the same ambiguity.

## The question this opus must answer

Which copy of an opus record is authoritative, for which field, and how
does a command know?

The candidate answers seen so far, none yet decided:

- **Per-field provenance.** W-026 considered certificates-from-branch and
  state-from-trunk, then rejected it: `merge` runs from a worktree on the
  branch as often as from the trunk, so "the checkout" is the ambiguity
  itself, and splitting reopens it for one field.
- **Branch-authoritative, by contract.** W-026 landed here — `verify` and
  `done` must be run and committed on the branch, mirroring each other.
  But reviews are run by a reviewer in a scratch checkout of its own, and
  `bisellium review` has no branch flag, which is finding 2 and 3 above.
- **Trunk-authoritative, with the branch carrying evidence only.**
  Untried.
- **Bookkeeping outside the work tree entirely** — a separate ref, or the
  append-only event log as the source of truth with front matter as a
  projection. The log already exists (`studio/.bisellium/events.jsonl`)
  and already records gate writes.

This is a design decision, not a defect to patch. It belongs to the
architect before any code is written.

## Out of scope

- Re-litigating W-026's branch-ref read, which is correct under its own
  contract and verified by two review rounds.
- The per-opus patches already landed. This opus replaces the need for
  more of them; it does not revisit them.

## Note

`bisellium review` writing to the reviewer's own checkout is the sharpest
instance: a review's verdict is evidence *about* a branch, produced by an
agent that deliberately works in an isolated copy. Whatever answer is
chosen has to say where that verdict belongs.
