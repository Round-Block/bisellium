# W-153 — time to completion: an estimated finish from the recent pace of points done

Status: **signed spec, revision 1** · architect sella (claude-opus-5-5) · 2026-10-06.

## Intent

Decree family: completion-estimate

The decree: **the time to completion is read from records, never typed:
one rule turns the recent pace of milestone points done into a number of
days and a range, and the Status page and the console print the same
sentence.**

The Patron asked on 2026-10-06 for an estimate of time to completion on the
Status page and the console, "still subject to adjustments along the way".
D-041 rules the audience is both. Today:

- **The meter exists only on the Status page.** W-152 put `computeMeter` in
  `scripts/status-page.mjs`. The console has no meter at all.
- **A prototype exists** at `~/.bisellium-evidence/pace.mjs` (data, not
  design). It dates each done opus by the first git commit whose record reads
  `state: done`, and it measures pace as % per day. Over 7, 14 and 30 days it
  gives 20, 25 and 32 days left.
- **The prototype's pitfall is its dating.** Git dates the closing commit,
  not the work. The codex research lane (W-102 to W-105, 5 points) was closed
  in one commit, 044bc88, on 2026-10-02. Their gates had passed between
  09-26 and 09-28. W-089's gates passed on 09-25 and it was marked done on
  10-01. Measuring % also lets a mass halt raise the pace: a halt shrinks
  the points planned, so the % rises with no work done.

**Measured at master `20b57e7`.** The survey is
`~/.bisellium-evidence/W-153-spec/survey.mjs` (`survey.out`), and the method
below is `measure.mjs` (`measure.out`) beside it. Both are kept.

- 84 opera are done, all mapped. 23 carry `end:`, the time the `done` verb
  writes, recorded since 2026-10-02. Where both exist, `end` and the git
  date agree within a day.
- Every other done opus but the first fifteen (W-001 to W-015, the
  2026-09-17/18 bootstrap) carries a gate `at`. Dating by `end`, else by the
  latest gate `at`, leaves those 15 undated. It also moves W-089 and
  W-102 to W-105 back to when their work passed review.
- With that dating, no clock hour holds more than 3 done opera. Git dating
  puts 4 in one hour on 2026-10-02 and 6 in one on 2026-09-17.
- **Today's estimate** (at 2026-10-06T08:30Z): 165 points left. Points done
  in the last three weeks, newest first: 76, 64 and 54 (mean 64.7 a week).
  That gives **about 18 days, 16 to 22, around 24 Oct 2026**.

So done-dates come from the records, not from git. A done opus is dated by
its `end`, else by its latest gate `at`, else it is not paced. Pace is points
done, not %, so a halt never speeds the estimate. A burst of more than 3
done opera in one clock hour is a bulk closure and is left out of the pace.
The computation moves into `packages/core` so the script and the server
share one formula.

## Interfaces

```ts
// packages/core/src/completion.ts — no imports; plain node loads it
export function computeMeter({ milestones, opera, findings }): { rows: MeterRow[]; overall: number };
//   moved verbatim; W-152-b4 keeps passing unchanged.

export function doneAt(opus: { end?: unknown; probationes?: Record<string, { at?: unknown } | undefined> }): string | undefined;
//   ISO instant: `end` when it parses as a date (string or Date), else the latest gate `at` that parses,
//   else undefined. An unparseable value is skipped, never thrown on.

export interface Estimate {
  kind: "estimate" | "none";
  reason?: "nothing-left" | "too-little-history";   // only when kind is "none"
  remaining: number;                  // Σ (planned − done) over meter.rows
  weekly: [number, number, number];   // paced points per 7-day window ending at now, newest first
  bulk: string[];                     // ids left out of pace, sorted
  days?: number; low?: number; high?: number;       // only when kind is "estimate"
  finish?: string;                    // YYYY-MM-DD (UTC) of now + days
  line: string;                       // the one sentence both surfaces print verbatim
}
export function estimateFinish({ meter, opera, now }: { meter; opera; now: Date }): Estimate;
```

The rule, in order:

1. **Events.** Each opus that is `done` and mapped to a row of the meter is
   an event of `value` points at `doneAt`. An undated event counts as done
   but is not paced. So does one later than `now`.
2. **Bulk.** Dated events are grouped by UTC clock hour
   (`toISOString().slice(0, 13)`). A group of more than 3 is bulk: its
   events are left out of the pace and listed in `bulk`.
3. **Weeks.** Window k (0, 1, 2) is `(now − 7(k+1) days, now − 7k days]`.
   `weekly[k]` sums the paced points in it.
4. **Result.** When `remaining` is 0: `kind: "none"`, reason
   `nothing-left`, and the line `Nothing left: every planned point is
   done.` When any week is 0: reason `too-little-history`, and the line
   `No estimate yet: it needs points done in each of the last 3 weeks.`
   Otherwise, with mean = Σ weekly ÷ 3, `days = ceil(7 × remaining ÷ mean)`.
   `low` uses the largest week and `high` the smallest, with the same
   formula. The line reads
   `Estimated finish: in about <days> days (<low> to <high> days), around <D> <Mon> <YYYY>, at the pace of the last 3 weeks.`
   The date is UTC, with an unpadded day and a three-letter English month.

```
GET /api/completion  →  200 { meter: { rows, overall } | null, estimate: Estimate | null }
```

The route reads the trunk's own records from disk, as the Status page does:
`readMilestones(studioDir)` and every `opera/*.md` front matter, with no
branch overlay. Both fields are `null` when `milestones.yml` is absent.
`checkStudio` is called once only when some milestone's exit is a `rule`,
and its findings feed `computeMeter`. `now` is the store's own clock. A
`milestones.yml` that does not parse throws, and the route answers the
generic 500.

**Status page.** In the Completion section, directly after
`<p><strong>Overall …</strong></p>`, comes
`<p class="estimate">` + the escaped `estimate.line` + `</p>`. With no
milestone records there is no estimate line.

**Console.** The Officina screen's first panel, above Posture and burn, is
a `<section>` whose `h2.officina__panel-heading` reads `Completion`. It
shows:

- `Overall <n.n>%` with a thin bar;
- the estimate line, verbatim;
- one row per milestone: id, title, `done/planned` points and `<n.n>%`,
  each with a thin bar.

Loading reads `Loading completion…`. A failure reads
`Could not load completion.` A `null` meter reads `No milestone records`.

## Out of scope

Each is a follow-on for the producer to file, or someone else's step.

- **An estimate per milestone,** or one per audience. W-158 splits the
  meter by audience; the estimate follows it there or in its own opus.
- **Accounting for work not yet filed, and for the 95% caps.** The
  estimate counts planned points only. Filing new opera moves it later.
  This is the Patron's "subject to adjustments".
- **The estimate's history,** a trend of past estimates.
- **A console screen of its own** for status, with a nav entry. This opus
  uses the Officina screen.
- **Live refresh.** The panel loads with the screen; it is not pushed over
  `/api/live`.
- **Branch-record overlay** for the meter. The console reads the trunk's
  records, as the Status page does.
- **Smarter bulk detection.** A burst that straddles a clock hour is
  counted. A sliding window is the upgrade, if a straddling burst ever
  shows.
- **`apps/web/src/lib/officinaLayout.ts`,** whose section list is already
  stale and is read by no screen.

## Defaults for the Patron to veto

Each ships as stated and can be overturned at the checkpoint.

1. **Status page placement.** One line right under the overall percentage.
2. **Console placement.** A new Completion panel at the top of the Officina screen.
3. **Console panel.** Overall % with a thin bar, the estimate line, then one row per milestone.
4. **Wording.** "Estimated finish: in about 18 days (16 to 22 days), around 24 Oct 2026, at the pace of the last 3 weeks."
5. **The range.** The fastest and slowest of the last three weeks, in brackets.
6. **Too little history.** "No estimate yet: it needs points done in each of the last 3 weeks."
7. **All done.** "Nothing left: every planned point is done."
8. **Pace window.** The last three weeks, counting points done, so halting a task never speeds the estimate.
9. **When a task counts as done.** Its recorded finish time, else its last passed check; the first 15 tasks have neither and are not paced.
10. **Bulk closures.** More than 3 tasks finished in one clock hour are left out of the pace.
