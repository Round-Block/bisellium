## Intent

On 2026-10-26 W-418's architect found two logins in the agent gh config (`$AGENT_GH`, default `~/.config/agent-gh`): the agent's own, `bisellium-agent`, active, and the Patron's, `edckt`, stored inactive beside it (`~/.bisellium-evidence/W-418-spec/probe-a-account.out`). An inactive login is still usable (`gh auth switch`, `gh --user`, or its token read from `hosts.yml`, which a sandboxed session can read), so a session could act as the Patron and pass code-owner review. `scripts/agent-workspace.sh verify` printed all ok: its token checks (`token_reads_repo`, `token_refused_admin`) judge only the active token. This opus makes `verify` and `verify --inside` fail, and `setup` refuse to finish, while that config holds anything but the agent's own login.

The rule: `$AGENT_GH` holds exactly one login, on host `github.com`, active, whose login is `AGENT_LOGIN`. `AGENT_LOGIN` is a new configured name beside `AGENT_GH` and `REPO`, default `bisellium-agent`. It is a configured name, not "whichever login is active": a token of the Patron's that can read the repo would pass `token_reads_repo`, so the active token alone cannot say whose it is.

How the logins are read, with no token (`probe.out`, gh 2.101.0 at `/usr/bin/gh`): `gh auth status --json hosts` lists every stored login per host, each account with the fields `active`, `gitProtocol`, `host`, `login`, `state` and `tokenSource`. It carries no token field (gh adds one only under `--show-token`, which this opus never passes). With `--json`, gh exits 0 whatever the tokens' state; it exits 1 only on a fatal error, such as an unreadable or malformed `hosts.yml` (both probed). An empty config gives `{"hosts":{}}`. The real config today gives the finding (`judge-real.out`: one FAIL line naming `edckt` and its logout command). `hosts.yml` itself is never read by the script: it holds the tokens.

The check, `agent_login_only` (behaviour 1), runs `agent_gh auth status --json hosts`: gh's stderr is dropped, and its stdout goes only to a judge run by `node`. The judge fails closed. A fault is any of these:

- gh exits non-zero: an unreadable or malformed config, or a gh with no `--json`.
- The output is not JSON with a `hosts` object of account lists.
- A host is not in host form, an account's login is not in login form, or an account has no boolean `active`.
- The config holds no login, a login other than `AGENT_LOGIN`, or a login on a host other than `github.com`.
- `AGENT_LOGIN` is listed twice, is absent, or is inactive.
- `AGENT_LOGIN` itself is not in login form.

Each fault is one line naming its fix: for a stray login, `log it out: GH_CONFIG_DIR='<AGENT_GH>' gh auth logout -h <host> -u <login>`, with the path single-quoted so the command pastes as it reads. `verify` runs it as one more `check_shown` line, in both modes. `setup` (behaviour 2) runs it after its token checks and, on any fault, prints the lines and stops before the clone, wiping nothing.

Nothing the judge prints can be a token. It prints a login only in login form: letters, digits and `-`, at most 39 characters. It prints a host only in host form: dotted labels of the same, with an optional port. Every GitHub token form either holds `_` (`ghp_`, `gho_`, `ghu_`, `ghs_`, `ghr_`, `github_pat_`) or, in the legacy form, is 40 hex digits with no dot. Neither fits either form. It also prints `$AGENT_GH`, a path from the environment.

Threat model: a mistake in the Patron's own config (a login stored by hand, or a setup run over a config that already held one), as found. A sandboxed session cannot write `$AGENT_GH` (D-045: mistakes, not adversaries); `verify` is a self-check, not a boundary against a session that skips it.
