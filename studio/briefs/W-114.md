## Intent

The opus title: an e2e proving a Patron reply carries through to the next workflow
step, in the record and in what the next actor sees, not merely that the write
succeeded.

Today `bisellium answer` is proven to **write** (`packages/cli/src/writes.test.ts`
calls `runAnswer` in-process and reads the file back). Nothing proves the reply is
**consumed**: that the record is what downstream readers parse, and that the actor
who was waiting on the Patron is actually shown the reply the next time it boots.
"The next actor" is whoever boots from `bisellium context --sella <id>`: that one
function, `buildContext`, is the system prompt of `talk` (`talk.ts:383`), the output
of the `context` verb, and the SessionStart/PreCompact hook bundle (`hook-event
context`). It is the real seam; no new one is invented.

**The investigation found a real carry-through gap** (measured below). A plain
`answer` sets `state: resolved`, and `buildContext` lists a petitio only when
`to === sella && state !== "resolved"` or `from === sella && state ===
"awaiting_reply"`. The asker (`from`) of a petitio is `to: patron` and sits at
`needs_you`, so it never saw the petitio before the answer, and after the answer the
petitio is `resolved`, so it is still excluded. The reply exists only inside the
petitio file; no boot surface shows it to the actor that was blocked on it. An e2e
that asserted the surface would therefore fail on current code. That red is the
point of the opus, and the fix is a few lines in one function, so it is in scope
(Interfaces). If the builder finds it larger than that, it stops and escalates; the
tests are still written and the fix is filed as a follow-on (Out of scope).

### The e2e harness (test side)

New file `packages/cli/src/answer-carry.test.ts`, a `node:test` TAP file modelled
on `next.test.ts` and `rules/tests.test.ts`: it reads `--behaviour N` from argv and
registers only that test. Rules:

- **Real CLI, argv-array spawn, no shell.** One helper `cli(args, input?)` wraps
  `spawnSync(process.execPath, ["--import", "tsx", MAIN, ...args], { cwd: REPO,
  encoding: "utf8", input, timeout: 120_000, env })`, where `REPO` and `MAIN` resolve off
  `import.meta.url` (a worktree's cwd is not the repo root), never from `process.argv`
  or a shell string. `env` is `process.env` copied with `TZ` set to `"UTC"` and `BISELLIUM_SELLA` and
  `BISELLIUM_ROLE` deleted, so a rerun under another zone or sella cannot change a
  row (the `timeout` and the pinned environment follow `next.test.ts` and
  `rules/tests.test.ts`). It returns `{ status, stdout, stderr }`; `r.error` is
  thrown.
  Every verb in a behaviour (`answer`, `context`, `check`, `query`, `hook-event`)
  goes through it. No row imports `commands/writes.ts` or `commands/context.ts`.
- **A temp officina fixture per behaviour.** `fresh()` is `mkdtempSync` under
  `os.tmpdir()` plus `cpSync("examples/sample-studio", dir, { recursive: true, dereference: true })`
  (so a symlink added to the sample later is copied as a file and no row can write
  through it into `examples/`),
  removed in `after()`. The sample officina is read, never written. Behaviours do
  not share a fixture, so `--behaviour N` runs in isolation. Nothing under `studio/`
  is read or written.
- **Pinned clock** `NOW = "2026-09-17T15:00:00Z"` passed as `--now` to `answer`,
  `context`, `check` and `query`; the stamp it produces is
  `[stated] 2026-09-17T15:00:00.000Z patron: <reply>`. Behaviour 5 is the exception:
  `hook-event` has no `--now`, so it uses the real clock (`new Date().toISOString()`
  captured once at test start and passed to `answer --now`), which sits inside the
  2-day window by construction. No sleeping, no timer, no polling: every spawn is
  synchronous and the next row reads its completed result.
- **Asserting what the actor sees** means asserting on `context`'s stdout (and the
  hook's), by exact substrings: the header line `A-1 · <state> · from <a> to <b>`,
  the line `--- data: petitiones/A-1.md ---`, the stamp line, and that the stamp
  falls between that data line and the next `--- end ---`. Not on file contents. A bare reply word (`Ship`, `Cut`) is never the
  assertion: the engineering lex contains "Ship greenlit features", so it passes on a
  pristine boot; every surface row uses the full stamp-line or header substring.
- **Red form.** Each behaviour is **one** `test("W-114 behaviour N: <title>", ...)`.
  A selected run is exactly `TAP version 13`, one `not ok 1 - W-114 behaviour N:`
  with `code: 'ERR_ASSERTION'`, `1..1`, `# tests 1`, `# fail 1`, `# pass 0`. The
  recorded command is `node --test-reporter=tap --import tsx
  packages/cli/src/answer-carry.test.ts --behaviour N`. Rows that pass today (the
  write, the record, the controls) come **before** the first row that needs the fix,

### The fix: a recently resolved petitio is shown to the sella it concerned

In `packages/commands/src/context.ts` section 5 ("petitiones addressed to the
sella"), keep both existing conditions exactly as they are and add **one** third
condition, which is the conjunction of the four tests below (not four alternatives).
A petitio is also listed for `sella` when **all** hold:

1. `state === "resolved"`;
2. `sella` is not the officina's patron (`manifest.patron ?? "patron"`), so the
   Patron's own boot is unchanged;
3. the counterparty is the patron: `(from === sella && to === patron) || (to ===
   sella && from === patron)`. A hand-written sella-to-sella resolved petitio (which
   `check` accepts: direction is enforced only for live states) is never carried to
   either sella;
4. the body has at least one line matching `^\[stated\] (\S+) ` (multiline), and the
   **last** such token matches `^\d{4}-\d\d-\d\dT\d\d:\d\d:\d\d(\.\d+)?Z$`, parses to a
   date `stamp`, and `stamp <= now` and `now - stamp <= DECISION_WINDOW_DAYS` days (2,
   the decisions constant). A stamp in the future, a non-ISO token (`1`, `2099`), or
   no stamp at all is never listed. (`daysBetween` clamps a future date to 0, so it
   must not be the only guard; the `stamp <= now` test is separate.)

**Bound.** Of the petitiones that qualify, only the **newest 3** by stamp (ties by
id) are listed, after the existing pending entries, and each such body is shown as
its last 1000 characters (prefixed `…` when cut) so the stamp lines at the tail
survive. The pending asks (`to === sella` unresolved, or `awaiting_reply` from the
sella) are unchanged, unbounded and listed first. Together these cap the carried
text at about 750 tokens, so a flood of stamped resolved files cannot push the
priority-5 section past the budget and cause truncation to drop the pending ask.

Rendering, priority (5) and truncation are otherwise unchanged: the same `<id> ·
<state> · from <from> to <to>` header and the same `--- data: petitiones/<id>.md ---`
block. A sella with no qualifying petitio gets output byte-identical to today. No
new front-matter key, no new verb, no change to `answer`'s writes, `readFront`, the
adapter, `query` or any web/inbox view.

**Landing behaviour on the real officina (stated, not hidden).** The stamp is the
only record of when a resolution happened, and a stamp written by `answer` cannot be
told from an older one, so there is no "answer-written only" gate. When this lands,
every stamped resolved petitio inside the window with the patron as counterparty
appears for its sella: today P-014 and P-015 (qa-lead) are in qa-lead's boot context
until 2026-10-03T11:03Z, then age out; the other eleven stamped petitiones are
outside the window and stay out. This tail is accepted: it is the intended
behaviour (qa-lead is being shown the Patron's reply to its own petitio). It means
"byte-identical to today" holds for the fixture and for sellae with no recent
petitio, not for qa-lead on the day of landing.

Rationale for the minimum: no `resolved_at` key and no new tunable. The alternative,
"show until acknowledged", needs a new state or verb and is a contract change (Out
of scope). If the builder finds that these four tests plus the bound do not fit in
the one section-5 block (a helper function in `context.ts` is fine; a new module,
schema or verb is not), it stops and escalates for a scope ruling.

## Stated residuals (accepted, with reason)

1. **`talk` is not spawned.** It needs a vendor harness. Its system prompt is
   `buildContext(root, sella, { now }).text` (`talk.ts:383`), the same function the
   `context` and hook rows exercise; the sharing is argued from that line, not
   asserted by a `talk` run. A harness-stub e2e is a follow-on.
2. **The hook row uses the real clock** (`hook-event` accepts no `--now`). It is
   safe because the answer is stamped moments earlier against a 2-day window; the
   cost is that this one row is not date-pinned.
3. **The next actor is defined as the sella opposite the patron on the petitio.** An
   opus owner who is neither `from` nor `to` (the usual builder on `--opus W-004`)
   sees nothing; a sella-to-sella resolved petitio is carried to neither; the
   `opus` link is recorded and surfaced in `query`/the record only.
4. **The window is a policy number** (2 days, the decisions constant). A sella that
   boots after two days no longer sees the reply in its context; the record still
   holds it.
5. **`dataBlock` does not escape a literal `--- end ---` in a reply.** Existing
   behaviour for every injected body; the reply is the Patron's own text. Not changed.
6. **Answering an already-resolved petitio** appends a second stamp and is allowed
   today; the rule reads the last stamp. Not changed.
7. **A forged last stamp hides the reply rather than showing it.** A reply that embeds
   a future `[stated]` line makes the petitio's last stamp unusable, so the real
   reply is not carried either (under-delivery, by design; the record still holds
   both). The stamp is unauthenticated body text and `BISELLIUM_ROLE=patron` is set
   for any caller of `answer`, so any shell actor can mint a "patron:" stamp inside
   the window; that predates this opus. The carry is a convenience view, not a
   confidentiality or authenticity control (`--sella` is a free argument).
8. **The cap is silent.** More than three recent resolved petitiones for one sella
   shows the newest three and omits the rest without a marker; the record holds all.
9. **No `opus.red_assertion` coverage of the TAP form** (pinned to W-096), as for
   W-124, W-125 and W-121.

## Out of scope

- An acknowledgement state or verb ("seen" / "closed by the asker"), a `resolved_at`
  key, or any change to petitio front matter or the `PETITIO_STATES` schema.
- Showing the reply to the owner of the petitio's `--opus` (needs a rule for builder
  instance ids and retired seats).
- Any web inbox, board or other UI change; `query` output changes.
- A `talk` e2e with a harness stub.
- Anything in `studio/` bookkeeping.
