## Intent

bisellium serve binds 127.0.0.1 and guards its writes with the session token and an `Origin` check (`checkWriteAuth`, `apps/server/src/http.ts:437`). Its reads guard nothing. Every `GET` route from `/api/officina` (`:664`) through `/api/inbox` (`:692`) to `/api/live` (`:742`) answers any caller. No route reads `Host` (the write check's doc, `:433`, says so on purpose). That opens a DNS-rebinding read. A page at a name the attacker controls re-resolves that name to 127.0.0.1. The browser then treats the console as the attacker's own origin, and the page reads the inbox, the opera, the receipts and the live event stream. The request carries the attacker's name in `Host`.

**The design: two gates at the top of `route()`, before any route.**

1. **Host (behaviour 1).** Every request, read or write, shell or asset, must name the bound socket in `Host`: `127.0.0.1:<port>` or `localhost:<port>`, with ASCII case ignored. Anything else gets `403 {"error":"host is not this console"}`. The two values are the authorities of the accepted origin pair (`acceptedOriginsFor`), so the Origin and Host checks read one tuple. This gate alone defeats rebinding, since a rebinding page cannot send the console's own name. It covers the shell and assets too, because one gate for every request is simpler to audit than a list of exemptions, and a rebinding page then cannot load the bundle either. Writes gain a check and lose none: Origin, token and Content-Type still run after it, in their order.
2. **Session token on reads (behaviour 2).** Every `GET` under `/api/` must carry the token serve prints, or it gets `401 {"error":"missing or invalid X-Bisellium-Token"}`. This is the same token and compare (`tokensMatch`) the writes use. It holds against what `Host` cannot stop: another local caller without the token, or a page that guessed a loopback name. It is checked before routing, so an unknown `/api/` path is also `401`.

**How the token reaches a GET.** The console's reads (`getJSON`, `apps/web/src/api.ts`) send it as `X-Bisellium-Token`, as `postWrite` already does. A browser's `EventSource` cannot set a header, so `/api/live` alone also accepts `?token=`. Every other route refuses a query token. The access log prints any `token=` value as `redacted`. The token stays where the Patron pastes it, in `sessionStorage` (D-023), and the page also holds it in memory, never persisted, so a browser that denies storage still reads. A page from another origin, a rebinding one included, can read neither.

**Why the shell and assets need no token.** `GET /` and `GET /assets/*` are a navigation and `<script>`/`<link>` loads, and those send no custom header. They hold no studio state, only the built bundle or the route index. D-023 keeps the token out of the bundle and out of any page `GET /` serves: injecting it there was rejected because "any local process that can `GET /` would obtain it". A cookie set by `GET /` would leak the same way. So they pass on `Host` alone.

**The browser flow (behaviour 3).** A fresh tab holds no token. `App.tsx` already opens the token prompt at mount when none is held (W-067). Each read the screens make is then refused in the page itself, with no request, so no `401` crosses the wire. The live stream does not open, and the screen shows its existing state behind the prompt. A stored token that is wrong gets a server `401`. The live stream gives no status, so one the server closed is checked by one read. Every refusal raises the same prompt (`setUnauthorizedListener`). In some cases the screens never got their data: no token was held, a read was refused before any read succeeded in the current routed-screen mount, or the stream was refused. Each mount (a route or a read epoch) begins with no successful read: `App.tsx` calls `beginReadMount` from a layout effect on the route and read epoch, which runs before the screen's own reads. So a stale token on a screen newly mounted after an earlier screen loaded (a serve restart, then a navigation) still owes the re-read. When the Patron then saves a token, the shell re-mounts its routed screen (`rereadAfterTokenSaved`, a keyed `Fragment`), and every read and the stream start again with it. This is a re-mount, not a reload, so the memory-held token survives. If the screens had loaded and only a later read or a write was refused, the prompt closes as it does today, and a drafted answer stays. The Inbox's answer path reads the opera before it writes (W-412), so a stale token there is refused on a read. A tab that already holds a valid token sees no change.

Real-browser proof: the served Playwright suite (`apps/web/tests-serve`) runs real Chromium against a real bisellium serve. Its specs paste the token into a fresh page or seed it, then read every screen, the stream included. It passes whole on the tip: 148 passed, 1 skipped (`serve-proto.out`).

## Interfaces

- `hostAccepted(req, acceptedOrigins): boolean` (new, not exported): `req.headers.host`, lower-cased, equals the part after `//` of one accepted origin.
- `readTokenOk(req, url, token): boolean` (new, not exported): `tokensMatch` on `X-Bisellium-Token`, or, when `url.pathname === "/api/live"`, on `url.searchParams.get("token")`.
- `loggedUrl(raw): string` (new, not exported): every `token=` query value becomes `redacted`.
- The refusals: `403 {"error":"host is not this console"}` and `401 {"error":"missing or invalid X-Bisellium-Token"}` (the existing write 401 body), both through `sendError`.
- The order in `route()`: Host; then, for a write path, Origin, token, Content-Type (unchanged); then, for a `GET` under `/api/`, the read token; then the routes (unchanged).
- `rereadAfterTokenSaved(): boolean` (new export of `apps/web/src/api.ts`): true once when a re-read is owed (see the console promise), then false until the next. `beginReadMount(): void` (new export of the same file): the current routed-screen mount has no successful read yet; `App.tsx` calls it from `useLayoutEffect` on `[route, readEpoch]`.
- `getToken()` now returns the token pasted this page first, then `sessionStorage`'s; `setToken` holds it in memory as well. The signatures are unchanged.
- Unchanged: `AcceptedOrigins`, `acceptedOriginsFor`, `checkWriteAuth`, `tokensMatch`, `StartServerOptions`, `StartServerResult`, every route's body, `postWrite`, `hasToken`, `TokenPrompt`, the serve CLI's printed lines.

Limits, stated:

- Unchanged code the promises lean on is a stated limit, not a guarantee (D-076 E): Node's `requireHostHeader` 400, `tokensMatch`, `acceptedOriginsFor`, `checkWriteAuth`, `sendError`, every route behind the gates, `TokenPrompt`, `postWrite`, every screen's reads and states, and the browser's `EventSource` and `sessionStorage`.
- W-070 (greenlit) will add a tailnet origin to the accepted tuple. Because the Host values derive from that tuple, it extends both checks at once. A proxy that rewrites `Host` to anything else is refused until then.
- The token on reads does not stop a local process running as the Patron, since it can read the studio and the terminal directly.
- A restarted serve prints a new token, so an open tab must be given the new one before it reads again. Before, only its writes needed it.
- serve bound to port 80 needs a Host with `:80`. Browsers omit the default port, so such a console is refused. serve defaults to 4477.

3. **The console's reads send the session token, a refused read raises the prompt, and a token saved after one re-reads the screens.** Row `W-501-b3` in `apps/web/test/w501.test.ts` stubs `fetch`, `sessionStorage` and `EventSource` under plain node. ## Defaults for the Patron

1. The console now checks every request's address line. A request must name the console itself (`127.0.0.1:<port>` or `localhost:<port>`), or it is refused. That alone stops a hostile web page from reading the studio through a renamed address. Agree?
2. Reading studio data now needs the same token that writing needs. The page and its scripts and styles load without it. In a fresh tab you paste the token once, as you already do before a first write, and the screen then loads. Agree?
3. When serve restarts it prints a new token, and an open tab now needs it before it shows data again. Until now the tab only needed it for writes. Agree?
4. The live update stream cannot send the token as a header, so it sends it in its address instead. Only that one route accepts it there, and the server log hides the value. Agree?
5. Once a screen has loaded, saving a new token just closes the prompt, so a half-written answer is kept; you then press the button again. The screen reloads its data only when it never got its data—a fresh tab or stale token before the current screen loaded—or when the live stream is authentication-refused and closed; an ordinarily dropped, reconnecting stream does not reload it. Agree?
6. No file this opus changes is one you own. Because it is security work, it waits for your yes on this design before the branch opens. Once the token is in, no screen’s look changes. A fresh tab shows each screen’s loading or error state behind the prompt, and the live stream waits until the token is saved. The pixel-baseline row skips here and in ordinary CI while no complete baseline set is committed; the remaining served browser rows still run. Agree?
