## Intent

D-071 G files "the step drawer (a read-only derivation of `next`)" so the console renders the functions the CLI already has. An open Board drawer says what state an opus is in and not what happens next: that lives in `next <opus>`, which only a terminal can run.

**The read writes nothing.** `next <opus>` in report mode is not read-only: `refreshTicket` writes or deletes the pending ticket, and a gated order takes a usage reading. Calling it from a server would also keep the problem of git itself, and that is what the prototype's own row found: the row snapshots every file under the repository, `.git` and HOME, bytes and mtime, and with those two paths removed it still failed on a new loose object in `.git/objects`. The review rung's `git merge-tree --write-tree` (`next.ts:655`) writes trees, and `git status --porcelain` may rewrite the index and takes its lock, which a working builder's `git add` can then trip on. So:

- A new file, `packages/cli/src/ladder-read.ts`, calls what `next --all` calls (`gather`, `deriveNext`, before the dispatch gate) and `next`'s own `readMarker`, `assess` and `silence` for the health. It never reaches `refreshTicket`, `gateDispatch`, `takeReading`, a marker or a step log: those are not on its path.
- Its git runs with `GIT_OPTIONAL_LOCKS=0` (no index refresh, no lock), and `GIT_OBJECT_DIRECTORY` at a scratch directory with the repository's objects as the alternate, so a tree it builds dies with the read.

`next.ts` itself changes by four words: `export` on `readMarker`, `assess`, `silence` and `silenceEntries`.

**It runs in a child process, and that is what keeps the Board fast.** `gather` and `deriveNext` block on `spawnSync` git and gh. In the server's process each read would stop every other request for its whole length. `serve.ts` injects `readLadder`, which spawns `ladder-read.ts` asynchronously, as it injects the runners, so `apps/server` imports no CLI module and `serve.ts` does not load `next.ts` at start.

**The cost, and the bound.** Measured on this repository on 2026-11-04 UTC at load 0.9, three runs each, from the child's start to its answer (`measure.out`): 0.25 s to 0.3 s on a rung with no `gh` read (W-300, W-500, W-502, W-413, W-001), 1.9 s to 3 s on one that asks `gh` (W-451, at `pr`). A silence read adds up to W-502's cost: at most 100000 entries, 2.36 s for 70024 at load 10, so about 6 s in the worst case this host has shown; the fingerprint of the main checkout's `.git/bisellium`, index, `.bisellium` and HOME's usage reading is the same before and after those eighteen reads. The bound:

- **A Board load runs no read at all**, at any number of opera: the route is read only when a drawer opens, and on a frame naming the open opus. W-502's cut is not spent here. `W-300-b3` pins that no ladder request leaves the page before a drawer opens, and `W-300-b2` that the Board's reads answer while a read runs.
- **One read at a time**, a request for an opus already waiting shares that answer, and past one running and eight waiting the route answers `unavailable` at once (`ladderQueue`).
- **15 s for one read** (`LADDER_READ_TIMEOUT_MS`), then `SIGKILL` and `unavailable`, which is more than twice the worst measured.

Why this and not the others:

- **`next <opus>` as the child, with its stdout parsed.** It writes the ticket, which is the whole problem, and parsing its report would make printed lines an API.
- **A `--read-only` flag on `next`.** It adds a user-facing flag, usage text and `parseArgs` to a read only the server needs, in the file W-298 is editing; a separate file keeps this opus's `next.ts` diff to four words.
- **A worker thread.** `spawnSync` inside it cannot be stopped by `terminate()` until it returns, so a hung `gh` has no hard bound, and the environment a child gets for free would be per-thread plumbing.
- **Serving every in-flight opus at once, with a cache.** That is a cost on every Board load, and a health line from a cache tells the Patron a working agent has stopped (W-502's own reason). W-500 reads this same route; how it asks for a list is W-500's to design, and the queue's eight is a stated limit it must meet (Limits).
- **Refactoring `next`'s report switch to share the health text.** It sits against W-298's call sites. The text is duplicated, and `W-300-b1` pins it word for word against a real `next` on every marker kind.

**What the line says.** `Next: <step>[ (held)] · <actor>[ · round <n>] · <health> · <why>`, with `PR #<n>` kept visible at its right end, one line under the title, cut by ellipsis, the whole text in `title`. Amber only when the actor is `patron`. A rung whose why is long is cut before its step and actor are. A done or halted opus has no line; an opus that cannot be read says `Next step not read: <why>` in the same quiet colour, since a line that vanishes would read as nothing to do. While it reads, `Reading the next step…`, which holds the height so the drawer does not jump.

**Who is amber.** On master the only rung that names the Patron is `greenlight` (`next.ts:1060`), so the route serves a backlog opus too, not only the states `next --all` calls open; otherwise amber would be dead until W-298. W-298's petitio hold (`held(actor, …)`) is the first in-flight case.

Threat model: mistakes, not adversaries (D-045). The route takes only an id the store already knows, and the child gets it as one argument, re-checked against `ID_RE`.
