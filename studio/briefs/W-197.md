## Intent

Decree family: patron-owned-github-configuration

A pull request that changes any path under `.github/` needs the Patron's GitHub approval before it can merge. That closes W-168's limit (a): a PR that edits `.github/workflows/ci.yml`, or adds another Actions job named `certify`, changes the YAML that certifies its own merge group. Under D-045 the threat is a mistaken edit, not an adversary.

Two parts, both reusing what exists:

- **GitHub:** a new `.github/CODEOWNERS` names `@edckt` for `/.github/`. The Patron then turns on "Require review from Code Owners" in ruleset `master_protection` (Patron setup).
- **Local:** `.github/` joins `PATRON_PATHS`. The `merge` rung then stops before an incoming `.github/` change reaches the main checkout and prints the Patron's command, as it already does for `.claude/`. A tracked, uncommitted change to a `.github/` path (staged or not; untracked files are not read) at `branch`, `pr`, `done` or the `merge` rung's fast-forward prints the Patron's recovery command beside the hold that rung already makes.

`isPatronPath` is unchanged: a path is the Patron's when it starts with a `PATRON_PATHS` entry. Its two readers are unchanged code whose answer changes:

- `dirtyReport` judges both sides of each tracked change (`trackedChanges` reads `git status --porcelain -z --untracked-files=no`, so untracked files never reach it). When either side is a Patron path, it picks the remedy by the change's two-column status code with surrounding spaces trimmed (W-141's rule, unchanged). A rename's or copy's original path, or a code other than exactly `A`, gets `patron: git -C <cwd> checkout [HEAD ]-- <path>`. A rename's or copy's destination, or code `A`, gets `patron: git -C <cwd> rm --cached -q -- <path>`. The `HEAD ` is added when any change that gets a `checkout` line is staged (its first column is not a space). Limit: the code stands in for "HEAD has the path". An intent-to-add ` A` trims to `A` and gets `rm --cached`. A path HEAD lacks, with a first column that is not a space and a trimmed code other than `A` (`AM`, `AD`, or an unmerged entry such as `UA` or `DU`), gets `checkout HEAD -- <path>`, which git refuses for a path HEAD lacks. The hold itself does not depend on the code, so the rung still holds; only the printed advice is wrong. That applies to `.claude/` today, and the fix is a separate opus. A tracked change already holds `branch` (`performBranch`, main checkout), `done` (`performDone`, main checkout, except the opus record and `docs/`), `pr` (`openPr`, opus worktree) and the `merge` rung's fast-forward of a checked-out master (`fetchTrunk`). - `patronStop` runs inside `fetchTrunk` whenever a reviewed merge commit is given (the `merge` rung through `landed`, and the `spec`/`done` landings through `landHead`). When local master is an ancestor of the merge commit and the tree diff between them names a `.github/` path, it returns `refusing: incoming paths belong to the Patron (<paths>); the main checkout is untouched`, followed by one `patron:` command. It runs first in `fetchTrunk`, so it returns before `fetchTrunk` fetches any ref or moves local master, HEAD, the index or a checkout file. Its own `git fetch origin <oid>` writes objects only: no ref, no tag, no `FETCH_HEAD`. Earlier parts of the same step are unchanged; for example, `gate` may already have fetched the opus remote-tracking ref. The hold depends on the tree diff, not on who made it: any PR whose change to `.github/` sits between local master and the reviewed merge commit stops the rung.

An opus PR that touches `.github/`, at each stage:

- **Today:** it merges through the queue with no approval, and the local `merge` rung brings local master to the merge commit as for any PR.
- **After W-197 merges, before the setting:** CODEOWNERS only requests your review, so the PR still merges with no approval. - **After the setting:** GitHub blocks the PR (review required) until `@edckt` approves. The merge queue does not change this: GitHub enqueues a PR only when its rules are met, and a merge group re-checks only the required checks. Its mode reads `merge-queue`, unchanged. `gate`'s existing check, alert and rules steps run first. Then `gh pr merge --auto` either arms auto-merge, or exits non-zero (`state=MERGE_FAILED`). After arming, the polls end in `state=QUEUE_TIMEOUT` while the PR waits, unless the PR changes under them (`gate`'s other existing states). The CLI's one merge call without `--auto` runs only in direct mode and requires `CLEAN`, which a blocked PR is not. GitHub merges nothing before your approval.
  - If auto-merge was armed, your approval lets GitHub queue the PR, and `certify` runs on the merge group.
  - If `gh pr merge` had exited non-zero, nothing is armed: re-run `merge` after approving, and it requests the merge again.
  - Once the PR is MERGED, re-run `merge`. Unless local master already contains the merge commit, it holds locally for your command, then `cleanup`.
  - A push after your approval dismisses it.
- **A PR that does not touch `.github/`:** no owner is requested and no review is required, so it merges as today. Limit: a voluntary approval on it is dismissed by a later push (default 4); nothing relies on one.
