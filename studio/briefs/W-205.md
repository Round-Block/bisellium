## Intent

Decree family: merge-queue-heavy-steps-once

Promise heavy-steps-once: before merge, the heavy steps run once, in the `merge_group` run on the merge-group commit, and no longer on the pull request (D-054 §2). For a source change these are the format check, `npm test` with its read guard, the sample-officina check, `officina`'s studio check, and `web-e2e`'s build and served E2E, with their setup and scope steps: 19 steps. For a records-only change they are the studio checks and `test:record`, with their setup and scope steps: 11 steps (`reads.txt` §2b) — limit: for a source change, five `gates` steps still run in both runs: checkout, setup-node, `npm ci`, typecheck and lint, the PR's fast early signal (Defaults 1). For a records-only change, three run in both: checkout, setup-node and `npm ci`. Typecheck and lint then run on the pull request alone, because the records-only merge group skips them. `certify`'s ten steps run only in the merge group, unchanged from master: for an opus head it reruns the six `CI_STEPS` and `verify`, which `gates` and `officina` also run in that group, as they do today. A records-only group takes W-203's short paths, and a head that is not `opus/W-*` mints nothing. So for a records-only non-opus head, the full suite runs only after the merge, on the `push`, as it does today.

The `pull_request` run still reports the four contexts that ruleset `master_protection` requires (`gates`, `officina`, `web-e2e`, `certify`, GitHub Actions integration 15368; `reads.txt` §3), so the PR can be enqueued:
- **`gates`** runs checkout, setup-node, `npm ci`, typecheck and lint. This is an early signal (Defaults 1).
- **`officina` and `web-e2e`** run as jobs whose steps all skip, so they conclude success, bucket `pass`.
- **`certify`** is skipped by its W-168 job condition. Its skipped check satisfies the required context, as on every PR since W-168 (PR 385: `certify=skipping`, merged).

The merge-group and push runs do not change. `reads.txt` §2 compares master's and this brief's step sets job by job, for each change kind under `merge_group` and under `push`, and finds them equal. Only the `pull_request` column changes.

No check is removed (production lex §11, D-054 §1):
- **Parity.** The `merge_group` run is master's, step for step: 24 steps records-only and 34 source, counted by job and step index (`reads.txt` §2).
  - Each step today's `pull_request` run executes has a merge-group counterpart: 14 of 14 records-only, 24 of 24 source (`reads.txt` §2b). So no step is lost by not running it on the pull request.
  - `certify`'s ten steps have no pull-request counterpart, today or under W-205.
  - What still runs in both is promise `heavy-steps-once`'s limit.
- **Tree.** The steps removed from the pull request ran on the PR head, a tree GitHub does not merge. The run that stays runs on the merge-group commit, the tree master will hold.
- **The mint.** For an opus head, `certify` runs W-168's mint from master's tooling on that tree. The mint runs `ci --opus`, which is the six `CI_STEPS` and then the opus's `verify` (`scripts/run-builder-host.mjs:843`). So CI still certifies at least what the local mint does. `certify` is unchanged from master, and W-205 removes none of its work.

Promise merge-result-parity: for each change kind, this brief's `merge_group` run executes every step that today's `pull_request` and `merge_group` runs execute together, on the merge-group commit — limit: `certify` mints only for an `opus/W-*` head (a non-opus head logs `nothing to mint`, W-168); a records-only group takes W-203's short path in `gates` and `web-e2e`; a group of several PRs is not this queue's setup (one PR per group).

Promise queue-only-merge: a PR reaches master only through a `merge_group` run of all four required jobs — limit: this holds only while ruleset `master_protection` requires the merge queue. Without the queue, GitHub would merge on the light `pull_request` checks, and the full suite would run only after the merge, on the `push`. Removing the queue therefore reverts W-205's conditions in the same change (Defaults 3).

**A PR that is never enqueued** loses its run on its head. For a source change, that is format, the tests, the read guard, the sample-officina check, the studio check, and the build and served E2E. For a records-only change, it is the studio check and `test:record`. That is acceptable for three reasons:
- It produces no merge result and cannot reach master (promise `queue-only-merge`).
- No certificate the studio records reads that run. The local mint and `certify` write the receipts.
- For an opus head, the local mint already ran the six `CI_STEPS` and `verify` on that head before `next`'s `pr` step (ADOPTION, Merge queue).

What it keeps is typecheck and lint.

**`push` to master** is unchanged. The scope step is skipped, its output is unset, and for either change kind the full `gates` and `web-e2e` paths and `officina` run. `certify` is skipped. **`certify`** is byte-unchanged.

The threat model is mistakes. Reused commands and jobs are judged by their exits (D-050); spec review judges the lines this change touches (D-054 §5).

## Defaults for the Patron to veto

1. **Typecheck and lint stay on the pull request** as the early signal. For a source change they are two of the five steps that still run in both runs (promise `heavy-steps-once`'s limit). Locally they take 11s and 4s, plus the runner's checkout and `npm ci`, against today's 15.7m. They catch the cheapest errors before a 16-minute queue pass. On a veto, `gates` defers them too. The PR run is then setup only, but the job must keep running (Correction 1).
2. **The post-merge `push` run stays full.** It runs after the merge, so it adds no queue time, and it is the safety net that W-131 and W-203 rely on.
3. **Removing the merge queue reverts W-205's conditions in the same change** (promise `queue-only-merge`). This is a rule in the `ci.yml` comment and ADOPTION, not a mechanism. On a veto, `gates` gains a pull-request step that reads master's rules and fails the job when the queue is not required. That costs one API call per PR.
4. **Conditions on existing steps, not new light jobs**, so the four context names and the ruleset stay as they are, and `officina` and `web-e2e` stay bucket `pass` (Correction 1).
