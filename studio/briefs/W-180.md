## Intent

Decree family: no-vendor-row-3-load-determinism

Row 3 of behaviour 9 in `scripts/no-vendor.test.mjs` checks that `runOnce` reads the violation log while its lock is still held. Since W-121 (commit 60a7ac7d, 2026-10-02) it does this by starting a second Node process A. A runs `runOnce` with a `beforeRelease` hook that prints `HOLD` and blocks on stdin. The test then probes the lock. A is spawned with `timeout: 30_000, killSignal: "SIGKILL"`. The handoff recorded on 2026-10-06 (commit 1fd95b85), after W-121, that row 3 "flakes under full-suite load (passes alone)".

The failure output was never kept: no log under `~/.bisellium-evidence` has a FAIL line from the post-W-121 row 3. The cause is therefore inferred, not captured. Every part of the row that depends on load comes from the child process: A's start-up and import, the `HOLD` pipe handshake, and the 30-second SIGKILL deadline that marks a slow but correct A as a failure. The lock is `openSync(lockPath, "wx")`, an exclusive create with no process owner. A second exclusive create inside `beforeRelease`, in the same process, gets the same `EEXIST` (`probe-inprocess.txt`). So the child is not needed, and W-180 removes it along with everything that depends on it.

Row 3 becomes one synchronous `runOnce` call. Its suite appends `row3-violation`. Its `beforeRelease` probes with `openSync(lockPath, "wx")` and expects `EEXIST`. After the call, the row expects the violation in `result.log` and the lock gone. It keeps three `check(9, …)` calls. `scripts/no-vendor.mjs`, the shims, `package.json` and CI do not change. The threat model is mistakes, not adversaries (D-045): the source contract catches someone accidentally putting a child or deadline back, not a disguised wait.

Promise no-row-deadline: row 3 decides pass or fail from `runOnce`'s returned log, the synchronous probe result and `existsSync(lockPath)` afterwards. It has no child process, pipe, wall-clock deadline, signal, poll or retry — limit: `runOnce` itself still runs `selfTest`'s shim `spawnSync` calls and the suite's `spawnSync`. Neither has a timeout, so no wall-clock deadline in row 3 or in `runOnce` turns a slow but correct run into a failure. Load can still fail a run for real: a failed process start (`EAGAIN`, out of memory) or a child the kernel kills. A failure before the suite writes its line fails check 1, and a thrown error fails the whole file. Row 3 does not check that the suite child completed: a suite killed after appending `row3-violation` still passes all three checks. That is still within what row 3 tests (the lock is held when the log is read and released after), and the suite is a one-line `node -e`. Two outer deadlines remain unchanged: W-121 behaviour 4's `spawnSync` of `scripts/no-vendor.test.mjs 9` (300 s, the whole of behaviour 9) and the `node:test` timeouts (900 s for behaviour 4, 600 s for behaviour 5). Under extreme load those can still report a hang, but they are not row 3's verdict. The flake's cause is inferred (Intent), so the promise is that the inferred mechanism no longer exists. It does not promise that no other cause exists.

Promise lock-held-at-adjudication: row 3 fails unless the violation is in `result.log`, the probe sees `EEXIST` at `beforeRelease`, and the lock is absent once `runOnce` returns — limit: the probe runs at the `beforeRelease` hook, which `runOnce` calls immediately before `releaseLock`, after the snapshot. W-121's behaviour 4's real-tree and mutant rows keep guarding where that hook runs. Old check 2 also required "A then exits 0". Its in-process counterpart is that `runOnce` returns. If it throws, the throw escapes `withCapturedStderr` and the file exits non-zero before printing row 3, which fails closed, but no FAIL line names row 3.

Promise rows-kept: behaviour 9 keeps three row-3 `check` calls, and W-121 behaviour 5 stays one `test()` row with the same title — limit: check 2's name and behaviour 5's row-3 assertions change, because the old assertions require the child and deadline that are the defect. The title's word "bounded" no longer describes row 3. It stays because W-121's recorded reds name the title.

No shortcut (production lex §11): no row is removed, skipped or weakened, no retry is added, and the deadline is not raised.

## Interfaces

No production interface changes. Row 3 uses the existing seam in-process:

```js
let probe = "beforeRelease was never called";
const { result } = withCapturedStderr(() =>
  mod.runOnce({ repoRoot: dir, shadowDir, lockPath, logPath, suiteCommand, beforeRelease: () => {
    try { closeSync(openSync(lockPath, "wx")); unlinkSync(lockPath); probe = "the lock was FREE before release"; }
    catch (err) { probe = err && err.code === "EEXIST" ? "held" : `unexpected probe error: ${err}`; }
  } }),
);
```

`suiteCommand` is master's `node -e` that appends `row3-violation\n` to `logPath`. A successful probe create is undone (`unlinkSync`) so the fixture is left clean, and it still fails check 2. The three checks are: `result.log` includes `row3-violation`; `probe === "held"`; `!existsSync(lockPath)`. Each prints its observed value as detail.

## Defaults for the Patron to veto

1. **Probe the lock in the same process.** An exclusive file create has no owning process, so a second create sees a held lock directly. A separate process added only start-up time and a deadline.
2. **Remove the deadline rather than raising it.** A larger timeout keeps the cause.
3. **Keep every row.** Row 3 keeps three checks, and W-121 behaviour 5 keeps one row and its title, with assertions that match the fixed mechanism.
4. **Leave production code alone.** W-121's `beforeRelease` seam is enough. W-180 changes only how the test uses it.
