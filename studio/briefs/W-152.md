# W-152 — the Status page: progress read from records, its sources guarded

Status: **signed spec, revision 1** · architect sella (claude-opus-5-5) · 2026-10-06.
The spec gate is written by `bisellium verdict W-152 --phase spec`, not by this text.

## Intent

Decree family: status-page

The decree: **how far the product has come is read from records, never
typed: milestones and each opus's score are data, the page is generated,
and a hand-written source of the page cannot silently lose most of itself.**

D-038 ("The Status page") is the ruling. Today:

- **The % lives outside the officina.** `acta/2026-10-06-milestones.md`
  holds two Markdown tables (ten milestones; 146 opus rows, 138 scored and
  8 `outside`). `~/.bisellium-evidence/milestones/compute.mjs` parses them
  and reads each opus's state. At master `0ddc2d9` it prints
  **overall 49.5%** (138 mapped, 8 outside). Nothing fails when a new
  opus is filed without a row.
- **Two pages say one thing.** `build.sh` builds Progress
  (`progress-body.html`, hand-written cascade rows) and Backlog
  (`backlog-body.html`, generated by `scripts/backlog-page.mjs` from front
  matter, W-041). The Patron approved one page, in this order: completion
  meter (overall and per milestone), in flight and next, backlog, cascade
  history.
- **A source was gutted unnoticed.** On 2026-10-02 `body.html` went from
  70 KB to 2.4 KB. Nothing failed, and PR 250 restored it by hand.

The formula is the Patron's, and it does not change. Milestone % = 100 ×
points done ÷ points planned (0 when nothing is planned). It is capped at
95 while the milestone's exit check is open. Overall % = Σ weight × % ÷ 100.
A met exit does not raise a milestone to 100. It only lifts the cap, so M1
can read 97.3% with its exit met. Points are planned for every mapped opus
that is not halted, and done when its record reads `done`.

Mapping is set by `amend`, a verb that already exists. It writes the record
through the D-021 guard, requires a reason and keeps an `amendments:`
history. Two flags are added; no new verb is needed.

**Initial data is produced by a kept script, never typed.**
`scripts/milestones-seed.mjs` reads the acta's two tables. It writes
`studio/milestones.yml` and runs `bisellium amend` once per scored row. Its
run on the real officina lands after this opus merges (see Acceptance).
D-021 refuses other opera's records from `opus/W-152`.

## Interfaces

```yaml
# studio/milestones.yml — the milestone records (D-038)
milestones:
  - id: M1                      # ID_RE, unique
    title: "Build process, first version"
    weight: 10                  # positive integer; all weights total 100
    exit: { opus: W-125 }       # exactly one of: opus <id> (met when done) |
                                #   rule <id> (met when check has no finding of it) |
                                #   needs <text> (never met — the check does not exist yet)
```

```yaml
# on each opus record, written only by amend
milestone: M4
value: 3                        # one of 1, 2, 3, 5, 8
```

```
bisellium amend <opus> [--title <text>] [--spec <path>] [--arc <id>] [--parent <id>] [--ui-ruling <decision-id>] [--milestone <id> --value <n>] --reason <text> [--sella <id>] [--studio <dir>] [--now <iso>]
```

`--milestone` and `--value` come together. The milestone must be declared in
`milestones.yml`, and the value must be one of 1, 2, 3, 5 or 8. Each
changed field appends its own `amendments:` entry and emits
`workflow.item_amended`, as `--arc` does today. A refusal exits 2 and
writes nothing.

```ts
// packages/cli/src/rules/milestones.ts — Seam S2, unchanged signature
export function checkMilestones(root: string, opts: RuleOpts): Finding[];
// milestones.shape (block): milestones.yml unparseable, id bad/duplicate, weight not a positive integer,
//   weights not totalling 100, exit not exactly one of opus|rule|needs.
// opus.milestone (block): an opus not halted with no milestone, more than one (a sequence),
//   an undeclared id, or a value outside 1,2,3,5,8. Inert when milestones.yml is absent.
```

`docs.dossier.shrink` (block) lives in `rules/docs.ts`. It runs only when
`--repo` is given. Its sources are `docs/design/dossier/body.html` and
`docs/design/dossier/*-body.html`. The baseline is
`git merge-base HEAD refs/remotes/origin/master`, and `HEAD` when that does
not resolve. Outside git, the rule is silent.

A file present in both the baseline and the working tree is flagged when
its size is under half its baseline size. The message names both sizes and
the base's short oid. A file that is new or deleted is not judged. A cut
also passes when the working-tree file carries
`<!-- dossier-shrink-ok: <reason> -->` and the baseline did not.

## Behaviours to test

Each row is named `W-152-b<n> behaviour <n>: …` and is selected by
`--test-name-pattern=W-152-b<n>`. Every row builds its own fixture under
the OS tmp dir and writes nothing in `studio/` or `examples/`.

1. **`milestones.shape` judges the milestone records.**
   File: `packages/cli/src/milestones.test.ts`, grep `W-152-b1`. Two
   milestones whose weights total 90 yield a `milestones.shape` block that
   names 90. Each of the following yields its own finding:
   - a duplicate id;
   - an exit with two keys;
   - an exit whose key is unknown;
   - YAML that does not parse.

   A valid file yields none. An officina with no `milestones.yml` yields
   none.

   **Genuine red:** with the module wired but returning `[]`, the row fails on its "weights total 90 yields milestones.shape" assertion.

2. **`opus.milestone` fails an opus that is not halted and maps to zero, or to more than one, milestone.**
   File: `packages/cli/src/milestones.test.ts`, grep `W-152-b2`. The
   fixture declares M1 and M2. Each of these opera yields one block,
   `where: opera/<id>.md`:

## Out of scope

Each is a follow-on for the producer to file, or someone else's step.

- **A console Status screen** (`apps/web`). This opus builds the dossier
  page only.
- **`new --milestone --value`**, so that filing and scoring are one
  command. Until then a new opus is filed, then amended in the same PR.
- **A verb for milestone records** (re-weighting by command). Until then
  `milestones.yml` changes by a reviewed PR.
- **The five `needs:` exit checks** (M2, M4, M5, M9, M10). Each is its own
  opus, and those milestones stay capped at 95% until their checks exist.
- **Generating the cascade history rows from records.** The checkpoint
  keeps writing them into `progress-body.html`.
- **Flagging a halted opus that still carries a mapping.** It is simply
  not scored.
- **Republishing artifacts and editing `docs/SESSION-HANDOFF.md`'s page
  links.** The orchestrator does this at checkpoint. Retiring
  `compute.mjs`, and the note that D-038's `kill_when` has fired, are the
  producer's.

## Defaults for the Patron to veto

Each ships as stated and can be overturned at the checkpoint.

1. **Verb.** A mapping is set with the existing `amend` command plus
   `--milestone` and `--value`, and it keeps a reason and a history. There
   is no new command.
2. **Where the data lives.** One file, `studio/milestones.yml`, holds the
   milestones. Each task's record carries its own `milestone:` and
   `value:`.
3. **Which tasks must be mapped.** Every task that is not halted: backlog,
   approved, under way and done, as in the acta's mapping. Halted tasks
   are exempt.
4. **Shrink threshold.** A dossier source that loses more than half its
   size, against where the branch left master, fails the check. New or
   deleted files are not judged. A deliberate big cut passes if the file
   carries a `dossier-shrink-ok` comment giving the reason.
5. **Retiring the old pages.** `build.sh` stops building Progress and
   Backlog, and their generated files are deleted. The history rows stay
   hand-written in `progress-body.html`. The Status page is published at
   the Progress page's existing link.
6. **How the meter looks.** A plain table: milestone, weight, points
   done/planned, exit check met or open, and %. Each row has a thin bar.
   Overall % is one line above the table. There is no gauge, donut or card
   strip (DIRECTION §7 bans them).
7. **Headings and extras.** "In flight" and "Planned" together are the
   "in flight and next" part. The decisions table ("Standing constraints")
   stays, last, after the history, so W-041's shipped rows keep holding.
   History rows keep their file order, oldest first.
8. **When the real data appears.** Right after W-152 merges, in its own
   small PR. Until then the meter reads "No milestone records".
