## Intent

Decree family: concurrent-opus-lanes

Production lex §11 keeps one lane until W-169 and W-197 land. W-169 lets one orchestrator run any number of lanes, each an opus in flight. Their briefs' Files owned must not share a file. Each lane gets its own section in the handoff. The change is a derived in-flight set, one overlap check with a lock at the `branch` rung, and handoff lane sections. There is no scheduler, coordinator, claim store or second orchestrator.

Promise atomic-claim: after any sequence of `next --perform --expect branch` runs, no two `opus/*` branches that `next` made and kept, whose trunk records are neither `done` nor `halted`, have overlapping Files owned, and no opus has two. Each run holds `<repo>/.bisellium/branch-claim.lock` with `flock -n` from its re-derive through `performBranch`, including its rollback. So a run that overlaps another in time is held at the lock, and a later run's check sees every branch an earlier run kept — limit: a halted opus's surviving branch leaves `inFlight()`, so it no longer holds overlapping starts, and resuming it is not a branch run and is not checked; a branch `performBranch` creates and then rolls back (a failed `git worktree add`) is not kept, and a later overlapping run may create its own; the lock orders only runs that overlap in time; two sequential runs can both pass the check when neither creates a branch (for example, both are held by `performBranch` on a dirty master), which creates nothing; this holds for runs in one clone on one machine that share that file and the kernel's lock table, across sandboxed calls and PID namespaces (W-183's probes); it needs util-linux `flock` on `PATH`, and without it every branch perform holds; a branch made by hand outside `next` skips the check; a holder that hangs alive keeps the lock until it is killed.

Promise disjoint-lanes: `next` holds an opus at `branch` when a path from its brief's Files owned (the `` - `path` `` bullet grammar) equals a path of any opus in flight, and names both opera and the path — limit: the check sees declared files only, not imports, generated files, ports or host load (W-183); a file named in prose rather than as a bullet is not owned; an in-flight opus with no readable brief or an empty set holds every new start.

Promise lane-handoff: a `next`-performed done commit is held unless the handoff has exactly one `### Lane W-<n>` section for each other opus in flight, with one `Next` field, and none for a done or halted opus (an absent handoff with any opus in flight is held) — limit: coverage is checked only at that hold, in the main checkout of the real `studio/` (`handoffHold`'s scope); `check` and CI validate the sections' form and staleness but cannot see local branches; done and halted are read from master's records, so a halt recorded only on an opus branch reads as in flight until it lands.

Promise retro-frontier: an owed retro holds only an opus with no local `opus/<id>` branch, so an opus in flight keeps its derived rung — limit: this is today's behaviour, kept by a regression assertion; the done opus's own `retro` rung still applies.

The threat model is mistakes (D-045). No test row is removed or weakened, no numeric lane limit is added, and nothing in CI, receipts, certificates or the merge queue changes.

## Interfaces

```text
export function readFilesOwned(briefText: string): Set<string>   // host grammar: ^- `([^`]+)` within ## Files owned
```

The branch claim is `<repo>/.bisellium/branch-claim.lock`. `branchClaim` refuses a path that exists and is not a regular file (`lstat`). It then spawns W-183's holder form, `flock -n -E 75 <lock> -c 'echo held; exec cat'`, with the child's stdin a pipe from `next`:
- `held` on stdout claims it;
- exit 75 holds the branch rung (`why: another branch is being claimed`);
- a spawn error (no `flock`), any other exit or a signal holds and names the cause.

Release closes the pipe, so `cat` exits and the kernel frees the lock. If `next` dies, the same EOF frees it. No PID is read and the file's content is never read. This is the interface shared with W-183: the same holder form and the same reliance on `flock`. W-169 lands after W-183, and if W-183 exports its holder as a helper, `branchClaim` calls it instead (D-057 re-review). W-169 does not use W-183's heavy-job slots or `BISELLIUM_HEAVY_JOB`.

The handoff form, under `## Resume point (YYYY-MM-DD)`:

```text
### Lane W-169

- **Next:** run the reds for behaviour 2.
```

A lane section runs from its heading to the next `### ` or `## ` heading. It holds at most 8 lines and exactly one `Next` field. Its id is unique, has a record, and is not `done` or `halted`.

## Out of scope

- A claim store, lane names other than the opus id, claims across clones or machines, automatic lane choice or priority.
- Semantic overlap (imports, generated files, ports, host load: W-183); globs or directories as ownership.
- Changing the host's ownership grammar, or making briefs list test files as bullets (a brief-format follow-up).
- Concurrent edits of the handoff (one orchestrator writes it); checkpoint pages (W-181); security passes (W-093).

## Defaults: questions for the Patron (pipeline work)

1. Should a lane simply be an opus in flight (a local `opus/<id>` branch whose record is not done), with no separate lane name or claim file?
2. Should overlap be an exact shared file from the brief's Files owned bullets, so that two opera touching `next.ts` never run at once, even in different functions?
3. Should an opus in flight whose brief lists no owned files hold every new start until that is fixed, rather than count as owning nothing?
4. Should lane coverage in the handoff be enforced only when a done commit is made, while `check` and CI only check the sections' form and staleness?
5. Should each lane's handoff section be capped at 8 lines, and left out of the 100-line handoff cap so the lane count has no limit?
6. May the branch claim rely on util-linux `flock` (W-183's question 3), so that branching holds wherever `flock` is missing?
