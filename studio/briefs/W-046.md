# W-046 — provider portability: the decreed model and a command policy reach both harnesses

**Proposed record title change.** The record reads "provider portability:
one opus end-to-end on both harnesses, model and policy passed". This brief
delivers the second clause and explicitly does not deliver the first: what
crosses both harnesses here is a **talk-shaped dispatch** (a bounded,
read-only, context-carrying turn), not an opus. Sol's round-1 finding 1 is
upheld. The title above is the honest one; the record is the orchestrator's
to change through the CLI. Opus-level portability is filed as the follow-on
named in Out of scope, and nothing in this brief may be read as delivering
it.

Spec of record, signed by the architect, 2026-09-24; revised the same day
after Sol's red-team (UNSOUND, 6 blocking — all six accepted, three of them
by removing or narrowing a claim rather than by adding work). Inputs
reconciled: `docs/research/agent-studio-landscape-2026-09-21.md` (the
standing landscape: `talk` has Claude and Codex profiles but passes neither
the requested model nor an equivalent command policy; hooks are Claude-only;
dispatchers may own leases/retries/quotas/recovery while files, decisions,
checks and certificates stay authority), `docs/research/herdr-landscape.md`
(the dispatch envelope: Bisellium constructs sella, decreed model, policy,
bounded task, working directory and context; the adapter returns transport
facts only), and `studio/decisions/D-020.md` (direct `codex exec` is an
interim transport, model tiers are decreed, codex output is input and never
a gate). This opus is cross-cutting and touches a permission boundary, so
Sol red-teams this brief (D-020) as input, not authority. The `ready` gate
is signed on `opus/W-046` after `bisellium branch` (D-021).

## Intent

`talk` is the one seam through which bisellium starts a vendor session
(`performTalk`, `packages/commands/src/talk.ts`; `tick`'s unattended
dailies and `serve`'s `POST /api/talk` both route through it). It resolves a
sella's **harness** from `sellae[].harness` and stops there. The manifest's
`sellae[].model` — the decreed tier, the thing D-020 exists to fix — is read
by **no dispatch path**. (It is not dead data: `adapters/native/src/index.ts`
copies it into snapshot metadata. It simply never reaches a vendor.)

So today a sella declared `model: claude-opus-5` is talked to on whatever
model `claude` happens to default to, and a sella declared
`model: gpt-5.6-sol` is talked to on **claude** (the default harness) with
that same vendor default. The decree is written down and then dropped on the
floor.

The policy half is worse than "missing". W-044 made the claude profile a
deny-by-default permission boundary: `--restricted`, `--strict-mcp-config`,
`--permission-mode dontAsk`, an enumerated `--tools`, and an enumerated
`--allowedTools` admitting exactly `bisellium context|query|check`. The
codex profile spawns `codex exec --json --skip-git-repo-check -` and
nothing else — no policy at all.

### Measured on this machine, 2026-09-24

Not assumed. `codex-cli 0.153.4`, `claude` 2.x, WSL, inside the studio's
bubblewrap sandbox. Sol's round-1 probes agree on the CLI facts; every claim
below that this brief acts on was re-run here.

- **The codex profile's own argv loads the operator's personal config.**
  Running exactly today's argv under the W-049 env projection produced six
  `https://chatgpt.com/backend-api/ps/mcp` connections: the operator's
  `~/.codex/config.toml` declares an `mcp_servers` entry and an enabled
  plugin, and the talked session started them. That file also pins a default
  `model` and a `model_provider`. `codex doctor` confirms: `config.toml
  ~/.codex/config.toml`, `MCP servers 1`, `feature flags 47 enabled`.
- **`--ignore-user-config --ignore-rules` removes that surface.** The same
  run with those two flags produced **zero** MCP connections. Scope of the
  claim, exactly: it removes what the **user config file** declared. It is
  not a general configuration or tool boundary (see the signed limit below).
- **`sandbox_mode=read-only` is a real write boundary, and it holds inside
  the studio sandbox.** A turn asked to run two commands: `cat package.json
  | head -2` returned exit 0 (the read ran), `touch
  <repo>/zz-w046-probe.txt` returned exit 1 and no file was created. No
  nested-sandbox failure: D-020's "codex's own sandbox off inside the studio
  sandbox" lesson does **not** apply to a read-only talk turn, and no bypass
  flag is needed. It bounds writes only — not reads, not MCP, not any tool
  feature.
- **Feature defaults are an open egress surface, and `--disable` closes the
  named ones.** `codex features list` shows `browser_use`,
  `browser_use_external`, `browser_use_full_cdp_access`, `in_app_browser`,
  `apps`, `plugins`, `remote_plugin` and `plugin_sharing` as **stable and
  enabled by default** — none of them governed by `sandbox_mode` or by
  `--ignore-user-config`. W-044 deliberately dropped `WebFetch` from the
  claude profile because "paired with `Read` it would be the profile's only
  egress"; a codex talk session has that egress today. `codex features list
  --disable browser_use --disable apps --disable plugins --disable
  in_app_browser` reports all four as `false`, so the mechanism is real and
  verifiable without a model call. Web search proper is already off on this
  version (`search_tool` removed, `standalone_web_search` false,
  `web_search_request` deprecated/false), so no web-search flag is
  specified — a `-c tools.web_search=false` guess is **not** in the policy,
  because its key name is unverifiable from the installed help.
- **The whole proposed codex argv works under W-049's ten-name env
  allowlist, unchanged.** `env -i` with exactly `PATH HOME SHELL TMPDIR
  HTTPS_PROXY https_proxy HTTP_PROXY http_proxy NO_PROXY no_proxy` plus the
  policy argv and `-m gpt-5.6-luna` completed a real turn: exit 0, one
  `agent_message`, usage reported. **No env name needs to be added.** The
  qualification is load-bearing and stays in the docs: this works for the
  **default login location only** — `$HOME/.codex/auth.json` (`codex
  doctor`: `auth storage mode File`, `stored auth mode chatgpt`).
  `CODEX_HOME` and `OPENAI_API_KEY` are off W-049's allowlist by design, so
  a custom config home and API-key-only auth do **not** work through a
  bisellium-spawned codex, and that is intended, not a gap.
  Dropping the six proxy names breaks DNS under the sandbox, which is why
  they are on W-049's list already.
- **`codex exec` and `codex exec resume` do not take the same flags.**
  `resume` accepts `-m`, `-c`, `--json`, `--skip-git-repo-check`,
  `--ignore-user-config`, `--ignore-rules`, `--disable` — and **rejects
  `-s/--sandbox`** (`error: unexpected argument '-s' found`). It also has no
  `-C/--cd`. One policy constant can therefore serve both spawns only if the
  sandbox mode travels as `-c sandbox_mode=read-only`. Measured on both:
  start and resume each accepted the identical constant (including every
  `--disable` token), and each denied the write. **This inventory is not
  exhaustive** — `--oss`, `--local-provider`, `--profile`,
  `--approve-for-me`, `--add-dir` and `--color` are also start-only (Sol,
  note 9). No profile may assume a flag crosses; the builder diffs the two
  help outputs (Order of work).
- **A project-level codex config did not override anything.** A fresh
  directory holding `.codex/config.toml` with `model_provider =
  "zzbogusproj"` ran a normal turn on the user config's provider, so that
  key at least is not a project-level channel on 0.153.4. This is one
  measurement of one key in an untrusted directory: it is **not** a proof
  that no project, managed, system (`/etc/codex/config.toml`) or cloud
  default channel exists. Those stay in the residual list, unmeasured.
- **Codex never reports a model.** No event in any successful run carried a
  `model` key, so `Turn.model` is `undefined` for every codex turn and the
  timeline records no model at all. Claude's JSON envelope does carry one.
- **The manifest's model names are valid on the claude harness, and a
  cross-vendor name fails closed and loudly.** `claude --model
  claude-opus-5` and `--model claude-sonnet-5` both returned exit 0;
  `claude --model gpt-6-astra` returned exit 1 with
  `[claude-code:unrecognized_model]`. Consequence worth stating: after this
  opus, a sella whose declared model does not belong to its harness stops
  silently running on the wrong model and starts failing. Two such rows
  exist today — `studio/bisellium.yml`'s `builder-sol` (`gpt-5.6-sol`, no
  `harness` key, so claude-code) and `examples/sample-studio`'s `art-lead`
  (`gpt-6-astra`, same). The real studio's row is fixed here (Files owned);
  the fixture's is left and filed (Out of scope).
- **`claude -p --resume` with `--model` is unproven live.** One attempt to
  resume a session id returned by a previous `claude -p` run answered "No
  conversation found with session ID". That may be a property of `-p`
  session storage rather than of `--model`, and it is **pre-existing**: it
  is the resume path talk already depends on at HEAD. Acceptance now forces
  a live claude resume turn and says what to do if it fails (it is a finding
  against the existing path, reproduced on `master` before it is blamed on
  this opus).
- **A turn can exit 0 with no reply.** D-020's recorded lesson ("output
  non-empty check before trusting exit 0") has a code home:
  `codex.ts`'s `exitCode: code ?? …` trusts the process code verbatim, and
  `claude-code.ts` returns `parsed.result ?? ""` with `exitCode: r.status`.
  Either path can hand `performTalk` a Turn with `exitCode: 0` and
  `reply: ""`, and `performTalk` then prints an empty line, writes a session
  file, appends two timeline entries **and closes a receipt** — a recorded
  success that never happened.

### The signed limit: W-044 equivalence is not achieved on codex

This is the finding Sol forced, and it is stated here rather than in a
review log, because a later brief must not be able to write "codex is
boundaried now".

**What the codex policy achieves:** no writes outside the sandbox mode; no
user-config-declared MCP servers or plugins; no user or project execpolicy
rules; no ambient default model or provider from the user config file; no
browser, in-app-browser, apps or plugin feature.

**What it does not achieve, and what W-044 does achieve on claude:**

- **No tool allowlist.** Claude's profile enumerates what exists
  (`--tools`) and what is approved (`--allowedTools`, ten literal rules), so
  a verb the CLI has not shipped yet is denied by construction (W-044
  behaviour 3). Codex offers only a **denylist of named features**. A
  denylist goes stale by the next release — this repo's own W-049 ruling
  says so. The `--disable` list in this policy is a denylist with a known
  ceiling, taken because a known-open egress surface is worse than an
  imperfect closure, not because it is equivalent.
- **Reads are unbounded.** `sandbox_mode=read-only` permits every read the
  operator can perform, including `~/.codex/auth.json`. A talked claude
  session cannot run `cat` at all. This is the largest asymmetry.
- **Instruction files still load.** `AGENTS.md` (user and project) is not
  covered by any flag specified here.
- **Configuration channels beyond the user file are unmeasured.** Project,
  managed, system and cloud defaults: one negative measurement above, no
  proof. Treat as residual.
- **The execpolicy `.rules` mechanism is not the enumeration fix.** Round 1
  of this brief said it was; Sol is right that execpolicy governs which
  commands may escape the sandbox or need approval, not which reads are
  permitted inside it. The upgrade path for a real command allowlist is
  **unknown** and is the follow-on opus's first question, not a claim made
  here.

Every one of these residuals is repeated in the `docs/ADOPTION.md` paragraph
this opus owns, and behaviour 6 asserts they are there.

### What this opus is, and is not

It makes the Herdr envelope real at the one seam that exists: **the decreed
model travels from the manifest through `performTalk` into both vendor
profiles, and the codex profile gains a command policy of its own, with its
limits signed.** It is not a universal adapter layer, it does not move build
dispatch into the CLI, and it does not deliver one opus end-to-end on both
providers.

D-020's `kill_when` names this opus. Say the residue plainly: bisellium
still cannot dispatch a **build** on either harness — builders are spawned
by the vendor's own Agent tool, and codex builds are still
orchestrator-mediated. W-046 landing retires the interim transport clause
for **talk-shaped** dispatch only. D-020's `kill_when` fires as written — it
triggers a *review* of that decision, not an automatic repeal of its build
clauses.

### What "end-to-end" means as a test

**A fixture officina, in-process, against stub vendor binaries** — that is
the honest testable unit for a talk-shaped dispatch, and it is behaviour 5.
Driving a real `claude` and a real `codex` from a test would put a paid,
non-deterministic, network-dependent call in `npm test`, and the recorded
reds would carry real session ids and real usage. The precedent is W-044 and
W-049: stub binaries that log their own argv, their stdin and their cwd and
never execute what they are handed; evidence is string-level.

The live dual-harness proof is **Acceptance-level, attended, run by the
censor**: the same command against the real `claude` and the real `codex`,
on a temp copy of `studio/`, using two sellae whose decreed models belong to
their harnesses. That proves the *seam*, not an opus. Opus-level
cross-provider evidence is the follow-on's, and D-020's codex-build trial
(W-050) is separate evidence on a separate transport; neither is claimed
here.

## Interfaces

- **Envelope, new fields.** `HarnessStartOpts.model?: string` and
  `HarnessResumeOpts.model?: string`. Doc comment, in both places:

  > The model bisellium decreed for this sella (`sellae[].model` in the
  > manifest). Absent means **no bisellium override** — the caller declared
  > no model, so the vendor decides (its own default, or, on a resume, the
  > model the saved session already runs). Never "look one up". A profile
  > passes this value to its vendor CLI verbatim and reads a model from
  > nowhere else: not from the environment (W-049), not from a vendor config
  > file (this opus's codex policy), not from the session being resumed.

  Documented reason for the seam change: this opus. It is additive and
  optional, so `fake` and `git-only` need no edit.
- **`Turn.model` is unchanged**: what the vendor echoed, or `undefined`.
  The requested-model fallback lives in `performTalk`, one expression,
  because it must hold for every profile and every caller — not per profile.
- **No new CLI flag.** `talk` gets no `--model`. Models are decreed
  (D-020); a per-call override would be a route around a decree, and
  `--harness` already exists for the one axis an operator legitimately
  switches. If an override is ever wanted it is a decision first.
- **Policy is a profile constant, not an envelope field.** The Herdr
  envelope names "permission policy" as a field; bisellium has exactly one
  policy per profile, and W-044's whole point is that a caller cannot weaken
  it. So the model travels in the envelope (it varies per sella) and the
  policy stays a module-local constant in each profile (it does not). The
  day a second policy exists — a build session, which needs write
  permission — the envelope carries a policy **name** and each profile maps
  it. That is the trigger; it is not today.
- **The codex policy, exactly.** One constant, applied identically by
  `start` and `resume`, because `codex exec resume` rejects `-s`:

      ["--json", "--skip-git-repo-check",
       "--ignore-user-config", "--ignore-rules",
       "-c", "sandbox_mode=read-only",
       "-c", "model_provider=openai",
       "--disable", "browser_use",
       "--disable", "browser_use_external",
       "--disable", "browser_use_full_cdp_access",
       "--disable", "in_app_browser",
       "--disable", "apps",
       "--disable", "plugins",
       "--disable", "remote_plugin",
       "--disable", "plugin_sharing"]

  `start` emits `["exec", ...POLICY, ...model, "-"]`; `resume` emits
  `["exec", "resume", <id>, ...POLICY, ...model, "-"]`, where `...model` is
  `["-m", <model>]` or nothing. The prompt is `-` plus stdin, never a
  positional token (unchanged). The working directory is the spawn's `cwd`
  option — **never** a `-C`/`--cd` argv token (D-020's lesson; `codex exec
  resume` does not even have the flag). No `--dangerously-bypass-*` token is
  ever emitted by a profile. `model_provider=openai` is D-020's decreed
  transport, and it must be passed explicitly precisely because
  `--ignore-user-config` drops the config file that used to supply it. The
  eight `--disable` names are a **denylist with a known ceiling** (the
  signed limit); write that in the header comment beside them, with the
  verification command (Order of work) that proves each one still names a
  live feature.
- **The claude argv ordering rule.** `--allowedTools` is variadic and
  terminal, so `POLICY_FLAGS` must stay last: any flag added to this profile
  goes **before** it. `--model` goes after `--output-format json`. Start:
  `["-p", "--output-format", "json", ...model, "--append-system-prompt-file",
  <file>, ...POLICY_FLAGS]`. Resume: `["-p", "--resume", <id>,
  "--output-format", "json", ...model, ...POLICY_FLAGS]`. A future flag
  appended after `--allowedTools` would be silently eaten as a tool name;
  write that in the header comment.
- **No env name is added.** `harnessEnv`'s ten-name allowlist
  (`packages/shim/src/harness/env.ts`) is unchanged and untouched. This was
  measured, not assumed (Intent), for the default login location only. If
  the builder finds any part of this policy needs an eleventh name, **stop
  and report it as a finding** — it is an amendment to W-049's ruling and
  belongs to the architect and the Patron, never to a silent edit.
- **Checked by review, not by tests** (W-044/W-049 precedent): the codex
  policy constant is module-local, not exported from `harness/index.ts` or
  the shim index, and not configurable by a caller. A violation is a review
  finding.
- **Carried from W-049:** every codex spawn bisellium makes goes through
  `codexProfile`. After this opus, a talk-shaped codex dispatch has a CLI
  path (`bisellium talk --harness codex`), and the orchestrator's own
  `codex exec` shell calls are the interim transport D-020 retires for that
  shape — and only that shape.

## Behaviours to test

All six live in a new `packages/cli/src/provider-portability.test.ts`. It
imports only exports that exist at HEAD — `claudeCodeProfile` and
`codexProfile` from `@bisellium/shim`, `runTalk` from `./talk.js` — so every
red is assertion-level, never a module-load error. Its
`BISELLIUM_ONLY_BEHAVIOUR` block harness is copied from
`lifecycle.test.ts`; block N is behaviour N.

**Stubs.** Node stubs named `claude` and `codex`, written into a temp bin
dir per scenario and selected with `PATH` (W-049's pattern: a scenario must
not travel in an env var, because the env is scrubbed). Each stub exits 0 on
`--version`/`-V`, and on every other call appends one JSON line —
`{bin, args, stdin, cwd}` — to a log path that is **a literal baked into the
stub's source text**, then prints a canned envelope. A stub never executes
what it is handed. Two stub fidelity rules, both mirroring measured vendor
behaviour: the codex stub exits 2 with `unexpected argument` if a `resume`
argv contains `-s`, `--sandbox`, `-C` or `--cd`; the claude stub exits 1
with `unrecognized_model` if `--model` names a model that is not
`claude-*`. Canned envelopes: claude prints
`{"session_id":"sess-w046","result":"ack","is_error":false,"model":"claude-opus-5-20260101"}`;
codex prints JSONL with `thread.started` (`thread_id: "thr-w046"`), one
`item.completed`/`agent_message`, and a `turn.completed` carrying usage —
deliberately with **no** `model` key anywhere, which is what the real CLI
does.

Behaviours 1, 2, 4 and 5 drive `runTalk` against a temp copy of
`examples/sample-studio` with `--model-only` (the deterministic query path
must not swallow the turn). `eng-lead` there is `claude-opus-5`.

1. **The claude session spawns carry the decreed model, in the right slot.**
   `runTalk --sella eng-lead --model-only` runs twice against the temp
   fixture (a start, then a resume of `sess-w046`). Both logged argvs
   deep-equal the literal expected arrays above with
   `["--model","claude-opus-5"]` in the model slot, and in both the
   `--allowedTools` group is terminal and its ten values are exactly W-044's
   list. A third assertion pins the ordering rule directly: the index of
   `--model` is lower than the index of `--allowedTools`.
   - At HEAD this fails: the argv carries no `--model` at all, so the
     deep-equal and the index assertions both fail on their own line.
2. **The codex session spawns carry the decreed model and the whole codex
   command policy.** `runTalk --sella eng-lead --harness codex --model-only`
   runs twice. The start argv deep-equals
   `["exec", …POLICY, "-m", "claude-opus-5", "-"]` and the resume argv
   deep-equals `["exec","resume","thr-w046", …POLICY, "-m","claude-opus-5",
   "-"]`, with POLICY written out literally in the test — all eight
   `--disable` pairs included (the test is the spec, not a mirror of the
   module). Four further assertions, each its own line, hold on **both**
   argvs: no token is `-C` or `--cd`; no token starts with
   `--dangerously-bypass`; the logged `cwd` is the studio root; the logged
   `stdin` is non-empty and ends with the message.
   - At HEAD this fails: the argv is
     `["exec","--json","--skip-git-repo-check","-"]`, so every policy token
     and the model are missing.
3. **A turn that exits 0 with no reply is a failure, and nothing is
   persisted.** Two scenarios, one per vendor, each on its own fresh fixture
   copy and its own stub dir: a claude stub printing a valid envelope whose
   `result` is `""`, and a codex stub printing `thread.started` plus
   `turn.completed` and **no** `agent_message`. Both exit 0. For each, four
   assertions: `runTalk` returns a non-zero exit code;
   `sessions/<sella>.json` does not exist; `timeline/<sella>.jsonl` does not
   exist; and **`receipts/<sella>/` contains no receipt for the turn**
   (Sol finding 3 — `performTalk` writes three artefacts, so proving two
   absent proves nothing). The message printed on stderr names the sella,
   the harness and the requested model.
   - At HEAD this fails: `runTalk` returns 0, the session file, both
     timeline lines **and** the receipt are written, and an empty reply is
     printed as success.
4. **The decreed model is what the timeline records, and a vendor-echoed
   model wins.** On the codex stub (no model in any event), the `out`
   timeline entry's `model` is `"claude-opus-5"` — the requested value. On
   the claude stub (which echoes `claude-opus-5-20260101`), the `out`
   entry's `model` is `"claude-opus-5-20260101"` — the vendor's answer, not
   the request, because that is the truth about what ran. The `in` entry
   carries no model in either case.
   - At HEAD this fails on the codex half: `model` is absent from the entry
     (no model was ever requested and codex echoes none). The claude half
     passes at HEAD, and is asserted so the fix cannot be "always overwrite
     with the request".
5. **One fixture sella, a talk turn on each harness, in one run.** Against
   a single temp fixture copy: `runTalk --sella eng-lead --model-only`
   (claude stub on `PATH`), then `runTalk --sella eng-lead --harness codex
   --model-only` (codex stub on `PATH`). Both return 0. Then, asserted as
   separate lines:

## Out of scope

- **One opus end-to-end on both providers.** The originating requirement

  not answer — how a codex session gets an enumerated command allowlist
