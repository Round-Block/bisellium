## Intent

At base 685a2eea the Board already groups cards by lifecycle phases served from `/api/officina`, shows a raw count in each column, applies the manifest's `wip_limit` to the In progress model, fills a 3px rule to that ratio, and classifies a card as blocked when a recorded check failed. It has no elapsed/completion timing, entry/exit explanation or task filter, and a count cannot distinguish visible cards from filtered cards. Source evidence is `/home/edckt/agents/bisellium/.worktrees/W-413-spec/apps/web/src/lib/board.ts`, `/home/edckt/agents/bisellium/.worktrees/W-413-spec/apps/web/src/screens/BoardView.tsx` and `/home/edckt/agents/bisellium/.worktrees/W-413-spec/apps/web/src/components/w025.css`.

The Patron's 2026-11-03 revision-14 screen ruling replaces the earlier visible-limit design. Every lifecycle-column header has exactly two plain count rows: row one is the column-local total (`1 task`, `N tasks`, or `Showing N of T tasks` while filtered); row two is `None blocked`, `1 blocked` or `N blocked`. No Board-level key, combined Building-plus-Verifying count, limit, over/under-limit wording or limit rule is visible anywhere on the Board. The repository's existing check enforcement and legacy cap model remain unchanged but have no W-413 surface or promise. The stage explanation remains below the name/count header. Every per-column median remains removed.

The Patron's 2026-11-03 revision-17 ruling makes a positive header blocked count red, matching the card's blocking-red family. Master has no text-safe blocking token, so the shared token file defines `--severity-blocking-text` as a named 75% `--severity-blocking` plus 25% theme `--ink` mix; Board CSS consumes only that name and introduces no one-off colour. `None blocked` stays quiet `--ink-3`; the total row also stays `--ink-3`, so only a real blocked count is red. The derived token measures 5.73:1 on dark `--surface` and 4.74:1 on dark `--wash`; against the approved light mapping it measures 6.94:1 and 6.44:1 respectively. Zero-state `--ink-3` measures 5.81:1/4.81:1 dark and 4.98:1/4.62:1 light. All text treatments exceed the 4.5:1 floor. Revision 15's card marker remains the exact `--severity-blocking` red and does not clash with the lighter text-safe dark-theme shade. Source and calculation evidence is `/home/edckt/.bisellium-evidence/W-413-spec/palette-census-r28.out`.

Card timing uses only two existing record instants. For open work, elapsed is `now - start`, where lifecycle `ready` records `start`; a missing, malformed or future `start` shows no elapsed value. For completed work, actual completion is the exact valid `start → end` span, where lifecycle `done` records `end`; missing, malformed or end-before-start values show nothing. This is the record-level cycle span available to the Board and corresponds to the dossier history row's cycle where those boundaries represent its first-spec-to-land interval; the Board does not guess a Git-derived boundary. Source evidence is `/home/edckt/agents/bisellium/.worktrees/W-413-spec/packages/commands/src/lifecycle.ts`, `/home/edckt/agents/bisellium/.worktrees/W-413-spec/packages/cli/src/checkpoint.ts`, `/home/edckt/agents/bisellium/.worktrees/W-413-spec/apps/web/src/api.ts` and `/home/edckt/agents/bisellium/.worktrees/W-413-spec/apps/server/src/store.ts`.

The remaining-time estimate is the median of valid actual `start → end` spans from opera whose served state maps to Done, with a minimum of three completed samples. For an open card with a valid `start`, remaining time is `max(0, median actual cycle - elapsed)`. It reads, for example, `Started 9 hours ago. About 1 hour left (estimate).`; fewer than three valid spans, or an unusable open start, says `No time estimate yet`. A done card says, for example, `Took 2 days`. Durations use full words; the model samples `now` on reconciliation and does not pretend to be a ticking clock. No event, handoff, author or inferred timestamp enters the calculation.

Rule copy explains the present condition and the condition for moving on: `Waiting to start. Moves on when approved and ready to build.`, `Being built. Moves on when the build is complete.`, `Being checked. Moves on when checks pass.`, `Waiting for review. Finished when approved.`, `Complete. No next step.`, and `Stopped. Resumes when the blocking condition is resolved.` A custom phase uses `In this stage. Moves on when its recorded condition is met.` Exit copy is fixed per standard phase id and does not read the served transition graph. The filter uses `All tasks` / `Blocked tasks`, is named `Choose which tasks to show`, defaults to all, filters lifecycle cards only, and never changes each column's total, blocked count, completion estimator or Waiting-on-you collection.

Card check progress stays in plain words. A failed recorded check says `A check failed: Tests`; otherwise zero, partial, all and no declared checks say `No checks complete yet — Tests next`, `2 of 3 checks complete — Approval next`, `All checks are complete`, and `No checks are required`. Passed and waived both count as complete. The names follow declared check order and labels; no record field is added. Planned retains W-493's omission. The card and column renderer contains no `x/y` progress form.
