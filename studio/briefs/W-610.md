## Intent

W-604 and W-608 each ran a 21-26 min `ci --opus`, then build review round 1 failed on code reads (presign-gate.ts:54, :495), and each fix round paid a second full ci. The reviewer does not use ci's output: build-review.md:10 only says the gates passed. The opus moves the one full suite after a passed review and orders the review on light gates:

1. **Light gates (behaviour 1).** After the builder's handoff (or a prototype replay, or a clean fix check), `next` names the build step `act: light-gates`, actor producer: a ladder-runner runs `bisellium next <id> --perform --expect build`. The perform runs, at the worktree's HEAD, master's kept list `bisellium.yml#light_gates` (typecheck, `check -- {studio} --repo .`) and then the brief's own test files (Files owned paths ending `.test.ts|.mts|.mjs`), one at a time, writes one log `ci/<id>-light-<8 hex>.log` (`certifies: tree:<hash>`, `command: sha256:<hex>` binding the exact command sequence, `exit code: <n>`, as a gate log) and commits it alone. Never the builder's own runs (evidence is produced, never backfilled). An officina that declares no `light_gates` (the sample studio, every existing fixture) keeps master's W-312 order and texts: the full gates before review, so no existing row flips; gates that cannot be read skip the rung as on master.
2. **Review on the light gates (behaviour 2).** Review is ordered when the light-gate log passed at the tip's source tree, committed, run for the current command sequence (recomputed), with no full gate log; the `review` verb admits the same log (the full gates at the tree still admit both, so a world with them is unchanged). This replaces the W-312 condition at next.ts:1349.
3. **One ci after the pass (behaviour 3).** A review passed and current at this tree with the full gates not passed at it: `next` names build, actor producer, the ladder-runner's `ci --opus` in a run session, with `reviewed: round <n> at <tree>`. The full suite is ordered at most twice at one reviewed tree (one rerun for an environment failure); after two committed runs at the tree with the gates not passed, `next` dispatches a builder (phase 2, the failed logs as input, `ci-runs: <n> at <tree>`), never a third ci there (w610-proof-meet-1112 item 4).
4. **The binding (behaviour 4).** `pr` is named only when the passed round's tree, the full gates' certified tree and the tip's source tree are one tree, compared through `source_excludes` (the ci and verdict bookkeeping commits keep it); its order prints `trees: reviewed <t> = gates <t> = tip <t>`. `--perform --expect pr` refuses before it; `--chain` stops after review at the ci order (`build` is not a chain rung). The whole loop is proven end to end in an officina that declares `light_gates` (w610-proof-meet-1112 item 1): handoff, light gates, round 1 failed, the fix, light gates again, round 2 passed, one ci, pr, with no ci order before the pass.
5. **A source change voids the pass (behaviour 5).** After a pass, a commit that changes the source tree makes the round not current: `next` orders the light gates again, never ci or pr on the old pass, then the next review round with `delta: since round <n> passed at <tree>`, then ci.
6. **The kept texts (behaviour 6).** `studio/prompts/build-review.md` line 10 names the light-gate log and says the full suite runs after a passed review; lex `studio/leges/production.md` §9 steps 3-4 state the new order; `studio/bisellium.yml` declares a well-formed `light_gates`, so the real officina takes the new order (absent, it would silently keep the old one; w610-proof-meet-1112 item 4). All three are Patron-reviewed (code-owned).

## Interfaces

1. **`bisellium.yml#light_gates`**: a non-empty list of shell command strings; `{studio}` is replaced by the officina's repo-relative path. Absent: master's W-312 order. Present but malformed: the light-gates order holds (`bisellium.yml#light_gates must be a non-empty list of commands`).
2. **Light-gate log** `ci/<id>-light-<8 hex>.log`: line 1 `certifies: tree:<40 hex>`, line 2 `command: sha256:<64 hex>` (`commandLine`: the SHA-256 of `JSON.stringify` of the command list in run order, never redacted; JSON encoding preserves command-list boundaries and order, and its SHA-256 digest binds that encoding with collision resistance), line 3 `exit code: <n>`, then each command's `$ <cmd>`, `exit:`, stdout and stderr.
3. **next lines**: build `act: light-gates` with `light-gates: <commands>`; build with `reviewed: round <n> at <tree>` (the ci order); pr with `trees: reviewed <t> = gates <t> = tip <t>`; review with `delta: since round <n> passed at <tree>`.
4. **`next <id> --perform --expect build`** performs only `act: light-gates`; it prints `light-gates: exit <n>`, `log:`, `branch:`; a non-zero exit is held and the log is committed (the builder's input).
5. **`@bisellium/shim`** `commandDigest(commands): string`, `commandLine(commands): string`, `bindsCommands(line, commands): boolean`.
