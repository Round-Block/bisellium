## Intent

W-604 and W-608 each ran a 21-26 min `ci --opus`, then build review round 1 failed on code reads, and each fix round paid a second full ci. The reviewer does not use ci's output: build-review.md:10 only says the gates passed. The opus moves the one full suite after a passed review and orders the review on light gates. It also carries two fixes the ladder needs before it can run: the daily retro's gate reader (D-198: without it every new opus is held at its spec start through 2026-11-25) and the two S1 that failed build review r2 (D-196).

1. **Light gates (behaviour 1).** After the builder's handoff (or a prototype replay, or a clean fix check), `next` names the build step `act: light-gates`, actor producer: a ladder-runner runs `bisellium next <id> --perform --expect build`. The perform runs, at the worktree's HEAD, master's kept list `bisellium.yml#light_gates` (typecheck, `check -- "$BISELLIUM_STUDIO" --repo .`) and then the brief's own test files (Files owned paths ending `.test.ts|.mts|.mjs`), one at a time, writes one log `ci/<id>-light-<8 hex>.log` (`certifies: tree:<hash>`, `command: sha256:<hex>` binding the exact command sequence, `exit code: <n>`) and commits it alone. Never the builder's own runs. An officina that declares no `light_gates` keeps master's W-312 order and texts.
2. **Review on the light gates (behaviour 2).** Review is ordered when the light-gate log passed at the tip's source tree, committed, run for the current command sequence (recomputed), with no full gate log; the `review` verb admits the same log (the full gates at the tree still admit both). This replaces the W-312 condition at next.ts:1366 (master b145ec4c).
3. **One ci after the pass (behaviour 3).** A review passed and current at this tree with the full gates not passed at it: `next` names build, actor producer, the ladder-runner's `ci --opus` in a run session, with `reviewed: round <n> at <tree>`. At most two runs at one reviewed tree; after two committed runs with the gates not passed, `next` dispatches a builder (phase 2, the failed logs as `ci/<log>` inputs, `ci-runs: <n> at <tree>`), never a third ci there.
4. **The binding (behaviour 4).** `pr` is named only when the passed round's tree, the full gates' certified tree and the tip's source tree are one tree, compared through `source_excludes`; its order prints `trees: reviewed <t> = gates <t> = tip <t>`. `--perform --expect pr` refuses before it; `--chain` stops after review at the ci order. The whole loop is proven end to end in an officina that declares `light_gates`.
5. **A source change voids the pass (behaviour 5).** After a pass, a commit that changes the source tree makes the round not current: `next` orders the light gates again, never ci or pr on the old pass, then the next review round with `delta: since round <n> passed at <tree>`, then ci.
6. **The kept texts (behaviour 6).** `studio/prompts/build-review.md` line 10 names the light-gate log and says the full suite runs after a passed review; lex `studio/leges/production.md` §9 steps 3-4 state the new order; `studio/bisellium.yml` declares a well-formed `light_gates` (the variable form). All three are Patron-reviewed (code-owned).
7. **The retro reads every gate status form (behaviour 7).** `packages/pipeline` writes a gate log's line 3 in four forms: `exit code: <n>`, `exit code: (timed out after <m>m)`, `exit code: (error <code>)` and `exit code: (signal <name>)` (index.ts:230-234). The daily retro's `gateFailure` (retro.ts:1309-1314) accepts only the first and refuses the whole retro on the others; the real `studio/ci/W-563-tests-90514cbc.log` carries the timeout form. The reader is changed to accept all four, any form but `exit code: 0` a failed gate, classed as today. The writer's bytes do not change: its status line is moved into one exported pure helper, `gateStatusLine`, beside a parser, `readGateExit`, that `gateFailure` uses, so one row runs every writer form through the reader and they cannot drift again. The rung is separable: its files (retro.ts, the pipeline helper, `w610-retro.test.ts`) touch nothing else in W-610 and can be split by `--parent W-610` if W-610 slips (D-198). Revision 5 (spec review r8 #1): a multiline command no longer reaches the head raw. Line 2 is written by `gateCommandLine` on one line (a command with no C0 control character except tab byte for byte as before; any other as `command: json:` and its JSON string), and `gateFailure` reads the head's one status field through `readGateStatus` (exactly one `exit code:` line among the lines before the first empty line, and it is line 3), so a failing `echo start\nexit code: 0` is a failed gate and a missing, duplicate or misplaced field refuses the retro naming the log.
8. **The officina path is data, never shell text (behaviour 8).** Each `light_gates` command runs under `sh -c` with `BISELLIUM_STUDIO` set to the officina's repo-relative path (`.` for a root officina); a command names it as `"$BISELLIUM_STUDIO"`. Nothing is substituted into the command string, so the shell never parses the path in any quoting context (a parameter's value is not re-scanned for substitutions or quotes).
