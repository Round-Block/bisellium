## Intent

Decree family: merge-queue-light-path-refusal

W-205 moved the heavy pull-request steps into the merge group. Its soundness rests on prose: ADOPTION and `ci.yml` say it holds only while the ruleset requires the merge queue. If the queue were removed, GitHub would merge on the light pull-request checks. W-210 makes that dependency a step: in each pull-request run, `gates` runs `next`'s own `readMergeQueue` once, right after `npm ci`, and that run fails unless the read returns `merge-queue`. The check is point in time. It narrows the light-only path to the window between a run's read and a merge. It does not close that window for a planned removal: ADOPTION's removal order makes runs started after the workflow change heavy again, but a pull request whose last run passed before it keeps its light green (a rerun replays its old workflow), so ADOPTION says to push to or close each such pull request before the ruleset changes, and nothing checks that this was done.

Promise light-path-refusal: in each `pull_request` run, `queue-required` exits 0 only when its one read of master's active rules, at that moment, returns W-168's exact queue setup, and a non-zero exit fails that run's `gates` — limit: point in time per guard run. A ruleset change or a GitHub outage after the read is not seen until `gates` reruns, whether it comes while that run's typecheck and lint still run or after the run is green. A pull request whose run already passed stays green, so if the queue is removed in that window, it can merge on the light checks. Administrator bypasses and edits to the step are outside the threat model (D-045).

Promise one-predicate: CI and `next` share one unchanged definition of the queue setup — limit: after any change to the queue parameters or the four required contexts, each guard run that reads the changed rules (a new pull-request run or a rerun) fails until `readMergeQueue` follows; a run already green stays green (Defaults 1).

Promise event-parity: the `merge_group` and `push` runs select the same steps as before — limit: a GitHub API or token failure during a guard run's read fails that run even when the queue is set up; one after the read is not seen (Defaults 2).

No check is removed (production lex §11, D-054 §1). The threat model is mistakes (D-045).

## Interfaces

```yaml
      # W-210: a pull request runs the light steps only because the merge queue
      # runs the heavy ones; fail this run unless its one read of master's rules
      # finds that queue (point in time: a later change is seen on a rerun).
      - id: queue-required
        if: github.event_name == 'pull_request'
        env:
          GH_TOKEN: ${{ github.token }}
          REPOSITORY: ${{ github.repository }}
        run: >-
          node --import tsx --input-type=module -e 'import { readMergeQueue } from "./packages/cli/src/integrate.ts";
          const mode = readMergeQueue(".", process.env.REPOSITORY ?? ""); console.log(`mode: ${mode}`);
          process.exitCode = mode === "merge-queue" ? 0 : 1;'
```

`readMergeQueue` (W-168, unchanged) makes one `gh api repos/<REPOSITORY>/rules/branches/master?per_page=100` call and returns `merge-queue` only for one exact queue rule and the four required GitHub Actions contexts; every error or other reply is `direct`. The step needs `npm ci` first, for `tsx` and the workspace links. Its text must not contain `verify` (`ci-workflow.test.mjs` and `W-168-b1` assert that).

## Defaults for the Patron to veto

1. **CI reuses `readMergeQueue`'s exact W-168 setup, not "any merge-queue rule".** After a queue parameter or a required context changes in the ruleset, each pull-request run or rerun that reads the new rules fails until `readMergeQueue` is updated; runs already green stay green. The pull request that updates it runs its own copy, so it can still land.
2. **An unreadable reply fails the run that reads it.** A GitHub API outage during a guard run's read fails that run's `gates`; every rerun fails while the outage lasts, and a rerun after the API answers again recovers. An outage that starts after a green run is not seen, and it does not change the mode: the queue is still required.
3. **The check is one inline command in `ci.yml`.** No new script, package command or CLI verb; `W-210-b1` runs the exact parsed command.
4. **A `.github/` change needs the Patron's approval (W-197).** The Patron approves this design before `branch` and the `ci.yml` diff as code owner before the PR is enqueued.
