## Intent

A red is evidence that a behaviour's own assertion fails. W-503's b1 red (spec review round 13) failed because `bisellium serve` crashed on a module the scratch tree did not have; the served wrapper's message opened with the declared pin `served Home behavior 1 holds:`, so the pin "held" and the red certified the tree, not the Home screen. Two places admit a red today, and neither sees it:

- `bisellium red` (`runRed`, `packages/commands/src/lifecycle.ts`) refuses an exit 0 and, since W-473, an output that does not fail at the declared pin (`redFailsAt`). For a brief with "Red order: one at a time" it also runs certify's classifier (`cellRefusal` -> `classifyReplay`), whose node-TAP route exempts the failing row's own block (`outsideOwnFailure`), so `ERR_MODULE_NOT_FOUND` or the harness's exit line inside the row's assertion message passes.
- The spec signature (`redReplayProblems`, `packages/commands/src/verdict.ts`, run for the signer of a prototyped brief) checks only that each cited red log records the written command. It reads nothing in the log's body: not the environment, not the declared pin. W-503's b1 logs were cited this way.

After this opus, one pure judge (`wrongTreeRed`, new `packages/commands/src/red-tree.ts`) names four patterns, and both places apply them:

1. An output carrying `ERR_MODULE_NOT_FOUND` anywhere, the failing row's own message included, is refused.
2. An output carrying the served harness's `serve exited (<code>) before printing port/token` line (`startServed`, `board.spec.ts`) is refused. The phrase alone is not: a row may name it.
3. An output that names a served spec and does not show every server start reading its port and token is refused. A served spec is any file under `tests-serve/`, at any depth, that Playwright's default testMatch (`**/*.@(spec|test).?(c|m)[jt]s?(x)`) discovers, named at `<path>:<line>:<col>` as Playwright's list reporter (`tests-serve/reconnect/w900.test.ts:3:1`) and a stack frame (its absolute path) print it. Each server start is an attempt: `startServed` (every call) and `board.spec.ts`'s `spawnAndWaitReady` (the first start and every `restart()`) name it (`servedAttempt`, `<pid>.<count>`), print `bisellium serve: attempt <id> starting` (`servedStart`) before they spawn, scrape the port and token into the attempt's own state, and print `bisellium serve: attempt <id> listening on port <n>, write-auth token read` (`servedLine`; the token itself is never printed) once both were read. The output is refused when it carries no start line, or when a started attempt has no port and token line of its own; one attempt's line never covers another's. The probe shows a served spec's `console.log` reaches the run's stdout (`probe-stdout.out:21`).
   Pattern 3 reads the literal `tests-serve/` and the default suffixes; row b5 fails when `apps/web/playwright.serve.config.ts`'s `testDir` is not `./tests-serve`, when the config sets a `testMatch`, or when a served red at a direct or nested location under that directory, with any default suffix, is admitted. Row b6 pins the harness's lines at their source: each of `harness.ts` and `board.spec.ts` names one attempt, prints `servedStart(attempt)` before it spawns and `servedLine(<port>!, attempt)` once, all three imported from `red-tree.ts`, scrapes into a port and a token declared in the attempt itself, and words one startup-failure message that, filled in, is the exit line pattern 2 refuses, so an edit to the harness (W-301's included) that drifts any of them fails the row.
4. At the spec signature, a behaviour that declares one failing assertion must cite at least one red log, recording its written command, that fails at it (`redFailsAt`). `red` already refuses this since W-473 (pinned by `W-473-b1`); row b4 checks that too.

The read enumeration (`r3/readers.out`) runs master's and the prototype's `redReplayProblems` over every brief on master, the W-503 and W-610 branch briefs and the five uncommitted briefs in the main checkout (W-280, W-301, W-488, W-644, W-648). It adds problems for two briefs only. W-503's b1 logs: at revision 2 (revision 10's logs) they carried the harness's exit line, the round-13 finding exactly; revision 11 re-recorded them clean (spec review r15 PASS), and those logs (`revision-11/b1-red-ordinary.log`, `b1-red-silent.log`) now meet pattern 3 instead: they name `tests-serve/w503.spec.ts:14:1` and no served line, because no harness printed one before this opus. Any served red recorded before W-645 lands is in that case: it is never re-judged at `red`, and only a fresh spec signature of its brief refuses it, so a served opus signed again after W-645 lands records its served reds again on a tree with the print (a stated limit, below). And W-227 (done) declares `W-227-b4` "the refusal names the cd" while its cited `red-b4.log` fails at `main thread refused: cd …`, a pin that was never the red's. No other in-flight brief changes.

Threat model: mistakes, not adversaries (D-045). A red's output is the repository's own test output; a test that prints the served line without serving is out of reach of any text check.

## Interfaces

**`servedAttempt(): string`** (`red-tree.ts`, exported): `<pid>.<count>`, the count this process's attempts so far. **`servedStart(attempt: string): string`**: `bisellium serve: attempt <attempt> starting`. **`servedLine(port: number, attempt: string): string`**: `bisellium serve: attempt <attempt> listening on port <port>, write-auth token read`.

**`wrongTreeRed(output: string): string | undefined`** (`red-tree.ts`, exported): in this order, `names a module that did not load (Node's module-not-found error): the red fails in the tree, not at the behaviour` (the output holds `ERR_MODULE_NOT_FOUND`); `carries the served harness's exit line (its server exited before printing a port and token): the served row's server never started` (the output holds `serve exited (<code>) before printing port/token`); for an output naming a served spec, `names a served spec (<location>) and no served attempt's start and port and token lines ("bisellium serve: attempt <id> starting", "bisellium serve: attempt <id> listening on port <n>, write-auth token read"): the served row never read its server's port and token` (no start line), then `names a served spec (<location>), and served attempt <id> printed its start and no port and token line: that attempt's server never read its port and token` (the first started attempt with no line of its own); else undefined.

**`runRed`**: the new refusal is `red: behaviour <k>'s output <why> — nothing recorded`, exit 1.

**`redReplayProblems`**: the new problems are ``behaviour <k>'s genuine red cites `<path>`, and <file> <why>`` and ``behaviour <k>'s genuine red declares pinned by `<row>` "<assertion>", and no cited red output recording its command fails at it: cite the red that does, or record it again``; `verdict` prints each with its existing `red command: ` prefix.
