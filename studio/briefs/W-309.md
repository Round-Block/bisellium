## Intent

A failed build review goes back to a builder, who fixes, runs the full suite (`ci --opus`, about 18 minutes) and hands off; then, before the re-review, the orchestrator runs a hand script, `~/.bisellium-evidence/codex-passes/fix-census.sh <id> <round>`: Codex `gpt-5.6-sol` in a fresh session lists every path to each finding's input and whether the fix closes it (D-072 C). D-086 D (Patron, 2026-10-19) moved that check before the suite, because W-322's check ran after its suite, found a missing test, and cost a second 18-minute run; until this opus the orchestrator applies that order by hand, and nothing in `next` knows it.

After this part, `next` orders it. In a fix round (the review gate recorded failed, at a source tree other than the current one), `next` names the `review` rung with the perform `bisellium next <id> --perform --expect review` until a fix check of that round is recorded at the current tree. The perform runs Codex as `fix-census.sh` did and writes the result beside the census. A result listing an open path sends the round back to the builder (build, phase fix), with the census as an input; a result listing none lets the ladder go on: the suite when the branch's automated gates are not passed at that tree, then the re-review. The fix order itself now tells the builder to stop after its fix commits. So one call replaces the hand script and the orchestrator's turn, and the suite runs only on a fix the check found closed.

**Where it lives.** One module, `packages/cli/src/next.ts`, as W-274's review perform: the derivation gains the fix-round branch before the build gates (W-312) and the review order, and the review rung gains a second perform, chosen by `act: "fix-check"` as the done rung chooses between its two. The result is a local file, `<repo>/.bisellium/reviews/<id>/fix-<n>/check.json`, beside W-274's review packets: the check is advisory input, not a verdict (D-066 C keeps Codex's review as the single gate), so it records nothing in the officina, takes no step ticket and makes no commit.

**Who runs it (W-310).** The perform is the `review` rung's, run as `next <id> --perform --expect review` (or by `--chain`). W-310's guard refuses exactly those forms from the main thread (`--expect review`, no `--expect`, `--chain`), so once W-310 lands a dispatched ladder-runner runs the fix check, as it runs the review round, with no change to `guard.ts`. Until then the orchestrator runs it as it runs the review perform today. Files owned here and W-310's do not overlap, and this part touches neither `docs/ADOPTION.md` nor a lex, so the two opera do not serialise.

**The cut (D-061 §4).** W-309's title holds six things across `next.ts`, `verdict.ts`, the done path, four scripts, the lex and `docs/ADOPTION.md`: well over one cycle's three points. This part is the one D-086's kill condition names for W-309 ("orders the fix check before a fix round's ci --opus") and the one that saves the most minutes per failed round. The rest is under Out of scope; the hand-script deletion stays last because it removes its own review path.

Promise fix-order: in a fix round, a review gate recorded failed whose round's `# tree:` is not the current source tree of `opus/<id>`, `next` names the review rung with actor producer, the command `bisellium next <id> --perform --expect review` and the why "review round <n> failed at an older tree and no fix check of its findings is recorded at this tree (D-086 D)", unless `readFixCheck` reads that round's `check.json` at the current tree; with one listing open entries it names build, phase fix, with the failing log and the census as inputs and the entries on an `open:` line; with one listing none the derivation goes on as before, except that gates not passed at that tree are the producer's suite order, not a builder's — limit: a gate failed at the current tree against an older brief is not a fix round and orders no fix check; `check.json` is a local file, neither committed nor certified, so a hand-written one passes the order (mistakes, not adversaries, D-045); the check is advisory and the review round stays the single gate (D-066 C).

Promise fix-stop: the build order of a fix round (phase fix) ends "the fix round stops after its fix commits, with no handoff and no ci --opus: next orders the fix check first (D-086 D)" — limit: it is order text; a builder that runs the suite anyway is not refused, and only the ordering of the fix check before the suite and the re-review is enforced.

Promise fix-perform: at that rung, `next <id> --perform --expect review` runs Codex through the harness adapter (`codexProfile.start`, model `gpt-5.6-sol`, reasoning effort high, read-only, the main checkout as its working directory, 25 minutes) in a fresh session on the census prompt naming the failing log, the brief, the fix diff and the worktree, and writes `check.json` (round, tree, session, open entries) only when Codex closes normally with exit 0, reports a valid session that no `# session:` header of the failed round's log names, and replies with exactly one `## Open` section holding at least one nonblank line, the lone line `None` or `None.` meaning no open entry and any other line an open entry — limit: the truth of Codex's census is not judged, nor its other sections; `fix-census.sh`'s optional host facts are not carried; a session another round's log names is not refused.

Promise records-nothing: the fix-check perform writes nothing under either studio, takes no step ticket and makes no commit; a refusal or a thrown step error is `next: <id> review held` with exit 1 and no `check.json`, and the step marker is released — limit: a held attempt's `fix.diff`, `prompt.md` and `census.md` stay in the packet until the next attempt removes them; the packet's containment is W-274's `packetBase`, reused unchanged (D-076 E).

Threat model: mistakes, not adversaries (D-045).
