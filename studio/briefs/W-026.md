# W-026 — parallel workstreams: per-opus branching and merge coordination

## Intent

Enable concurrent cascades on separate opera without collision. Today
everything commits to master sequentially; two cascades stepping on
each other's files cannot run in parallel.

The git model: `opus/<id>` branches forked from master, builders work in
worktrees off the opus branch, `bisellium merge` lands the opus branch on
the trunk once it's `done`, using whichever `integration.strategy` the
officina's manifest configures (D-015): fast-forward-only by default, or
`rebase` (replay the branch onto the trunk first); `merge_commit` is
declared but not built (see the brief's Out of scope). A rebase is refused
if it would land a `tree:` certificate that no longer matches what's about
to ship.

## Files owned

- `packages/cli/src/branch.ts` — branch helpers: create, merge, cleanup
- `packages/cli/src/branch.test.ts` — pure function + integration tests
- `packages/cli/src/check.ts`, `packages/cli/src/check.test.ts` — D-015
  authorises this: `integration:` is a manifest key `check` must validate,
  and round-3 review's B1 finding (`probatio.certifies.stale` never fires
  for an opus `merge` will accept) is fixed on the `branch.ts` side, but the
  manifest-shape validation for `integration:` belongs with `check`'s other
  manifest-shape rules.
- `adapters/native/src/index.ts` — the `Manifest` interface's `integration?`
  field (D-015's manifest contract).
- `studio/bisellium.yml`, `examples/sample-studio/bisellium.yml` — the two
  manifests exercising `integration:` (the real officina's flow and the
  fixture).
- `docs/ADOPTION.md` — the `integration:` key and its manifest block
  (round-3 review's A7 finding: the feature was undocumented).

## Interfaces

- `bisellium branch <opus-id> --studio <dir>` — create `opus/<id>` from HEAD
- `bisellium merge <opus-id> --studio <dir> --repo <dir>` — merge opus
  branch to master after gates pass, push, delete branch
- `bisellium run` gains `--opus <id>` — forks worktree from `opus/<id>`
  instead of HEAD

## Behaviours to test

Numbers below match `packages/cli/src/branch.test.ts`'s own numbering
comment; 0, 8-9 are extra regression coverage outside the original 1-7,
never renumbered once evidence exists against them (P-005).

1. `createOpusBranch(repo, opusId)` creates `opus/<id>` from HEAD
2. `createOpusBranch` refuses if branch already exists
3. `mergeOpusBranch(repo, opusId)` fast-forwards master when clean,
   regardless of what's checked out when merge runs
4. `mergeOpusBranch` refuses when opus state is not `done`
5. `mergeOpusBranch` refuses when branch has conflicts with master
6. `mergeOpusBranch` deletes the branch after merge, and reports a failed
   deletion as a failure, never a silent success
7. `bisellium run --opus <id>` forks worktree from opus branch, not HEAD
   (tested in `packages/commands/src/run.test.ts`, since that's where
   `run.ts` lives)
8. extra: a missing branch is refused
9. extra: a clean-but-diverged branch is refused under the fast-forward-only
   default rather than silently rebased
10. `bisellium check` validates the `integration:` manifest key's shape (an
    unrecognised `strategy` etc.) — tested in `check.test.ts`, not
    `branch.test.ts`
11. D-015: `integration.strategy: rebase` actually rebases the opus branch
    onto the trunk, then fast-forwards
12. a genuine rebase conflict under `strategy: rebase` is refused, distinctly
    from behaviour 9's fast-forward-only divergence
13. `integration.push`/`pull_after_push` reach a real, local-only origin
14. `integration.pr.required` stops `merge` short of landing locally,
    leaving the branch for a PR
15. `strategy: merge_commit` is declared but refused, not silently
    downgraded
16. the trunk name is never hardcoded to "master" (a repo whose trunk is
    `main` merges into `main`, reported as `main`)
17. D-015 B1 (round-3/4 review): the rebase note names the real consequence,
    not a check rule (`probatio.certifies.stale`) that can't fire for a
    `done` opus
18. a recorded `tree:` certificate that does NOT match the rebased tree
    refuses the merge
19. a recorded `tree:` certificate that DOES match the rebased tree does not
    refuse the merge
20. every post-rebase failure path still carries the rebase note, not only
    the success path
21. a rebase-then-push uses `--force-with-lease` against a branch already
    open on origin (a PR already open against the pre-rebase history)
22. round-4 review (A4.4, mutation-record): the SOURCE-tree exclude set is
    pinned with the studio INSIDE the repo — round 4's own mutation of
    `sourceExcludeDirs` found 0 FAIL with the studio outside the repo
23. round-4 review (B1.4, pre-implementation): a stale certificate refuses
    on every retry, not only the run that performed the rebase
24. round-4 review (B1, pre-implementation): a fast-forward-ready branch
    that never needed a rebase is refused too when its own certificate
    predates its own last commit
25. round-4 review (B1.5, pre-implementation): the refusal names an
    achievable remedy — check out the branch, then verify — instead of a
    command that certifies the wrong tree
26. round-5 review (B5.1(a), pre-implementation): the opus record used for
    the state and certificate checks is read from the branch being merged,
    not the trunk checkout `merge` happens to run from — closing the
    fail-open direction: a branch whose own certified commit is followed by
    one more, never-certified commit is refused even when the TRUNK's own
    copy of the opus record has no certificate to compare at all (studio
    INSIDE the repo, the real layout)
27. round-5 review (B5.1(b), pre-implementation): the same branch-record
    read closes the fail-closed direction — a stale/wrong `tree:`
    certificate that survives only in the TRUNK's copy of the opus record
    no longer refuses a branch whose own copy correctly certifies its
    current tree (studio INSIDE the repo)
28. round-6 review (B6.1 — RETIRED, kept at this number per P-005): this
    used to pin the round-5 "absence rule" (a `kind: automated` gate with no
    recorded `tree:` certificate at all refused rather than passing on the
    absence). Round 6 found it refuses a Patron-waived gate with no
    achievable remedy, and its scope was pinned by nothing (A6.3); it is
    removed as redundant with `bisellium done`'s own gate (lifecycle.ts),
    which already refuses to write `state: done` while an automated
    probatio is uncertified. The assertion is flipped: an uncertified
    automated gate no longer refuses a merge by itself.
29. round-6 review (B6.3, pre-implementation): the opus record's `state`,
    like its certificates (26-28), is read from the branch being merged,
    not from whatever `--studio` shows on disk when `merge` runs — a
    branch correctly marked `done` merges even if the trunk's own disk
    copy is stale, and a branch that is NOT done refuses even if the
    trunk's disk copy was (wrongly) edited to say `done`, naming the
    branch and its real state in the refusal
30. round-6 review (B6.2, pre-implementation): the stale-certificate
    remedy, followed literally — check out the branch, re-verify, commit
    the result there, switch back, retry — lands the merge end to end; the
    refusal names the commit step the branch-ref read (B5.1) made
    mandatory

## Acceptance

Two opera can be worked concurrently in separate sessions, each on its
own branch, and merged independently when done.

## Out of scope

- GitHub PR creation (manual or patron-as-agent, W-028)
- Container orchestration (W-027)
- Automatic conflict resolution
