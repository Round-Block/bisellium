## Intent

High (greenlit, Patron 2026-10-23). For a `kind: ui` opus the ladder orders the pr step, and then the merge, with no Patron ruling on the branch's screens; the ruling is collected only after merge, beside verify on master, because that is the one place the done rule reads it. W-366 is the live case: its review round 2 passed at 07:54Z (`ci/W-366-review-2.log`), its handover at 08:03Z says "open the PR and enqueue", the PR merged as #706, and its record on master still carries no `ui_rulings`: the Patron's approval of the colours came after the PR was queued. W-361 (D-104) and W-339 (D-096) show today's ruling path: after verify on master, the clerk writes a structured decision (`by: patron`, `provenance: stated`, `opus`, `certifies`, `design_digest`, `at`) from the Patron's word, and the producer attaches it with `bisellium amend <id> --ui-ruling D-<n>`.

The fix moves that same ruling before the PR, on the branch. The ruling record is extended, not paralleled (D-042): no new field, no new decision shape, no new flag. Three decisions:

- What binds a ruling to the branch's screens. The decision's existing `certifies` must equal the branch's current source tree (the tree `next` already computes for the review rung, and the one the pr step pushes), its `design_digest` the current design digest, and its `at` must be at or after both the ui-lead input and the branch's served-e2e run, which produced `ci/shots/<id>/`. Those are today's `ruling` reader's terms, with the branch tree in place of the served tree. A later push that changes the source tree changes the tree the ruling must name, so it needs a fresh ruling; a commit that changes only the officina or an excluded path leaves the screens and the ruling as they were.
- What a missing or refused ruling prints. The pr step is held (never named, so `--perform` cannot open the PR), and the why names each attached ruling's reason (the reader's refusal, "rules another served tree or design digest, or an earlier time", or a malformed `ui_rulings`), or "no Patron ruling on these screens is recorded", then the exact tree, digest and earliest time a ruling must bind, and how to record one. A Patron's "no" is not a record: the producer sends the notes to a builder, whose fix moves the tree, so the gates, the review and this wait follow on the next pass.
- How the Patron records one: the existing path, run on the branch. The clerk writes `decisions/D-<n>.md` in `.worktrees/<id>/studio` from the Patron's word on the screenshots, `bisellium amend <id> --ui-ruling D-<n> --reason "<the Patron's word>" --studio .worktrees/<id>/studio` attaches it (amend already refuses a decision the reader refuses, and attaches a stale one with an advisory), and both are committed on opus/<id>. The wait reads the worktree and releases only when the record and the worktree's `decisions/` folder are clean against HEAD, with no ignored entry and no index flag hiding a file from status, so the PR carries the ruling.

The same wait holds the merge of a PR already open on the tip (opened by hand, or pushed past a ruling), named as the merge step. A merged PR (settled or behind) is not held. verify on master stays the final check, and done's own ruling rule is unchanged: done still needs a ruling current at master's served tree. When master's tree after the merge equals the ruled branch tree, the branch ruling carries over; when master moved under the queue, done asks again (the Patron ruled that done should accept the branch ruling then, as a follow-on opus: Defaults, item 4).

Threat model: mistakes, not adversaries (D-045).

## Interfaces

The prototype is `prototype.mbox`: four commits on master 81c6b96c, one red and one behaviour each, built by `build-prototype.sh` from `apply.sh <checkout> row1|src1|row2|src2`, each a `git apply` of one kept patch. The build reproduces it; a hunk that no longer applies after a rebase is redone by hand to the same text.

`branchUiRuling(root: string, record: NativeRecord, id: string, tree: string): { ruling: string } | { why: string }` (`opus-model.ts`, new, exported). It reads the current design digest (`currentDesign`), the ui-lead input (`authoritativeUiInput`) and the served-e2e gate with its screenshot manifest (`validateServed`); a problem in any of them is the `why`, joined by "; ". `ui_rulings` must be absent (no ruling) or a non-empty sequence of distinct strings; a scalar, `null`, an empty sequence, a duplicate or a non-string entry refuses the whole field with `ui_rulings must be a non-empty sequence of distinct decision-id strings`, and no entry of it is read. Otherwise it walks the sequence in order: the first id whose `ruling(...)` is current, with `tree` as the served tree, is `{ ruling: id }`. Otherwise `why` is `<refusals or "no Patron ruling on these screens is recorded">; it waits for one that binds certifies: <tree>, design_digest: <digest>, at or after <ISO of max(input at, served-e2e at)>`, where each refusal is `ruling`'s own problem, or `<id> rules another served tree or design digest, or an earlier time` for a valid ruling that is not current.

`uiRulingWait(f: Facts, b: Dict, tree: string): string | undefined` (`next.ts`, new). A branch record whose kind is not `ui` returns undefined. Otherwise it calls `branchUiRuling(f.wt.studio, b, f.id, tree)` (a throw becomes `the UI ruling cannot be read (<message>)`). A `why` returns `<why>: the clerk writes decisions/D-<n>.md (by: patron, provenance: stated, opus: <id>) in .worktrees/<id>/<studio> from the Patron's word on its ci/shots/<id>/, then bisellium amend <id> --ui-ruling D-<n> --reason "<the Patron's word>" --studio .worktrees/<id>/<studio>, commit both on opus/<id>, then rerun` (behaviour 1). With a ruling, behaviour 2 adds two reads in the worktree, `git status --porcelain --untracked-files=all --ignored -- <studio>/opera/<id>.md <studio>/decisions` and `git ls-files -v --` over the same two paths (the whole folder: no id is joined onto a path, so W-047's inventory B in `containment.test.ts`, W-369's file, gains no entry); a failed call returns `git status of <paths> failed in .worktrees/<id>`; any status entry (an ignored one, `!!`, included) and any index entry whose `ls-files -v` tag is not `H` (`S` skip-worktree, a lowercase assume-unchanged tag, an unmerged or any other tag), listed as `<path> (index flag <tag>)`, return `the Patron's ruling <ruling> is not committed on opus/<id> (<sorted paths>); commit it, then rerun`.

The rung (`deriveNext`, "8 pr, 9 merge"). Behaviour 1 calls `uiRulingWait(f, b, cur)` first inside the no-settled-PR branch, before W-275's stale-handover hold, and holds `pr` with its text. Behaviour 2 moves the call to just after the PR read's own hold: for a PR read that is not settled and not behind, a wait holds `merge` when the PR is open on the local tip and `pr` otherwise (none, open but stale, unrelated). `cur` is the current source tree the review rung already computed (`f.curTree()`).

Promise pr-waits: for a kind: ui opus whose review is met, the ladder holds the pr step, naming what binds a ruling and how to record one, until the worktree record's ui_rulings holds a Patron ruling current at the branch's current source tree, design digest and served-e2e run — limit: currentness and refusal are the existing `ruling` reader's terms (by: patron, provenance: stated, the at-time order), reused unchanged; the decision itself is the clerk's hand-written file (there is no decide verb, W-157).

Promise fresh-after-push: a source change after a ruling, gated and reviewed again, holds the pr step until a fresh ruling names the new tree — limit: a commit that changes only the officina, `.bisellium` or a `source_excludes` path does not move the tree, so a ruling stays current over it.

Promise committed-ruling: the wait releases only once the record and the worktree's decisions folder, including the ruling's decision, are clean against HEAD and hold no ignored untracked entry and no index entry flagged out of status — limit: it combines git status --porcelain --untracked-files=all --ignored with git ls-files -v for those paths, so a listed, ignored, flagged or unclassifiable entry holds, a stray uncommitted decision included; a git status that misreports through an fsmonitor hook or a stale untracked cache is not detected, and what reaches the remote is the pr perform's push, unchanged.

Promise merge-waits: a PR open on the local tip of a kind: ui opus with no current committed ruling holds the merge step with the same text — limit: a merged PR (settled or behind) is not held, and done's own rule, a ruling current at master's served tree after verify, is unchanged, so a merge whose tree differs from the ruled branch tree asks for a second ruling at done.

Promise non-ui: an opus whose branch record carries a registered native kind other than ui reaches the pr and merge rungs with no new read — limit: those rungs, the PR read, the handover hold and the pr and merge performs are unchanged code and a stated limit, not a new guarantee (D-076 E).

Limits, stated:

- The ruling is read from the worktree (`f.wt.studio`), as the review rung reads the UI input; a branch with no usable worktree has stopped at the build rung before this one.
- The kind read is the branch record's alone; a trunk record whose kind differs from the branch's is not consulted here. A kind that is not a registered native kind never reaches this rung: W-312's gate configuration reader holds the build rung on it first (pinned in `W-377-b1`). A ui opus whose record is edited to a registered non-ui kind is a non-ui opus here (a stated limit).
- A Patron's refusal is not recorded by this opus; the wait keeps printing until a fix moves the tree and a fresh ruling is attached.
- `next --perform --chain` that performs a UI review and then meets this wait ends there with the chain's existing held exit.
- Opus W-360 (kind: ui, in flight) meets this wait at its pr step once this opus lands; W-366 is past its PR and is not affected.
- Unchanged code the promises lean on is a stated limit, not a guarantee (D-076 E): `ruling`, `currentDesign`, `authoritativeUiInput`, `validateServed`, `readServedShots`, `f.pr()` and its classification, `f.curTree()`, `integrate.ts`'s `git`, the amend verb's `--ui-ruling` path, the pr and merge performs, and done's ruling rule.
