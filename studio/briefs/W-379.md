## Intent

Since W-362 every hook runs `~/.local/bin/bisellium`, a link into `~/projects/bisellium-guard`, a linked worktree of the Patron's clone that the Patron's `agent-workspace.sh guard` moves to origin/master. The Patron ruled on 2026-10-23 that the install runs from their own clone, `~/projects/bisellium`, at master, with no second worktree. W-369 round 3 drafted that as its behaviour 4; spec review 4 failed it on two inputs the guard did not judge, and D-061 §4 moved it here.

After this opus:

1. **The guard judges the Patron's clone as the sync does.** `guard_inputs` (so `guard`, `guard-check` and `verify`) refuses `PATRON_DIR` off master or with an uncommitted tracked change, with W-369's `patron_on_master` lines naming the guard.
2. **The guard installs only as that clone's own copy.** `guard` refuses, changing nothing, unless its own real directory is exactly `<PATRON_DIR's real path>/scripts` (spec-4 finding 1). Then it fetches origin's master into the clone, fast-forwards the clone's master to it, runs npm ci there, links `GUARD_BIN` into the clone's real path, merges the user settings with the clone's merge script and probes the guard, as W-362 did for the worktree. `GUARD_DIR` and its checks go; `verify` reports the link into `PATRON_DIR`.
3. **The old guard worktree goes only when proved.** After the probe, `guard` removes `OLD_GUARD_DIR` (default `~/projects/bisellium-guard`) only when `GUARD_BIN`, read as the run began and before it was relinked, led into it, and git lists it as a linked worktree of `PATRON_DIR`, and git's `worktree remove` (never forced) finds it clean. Any other candidate is left with its reason and the Patron's command (spec-4 finding 2).
4. **Every git the guard runs is clean.** A new `cgit` runs git under `env -i` with `HOME` and `PATH`, no global or system config, no hooks, no fsmonitor, no submodule recursion, no prompt and no replacement refs; W-369's `agit` becomes `cgit` on the agent clone. `top_is`, `guard_inputs`' origin/master read, `patron_on_master`, the merge, `rev-parse --short` and `old_guard`'s `worktree list` and `worktree remove` go through it. The fetch keeps the Patron's environment and config, with hooks and fsmonitor off: the Patron's clone fetches over ssh (`git@github.com:…`), which needs their ssh agent, and their url rules and credentials live in their global config.

Why the own-copy check is in `guard` and not in `guard_inputs`. `verify` calls `guard_inputs`, and a session runs `verify --inside` from the agent clone's copy; the install is the only step that must run the copy it installs.

Why the proof is `GUARD_BIN` as the run began. W-362's install made `GUARD_BIN` a link into the old worktree, so on the first run after this merge it names that worktree exactly; a typo or another worktree of the clone never holds it. The cost: once a run has relinked `GUARD_BIN`, a later run cannot prove the old worktree any more and leaves it with the command (Defaults 3).

Promise guard-clone: `guard_inputs` accepts `PATRON_DIR` only when `patron_on_master "the guard"` holds, and otherwise prints `PATRON_DIR <dir> is on <ref>, not master; the guard runs only while it is on master` or `PATRON_DIR <dir> has uncommitted tracked changes (<first line>); the guard runs only while it is on a clean master`, so `guard` stops with "nothing was changed", `guard-check` exits 1 and `verify` prints FAIL for the inputs — limit: an untracked file and an unborn master are not seen; `patron_on_master` called with no subject keeps W-369's sync lines.

Threat model: mistakes, not adversaries (D-045): a wrong `PATRON_DIR`, a wrong script or a wrong `OLD_GUARD_DIR` typed by the Patron, and a hook or global setting that a clean git call must not run. No session can write the Patron's clone, `~/.local/bin` or the old guard worktree (W-362's deny and the sandbox's write list); the agent clone's `.git`, which a session can write, is read by the guard only through `cgit` (`top_is`).
