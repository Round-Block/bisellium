## Intent

The repeat S1 class `tests×one-sided-bound-assertion` (D-076 D, high) came back after its cause fix W-376 (`test.one_sided`, PR #708). W-381's build review round 1 (`ci/W-381-review-1.log` #1) found `next.ts:1422` and `:1424` at head a1fa6f4e: `/(?<![\w-])high(?![\w-])/i.test(title)` and `` new RegExp(`(?<![a-z0-9-])${esc(c)}(?![a-z0-9-])`).test(title) `` bound a title token by an ASCII set, so `high` beside a non-ASCII letter counted as a whole word. Round 2 (`ci/W-381-review-2.log` #1, head 1a406822) found the same class again: the new helper `titleToken` built its set from a substitution, `` (?<![${boundary}]) ``, and its callers passed `"\\p{L}\\p{N}_-"`, with no combining marks.

Why W-376's rule missed it, checked on master: W-376's rule is in that head's tree (ff89317f is an ancestor of a1fa6f4e), and on both heads it finds no site (`would-catch-master.out`: 0 and 0). Each of the forms the opus names was checked:

- A file the rule does not scan: yes. The defect lines are in `packages/cli/src/next.ts`. W-376 reads only files that `isTestPath` holds for.
- `assert.match` and regex literals: W-376 reads a pattern only as the second argument of `assert.match`. W-381's patterns are a regex literal and a `new RegExp` template used with `.test(title)` inside a filter, outside any assertion.
- Anchors: W-376's `sidedPattern` reads only `^` and `$`. W-381's bound is a token boundary, a lookbehind and a lookahead over an ASCII class. It is not an end anchor.
- `RegExp` built from strings: W-376 reads `new RegExp(` with a literal argument, in `assert.match` only. Round 2's helper builds its set from a substitution.

W-381's test rows asserted whole strings (`assert.equal(o.kv.get("why"), why, …)`), so no test line was one-sided. The one-sided bound was the pattern, and the rows only probed its ASCII side (`tests×ab`, `highly`). So the path to close is the pattern itself, wherever it appears.

The cause fix extends the same rule, `test.one_sided`, in `rules/tests.ts`. Its diff scope, its annotation (`// one-sided: <reason>`) and its rule id stay the same. Two behaviours:

1. The boundary form (behaviour 1). On a changed line of any tracked code file (W-121's extensions, test or not), the rule reads every pattern. A pattern is a regex literal wherever an expression may open, or the literal first argument of `RegExp(` or `new RegExp(` (a string, a template or `String.raw`). A token boundary over part of the alphabet is a block, unless annotated. Such a boundary is a `\b` or `\B`, or a lookaround whose body names letters (`\w`, `\W`, an ASCII letter range, or a letter property) without the whole set, or whose body is built from a substitution. The whole set is `\p{L}`, `\p{M}` and `\p{N}`, or `\p{ID_Continue}`. That is W-381 brief:75's own definition of a word.
2. The anchor forms reach the remaining pattern spellings in an assertion (behaviour 2). In a test file, `assert.ok(` or `assert(` whose first argument holds a pattern anchored at one end (`/^x/.test(s)`, `new RegExp("x$").test(s)`) is a block. `assert.match` also reads `RegExp(` with no `new`, and a `String.raw` template.

What it would have caught (`would-catch.out`, the prototype's rule on each reviewed head against its merge-base with master): W-381 round 1, `next.ts:1422` and `:1424` (`a word boundary over ASCII letters only`) and `verdict.ts:593`. W-381 rounds 2 and 3, `next.ts:1433` (`a word boundary built from a substitution`). W-376's own cases are unchanged: W-328 review 1 has 2 sites and W-310 review 1 has 6. Round 2's missing `\p{M}` sits in a caller's string argument, which no line rule can read. The rule blocks the helper whose set it cannot see instead, and the annotation then has to say where the set comes from.

Its cost (`feats-census-new.out`): over master's last 40 feature merges, the closed rule finds 11 more lines than W-376's (53 against 42), all of the boundary form, in 6 merges. One is the class itself (`next.ts:1433`). Ten bound grammars that are ASCII by their own definition: an id or citation token (`verdict.ts:158`, `:419`, `:593`), the rule's own identifier sites (`tests.ts:561`, `:564`), CSS names and hex digits (`tokens.test.ts:62`, `:63`, `:110`, `:196`) and a CLI flag (`next-spec.test.ts:1185`). Each of those takes a one-line annotation. That is about one line in four opera.

False positives, stated: a two-sided pattern (`^…$`) passes, as in W-376. A whole boundary passes. A lookaround over digits, punctuation, spaces or a backslash names no letter and passes. A slash after a name, a `)` or a `]` is a division, not a pattern. An ASCII grammar is the rule's one false-positive form, and its annotation is the way through.

Threat model: mistakes, not adversaries (D-045).
