## Intent

D-087 B. The done perform records the merge queue's certify certificate (W-259) only while master has changed nothing but records since the opus's merge commit. When a second lane merges first, master's source has moved and the perform asks for a 24-minute `verify` on the host. That happened to W-297 after W-313 (#594, #595), and it is the live case now: W-317 merged at 30a5943d (#606), then W-299 at 5e7dbb0c (#605), then a records PR, cf8a96f8 (#607, W-317's done, which edited the handoff).

After this opus, master's source may have moved since the merge commit. The done perform still records certify's certificate when every first-parent commit since is either records-only or a merge-queue merge whose certify run succeeded. It reads the newest such merge's run and names that merge's source tree with its receipt. The two policy refusals stand: a change to `<studio>/bisellium.yml` or to the opus's own record since the merge commit holds. The probe shows the prototype accepting the live case on the real repository, with the real `gh` run and artifact. It accepts master at 5e7dbb0c, and also with #607's handoff and dossier page edits committed after it. A further local source commit with no run is refused (`probes.out`). On master the same perform holds (`probe-master-chain.out`).

The four questions the record leaves to this brief:

1. **How a commit is classed records-only.** `recordOnly` in `scripts/ci-scope.mjs` classes it. That is the one list of officina record paths (`<studio>/`, `docs/SESSION-HANDOFF.md`, a page directly in `docs/design/dossier/` ending `.html`; W-131, W-209, W-243). The merge queue's scope step (`ci-scope.mjs <base> HEAD` in `ci.yml`), certify (`ci-certify.mjs`) and next's done and landing guards already read it. Each commit's own diff against its first parent is read through `diffPaths`, the one diff reader. An empty diff is not records-only, as `recordOnly` already rules, so such a commit needs a run.
2. **How a first-parent commit is tied to its certify run.** The tie is the commit's sha as the `merge_group` run's `headSha`. The queue fast-forwards master to the group's head commit; W-259 relies on the same for the opus's own merge commit, and on #605 the run's `headSha` is master's commit 5e7dbb0c. Each source commit gets the two reads the perform already makes for the merge commit. `gh run list -R <repo> --workflow ci.yml --event merge_group --commit <sha> --limit 20 --json databaseId,headSha,event,status,conclusion` must give exactly one such run, completed with success. `gh run view <run> --json jobs` must give exactly one `certify` job with conclusion success. The newest source commit adds a third read, `gh run download <run> -n certify-<run>`. Its PR is the squash subject's trailing `(#<n>)`, and its certify.log must show `certify: merge group for PR #<n>` and `certify: the mint exited 0`. Its receipt must be that of the opus whose head the log rebased (`certify: rebasing opus/<id> onto <hex>`, which `ci-certify.mjs` prints). A one-merge chain costs the three calls the perform makes today; each older source commit adds two. The opus's own merge commit's run is not read on a chain: the newest run's receipt certifies a tree that contains it.
3. **Which receipt and tree the certificate names.** It names the newest source commit's run receipt and that commit's source tree (the receipt's `finalSourceTree`). It does not name master's tip. A records commit after that merge can change a records path that the source tree hashes, such as the handoff (#607 did), and master's tree then differs from the tree certify ran. Naming the merge's own tree is W-259's rule for the opus's merge commit, applied to the newest merge: master's source equals it except for records-only paths. The record's "master's tree" is read this way (Defaults 1). `mergedTree` returns that tree, so `certificate`, its other caller, accepts it without a new branch. The one diff-bound acceptance stays one function (D-076 D).
4. **A link it cannot read** fails closed, and the perform behaves as it does today. These all hold the perform before anything is written, with `why: refusing: the merge queue's certify certificate cannot be recorded: <reason>; run: bisellium verify <opus> --studio <dir> --repo .`: a listing, a diff, a `gh` call that fails or returns no JSON array, the wrong number of runs or certify jobs, a run or job that did not succeed, a subject with no PR, a failed download, the wrong number of receipts or logs, a log naming another PR or no one rebased opus, a receipt of another opus or tree, and the merge commit off master's first-parent line.

Promise chain-certificate: when master's source changed since the opus's merge commit, every first-parent commit since is records-only by `recordOnly` or has one completed, successful `merge_group` run with one successful `certify` job, and neither `<studio>/bisellium.yml` nor `<studio>/opera/<id>.md` changed since the merge commit, the done perform records the newest such commit's certify certificate (its run, its subject's PR, its receipt, naming its source tree) and commits the done record — limit: it trusts what `gh` reports for the repository's own Actions runs and reads no signature, as W-259 does; a later records commit that changes a records path the source tree hashes leaves master's tree unlike the named one, as W-259's records commits do; the artifact expires after 90 days, and then the perform holds; whether certify's checks judged each older commit's group is GitHub's run record, read, not re-run.

Promise chain-holds: a link of the chain the perform cannot read or that fails its check (the commit listing, a commit's diff, a run listing or view, its run or job, the newest commit's PR number, the download, the artifact's receipt or log, the log's PR or rebased opus, the receipt's opus or tree, the merge commit off master's first-parent line) holds the perform with exit 1 and a `why:` line naming the reason and `bisellium verify <opus> --studio <dir> --repo .`, before any certificate log, record edit or `chore/done-<id>` is written — limit: a hold after the record is written (the history row, say) leaves the certificate in the working tree, as W-259's does, and the next perform finds it certified.

Promise records-path: when master changed nothing or only records since the merge commit, the perform reads the merge commit's own run, PR and receipt and names the merge commit's tree, as W-259 rules; only the reason for a source change by a commit with no certify run is new (W-259-b1's flip) — limit: the reused W-259 code (`receiptProblem`, `artifactFiles`, the download and the log write) is a stated limit, not a guarantee (D-076 E).

Threat model: mistakes, not adversaries (D-045), as W-259: the perform reads the repository's own Actions runs through `gh` and its own git history.

## Interfaces

The prototype is `apply-src.py <checkout> <1|2>` (stage 2 includes stage 1), the rows are `apply-test.py <checkout>`, and the flip is `apply-flips.py <checkout>`, staged by `stages.sh <master|s1|proto>`. `prototype.diff` is the whole diff on master cf8a96f8. The build reproduces it; a hunk that no longer applies after a rebase is redone by hand to the same text.

1. **`mergedTree(repo, studioRel, excludes, merged, id): { tree: string; chain?: SourceCommit[] } | { why: string }`** (behaviour 1).
   - `since` is `diffPaths(repo, merged, TRUNK)`, as today.
   - When `since` is non-empty and not `recordOnly`, `chain` is `sourceCommits(repo, studioRel, merged)`, and its `why` is returned when there is one.
   - The policy filter (`<studio>/bisellium.yml`, `<studio>/opera/<id>.md`) runs over `since` whether or not there is a chain, with today's message.
   - `tree` is `tree:<sourceTreeHash(repo, excludes, at)>`, where `at` is the newest chain commit or else `merged`. The hash failure keeps today's message with `at`.
   - `certificate` is unchanged: it accepts `m.tree`.
2. **`sourceCommits(repo, studioRel, merged): { chain: SourceCommit[] } | { why: string }`** (new; `type SourceCommit = { sha: string; source: string[] }`).
   - It runs `git rev-list --first-parent --parents --reverse <merged>..refs/heads/master`. A failure is "could not list master's commits since the merge commit <12 hex>".
   - Stage 2: the oldest listed commit's first parent must be `merged`; otherwise "the merge commit <12 hex> is not on master's first-parent line".
   - For each commit it reads `diffPaths(repo, <first parent>, <sha>)`. Undefined is "could not read what <12 hex> changed on master". A list that is not `recordOnly` adds `{ sha, source: <its non-records paths> }`.
   - An empty chain is a `why`.
3. **`certifyRun(repo, slug, sha, what): { runId: number } | { why: string }`** (new). It is `recordCertify`'s run list and run view checks today, moved out unchanged, with `sha` for the merge commit and `what` naming it in "`<n>` merge-queue CI runs name `<what>`".
4. **`recordCertify(f)`** (behaviours 1 and 2).
   - With no chain, it reads `certifyRun` for the merge commit (`what` is "the merge commit <12 hex>") and the opus's PR number, as today.
   - With a chain, it calls `certifyRun` for each source commit, oldest first (stage 1: the newest only), with `what` "the commit <12 hex>". A `why` becomes "master's source changed since the merge commit <12 hex> at <12 hex> (<up to 5 source paths, or "an empty diff">), and <why>".
   - The PR is `(#<n>)` at the end of the newest commit's subject (`git log -1 --format=%s`), else "the commit <12 hex>'s subject names no PR as (#<n>)".
   - After the artifact read (unchanged), the log's lines are read before the receipt. The receipt's opus is the opus itself without a chain; with a chain it is the one `opus/<id>` that a line `certify: rebasing opus/<id> onto <hex>` names, else "certify-<run>'s certify.log does not name the one opus head it rebased". `receiptProblem(receipt, <that opus>, m.tree)` follows, then the PR and mint-exit check with the PR.
   - The log's `command:` line names `CI run <run>, PR #<n>, merge commit <sha>`. A chain appends ` (the newest of <k> certified source commit(s) on master since <opus>'s merge commit <oid>)`.
   - The perform prints `certificate: certify run <run>, PR #<n>, merge commit <12 hex>, tree:<hash>`. A chain adds `certificate: the certified chain since <opus>'s merge commit <12 hex>: <12 hex>, …`.
   - The gate logs and record writes are unchanged.

Limits, stated:

- Unchanged code the promises lean on is a stated limit, not a guarantee (D-076 E): `recordOnly` and `diffPaths` (`scripts/ci-scope.mjs`), `ghRead`, `sh`, `sourceTreeHash`, `receiptProblem`, `artifactFiles`, `readContainedRegularFile`, `certificate`, `performDone`, `dirtyHold`, `historyRowRefusal`, `mergeRefusal`, `runDone`, the `pr()` read of the merged PR, and the lines `scripts/ci-certify.mjs` writes to certify.log.
- `certificate` (the derivation's `certified()` and the done commit's re-check) walks the chain with git only, about one `git diff` per commit since the merge commit. It does so only when the working record already names a tree other than master's.
- A merge group of several PRs (D-087 E keeps one) gives each PR's commit its own run, as GitHub creates one per queued entry. A commit with no run of its own holds.

## Defaults for the Patron

1. When other changes have landed since a task merged, the certificate names the code that the newest merge-queue check actually tested. Later records-only changes, such as a session-note edit, do not count, as today's rule already treats records after the task's own merge. Agree?
