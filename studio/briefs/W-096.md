# W-096 — a typed officina work model: kinds, UI obligations, arcs, dates, and summary/body

Status: **draft, unsigned** · architect · 2026-10-01 · `spec/W-096`.
This document does not pass the spec gate or authorize an opus-record edit.

## Intent

Give the native officina a closed work-kind vocabulary and enforce the extra
obligations of UI work. Settle the record model before extending its screens:
an arc groups opera; a subtask names its parent; start/end describe actual
lifecycle transitions; `title` is the one-line summary and the Markdown below
the front matter is the description. W-096 owns this model, its command
boundaries and checks, not Jira-like drawer layout.

The amended W-096 title is the Patron's decree. D-022 delegates design
leadership to `ui-lead` without replacing D-014's single censor review/QA
gate. D-029 maps munera directly to seats; this opus must not introduce a
tier indirection or implement the separate delegation migration.

## Decrees and model decisions

### 1. Close the native kind vocabulary without retiring measured values

The exact set is `opus`, `task`, `subtask`, `bug`, `research`, `feature`,
`hygiene`, `art-batch`, `ui`, `arc`. Export one readonly enumeration and its
derived TypeScript union. `opus` remains the existing general-work value;
do not silently translate it into `task`. `arc` is the grouping record kind.
Kinds are case-sensitive; whitespace, aliases and unknown strings are errors.
`opus.kind` is blocking for every native record, regardless of state. Missing
or ill-typed values retain the existing required-key findings as well.

Both creation entry points validate before allocating or creating a brief.
Raw YAML/argv remains untrusted input until validated. Do not narrow the
cross-adapter `Opus.kind` contract: this closed set is native-officina policy,
not a ban on external adapters' kinds. Other kind domains (actor, gate,
actum, API-result discriminants) remain unchanged.

No measured value is retired, so this build requires no migration. If a later
Patron amendment retires one, implementation stops at the ownership boundary
until the brief names a kept, tested, idempotent migration script with dry-run
output and explicit old-to-new mapping. No bulk replacement or manual record
rewrite is authorized by this draft.

### 2. UI routes design review to ui-lead and cannot bypass its evidence

Routing means a model policy, enforced at readiness and completion: a `ui`
opus requires design review by the live design seat `ui-lead`. Missing,
retired or wrong-collegium routing blocks `ready` and active-state checks
with `opus.ui.route`. No new collegium, model hardcode, generic dispatch
engine, munus tier or second QA reviewer is introduced. D-022's dispatch
effort remains medium; dispatch itself is outside this opus.

Use existing `verdict --phase spec` evidence for that design review. Among
this opus's spec verdicts attributed to `ui-lead`, the highest numeric round
is authoritative; it must have exact outcome `passed`, a valid timestamp and
a nonempty transcript. Validate the command-produced header, including opus,
phase, round and actor, rather than searching the body for those words.
It must not predate the latest title/spec amendment. A newer failed or
malformed ui-lead verdict cannot be bypassed by pointing at an older pass.
`opus.ui.design` blocks active/done UI records lacking this evidence; `ready`
and `done` use the same predicate. This is design evidence, not a second
probatio or a substitute for the existing spec and censor gates. Non-UI
design-review routing remains unchanged.

UI's effective probationes include one reserved automated gate,
`served-e2e`, even when absent from the manifest. One shared helper supplies
this effective list to `check`, `verify` and `done`; it does not rewrite the
manifest. Its command is `node scripts/served-e2e.mjs`. The kept script
first runs the web build and, only after success, runs the web workspace's
`test:serve`. It uses argument arrays, propagates failure and never points
tests at the real studio. A same-id manifest declaration must be automated
and have that exact command; conflicting declarations block `opus.ui.e2e`.
For non-UI opera, the manifest's existing gate semantics are untouched.

`verify` produces the served gate through the existing pipeline, evidence
writer and SOURCE certificate, also recording its run timestamp as this
gate's `at`. A missing, pending, failed, waived or dirty
result cannot satisfy UI completion. Its log must exist and corroborate its
successful result, command and certificate; a hand-written success word in
an unrelated log is insufficient. Require it for `review` and `done`, with
`opus.ui.e2e` blocking unsupported terminal claims. At `done`, also require
a clean current SOURCE tree matching the served certificate, using existing
source exclusions; unavailable tree identity refuses completion. General
certificate-staleness advisories stay advisory. Historical done records are
checked against their recorded evidence, never today's moving source tree.

The Patron's look-and-feel rulings are a nonempty `ui_rulings` list of
decision ids on a UI opus. Every id resolves within the same officina to a
valid Patron-authored decision with a nonempty body and kill condition;
the decision additionally names `opus: <this opus>` and a valid
`certifies: tree:<SOURCE hash>`. Completion requires at least one ruling
for the current successful served run's SOURCE hash whose `at` is no earlier
than that run. Earlier source-bound rulings stay in the append-only list as
history and cannot satisfy the current run. The body records the actual visual rulings,
including accepted residuals. A decision's mere presence or ui-lead's
opinion is not Patron acceptance. This structural contract cannot judge the
truth of prose or authenticate a person beyond the repository's existing
attribution model; it makes the ruling and attribution inspectable.

`opus.ui.rulings` checks present references in every state, and requires a
nonempty list with a current ruling at done. `done` refuses an absent list,
wrong actor/opus, empty or dead decision, or a list containing only wrong-tree
or too-early rulings before any write or event. A generic
human waiver does not bypass this requirement: any Patron exception is
itself a recorded, scoped look-and-feel ruling. A new source tree requires
new served evidence and new Patron rulings; old decisions remain history.

### 3. An arc is a parent reference, not a new lifecycle

An arc is an ordinary `opera/W-*.md` record with `kind: arc`, its own title,
optional body, collegium, state and the existing lifecycle obligations.
No new id allocator, directory or lifecycle is needed. Membership is the
optional scalar `arc: W-123` on a non-arc opus; it must resolve to an arc
record in the same officina. Arcs themselves cannot name an arc or parent.
There are no roll-ups, inferred completion or nested arcs in this opus.

`parent: W-124` is required for `subtask`, forbidden for other kinds, and
must resolve to a non-arc, non-subtask opus in the same officina. This makes
subtasks one level deep, with no cycles or self-parenting. A subtask may omit
`arc` and inherit its parent's membership in the model; if it explicitly
sets `arc`, that reference must equal the parent's arc. If the parent has no
arc, the subtask cannot introduce one. No inherited value is written back.

`opus.arc` and `opus.parent` block malformed, dangling, wrong-kind, cross-
officina and conflicting references. Resolve validated ids against an
enumerated record map, never arbitrary paths. Hierarchy does not imply
`depends`, change WIP accounting or constrain parent/child completion order;
dependency scheduling remains W-068.

### 4. Start/end are optional actual dates, never guessed history

Canonical fields are `start` and `end`, each an optional quoted RFC 3339
timestamp with an explicit UTC offset. Writers use UTC ISO strings. Reject
invalid calendar dates, nonstrings, date-only values and offset-less times.
When both exist, end must be at or after start; end without start is valid
for an older active opus whose beginning was never recorded. `end` is valid
only in `done`; absence of either field is legal, including on old done
records. Rules: `opus.dates` and `opus.dates.order`.

Derive new dates from successful lifecycle transitions: `ready` records the
first start when absent, and `done` records end, using exactly the timestamp
emitted with that transition. Resuming a halt preserves start; a failed
review reopening done clears end and preserves start; a later done stamps
a new end. These are persisted transition facts so losing the local event
log does not lose dates. Refused commands change neither dates nor events.
Validate supplied existing dates before a transition could overwrite them.

Do not backfill from mtime, traditio, first observation, `item_appeared`, or
snapshot-derived event times (`workflow.time.derived`). Start/end are actuals,
not planned dates or deadlines; planned dates would be a separate decree.

### 5. Summary is title; description is the Markdown body

There is exactly one summary source: existing front-matter `title`, a
nonblank string containing no CR or LF after YAML decoding. “One line” is a
logical field constraint, not a character limit or a prohibition on visual
wrapping. Long existing titles, including W-096's decree, remain intact.
`opus.title` blocks multiline/blank/nonstring titles; `newItem`, `runNew`
and `amend --title` reject them before writing.

Description is all authored Markdown below the front-matter delimiter. Empty
is legal; it is not derived from title or `spec`, and no `summary:` or
`description:` duplicate field is introduced. Existing body-preserving
mutation stays byte-for-byte. Do not alter W-087's bounded HTTP body reader,
its truncation marker, literal rendering, whitespace or summary/title layout.

  `NativeOpusKind`, plus native field types for arc/parent/start/end and
  `ui_rulings`. Keep generic adapter inputs permissive and validate at native

- `packages/commands/src/opus-model.ts` (new): shared runtime narrowing,
  hierarchy/date validation, UI design-seat/evidence/ruling validation and
  effective-probatio calculation. Accept parsed records and explicit time/
  source identity dependencies; return structured problems, not writes or
  inferred success. CLI rules translate problems to the named blocking ids.
  Reuse containment and source-certificate helpers. No new server dependency
  on commands, and no commands import back into the native adapter.
- Extend `new`/`newItem` with optional `arc` and `parent` inputs (CLI flags
  `--arc` and `--parent`); validate the complete proposed record before
  allocation. Existing flags, output and W-101 collision/rollback stay intact.
- Extend `amend` with `--arc <id>`, `--parent <id>` and
  `--ui-ruling <decision-id>`. The first two set references; the last appends
  one unique reference to `ui_rulings` per invocation. These are **proposed
  new flags**, not callable in today's CLI. Require the existing reason,
  actor and owner-ref checks; validate the entire proposed result before
  writing; preserve body and record old values in the existing amendment
  history. A duplicate ruling is a no-op refusal. No remove/clear operation
  or kind editing is added. These flags attach references, never author a
  verdict, decision, gate result or certificate. Ready/done own dates.
- UI design evidence is written by existing `verdict --phase spec`; censor
  evidence still uses existing `review`. Rulings use the existing decision
  record contract (there is presently no `decide` verb). This opus does not
  grant permission to fabricate evidence or retrofit old UI records.
- `checkStudio` reports each named rule against the opus path, including
  invalid data on disk that bypassed a command. Do not rely only on a TypeScript
  union or only on writer validation. Register every new rule id.
  `ready` and `done` also validate kind, title, hierarchy and dates before
  transition-specific policy, so a misspelled UI kind cannot bypass the UI
  guards. Refusals occur before any mutation or event.
