# W-096 — a typed officina work model: kinds, UI obligations, arcs, dates, and summary/body

Status: **revision 3, draft, unsigned** · architect · 2026-10-01 · `spec/W-096`.
This document does not pass the spec gate or authorize an opus-record edit.

## Intent

Give the native officina a closed work-kind vocabulary and enforce the extra
obligations of UI work. Settle the record model before extending its screens:
an arc groups opera; a subtask names its parent; start/end describe actual
lifecycle transitions; `title` is the one-line summary and the Markdown below
the front matter is the description. W-096 owns this model, its command
boundaries and checks, not Jira-like drawer layout.

The amended W-096 title is the Patron's decree. D-022 delegates design
leadership to `ui-lead` without replacing D-014's single censor review/QA
gate. D-029 maps munera directly to seats; this opus must not introduce a
tier indirection or implement the separate delegation migration.

## Decrees and model decisions

### 1. Close the native kind vocabulary without retiring measured values

The exact set is `opus`, `task`, `subtask`, `bug`, `research`, `feature`,
`hygiene`, `art-batch`, `ui`, `arc`. Export one readonly enumeration and its
derived TypeScript union. `opus` remains the existing general-work value;
do not silently translate it into `task`. `arc` is the grouping record kind.
Kinds are case-sensitive; whitespace, aliases and unknown strings are errors.
`opus.kind` is blocking for every native record, regardless of state. Missing
or ill-typed values retain the existing required-key findings as well.

Both creation entry points validate before allocating or creating a brief.
Raw YAML/argv remains untrusted input until validated. Do not narrow the
cross-adapter `Opus.kind` contract: this closed set is native-officina policy,
not a ban on external adapters' kinds. Other kind domains (actor, gate,
actum, API-result discriminants) remain unchanged.

No measured value is retired, so this build requires no migration. If a later
Patron amendment retires one, implementation stops at the ownership boundary
until the brief names a kept, tested, idempotent migration script with dry-run
output and explicit old-to-new mapping. No bulk replacement or manual record
rewrite is authorized by this draft.

### 2. UI requires ui-lead input; the censor remains the single review gate

Routing means a model policy, enforced at readiness and completion: a `ui`
opus requires design input from the live design seat `ui-lead`. Missing,
retired or wrong-collegium routing blocks `ready` and active-state checks
with `opus.ui.route`. No new collegium, model hardcode, generic dispatch
engine, munus tier or second QA reviewer is introduced. D-022's dispatch
effort remains medium; dispatch itself is outside this opus.

Use existing `verdict --phase spec` to capture that input without signing a
gate. Among this opus's spec transcripts attributed to `ui-lead`, the highest
numeric round is authoritative. Require an outcome matching exactly
`^(passed|failed|revise)$`, a valid timestamp, a substantive transcript as
defined below and a valid command-produced header
whose opus, phase, round and sella match the filename and routing. Duplicate
header keys, malformed latest rounds and stale digests fail closed; do not
fall back to an older round. **No outcome value, including `failed`, vetoes
readiness or completion.** The architect owns the spec gate; the censor
alone decides the review gate after considering the input, including dissent.
`opus.ui.design` requires current input at `ready`, `done`, and in `check`
for building/verifying/review/done UI records. A halted UI record with a start
also retains this obligation. Earlier states validate evidence if present.

For `opus.ui.design`, substantive means exactly one `## Findings` section
containing at least one line matching `^[1-9][0-9]*\. \S.*$` or the exact
line `No findings`, and exactly one `## Recommendation` section containing
exactly one verdict line matching `^Verdict: (passed|failed|revise)$`, equal
to the header outcome. A section ends at the next level-one or level-two
heading. Require at least four nonblank, non-heading body lines, including
at least two explanatory lines other than the finding markers, `No findings`
and verdict line. Each explanatory line and each numbered finding's text
must contain at least 20 non-whitespace characters. Fenced code and HTML
comments cannot supply sections or counted lines. Reject any content line,
finding text, verdict value or outcome whose trimmed, case-folded value is
one of `tbd`, `todo`, `pending`, `placeholder`, `n/a`, `...`, `insert findings`,
`insert recommendation`; reject these tokens as standalone words in finding
text or explanatory lines as well. These are mechanical content minima,
not automated judgment of the recommendation's correctness.

Retain the actual dispatch prompt as a regular file under `ci/`. For UI spec
input only, `verdict` requires a proposed `--dispatch-prompt <ci-relative-path>`
argument and emits exactly one `# dispatch_prompt: <path>` header, validated
with the same contained-read policy as transcripts. `check`, `ready` and
`done` require that file and reject a transcript body equal to its contents
after CRLF-to-LF conversion and trimming outer whitespace (strip only the
command-produced verdict header from the transcript). Missing/unreadable
prompt evidence fails closed; no caller assertion of inequality suffices.
The dispatch engine remains out of scope. The writer and all three readers
enforce these content rules on the authoritative round without fallback.

Define `design_digest` exactly as `sha256:` plus the 64 lowercase hex digits
of SHA-256 over `D || U64BE(T.length) || T || U64BE(B.length) || B`.
D is the ASCII bytes of `W-096/ui-design/v1` followed by one NUL byte;
U64BE is an unsigned 64-bit big-endian byte length. T is UTF-8 of the exact decoded title scalar
(no trimming, Unicode normalization or newline conversion), B is the entire
referenced brief's raw file bytes (including front matter, if any), and
lengths count bytes. Read the brief selected by the current spec pointer;
no SOURCE exclusion applies to this digest. Missing/unreadable brief refuses
clearance. `verdict` computes and records `# design_digest: <digest>` for UI
spec input; the caller cannot supply it. `check`, `ready` and `done` recompute
and compare it, even if the spec path and amendment history are unchanged.
An in-place revision invalidates input and any Patron ruling for the older
digest. SOURCE identity remains a separate build certificate.

For UI censor evidence, require exactly one `# ui_input: ci/<opus>-spec-<round>.log`
and one `# design_digest: <digest>` in the leading verdict header. The cited
round must be the current input above. Its transcript must contain a nonblank
`## UI input disposition` section explaining how the censor handled that
input. `review --pass`, done and checks of a passed review enforce this under
`opus.ui.design`; the build-phase `verdict` writer gains a UI-only `--ui-input`
reference flag, computes the digest, validates the reference and preserves
the censor's supplied disposition. This cites evidence, never promotes
ui-lead to gate signer. No automated check decides whether dissent is right.
Non-UI routing remains unchanged. This honours D-022 and D-014 without an
amendment: “routes review” requires input, not ui-lead assent.

UI's effective probationes include one reserved automated gate,
`served-e2e`, even when absent from the manifest. One shared helper supplies
this effective list to `check`, `verify` and `done`; it does not rewrite the
manifest. Its command is `node scripts/served-e2e.mjs`. The kept script
first runs the web build and, only after success, runs the web workspace's
`test:serve`. It uses argument arrays, propagates failure and never points
tests at the real studio. A same-id manifest declaration must be automated
and have that exact command; conflicting declarations block `opus.ui.e2e`.
For non-UI opera, the manifest's existing gate semantics are untouched.

`verify` produces the served gate through the existing pipeline, evidence
writer and SOURCE certificate, also recording its run timestamp as this
gate's `at`. A missing, pending, failed, waived or dirty
result cannot satisfy UI completion. Its log must exist and corroborate its
successful result, command and certificate; a hand-written success word in
an unrelated log is insufficient. Require it for `review` and `done`, with
`opus.ui.e2e` blocking unsupported terminal claims. At `done`, also require
a clean current SOURCE tree matching the served certificate, using existing
source exclusions; unavailable tree identity refuses completion. General
certificate-staleness advisories stay advisory. Historical done records are
checked against their recorded evidence, never today's moving source tree.

The Patron's look-and-feel rulings are a nonempty `ui_rulings` YAML sequence
of distinct decision-id strings on a UI opus. Exact grammar: each id matches
`^D-[0-9]{3,}$` and resolves to `decisions/<id>.md` in the same officina.
The decision's YAML front matter, not its body, must contain scalar fields
`id` (equal to filename), `by: patron`, `provenance: stated`, nonblank `title`
and `kill_when`, `opus` (this opus id), `certifies` (a string matching
`^tree:[0-9a-f]{40}$`, the existing clean SOURCE certificate),
`design_digest` (the digest above),
and `at` (the exact UTC profile in §4). Reject duplicate mapping keys,
aliases, merge keys and non-scalar values in these required fields; inspect
YAML nodes before scalar coercion. Existing decision-shape/kill checks also
apply. The nonblank Markdown body records actual visual rulings, including
accepted residuals, but body pseudo-fields never supply metadata. No table
row or phrase such as “Patron approved” satisfies this contract.

Completion requires at least one structurally valid ruling matching both
the current successful served run's SOURCE hash and current design digest,
with `at` no earlier than that run or the current ui-lead input. Earlier
valid rulings remain append-only history; their digest/tree mismatch makes
them nonqualifying rather than corrupt. `check`, `ready` and `done` all
validate references and compare digests: ready does not require a ruling
before a build exists, but must treat old rulings as stale, never clearance.
Check reports stale-only supplied rulings before done as advisory; at done
they block. A done record is checked against its recorded served SOURCE
certificate and its current title/brief digest, not today's moving SOURCE.

Threat model: these officina checks guard against stale, mismatched or
prose-only evidence. They do not authenticate a person or prevent a
repository writer fabricating attributed records, matching hashes or logs.
No attestation or tamper-resistant provenance is claimed. The censor and
Patron retain responsibility for the substance and attribution of evidence.

`opus.ui.rulings` checks present references in every state, and requires a
nonempty list with a current ruling at done. `done` refuses an absent list,
wrong actor/opus, empty or dead decision, or a list containing only wrong-tree
or too-early rulings before any write or event. A generic
human waiver does not satisfy this requirement: any Patron exception is
itself a recorded, scoped look-and-feel ruling. A new source tree requires
new served evidence and new Patron rulings; old decisions remain history.

### 3. An arc is a parent reference, not a new lifecycle

An arc is an ordinary `opera/W-*.md` record with `kind: arc`, its own title,
optional body, collegium, state and the existing lifecycle obligations.
No new id allocator, directory or lifecycle is needed. Membership is the
optional scalar `arc: W-123` on a non-arc opus; it must resolve to an arc
record in the same officina. Arcs themselves cannot name an arc or parent.
There are no roll-ups, inferred completion or nested arcs in this opus.

`parent: W-124` is required for `subtask`, forbidden for other kinds, and
must resolve to a non-arc, non-subtask opus in the same officina. This makes
subtasks one level deep, with no cycles or self-parenting. A subtask may omit
`arc` and inherit its parent's membership in the model; if it explicitly
sets `arc`, that reference must equal the parent's arc. If the parent has no
arc, the subtask cannot introduce one. No inherited value is written back.

`opus.arc` and `opus.parent` block malformed, dangling, wrong-kind, cross-
officina and conflicting references. Resolve validated ids against an
enumerated record map, never arbitrary paths. Hierarchy does not imply
`depends`, change WIP accounting or constrain parent/child completion order;
dependency scheduling remains W-068.

Physical containment applies to all W-096 reference readers: opus records,
parent/arc targets, spec briefs, UI input/censor/served logs and decisions.
Use existing safe-path helpers plus lstat and realpath checks before reading:
regular files only, no symlink leaf or intervening symlink directories, and
real paths contained under the selected officina and expected subdirectory
(`opera`, `briefs`, `ci`, `decisions`). Reject escaping, dangling or aliased
paths even when their ids are lexically valid. Enforce in check enumeration
and all affected writers/transition readers, not just after loading a record
map. Report `opus.reference` (block) for unsafe files, with the field-specific
rule as appropriate; unreadable required evidence fails closed. This bounds
W-096 reads; adapter snapshot/server delivery hardening remains the named
“Reject symlinked opus records before snapshot projection and detail delivery”
follow-on. This does not claim protection against concurrent hostile writers.

### 4. Start/end are optional actual dates, never guessed history

Canonical fields are `start` and `end`, each an optional scalar string in
this exact ISO-8601 UTC profile:
`^[0-9]{4}-(0[1-9]|1[0-2])-(0[1-9]|[12][0-9]|3[01])T([01][0-9]|2[0-3]):[0-5][0-9]:[0-5][0-9](\.[0-9]{3})?Z$`.
Years are 0001–9999; validate actual Gregorian month lengths and leap years
(divisible by 4, except centuries unless divisible by 400). Reject year 0000,
24:00, leap seconds, offsets including +00:00/-00:00, lowercase t/z, missing
seconds, fractional precision other than exactly three, and date-only values.
Absent milliseconds mean zero. Writers emit exactly three fractional digits.
Inspect the YAML scalar node's decoded string and match this regex before
calendar validation; reject explicit non-string tags, aliases and coercion
to Date objects. Quoted and plain string scalars are equally legal; quote
style is not enforced. Do not validate by permissive `Date` parsing or
normalization. Compare validated components/numeric instants for ordering.
The same profile governs new UI evidence and ruling timestamps. Validate
lifecycle `--now` under this profile before conversion or any mutation.
When both exist, end must be at or after start; end without start is valid
for an older active opus whose beginning was never recorded. `end` is valid
only in `done`; absence of either field is legal, including on old done
records. Rules: `opus.dates` and `opus.dates.order`.

Derive new dates from successful lifecycle transitions: `ready` records the
first start when absent, and `done` records end, using exactly the timestamp
emitted with that transition. Resuming a halt preserves start; a failed
review reopening done clears end and preserves start; a later done stamps
a new end. These are persisted transition facts so losing the local event
log does not lose dates. Refused commands change neither dates nor events.
Validate supplied existing dates before a transition could overwrite them.

Do not backfill from mtime, traditio, first observation, `item_appeared`, or
snapshot-derived event times (`workflow.time.derived`). Start/end are actuals,
not planned dates or deadlines; planned dates would be a separate decree.

### 5. Summary is title; description is the Markdown body

There is exactly one summary source: existing front-matter `title`, a
nonblank string containing no forbidden controls after YAML decoding. The
exact forbidden set is U+0000–U+001F (C0, including NUL, TAB, LF and CR),
U+007F–U+009F (DEL and C1), U+2028–U+2029, and these format-control ranges:
U+00AD, U+0600–U+0605, U+061C, U+06DD, U+070F, U+0890–U+0891, U+08E2,
U+180E, U+200B–U+200F, U+202A–U+202E, U+2060–U+2064, U+2066–U+206F,
U+FEFF, U+FFF9–U+FFFB, U+110BD, U+110CD, U+13430–U+1343F,
U+1BCA0–U+1BCA3, U+1D173–U+1D17A, U+E0001 and U+E0020–U+E007F.
This explicit set includes bidi controls and is frozen, not dependent on the
runtime Unicode property's version. Validate code points, including astral
ones, at both disk and writer boundaries. “One line” is a
logical field constraint, not a character limit or a prohibition on visual
wrapping. Long existing titles, including W-096's decree, remain intact.
`opus.title` blocks control-bearing/blank/nonstring titles; `newItem`, `runNew`
and `amend --title` reject them before writing.

Description is all authored Markdown below the front-matter delimiter. Empty
is legal; it is not derived from title or `spec`, and no `summary:` or
`description:` duplicate field is introduced. Existing body-preserving
mutation stays byte-for-byte. Do not alter W-087's bounded HTTP body reader,
its truncation marker, literal rendering, whitespace or summary/title layout.

### Blocking evidence and preservation rules owned by W-096

W-096 owns `opus.red_assertion` (block), implemented in the evidence rule
module. Scope it to W-096's seven numbered behaviours, in building,
verifying, review and done; do not retroactively reclassify other opera's
historical reds. Missing `ci/reds` is a failure, not an early-return exemption.
In addition to existing per-behaviour command/exit/identity checks, require a
completed Node TAP test report for exactly the selected behaviour, with at
least one failed test diagnostic whose `code` is `ERR_ASSERTION` and whose
test name starts `W-096 behaviour N:` for that log's N. Parse TAP structure,
including its plan and diagnostic blocks; quoted examples and echoed command
text are not tests. The focused test must use Node's test/assert reporting
and select N from argv, so one aggregate failure cannot count as seven reds.
Reject missing/zero-test plans, arbitrary nonzero output, skipped-only runs,
module-load errors, SyntaxError, command-not-found, unknown flags and sandbox
or Git permission failures even alongside an assertion. A failing assertion
must execute existing code, not assert module availability. These checks
judge recognizable test output, not maliciously fabricated output under the
threat model above. Do not rewrite old logs into the new format.

W-096 also owns `opus.records_unchanged` (block) in the evidence rule module,
delegating comparison to a shared helper in commands' `opus-model.ts` so
verify and check use one implementation without a commands-to-CLI import.
The immutable baseline is **the signing commit of this brief**: the commit
that first records the architect's passed spec gate for this revision and
its signed brief. After that commit exists, the authorized readiness writer
records its full 40-lowercase-hex object id once as `baseline_commit` on
`studio/opera/W-096.md`, before implementation begins. This draft neither
signs nor invents that future hash. `check` and `verify` learn the baseline
from that field, resolve the exact commit object and validate its W-096
spec-signing evidence and referenced brief. The first recorded value is
immutable: compare it with its first introduction in W-096's record history;
missing history or a changed pin is unverifiable. No rebase, merge, later
signature or integration-ref movement repins it; never use a current
merge-base or infer a baseline from a branch name.

The exact protected path set is the set at the baseline: all Git tree entries
matching `studio/opera/*.md` or `examples/sample-studio/opera/*.md` (direct
children only), minus `studio/opera/W-096.md`. Enumerate these paths from
that immutable tree, not a supplied checksum manifest or today's census.
Require regular files and compare their raw bytes and regular-file modes
against both HEAD and the working tree. Every protected record must remain
byte-identical; deletion, rename, symlink substitution or mode change fails.
Capture the full baseline object id and sorted protected path set in
command-produced validation output. The measured 101/7 table above is
historical context, never a required count.

Explicit exemptions are W-096's own record, whose authorized verification,
review and lifecycle/date bookkeeping must change normally, and new records
created by this opus's acceptance filings. Acceptance filings may create
new paths only; they cannot exempt or overwrite another baseline record.
New unrelated records, including records arriving through a rebase, are
outside the pinned set and do not alter it. All such records still undergo
ordinary model checks. No other baseline record is exempt.

Run these rules via check with repo context and W-096's verify/CI before
review/merge. The preservation rule activates on the W-096 implementation
branch even if W-096's record has not entered an active state; both rules
also apply when verify explicitly targets W-096. In that applicable context,
missing Git, baseline commit/history, repository identity or unreadable baseline is blocking
(“unverifiable”), not a pass. Unrelated branches/targets do not replay this
opus-specific pinned-baseline obligation. `verify` calls the same preservation
predicate before issuing success; no second implementation of the rule.
Rule regression rows live within behaviours 1 and 2 below, preserving seven
product behaviours. This unsigned draft claims no produced red evidence.
