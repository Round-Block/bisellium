`deriveNext`, spec rung, while `refs/heads/opus/<id>` is absent (`pre`):

- the spec is `specEvidence(f.work, …)`, not the trunk's. Part 1's strict guard on new logs is not applied here: a malformed log at or below the newest signature stays history, so signing again recovers (W-162, `W-162-b2` and `W-162-b4` pin it; applying the guard flipped both on the prototype); `performBranch` refuses a renamed, removed or rewritten committed log;
- a spec that has not passed gets `specOrder` in the main checkout (as the `tree` branch does today); without a reviewer, `dispatch` as today;
- without a reviewer `signedSpec` is bound here (`specEvidence(…, pre)`): a passing architect log counts only when its `# brief:` header names the current brief's blob (`briefs/<id>.md blob:<sha1>`, the pin the verdict writer has put on every spec verdict since W-162), so an edit after it, even one that keeps every section, orders the architect again. A log with no `# brief:` header was written before W-162 and stays unbound (`W-162-b3`'s past-ready record and `W-128 behaviour 7`'s fixture are such logs);
- a passed spec goes on to the `branch` rung; `next` names no `spec` perform before the branch.

Once `opus/<id>` exists master no longer carries a first spec, so the branch is read: with a reviewer `f.branch`, as part 1 does, unchanged; without one the committed `refs/heads/opus/<id>` (an unlistable worktree `ci/` stays the review rung's hold, which `W-167-b1` pins: reading the worktree instead flipped it on the prototype).

Limit: without a reviewer, `signedSpec` is not bound after the branch: a brief edit committed on `opus/<id>` leaves the spec passed, as today (master's rung reads the trunk's spec after the branch, so it never sees a branch edit at all). Binding it there flipped `W-166-b3`, whose brief gains a `Red order` line after `ready`, and it would leave no way forward: the architect's new signature is written in the worktree, which this read does not see until someone commits it. Re-judging an amended brief on the branch is what a configured spec reviewer does (W-206, part 1).

`performBranch`, after today's HEAD and master-tip checks: `mainChanges()` (failure or a `bad` path refuses); `paths` = the spec paths plus the record when it is plainly modified; `dirtyHold(repo, p => paths.includes(p))`, so any other tracked change refuses as today and no other untracked file is staged. With `paths` empty it cuts the branch at master as today. Otherwise it runs `git switch -c opus/<id>`, `git add` and `git commit -- <paths>` (subject `spec(<id>): signed`, the design magister's trailer), then switches back to master: the committed files leave the main checkout. A failed add or commit runs `rollback` (unstage what the index holds, switch back, drop the branch). A failed switch back holds with the recovery commands. Either way success is not reported. Then `git worktree add`. If that fails, a branch carrying the spec commit is kept and the hold names `git worktree add`; a bare cut is dropped by `update-ref -d`, and if that deletion fails the hold names the kept branch and `git branch -D opus/<id>`.

Every cleanup command's exit is checked, and no failure reports success (no `branch:` line). After a failed add or commit, the paths unstaged are the ones the index holds (`git diff --cached --name-only -z`), never the paths `git add` was given: a failed add can leave new files unstaged, and `restore --staged` refuses a path the index does not know. If the index cannot be read, the hold keeps HEAD on the branch and names `git reset -q`, `git switch master` and `git branch -D opus/<id>`. `rollback` (shared with `performDone`) checks its `update-ref -d`: a failed deletion is reported with the kept branch and `git branch -D <branch>`, never as a restored master. A failed unstage or switch back holds with its recovery commands, as it does today.

`gateDispatch`: before `opus/<id>` exists, a resumed order's handover is read only from the main checkout's record (`recordOf(f.work, f.id)`). An absent or unparsable record holds (`stale handover: … cannot be read`), as does an absent or unreadable `at`; the trunk's record is never a fallback, so a deleted or corrupt record cannot pass on an older committed handover. Once the branch exists, `f.branchRecord`, else the trunk's, as today.

Limit: before the branch, `next` reads whatever the main checkout has checked out. `performBranch` refuses unless HEAD is master at its tip, but a report on another branch judges that branch's files.

Limit: the direct `bisellium branch` verb is unchanged. It cuts at HEAD and carries no spec; the ladder's path is `next --perform --expect branch` (`scripts/opus-start.sh`).
