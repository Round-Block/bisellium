# W-038 — petitio: file a governance ask through the CLI

## Intent

A petitio is the only channel a sella has for a judgment call, and nothing
writes one. Two producers of petitiones exist — `draftRetro`
(`packages/cli/src/retro.ts:365-390`) and a `talk` reply's `PETITIO:` line
— and both are side effects of some other act. A sella that simply needs to
ask the Patron something has no command.

The consequence is already on disk. P-004, P-008 and P-009 were hand-written
front matter, which CLAUDE.md's "Never by hand" forbids for exactly this
class of file. P-009 shipped without `opened:` and tripped
`petitio.opened` on the next `check`. Nothing was malicious and nothing was
careless; the only available path was the forbidden one.

Governance artifacts are core product: every cascade produces at least one.

## Files owned

- `packages/commands/src/writes.ts` — `runPetitio`, `PETITIO_USAGE`
- `packages/commands/src/usage.ts` — the banner's `petitio` line (verbatim
  twin of `PETITIO_USAGE`; `usage.test.ts` pins the scanned-line count and
  asserts set membership — read that guard before touching either file)
- `packages/cli/src/main.ts` — dispatch
- `packages/cli/src/writes.test.ts` — behaviours (the cli-side test is what
  `npm test` runs; `packages/commands/src/writes.test.ts` does not exist)
- `docs/ADOPTION.md` — the command's section

Not owned: `packages/cli/src/retro.ts`. See Out of scope.

## Interfaces

```
usage: bisellium petitio --from <sella> [--to <id>] [--opus <id>] [--state <state>] [--studio <dir>] [--now <iso>] <text…>
```

The verb is the artifact's own name, matching `answer --petitio <id>`,
which already names the other end of the same exchange. It is **not**
`new --kind petitio`: `--kind` is the opus's own front-matter field
(`feature`/`task`/`hygiene`) and overloading it would make `new` allocate
into two id spaces off one flag.

Written file, `petitiones/P-nnn.md`:

```yaml
---
id: "P-nnn"
from: <sella>
to: patron
state: needs_you
opened: <now ISO>
opus: <id>        # only when --opus was given
---
<text>
```

- **Id allocation** reuses `nextId(petitionesDir, "P")` from `retro.ts`.
  Hoist it to a shared module rather than copying it — the two allocators
  must not drift, and W-035 is already deleting `retro.ts`'s off-by-one
  wrapper around it. Sequence below.
- **Defaults**: `--to` defaults to the manifest's patron, `--state` to
  `needs_you`. Both are the overwhelmingly common case and a flagless
  invocation must produce a valid file.
- **The path goes through `safeItemPath`** (engineering lex §2): a raw join
  fails review.

Refusals, each before anything is written, exit 2:

- `--from` absent, or naming neither a declared sella nor the patron
- `--to` naming neither a declared sella nor the patron
- `--state` not in `PETITIO_STATES`
- `state: needs_you` with a `--to` that is not the patron, or
  `state: awaiting_reply` with a `--from` that is not the patron — the two
  `petitio.direction` conditions, refused at the source instead of caught
  a `check` later
- `--opus` naming an opus that does not exist (`safeItemPath` +
  `existsSync`, the shape `runAnswer --opus` uses)
- empty text

The refusal list is not defensive programming: it is `check.ts:557-587`
read backwards. Every blocking `petitio.*` rule that a command can prevent,
this command prevents. A file this writes is green under `check` by
construction, and behaviour 7 asserts exactly that rather than restating
the rules a second time.

## Behaviours to test

1. `petitio --from <sella> "text"` writes `petitiones/P-nnn.md` with the
   next free id, `to: patron`, `state: needs_you`, an ISO `opened:`, and
   the text as the body
2. Two consecutive runs allocate consecutive ids (the `retro.ts` off-by-one
   does not get copied in)
3. `--opus <id>` records `opus:`; `--opus <unknown>` exits 2 and writes
   nothing
4. An undeclared `--from` exits 2 and writes nothing
5. `--state awaiting_reply` from a non-patron `--from` is refused (the
   `petitio.direction` condition, refused at the source)
6. `--state` outside `PETITIO_STATES` is refused
7. A file written by this command produces zero `petitio.*` findings from
   `checkStudio` — the acceptance stated as a test, in a temp officina

Reds via `bisellium red W-038 --behaviour <n>`, one per behaviour,
assertion-level, no two sharing an output (engineering lex §2,
`opus.red_evidence`). Every behaviour builds its own officina under
`$TMPDIR`; neither `studio/` nor `examples/sample-studio` is written.

## Acceptance

1. `npm test` green with the 7 new behaviours; `typecheck`, `lint`,
   `format:check` clean.
2. `bisellium petitio --from architect --studio studio "…"` on the real
   officina produces a file that `bisellium check studio --repo .` reports
   no new finding against.
3. `nextId` has exactly one definition in the tree.

## Out of scope

- **Decisions (`D-nnn`) and lessons (`L-nnn`).** Same gap, same shape, and
  D-016 in this batch had to be hand-written for want of it. One command at
  a time; open the sibling when a second decision is hand-written.
- **Editing or closing a petitio.** `answer` owns the reply side.
- **`--body <path>`.** Text on the command line covers every petitio on
  disk. Add it when a heredoc actually fails.
- **Rewriting `draftRetro` to call this command.** The retro writes inside
  a loop with its own numbering comment; converting it is a refactor with
  its own review, and `nextId` being shared already removes the drift risk
  that would motivate it.
