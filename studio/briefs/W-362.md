## Intent

W-310 put the guard (`bisellium hook-event guard`) in the repo's hooks and left four things to this opus. The guard is carried by the Patron's hand-made install, `~/.local/bin/bisellium` linked into `~/projects/bisellium-guard`; nothing checks that install or makes it again. The Patron's ruling of 2026-10-22 (W-310's Default 3) that the agent clone's source is closed to shell writes has no mechanism. And two command forms reach a hand ladder record write past the guard: `env -S 'bisellium merge …'` and `bash -O extglob scripts/record-review.sh …`.

After this opus:

1. **The guard reads both forms.** `env`'s split string (`-S`, `--split-string`, a short cluster ending in `S`, any prefix of the long name) is split into words and read as env's own arguments, as env does; a shell option that takes a value (`-o`, `-O`, `+o`, `+O`, a cluster holding `o` or `O`, `--init-file`, `--rcfile`) takes its operand, so the script file after it is read.
2. **The user-settings merge turns the sandbox on and closes the agent clone's source.** `scripts/agent-settings-merge.mjs` writes `sandbox.enabled: true` whatever the file held (an explicit `false` used to switch every deny off), and, given the agent clone's absolute path, adds `<clone>/packages`, `<clone>/apps`, `<clone>/adapters` and `<clone>/scripts` to `sandbox.filesystem.denyWrite`.
3. **One install step, judged before it changes anything.** `scripts/agent-workspace.sh guard` (the Patron, in their own terminal) judges AGENT_DIR, PATRON_DIR, GUARD_DIR, GUARD_BIN and PATH (`guard_inputs`, also run alone as `guard-check`) and changes nothing unless all hold; then it moves GUARD_DIR, a linked worktree of the Patron's clone, to origin/master, runs npm ci there, links GUARD_BIN to it, merges the user settings with that worktree's own merge script and probes the guard. It refuses to run from the agent clone's own copy. `setup` runs it; the script's verify step reports it.
4. **The merge rung does not half-update the main checkout.** With the deny on, a fast-forward of the main checkout that brings a file under `packages/` fails part-way (git unlinks and creates files one by one). The merge rung's existing Patron stop (`patronStop`, which already hands `.claude/` and `.github/` changes to the Patron) now also stops, before any change, when an incoming path lies in a directory this session cannot write, and prints the Patron's one command.

The deny binds the sandbox, which is the whole session's: the main thread and every helper. Helpers build in `.worktrees/<id>/`, outside it. The main thread's file tools stay the guard's (W-310's write rule).

Promise split-string: from the main thread, a Bash call whose `env` carries a split string of Input domain row 1's forms holding a hand ladder record write in a form W-310's rule recognises is refused with exit 2 and the ladder-runner line, a background `while`/`until` loop inside one is judged as W-310's loop rule judges it, and the same call from a subagent runs — limit: env's own escapes (`\_`, `\c`) and its `${VAR}` inside the string are read as plain text; `commandSeq`, `ladderWrite`, `ladderStep`, `cliArgv`, `unboundedLoop` and `guardRefusal` are reused unchanged (D-076 E).

Promise option-operand: a shell option of Input domain row 2's forms takes the next word, so the script file after it, or the `-c` script, is read and judged as W-310's rule judges a script file — limit: a cluster holding both `c` and `o`, and zsh's and dash's own option letters, are read as bash's; `scriptText`, `wordPath` and W-310's `cd` domain are reused unchanged (D-076 E).

Promise sandbox-on: `merge()` writes `sandbox.enabled: true` whatever the file held and keeps every other key it held — limit: Claude Code reading the setting is reused; `allowUnsandboxedCommands` and `excludedCommands` stay as the Patron set them (the Patron's file holds `allowUnsandboxedCommands: false` on 2026-10-23), so an excluded command, or an unsandboxed retry the Patron approves, runs outside the deny.

Promise source-deny: given the agent clone's absolute path, `merge()` adds its `packages`, `apps`, `adapters` and `scripts` folders to `sandbox.filesystem.denyWrite`, each once — limit: the deny binds the shell of every session the user settings load, helpers included; a build or test run in the main checkout that writes under those folders (`apps/web/dist`, `apps/web/test-results`) fails, and a `git pull` there fails part-way (git's behaviour); whether Claude Code's sandbox enforces a `denyWrite` path is Claude Code's, checked on this host by `agent-workspace.sh verify --inside`, not proved by a test here.

Promise installer-inputs: `agent-workspace.sh guard` changes nothing (no fetch, checkout, worktree, npm, link or settings write) unless `guard_inputs` accepts Input domain rows 5 and 6, and stops with "nothing was changed" when they fail or when the script runs from inside the agent clone; `agent-workspace.sh guard-check` prints the same lines and exits 1, or prints "guard inputs: ok" — limit: the inputs are judged once, before the steps, so a change made between the judgement and a step is not seen.

Promise install: with valid inputs, `guard` fetches origin's master into the Patron's clone, checks GUARD_DIR out detached at it (or adds it as a detached worktree), runs npm ci there, links GUARD_BIN to its `packages/cli/bin/bisellium.mjs`, stops unless the link leads into GUARD_DIR, merges the user settings with GUARD_DIR's own merge script and the real paths, and stops unless the probe (`hooks check --repo`) passes — limit: the Patron runs it unsandboxed; origin/master's content, git, npm ci's own effects and `guardProbe` (reused unchanged) are trusted; a step that fails stops it with the earlier steps done, and running it again repeats them.

Promise verify: `agent-workspace.sh verify` prints one `ok` or `FAIL` line each for the guard's installer inputs, GUARD_BIN leading into GUARD_DIR and the probe, and with `--inside` for the installed guard and the agent clone's four source folders being unwritable — limit: run inside a session it judges that session's PATH and that session's sandbox; its other lines are reused unchanged.

Promise merge-rung-deny: when the main checkout holds master and a path the reviewed merge commit brings lies under a directory this process cannot write (its nearest existing directory), the merge rung holds before any fetch into master or ref move, with "refusing: this session may not write incoming paths (…) in the main checkout (the sandbox's deny, W-362); the main checkout is untouched" and the Patron's one command, `git -C <repo> merge --ff-only <commit>`; an incoming Patron path keeps today's reason — limit: `fetchTrunk`'s other holds, the Patron-path rule and `listWorktrees` are reused unchanged; a write git still cannot make (a full disk) is today's "partly updated" hold; the pr rung's advice to run `git pull` in the main checkout is unchanged, and a session that follows it after a source merge fails part-way (Default 2).

Threat model: mistakes, not adversaries (D-045). The installer stops the Patron's ordinary variable mix-ups and a stale or misplaced link; the deny stops a session's habitual shell writes to source; the guard's forms stop a habit, not a hostile agent.
