# W-067 — the console can write

Spec of record, signed by the architect, 2026-09-24.

Carved out of W-065 at the producer's ruling, on the distribution of the
ui-lead's findings across three review passes: rev 1 had 8 of 9 blocking in
the screen, rev 2 had **4 of 6 in this write-path plumbing and 0 in the
screen**. What kept reopening W-065 was a different opus wearing its clothes.
This is that opus.

Binding inputs: `apps/server/src/http.ts`, `apps/web/src/api.ts`,
`packages/cli/src/serve.ts`, `apps/web/playwright.config.ts`,
`.github/workflows/ci.yml`, `docs/ADOPTION.md` §"Running serve",
`studio/decisions/D-023.md` (the PATRON-5 amendment, which decrees this
opus's shape), and W-016's behaviour 5 ("loopback alone never authorizes"),
which this opus must not break.

## Intent

**The served console has never been able to write, and nothing in the repo
notices.** W-024's Inbox answer button — a shipped, reviewed, `done` feature
— fails in a browser today. W-065 (the Patron's decree surface) is blocked on
it, W-064 (the Board) will be, and every Web II screen after them.

W-067 makes a browser write work, and proves it by **bringing W-024's answer
button back to life**. It builds no new screen. That is the point: the fix is
validated against a UI that already exists and already has a review behind
it, so the opus carries no new UI risk and its acceptance is unambiguous.

### Measured 2026-09-24, on this machine

Playwright against a live `bisellium serve` — temp copy of
`examples/sample-studio`, port 4488, the real generated token, the real built
`apps/web/dist`:

```
POST /api/greenlight 403
{"error":"cross-origin writes are refused"}
```

That was a **same-origin** `fetch` from the served console page, carrying a
**valid** `X-Bisellium-Token`. `checkWriteAuth` (`apps/server/src/http.ts:262`)
refuses any request carrying an `Origin` header at all:

```ts
if (req.headers["origin"] !== undefined) return 403;
```

and the Fetch spec requires browsers to send `Origin` on every non-GET/HEAD
request, same-origin included. There is no configuration that makes it pass.

Three defects, each verified in source, each fixed here:

1. **Every browser write is refused.** The rule above. W-016 bought a real
   property with it — "loopback alone never authorizes" — and that property
   is preserved below, but the rule as written also refuses the console.
2. **The browser cannot learn the token.** `apps/web/src/api.ts` reads it from
   `import.meta.env.VITE_BISELLIUM_TOKEN`, baked at build time, while `serve`
   generates a fresh random token per start (`packages/cli/src/serve.ts:117`)
   and prints it to stdout. The two never meet.
3. **A command refusal looks like a success.** `writeResponse`
   (`apps/server/src/http.ts:218`) sends **HTTP 200** with `ok:false` and a
   nonzero `exitCode` for *every* command failure. Any client branching on
   `res.ok` from `fetch` reads a refused write as a successful one.

And the reason none of this was caught: `apps/web/playwright.config.ts` runs
`vite dev` against the screens' own `?demo=1` fixtures and **never issues a
POST**. There is no test anywhere in the repo that exercises a write from a
browser.

### What D-023 already decreed

The PATRON-5 amendment settles the shape, so this brief implements rather
than proposes:

> the server's write auth accepts an `Origin` equal to its own origin and
> refuses every other; the write token `serve` prints is pasted once per
> session and held in `sessionStorage`. Injecting the token into the served
> page was considered and rejected (any local process that can `GET /` would
> obtain it — the property W-016 bought). W-016's "loopback alone never
> authorizes" survives intact.

## Interfaces

### The accepted-origin pair

`checkWriteAuth` currently refuses any `Origin`. The replacement, stated as a
closed set rather than a pattern:

**Accepted `Origin` values — exactly these two strings and no others:**

```
http://127.0.0.1:<boundPort>
http://localhost:<boundPort>
```

- `<boundPort>` is **`server.address().port`** — the port actually bound, not
  `opts.port`, which is `0` or `undefined` in exactly the cases that matter
  (including the tests, which bind `0` deliberately so the assertion cannot
  pass against a configured constant). The pair is computed once at startup
  and passed in; it is never recomputed per request.
- **Both hosts are accepted, deliberately.** The server binds `127.0.0.1`
  only (`http.ts:715`), but a browser's `Origin` follows the URL the page was
  loaded from, and `http://localhost:<port>/` reaches the same socket on
  every platform this runs on. Accepting only the canonical form would refuse
  the URL most operators type; both map to the same bound loopback socket, so
  accepting both admits nothing the other does not.
- **An absent `Origin` is still accepted** — that is `curl`, the CLI, and
  every existing server test. The token is what authorizes them, unchanged.

**Refused with 403:** the literal string `Origin: null` (sandboxed iframe,
`file://`, some redirect chains — it is a value, not an absence, and must not
be confused with one); the right host on the **wrong port**; `https://`
against either host; `http://[::1]:<port>`; any other host.

**No trust is derived from `Host`, `X-Forwarded-For`, `X-Forwarded-Host` or
any other request-supplied header.** Only `Origin`, compared against the two
strings computed from the bound socket.

**Reverse-proxy access is unsupported**, and `docs/ADOPTION.md` says so: a
proxy's `Origin` will not match, and the remedy is to reach `serve` directly,
never a header allowlist.

Order is unchanged: Origin (403), then token (401), then Content-Type (415).
**W-016 behaviour 5 survives intact** — the token is still required and still
the thing that authorizes; loopback alone still authorizes nothing.

### Token delivery

`serve` already prints the token to stdout (`serve.ts:120`). The served
console:

- reads `sessionStorage.getItem("bisellium.token")`, and **nothing else**.
  The `import.meta.env` fallback is removed: keeping it while claiming the
  token is not baked into the bundle is a contradiction, and the build-time
  path is precisely what D-023's amendment rejected.
- shows a one-field prompt when the key is absent **or when a write returns
  401**. The 401 is the trigger, not emptiness — a nonempty **stale** token
  must not suppress the prompt, which is the failure mode an emptiness-only
  check produces.
- **The prompt is screen-agnostic and mounts once, in `App.tsx`, above the
  routed screen.** It is not a member of any screen. `postWrite` returning
  `{ kind: "unauthorized" }` raises it from wherever the write was issued, so
  every later screen — W-065's Seats, W-064's Board — inherits a working 401
  path with no code of its own. An Inbox-local prompt would satisfy this
  opus's own behaviours while making W-065's mounted 401 case unbuildable;
  that is the seam, and this is which side it falls on.
- never writes the token to `localStorage` or to disk, and never puts it in a
  URL.

### The `ok:false` contract

`writeResponse` (`http.ts:218`) sends `{ ok, exitCode, output }` with status
**200** for every command outcome. A refused command — unknown petitio,
validation failure, nonzero exit of any kind — arrives as 200 with
`ok:false`. It is never a 4xx.

The client contract, consequently:

```ts
// res.ok from fetch means "the HTTP call completed", and nothing more.
export async function postWrite(path: string, body: unknown): Promise<WriteResult>;
export type WriteResult =
  | { kind: "ok"; output: string }
  | { kind: "refused"; exitCode: number; output: string }  // HTTP 200, ok:false
  | { kind: "unauthorized" }                               // 401 -> re-prompt
  | { kind: "error"; status?: number };                    // 400/415/network
```

`submitAnswer` moves onto `postWrite`. `"refused"` renders `output` to the
operator; `"unauthorized"` re-opens the token prompt; `"error"` renders a
generic failure. **No branch treats a 200 as success without reading `ok`.**

### The served-dist Playwright harness

`playwright.serve.config.ts` exists so later opera (W-065's mounted
interaction and layout suites, W-064's Board) inherit a working harness
instead of each building one. Its contract:

- `testDir: "./tests-serve"`; chromium only, matching the existing config.
- **No `webServer` block.** Each spec spawns
  `node --import tsx packages/cli/src/main.ts serve --studio <tmp> --port 0`,
  captures the token from stdout, and polls `GET /api/officina` until it
  answers 200 before navigating. A fixed sleep is not a readiness test and a
  `webServer` block cannot surface the token.
- **The studio is always a temp copy** (`cp -r examples/sample-studio <tmp>`).
  These specs write. Nothing ever points them at `studio/`.
- It runs against `apps/web/dist`, so it is also the repo's first real
  dist-freshness evidence: a stale bundle cannot satisfy it.

### CI

A `web-e2e` job in `.github/workflows/ci.yml`: `npm ci`, `rm -rf
apps/web/dist`, the web build, `npx playwright install --with-deps chromium`,
then `test:serve`. **Required** — not `continue-on-error`, and not merged
into the deliberately non-required `officina` job. An interaction guard that
runs only on the builder's machine is not a guard.

## Behaviours to test

Each is one test output, one recorded red, assertion-level (engineering lex
§2, `check: opus.red_evidence`). Numbers are the `--behaviour` argument and
the `ci/reds/W-067/NN.log` name.

1. **The auth ladder, with the origin tuple pinned.** Against a server
   started with `port: 0`, bound port `P`; every refusal also asserts that
   the target record is unchanged:
   - no `Origin` + valid token + `application/json` → **200**
   - `Origin: http://127.0.0.1:P` → **200**
   - `Origin: http://localhost:P` → **200**
   - `Origin: null` (the literal string) → **403**
   - `Origin: http://127.0.0.1:<P+1>` → **403**
   - `Origin: https://127.0.0.1:P` → **403**
   - `Origin: http://[::1]:P` → **403**
   - `Origin: https://evil.example` → **403**
   - a valid `Origin` + wrong token → **401**; + `text/plain` → **415**;
     + a body missing a required field → **400**
   - `Host: evil.example` with no `Origin` → **200** (no trust from `Host`);
     `X-Forwarded-Host: 127.0.0.1:P` with a foreign `Origin` → still **403**
   (`apps/server/test/server.test.ts`)
2. **Token delivery, mounted.** Against the built dist served by a real
   `serve`: with `sessionStorage` empty the console prompts; the entered
   token is used on the next write and **survives a reload without
   re-prompting**; seeding `sessionStorage` with a *wrong* token and
   attempting a write produces a 401 that **re-opens the prompt**, and the
   replacement then succeeds. And: `grep` of the built assets for the live
   token string finds nothing — the bundle carries no token.
   (`apps/web/tests-serve/auth.spec.ts`)
3. **A command refusal is not a success.** Server half: against a runner stub
   that exits 3, the route answers **HTTP 200** with `ok:false` and
   `exitCode: 3`. Client half: `postWrite` maps that to `kind: "refused"`
   carrying `output`, a 401 to `"unauthorized"`, a 415 and a 400 and a thrown
   network error to `"error"`, and only a 200 with `ok:true` to `"ok"`.
   (`apps/server/test/server.test.ts` + `apps/web/test/api.test.ts`)
4. **The interaction suite is gated by required CI.**
   `.github/workflows/ci.yml` declares a job that installs deps, builds the
   web app from a **removed** `dist`, provisions chromium with
   `playwright install --with-deps chromium`, and runs the served-dist
   config; the job carries no `continue-on-error` and is not the
   `officina` job; `apps/web/package.json` has `test:serve` pointing at
   `playwright.serve.config.ts`, and `test:e2e` still selects `./tests`.
   (`scripts/ci-workflow.test.mjs`)

Not behaviours, so no red: the `docs/ADOPTION.md` prose; the
`playwright.serve.config.ts` scaffolding itself (behaviours 2 and the
acceptance smoke exercise it).

## Out of scope

- **Any new screen.** W-065's Seats and W-064's Board both wait on this. The
  only UI touched here is the minimum inside W-024's Inbox to enter a token
  and show a failure.
- **Restyling the Inbox**, or moving it to the Web II visual language.
- **Fixing the identity gap.** `packages/cli/src/main.ts` stamps
  `BISELLIUM_ROLE=patron` for any CLI caller and authenticates nobody
  (`docs/research/w044-threat-model-sol.md`). This opus changes what the
  *browser* may do; it does not authenticate who is at the keyboard, and must
  not be read as doing so.
- **CSRF tokens, cookies, sessions, or any auth scheme beyond the shared
  token.** The token plus the origin pair is the whole boundary.
- **A cross-process lock over officina writes.** Out of scope here and in
  W-065; if the studio ever has two concurrent operators it is its own opus,
  covering all eight write commands rather than one.
- **Serving the console over anything but loopback.** No TLS, no bind
  address option, no proxy support.

## For Sol (red-team targets)

1. **The accepted-origin pair.** Two strings computed from the bound port.
   What produces a matching `Origin` that is *not* the console — a browser
   extension's content script, a second local tool that binds the port after
   `serve` exits while a tab is still open, a page served from
   `http://localhost:P` by something other than `serve`? Is accepting both
   hosts materially weaker than accepting only the canonical one?
2. **`Origin: null` is one of many.** The refusal list was built from the
   cases I could name. What other `Origin` values does a browser actually
   send that the whitelist neither accepts nor was tested against — and does
   a whitelist make that question moot, or is there a comparison bug (case,
   trailing slash, default port elision — does a browser ever send
   `http://localhost` with no `:80`, and could `serve` ever bind 80)?
3. **The token in `sessionStorage`.** A page that can read it is already
   same-origin, so the attack is stored-XSS in the console. W-065's brief
   pins literalness at its new render sites; this opus adds a token input and
   an error line to the **Inbox**, which renders petitio subjects and bodies
   and now server `output`. Is there a sink there — a `title`, a `style`, an
   `href` built from officina content?
4. **Behaviour 3's enumeration.** Four `WriteResult` kinds. Is there a fifth
   real outcome — a 200 with malformed JSON, a 200 with `ok` absent entirely,
   a 5xx from `serverError`, a response that never arrives? Which of those
   does the client currently mis-file as success?
5. **The answer smoke is the acceptance and it is the least deterministic
   thing in the repo.** It spawns a server, scrapes a token from stdout,
   polls for readiness, and drives a browser. If it flakes in required CI the
   branch is blocked rather than the coverage merely lost. Where is the
   readiness probe wrong, and what is the honest fallback when chromium
   provisioning fails on a runner?
6. **This opus claims W-016 behaviour 5 survives.** Verify that directly
   rather than taking the claim: is there any request the new rule admits
   that the old one refused, other than a same-origin browser write with a
   valid token?
