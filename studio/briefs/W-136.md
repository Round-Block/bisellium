# W-136 — board liveness: serve broadcasts every appended event, follows the loop logs and agent transcripts, and shows a pulse per seat and an activity feed per card — telemetry only

Draft, backlog only (Patron, 2026-10-04). Not specified; no build is
authorised. The pulse row and activity feed are UI, so they need the
Patron's UI/UX ruling at spec time. Linked: W-135 (containment setup
becomes init/adopt), which takes over writing the registry in step 1.

## Intent

Patron ruling: the Board always shows current state, on any project, with no
flags and no manual refresh.

Problem: the Board cannot show who is working or what has just changed.

- `serve` needs `--studio` and shows whatever checkout it was pointed at.
  That is often a stale or wrong copy, not the agent clone where work
  actually happens.
- `serve` broadcasts only the events it appends in-process. Events appended
  by hooks or `bisellium emit` from other processes are never re-read, so
  they never reach SSE clients (`store.ts:517`, `http.ts:551`).
- The restart loop's stream-json logs (`.cascade-loop/logs/*.log`) and the
  agent transcripts (Claude under `~/.claude/projects/<clone-key>/`, Codex
  under `~/.codex/sessions/`) are written live and never read.
- Receipts carry start, end and pid, and `next` already has PID-birth plus
  output-mtime health logic, but the Board ignores both.

Scope, in this order:

1. **Live state on any project (Patron, 2026-10-04).**
   - **Registry.** `scripts/agent-workspace.sh setup` (later W-135's
     init/adopt) records each project in a per-machine config that is
     owner-only and outside every repo. Each entry holds a name, owner
     folder, agent clone and studio path, and never a token. Agents cannot
     write it; the sandbox denies it, the same way it denies the owner
     folder.
   - **Default target.** `serve` with no `--studio` reads the registry and
     serves that project's agent-clone studio, which is the live state.
     `serve <project>` picks a project by name. An unregistered project is
     refused with a clear message that says how to register it.
   - **Origin too.** `serve` fetches origin about once a minute, so merged
     work shows even when the agent clone is missing or stale. Branch
     records come from both the clone's `opus/*` and `origin/opus/*`.
   - **Board actions.** Actions taken on the Board (greenlight, answer and
     the rest) keep working against the served studio. The spec must state
     where those writes land (the agent clone's working tree) and who
     commits them. They are uncommitted until then, so the Board shows them
     as pending, never as merged.
   - **No hard-coding.** Nothing names bisellium or this machine: no
     `/home/edckt`, no `~/agents/bisellium`, no "WSL only". Fix
     `packages/cli/src/instructions.template.md:28-29` in the same pass, and
     sweep the rest of the source for the same.
2. **External appends broadcast.** `serve` broadcasts events appended by
   hooks or `emit`, not only its own. Step 1's 5-second acceptance likely
   depends on this re-read; the spec decides whether 1 and 2 ship together.
3. **Activity and pulse.** `serve` follows `.cascade-loop/logs` and the
   agent transcripts, and turns them into one small allowlisted activity
   event (session, sella, opus, kind, repo-relative target, outcome,
   timestamp). The Board shows a pulse row per seat (moving / waiting /
   stalled / lost, plus last-seen age) and an activity feed on each card.

Constraints to design in:

- Telemetry only, never gate evidence.
- Never persist raw tool arguments, commands or environment: allowlist the
  fields and discard everything else by default.
- Never render transcript text as markup or instructions: escape it, cap it
  or omit it.
- Coalesce heartbeats and cap volume per session.
- Paths come from the registry, not constants. Each harness's transcript
  parser fails soft when the format changes.
- The registry holds paths only. A token, or a path into a credential
  store, is refused at write time.

Background: the Patron's brainstorm notes (2026-10-04), approaches 1 + 2
behind one normalizer. Cooperative hooks are enrichment for later.

## Files owned

To be set at spec time. Starts from `apps/server/src/store.ts`,
`apps/server/src/http.ts`, the `serve` command, `apps/web/src/lib/board.ts`,
`scripts/agent-workspace.sh` and `packages/cli/src/instructions.template.md`.

## Interfaces

To be set at spec time: the registry's location and schema, `serve [project]`,
the fetch cadence, and how branch records merge the clone's refs with
origin's.

## Behaviours to test

To be set at spec time. Anchors:

- `serve` with no flags serves the registered agent-clone studio, and it
  refuses an unregistered project by name.
- An event appended to the event log by a separate process reaches a
  connected SSE client without a restart.
- A record that exists only on `origin/opus/*` appears after a fetch.
- No source file names this machine's user, home paths or this repo's clone
  (a check or test row, so the regression cannot return).

## Acceptance

Step 1 (Patron):

- Start `serve` with no flags from any folder. The Board matches the agent
  clone within 5 s and `origin/master` within about 60 s, with no manual
  refresh.
- Repeat for a second registered test project.

The other steps are to be set at spec time.

## Out of scope

- Using any activity event as gate, review or receipt evidence.
- Cooperative hooks or verbs that report "waiting for review" and similar
  (later enrichment; hooks run unsandboxed and must never call clone code).
- Displaying raw transcript text.
- Moving setup into init/adopt (W-135). This opus only makes
  `agent-workspace.sh setup` write the registry.
