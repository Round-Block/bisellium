## Intent

The main thread (the orchestrator session) still runs heavy work and writes records by hand. A gate run (`bisellium ci --opus`, `bisellium verify`) or a Codex pass (`codex exec`) from the main thread holds the session for twenty minutes and lands a failure with the one session that must not diagnose it (Patron 2026-10-22, D-039 high). Shell writes into `studio/ci/`, `studio/opera/`, the decisions and the handoff bypass the verbs that own them (W-290's class, seen again on 10-22), and the dossier (`docs/design/dossier/`) is written by hand from the main thread. W-310's guard refuses only the ladder verbs and the file tools' source writes; nothing else refuses these.

**The design.** Two layers, as the provider parity report (10-24) recommends:

1. **The CLI half (behaviour 1).** `bisellium verify <id>` and `bisellium ci --opus <id>` refuse (exit 2) unless they run inside a `bisellium run` session, read from `BISELLIUM_SESSION`, which `bisellium run` sets for the command it runs (`run.ts`, `builder-run.ts`, the host runner's builder cell). So a heavy run from any harness's main thread (Claude Code, Codex, a shell) is refused by the verb itself. A dispatched agent runs it as `bisellium run --sella <seat> --no-worktree --studio studio -- npm run -s bisellium -- ci --opus <id> --studio studio --repo .` from the opus worktree, which the refusal names; `npm run` runs at the package root, so the paths read as before. The seat is not a builder template: `run` refuses `--no-worktree` to a builder template, whose only route (`run --sella builder --opus <id>`) runs in a disposable confined clone that keeps no gate log and may not commit under `studio/`, so the gate run whose logs reach the opus branch is the producer's, run by the ladder-runner (Default 3). A heavy run admitted inside a session then leaves it (behaviour 5): `main.ts` drops the session's three variables (`BISELLIUM_SELLA`, `BISELLIUM_STUDIO`, `BISELLIUM_SESSION`) before `verify` or `ci --opus` runs, so its steps and gates, the suite among them, run as they run outside any session; on 11-03 the suite's nested done verb in `close.test.ts` read the run's seat `producer`, undeclared in its fixture, and failed. The host runner (`scripts/run-builder-host.mjs`), whose gate cell runs `ci --opus` for certify and a builder run with a cleared environment, now gives that cell its run's session. `verify` with no argument keeps its usage line and `ci` without `--opus` (the CI workflow's steps) runs.
2. **The hook half (behaviours 2 to 4).** For Claude Code, `bisellium hook-event guard` refuses from the main thread, before the run starts and with the route named: a heavy run (`codex exec`, `verify`, `ci --opus`, directly, as the command `bisellium run` runs, in a `-c` script or in a script file, read as W-310's ladder walk reads them); a Write, Edit or NotebookEdit under `docs/design/dossier/`; and a shell write (a redirection, `tee`, `cp`, `mv`, `install`, `sed -i`) into `studio/ci/`, `studio/opera/`, `studio/decisions/`, `docs/SESSION-HANDOFF.md` or `docs/design/dossier/`. The shell-write rule is an early warning: the verbs own the records and the check rules read them; a lexical rule cannot see every write.

**How the main thread is told apart, and the limits of that signal.** The guard reads Claude Code's hook input: a call with no `agent_id` is the main thread (W-310, D-073 B); any dispatched subagent carries one, so a builder, an architect and a ladder-runner (`agent_type` ladder-runner) all pass these rules alike, and a clerk is not singled out here. `bisellium run` is not seen by the hook as a session: the hook sees only command text, so it reads `bisellium run … -- <command>` and judges the command after `--`; from the main thread, wrapping a heavy run in `bisellium run` is still refused. The CLI cannot see Claude Code's `agent_id` (the main thread and its subagents share one environment), so its one signal is `BISELLIUM_SESSION`: a dispatched Claude subagent runs the heavy verbs through `bisellium run` too, and any process that sets the variable itself passes. That is a claim, not an attestation (D-045: mistakes, not adversaries); the hook is the second line for Claude Code only, and a Codex or shell main thread meets the CLI refusal alone.

**The heredoc misread (11-03).** W-310's ladder walk read a heredoc's body as commands, so a Python heredoc holding `Limits: popd` and a later `scripts/x.sh` was refused as a script run in an unknown directory. This opus moves the walk into one `walk` shared by the three Bash rules, reading each line through W-496's `shellCode` without its comments and heredoc bodies (its new `bare` text, quotes kept), so that heredoc runs; a heredoc fed to a shell (`bash <<EOF`) is no longer read by any of the three rules, a stated limit.

Threat model: mistakes, not adversaries (D-045). The guard stays deny-only and fail-open (W-310): an unreadable input, an unknown event, a throw or a timeout lets the call run.
