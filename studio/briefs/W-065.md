## Intent

### Dependency: W-065 builds on W-067 and does not re-specify it

**W-065 must not start before W-067 has landed on the trunk.** The opus
record carries no `depends` field, so the dependency is stated here and is
binding as spec:

> W-065 requires W-067 (*the console can write*) to be `done` and merged
> first. W-067 delivers the accepted-origin rule in `checkWriteAuth`, the
> pasted-token delivery in `apps/web/src/api.ts`, the `postWrite`/`WriteResult`
> contract that distinguishes an HTTP 200 carrying `ok:false` from a success,
> the `playwright.serve.config.ts` served-dist harness, and the required
> `web-e2e` CI job. W-065 **consumes all five and re-specifies none of them.**
> A builder who finds any of the five absent has been dispatched too early
> and should stop, not rebuild it here.

Concretely, that means:

- `submitDelegate` is written on **W-067's `postWrite`**, and inherits its
  four `WriteResult` kinds. W-065 adds no auth handling and no token UI: the
  prompt is W-067's, screen-agnostic, mounted in `App.tsx`.
- W-065's mounted behaviours (14, 15) are new spec files under W-067's
  existing `tests-serve/` directory and config. W-065 does not touch
  `playwright.serve.config.ts`, `.github/workflows/ci.yml`, or
  `apps/web/package.json`'s scripts.
- Everything W-065 asserts about a browser write assumes the origin rule
  already holds. It is not re-asserted here; W-067 behaviour 1 owns it.

If the producer ever runs the two in parallel, the seam is `postWrite`'s
signature and `tests-serve/`'s existence. Both are W-067's to define.

### The two decrees

Two decrees, made clickable, and nothing else:

- **(a) which model holds which seat** — `sellae[].model` in the manifest.
- **(b) which task type is delegated to which tier** — `munera` and `tiers`,
  the two keys D-023 adds to the manifest.

W-041's lesson binds: the screen renders **from** those records, never from a
hand-maintained copy.

### The honest claim, stated up front

Nothing dispatches on either value. `sellae[].model` is read by **no dispatch
path** (measured; W-046's brief establishes the same). `munera` will be read
by nothing on the day this lands, and W-046 alone does not implement task
routing. W-065 delivers **"the decree is recorded, attributed and rendered"**
— D-023's own words — not "the decree takes effect".

This is an acceptance criterion, not a hedge. The screen carries the
ui-lead's ruled wording (behaviour 12) and the brief fails review if it does
not.

### Why W-067 exists (the discovery, kept as provenance)

This opus's revision 1 measured, with Playwright against a live `bisellium
serve`, that a **same-origin** `fetch` POST from the served console carrying
a **valid** token is refused `403 cross-origin writes are refused` — so no
browser write in this repo has ever worked, W-024's Inbox answer button
included. Two more defects followed from the same probe: the browser cannot
learn the token, and a refused command arrives as HTTP 200 with `ok:false`.

Those three, plus the missing browser CI gate, are **W-067**. The full
measurement, the fix, and the acceptance (W-024's answer button coming back
to life) live in `studio/briefs/W-067.md`. Nothing here restates them; they
are recorded above as this opus's dependency.

**The `Manifest` type's owner is `adapters/native/src/index.ts:49`** — not
`packages/schema`. It has neither new key.

**The manifest can be edited without destroying it, within limits.** The
`yaml` package is already a dependency of `packages/cli` and
`adapters/native`. Probed against the real `studio/bisellium.yml`:

- `toString()` with defaults re-wraps every flow map (`lineWidth: 80`).
  Unusable.
- `toString({ lineWidth: 0 })` changes exactly the target line, and comments
  including the 5-line D-015 block survive byte-for-byte — **but** it also
  normalizes `source_excludes: [examples/]` → `[ examples/ ]`.
- `flowCollectionPadding: false` fixes that and breaks every flow map
  instead. Worse.

The ui-lead's independent probes found four more limits, which I accept as
the real boundary of the technique: an unrelated `other: [x,y] # inline`
normalizes the same way; **CRLF input becomes LF throughout**; a node reached
through a **YAML alias throws** during `setIn`; a **multi-document file
throws** during serialization. A leading-`*`-and-colon model value is
correctly quoted and reparses as a string.

Consequence: `{ lineWidth: 0 }` does **not** establish preservation in
general. The command declares its supported forms and refuses everything else
without writing. See *Interfaces*.

**Test harness for `apps/web`, honestly.** UI coverage is thinner than CLI
coverage:

- In `npm test`: pure modules under `apps/web/src/lib/*.test.ts` (behaviour

### A narrowed claim: what `--from` actually protects

The ui-lead is right that `--from` is a **precondition check**, not an atomic
compare-and-set: console reads A, CLI writes B, console writes its A-derived
document and B is gone. The brief now says so plainly rather than implying
mutual exclusion.

What is **not** built, and why: a cross-process lock over `bisellium.yml`.
Every officina write in this repo races identically today — `greenlight`,
`answer`, `budget`, `handoff` all read-modify-write with no lock, and
`withWriteLock` covers exactly one server process. Introducing a lock for
this one command would be a new concurrency primitive for a single-operator
local tool, protecting one write out of eight. `ponytail:` precondition
check only; a shared lockfile across CLI and server belongs in its own opus
covering **all** officina writes, if the studio ever has two concurrent
operators.

What `--from` **does** deliver, and all it claims: it closes the
stale-**draft** window the console itself creates — the gap between the
Patron reading a value on screen and clicking Confirm, which can be minutes.
The residual is the read→write window inside one `runDelegate` call.

Consequently `runDelegate` performs **exactly one** read of the manifest.
The document it validates is the document it mutates and the bytes it rolls
back to — no second snapshot, which is the defect the ui-lead flagged in the
rollback path.

### A stated ceiling: rollback is best-effort, not atomicity

`greenlight`'s pattern swallows restore errors (`writes.ts:818`). Copied
verbatim, so does `delegate`. The honest statement, which replaces revision
2's "no change without attribution":

> The timeline line, the event and the manifest write land together or the
> manifest is restored from the pre-read copy. If the **restore itself**
> fails, the manifest may be left changed or partially written and an
> already-emitted event remains. That case is reported distinctly — a
> different message and exit code from the original failure — and is a
> stated limit, not an atomicity guarantee.

Behaviour 7 tests both the ordinary rollback and the restore-failure path.

## Interfaces

### `packages/commands/src/delegate.ts`

```ts
export function runDelegate(args: string[]): { exitCode: number };
```

```
usage: bisellium delegate --sella <id> --model <model> [--from <current>] [--studio <dir>] [--now <iso>]
       bisellium delegate --munus <id> --tier <tier>   [--from <current>] [--studio <dir>] [--now <iso>]
```

**Supported manifest forms.** Anything not in this list is refused with a
message and exit 2, **before any write**. The predicate is a whitelist, not a
blacklist — an unrecognised construct refuses rather than proceeds.

Accepted: a single YAML document with no parse errors, whose `sellae`,
`tiers` and `munera` are sequences of maps in either flow or block style.
Measured as working: block maps, `!!str` tags, an empty `munera:` (parses as
`null` — treated as absent, not as an error).

Refused, each with its own message:

- **any anchor or alias anywhere in the document.** Not "an alias on the path
  to the target" — that was revision 2's rule and it is insufficient. Probed
  here: a manifest with `- &sa { id: builder-a, … }` in `sellae` and
  `backup: *sa` elsewhere passes the path restriction, and
  `setIn(["sellae",0,"model"], …)` then changes **both** semantic locations
  while the alias site shows no textual diff. One `visit()` pass counting
  `node.anchor` and `isAlias(node)` detects both in a single traversal; a
  nonzero count refuses. A manifest with shared nodes cannot be edited
  field-by-field without collateral damage, so it is not edited at all.
- **more than one document** (`---`-separated) — throws on serialize.
- **any parse error** (`doc.errors.length > 0`), which includes
  `DUPLICATE_KEY`.
- **a merge key (`<<`)** — default parsing treats it as an ordinary key
  rather than resolved inheritance, so what is written back would not mean
  what was read.

Line endings: if the source contains `\r\n`, the output is converted back to
`\r\n` after serialization. The library normalizes to `\n`, and silently
rewriting every line of a CRLF manifest is not acceptable.

**Flow-collection normalization, and why the smoke's "one line" was false.**
`toString({ lineWidth: 0 })` pads flow *sequences*:
`source_excludes: [examples/]` → `[ examples/ ]`. Revision 2's attended smoke
claimed a one-line diff; measured, the first write produces two. Rather than
document the lie, **this opus normalizes both manifests once**: `studio/bisellium.yml`
and `examples/sample-studio/bisellium.yml` are already being edited to add
`tiers` and `munera`, so they are written in the serializer's own output form
in the same change. Every subsequent write then really does diff one line,
and behaviour 4's live-manifest assertion holds against the tree as shipped.

Order of operations, **reusing `greenlight`'s existing discipline verbatim**
(`packages/commands/src/writes.ts:785-825`) — this is ui-lead finding 6's
remedy and it is already in the house:

1. Parse args. Neither shape, both, or a missing partner flag → usage, exit 2.
2. Resolve `<studio>` through the shared containment helper (lex §2,
   `check: path.escapes.officina`). No raw `join`.
3. **Read the manifest exactly once** — `const before = readFileSync(path)`,
   then `parseDocument(before)`. Every later step uses that one read: the
   document validated is the document mutated is the bytes restored. No
   second snapshot (ui-lead pass 2, finding 3).
4. Validate the supported forms above; resolve the target. An unknown
   sella / munus / tier → message, exit 2, nothing written.
5. **Precondition check.** When `--from` is given and the current value
   differs, exit 3 naming both values and write nothing. This closes the
   stale-**draft** window, not a concurrent-writer race — see *A narrowed
   claim*. The console always sends it.
6. Inside one `try`: write the manifest; emit `workflow.actor_assigned` (the
   `--sella` shape only); append **one** line to `timeline/patron.jsonl` via
   the **existing** `appendPatronTimeline` (export it; do not copy it),
   carrying `action`, the target, `from` and `to`. On any throw, restore
   `before` and exit 2 — and if the **restore** throws, exit 4 with its own
   message naming the manifest path as possibly inconsistent (*A stated
   ceiling*).
7. Exit 0.

The `--munus` shape emits no event: it is manifest configuration, not an item
lifecycle transition (D-023 §"What this changes"), and `/api/officina`
re-reads the manifest on every call.

**No new `workflow.*` attribute name is added.** If the builder concludes one
is needed, that is a stop-and-ask (CLAUDE.md, "Never by hand").

`main.ts` does **not** force `BISELLIUM_ROLE=patron` for `delegate`. D-023 §3
decrees that both the Patron and the producer may write the mapping and that
every write records the **acting** role. Forcing it would launder the
producer's writes into the Patron's name — the precise contradiction ui-lead
finding 4 caught in revision 1.
