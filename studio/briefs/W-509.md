## Intent

Only `next --perform` pushes and opens PRs, and only for an opus `next` recognises: `performDone` carries its own record, the handoff and the dossier pages, and `next` refuses an opus not on master. So a new opus record with its Queue line, a `kind: ui` master verify's logs (W-451 is blocked on this today), a handoff refresh, a queue edit and a decision can land only by a raw `git push` and `gh pr create`, which the Patron denied on 2026-11-05. After this opus each lands by one verb: `bisellium land <path>...`.

**Decided: the verb takes paths, not a branch.** The verbs that write records (`new`, `verify`, a clerk's edit) leave them uncommitted in the main checkout, so what is to land is a list of files. A verb taking a committed branch would keep the raw `git commit` and the throwaway records worktrees (about thirty of them under `.worktrees/`) that this opus exists to end. D-181's later verbs (`decide`, `rank`) can call the same code with the paths they wrote.

**Decided: one landing helper.** `performLanding` in `next.ts` is exported, its first parameter narrowed from `Facts` to the two fields it reads, and `land` calls it, so the push, the PR, the merge gate, the trunk fetch and the cleanup are the done perform's own (`landHead`, `mergeGate`, `cleanup`). `Ctx` gains two optional fields, read only when set, so `next`'s callers do not change: `own`, the paths the head carries, and `beforeMerge`, read once before the gate.

**Decided: a temporary index, from the main checkout on master.** The commit is cut with `GIT_INDEX_FILE` pointing at a temporary file (`read-tree HEAD`, `update-index --add --remove -- <paths>`, `write-tree`, `commit-tree -p HEAD`). The checkout's branch, real index and working tree are not touched, so other work stays. HEAD is the parent, not origin's master: the edit was made on HEAD's copy, and a parent on origin's master would silently undo whatever master changed since; on HEAD, GitHub's own merge shows that as a conflict. A linked worktree is refused, as `next` refuses one, because `landed` can only move master where master is checked out.

**Decided: the head is named from its contents.** `records/land-<first 12 hex of the sha256 of the changed paths and their tree entries>`. There is no resume flag: the same paths with the same contents are the same head, and `landHead` reuses its PR, so the same command run again resumes after a failed push, a timeout or the Patron's approval, on a moved master too.

**Decided: never lose a tracked edit.** The trunk fetch refuses any dirty checkout today, which would end every landing with other work present at `MERGED_NOT_FETCHED`. With `own` set, `fetchTrunk` holds only on a dirty path the merge would write and is not the head's own, staging nothing. Then `settleOwn` judges every own path before staging any: no merge or cherry-pick may be unfinished and no entry unmerged, which git's fast-forward refuses; the merge commit's entry must be absent or a regular file; the working copy must hold its content; and the index entry must be HEAD's or the merge commit's, on mode and blob. If so it writes the merge commit's own entries to the index, and `git merge --ff-only` passes with the index already at its target. It does not write the working tree. Every other hold leaves the edit where it was and says so; git's own fast-forward checks the same again. A caller with no `own` is unchanged.

**Decided: a mode is the merge commit's, never the copy's (revision 2).** The rule is one line: the index takes the merge commit's entry by mode and blob (`update-index -z --index-info`), and the working copy is judged on kind and content. Staging from the working copy is what both reviews found: `update-index --add` takes the mode from the copy's bit, or from the old index entry when `core.fileMode` is false, so the index could differ from the merge commit after the content was staged, and the fast-forward then refused. Written from the commit, the index cannot differ, under either setting, so no mode case needs a hold. A hold on a mode difference was the other option and is worse: a merge that changes a mode would stop every rerun of the same command, with a mode change this verb carried among them. So a mode on a staged entry still holds (it may be someone's work, and overwriting it was review 1's finding), and a mode on the copy is left alone and shown by `git status`.

**Decided: `check` runs on exactly the tree being landed.** In a throwaway worktree on a throwaway branch at the new commit, so unrelated work in the checkout neither blocks nor excuses it. A branch, as CI attaches its event commit to one: `realcheck.out` and row b3 show why (`opus.records_unchanged` blocks on a detached HEAD). Master holds 0 blocking findings and the `officina` check is required, so no baseline is compared: any blocking finding refuses with nothing pushed and prints up to ten. It runs only while the head has no PR.

**Decided: the allowlist is narrower than `recordOnly`.** `recordOnly` takes all of `studio/`, which includes the rules. `land` takes `recordOnly`'s paths less everything but `<studio>/opera/`, `<studio>/ci/`, `<studio>/decisions/`, `<studio>/acta/` and `<studio>/queue.yml`. Those, the handoff and the dossier pages are what the last 150 records commits touched, less the rules. Left out: `leges/`, `prompts/`, `bisellium.yml` (code and rules keep real PRs, D-181 line 6); `briefs/` (a brief lands on its opus's branch); `milestones.yml` (one touch in 150, and a plan, not a record); `lessons/`, `petitiones/`, `aerarium/` (no touch in 150; a later opus adds a line when a verb needs it). `performLanding`'s own `recordOnly` screen still runs after it.

**Way past (D-181 line 8).** Each refusal names one. A path outside the list: a real PR through an opus. A blocking finding: fix it, or `--past-check "<reason>"`, which rides the commit and the PR; it skips only this local check, and CI's `officina` check still judges the merge. Off master: the `git switch` command. A linked worktree: run it from the main checkout. A head that gained a commit outside the list: the `git branch -D` command.

**Where D-181 line 6 meets code-owner review.** D-181 line 6 says records and settings land by verb with no review from the Patron. `.github/CODEOWNERS` lists `/studio/decisions/`, and D-181 says it makes no rule edit, so a decision today needs the Patron's review on GitHub. This opus does not choose between them: `land` carries a decision, opens the PR, requests their review through W-418's `reviewNotice`, prints `state=PATRON_REVIEW` and a plain `patron:` line, exits 1 and requests no merge. It merges on a rerun once GitHub reads the PR `APPROVED`. It does nothing to get round the rule. Every other path it carries lands with no review from the Patron. Whether decisions stay code-owned is the Patron's call, Defaults 1, and only they can edit that file.

**Decided: a stuck queue entry is reported, not repaired.** The wait is `mergeGate`'s (20 s, 60 polls, flags as `next` takes them). When it ends at `state=QUEUE_TIMEOUT`, `land` reads the PR's queue entry and prints `queue-entry: PR #<n> <state> since <when>, position <p>, checks <rollup>`. An entry `AWAITING_CHECKS` whose merge commit's checks read `SUCCESS` also prints `stuck:` and its way past, Remove from queue on the PR's page, then the same command, which adds it again. That is the #1056 shape of 2026-11-05: 100 minutes with every required check passed, freed by removal and re-adding. The two new reads were run against the real API on #1056 (`graphql-probe.out`): `mergeQueueEntry` is `null` on a merged PR, and `reviewDecision` is an empty string with no review. Removing it by itself would need a new mutation with a real effect on the queue; that is a later call if stuck entries recur.

## Interfaces

The prototype is twelve commits on master 63a671dc (`prototype.mbox`, `series.out`): per behaviour `test(W-509): row b<k>, red`, then `feat(W-509): behaviour <k>`. `apply-src.py` and `apply-test.py` render each stage from `tpl/` and exact-once replacements.

1. **The verb.** `bisellium land <path>... --title <text> --sella <id> [--body-file <path>] [--past-check <reason>] [--poll-ms <n>] [--max-polls <n>] [--studio <dir>] [--repo <dir>] [--now <iso>]`. Paths are relative to the repository's top. `--repo` defaults to `.`, `--studio` to `<repo>/studio`, as `next`. `--title` is the commit's subject and the PR's title; `--body-file`, on `next`'s rule (a regular file of at most 64 KiB under the repository or the temp folder), the body; the trailer is `Co-Authored-By: <sella> (bisellium land) <noreply@anthropic.com>`. `--sella` is required because the repository's commit rule names the sella that wrote a commit, and it must be in the manifest. `--now` is `check`'s clock. Exit 0 once the records are on the local master, 1 at a refusal or a hold (a wait on the Patron included, so a caller never reads exit 0 as landed when it is not), 2 on a usage error.
2. **Its output.** `land: refused`, or `land: <head>`, `land: <head> held`, `land: <head> landed`; `carries: <paths>`; then the helper's own lines (`state=…`, `why: …`) and `way past:` or `run:`.
3. **`Ctx`.** `own?: readonly string[]` and `beforeMerge?(pr: Pr): StepResult | undefined`, both unset by `next`. `fetchTrunk(repo, target?, own?)`.
4. **Who may run it.** It is not a hand ladder write: the guard's `LADDER` does not list it, and it records no rung. The main thread may run it, in the background for the merge wait. `.claude/` is not touched.

Limits, stated:

- Unchanged code the promises lean on is a stated limit, not a guarantee (D-076 E): `landHead`, `mergeGate`, `gate`, `cleanup`, `identifyPr`, `readMergeQueue`, `reviewNotice`, `screenDiff`, `checkStudio`, `recordOnly`, git, `gh` and GitHub.

- `--past-check` is one more way to open a PR that CI will then refuse. It lands nothing CI blocks.
