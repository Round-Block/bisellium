## Intent

Decree family: ci-claims-match-workflow

W-205's first two review rounds each found a CI sentence that was false for one event or change kind, and W-209's first round found four comments that overstate the read guard (L-136). No test read those sentences. W-212 ties each CI claim to the cells it describes, so a workflow change that falsifies one by changing which steps a job selects fails `npm test` and names it, and a reworded claim fails until its row follows. A change that stops selected steps without changing the selection, such as an allowed key's value, is not seen by the test (promise `closed-model`'s limit).

A **CI claim** is a sentence in ADOPTION's `## Running ci` or `## Merge queue` section, or in a `ci.yml` comment, that says which of the four jobs, or which of their steps, run or skip for an event or a change kind. W-212 checks it against the steps the workflow's conditions select, not against what a run executes.

Promise ci-claim-parity: each CI claim at 63efbd68, the 34 that `claims-inventory.txt` marks pinned, is present word for word (whitespace-normalized) and tied to its cells. For each of the 24 cells (event `pull_request`, `merge_group`, `push` × change kind source, records-only × job `gates`, `officina`, `web-e2e`, `certify`), the steps the workflow selects equal the literal `EXPECTED`, and at least one claim names the cell — limit: a CI claim added later is checked only once its row is added, since nothing detects an unpinned new sentence. The 50 sentences that are not CI claims, and what a step does inside its job, are not checked.

Promise closed-model: selection is computed only from what the model reads, `on`, each job's `if` and `steps`, and each step's `if`, and everything else is held to an allowlist. `on` must equal the modelled triggers. The jobs must be the four, in order. A workflow key outside `name`, `on`, `permissions`, `jobs`, a job key outside `runs-on`, `if`, `steps`, `permissions`, `timeout-minutes`, and a step key outside `id`, `if`, `uses`, `with`, `run`, `env`, `shell`, `working-directory` is a problem. A condition outside the seven forms throws. So `needs`, `concurrency`, a matrix, a job-level `continue-on-error` or a trigger filter fails the script until the model learns it — limit: an allowlist, not a GitHub Actions evaluator. It checks which steps each job selects, not that they run to the end: the values of the allowed keys are not checked. A `runs-on`, `timeout-minutes` or `permissions` value can stop a job's selected steps while `W-212-b1` stays green; that job then fails, is cancelled or never starts, and all four jobs are the ruleset's required contexts (`QUEUE_CONTEXTS`, `packages/cli/src/integrate.ts:140`), so a pull request or merge group cannot merge on it, and a `push` run goes red. A step's `with`, `env`, `shell` or `working-directory` value changes what the step does, which promise `ci-claim-parity` does not check.

Promise guard-words: the two `ci.yml` comments and `scripts/record-reads.mjs`' header say the guard sees only reads through the preload's wrapped fs calls by node processes — limit: wording only; the 18 wrapped calls and the guard are unchanged, and `record-reads.mjs`' header is not pinned by a test.

No check is removed and no workflow behaviour changes. The threat model is mistakes (D-045).

## Defaults for the Patron to veto

1. **The check extends `scripts/ci-workflow.test.mjs`**, which already holds ADOPTION's `Running ci` parity; no new test file or package script.
2. **Claims are pinned word for word, each tied to its cells, and a new CI sentence is pinned by its author.** Rewording a CI sentence means updating its row in the same change. That friction is what turns a sentence that misstates the selection into a failing test. A brand-new sentence is not detected (promise `ci-claim-parity`'s limit).
3. **The model is closed.** It allowlists seven condition forms, the triggers, and the workflow, job and step keys. Any new form or key, `needs` for one, fails the script until the check learns it, which is when its claims are re-read. The allowed keys' values are not pinned: a value that stops a job fails that job's required check instead.
4. **A `.github/` change needs the Patron's approval (W-197)**, though W-212 changes only two comments there. `record-reads.mjs`' header is corrected but not pinned by a test.
