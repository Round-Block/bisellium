## Intent

High under D-039, W-275 part 2. PR #488 remained approved, `CLEAN` and outside the merge queue for about 30 minutes after its merge perform. `gate` requests `gh pr merge --squash --auto` once, but in queue mode its poll treats `CLEAN` as a reason only to wait; it does not read whether GitHub actually enqueued the PR. The operator workaround is to disable auto-merge and enable it again.

Separately, each Bash sandbox call has its own pid namespace. A perform marker records the `next` process's pid, but the next Bash call may receive `ENOENT` for that live pid. `assess` currently calls that proof of death, prints a resume command and lets another perform take over.

After this opus:

- The fixed `gh pr view` read includes boolean `isInMergeQueue`. In merge-queue mode, the first poll that sees `CLEAN` and `false` disables auto-merge, enables `--squash --auto` again with the reviewed head pin, and does that recovery at most once in one perform. A queued `CLEAN` PR continues to wait without a second merge call; direct mode retains its direct-merge fallback.
- `/proc/<pid>/stat` `ENOENT` means absent from this call's pid namespace. For a `writer: perform` marker, `assess` uses the contained output's age: within its budget the step is `running` and says the pid is outside this namespace; beyond the budget it is `dead` and stalled. `writer: track`, a visible zombie, and a visible reused pid retain their existing death rules.

Threat model: mistakes and platform isolation, not adversaries (D-045).

1. `Pr` and `readView` (`integrate.ts`, extended). `PR_VIEW_FIELDS` appends `isInMergeQueue`; `checkShape` accepts only a boolean and otherwise refuses the whole view; `toPr` carries that boolean. The list read and PR identity tuple are unchanged.

2. `gate(ctx, pr, "merge-queue")` (`integrate.ts`, extended). After the initial pinned `gh pr merge <n> -R <repo> --squash --auto --match-head-commit <pin>`, a poll that reads `OPEN`, `CLEAN`, and `isInMergeQueue: false` runs, once:

   `gh pr merge <n> -R <repo> --disable-auto`

   then:

   `gh pr merge <n> -R <repo> --squash --auto --match-head-commit <pin>`

   Either non-zero call returns `state=MERGE_FAILED` with which half failed. Later polls in that perform do not toggle again. A `CLEAN` view with `true` takes no recovery call. The direct-mode `CLEAN` branch remains below it and still requests a direct pinned squash.

3. `readProc(root, pid)` and `assess(read, derived, env)` (`next.ts`, extended). `readProc` still returns `absent` on numeric-pid `ENOENT`, but that now means absent from the reader's namespace. `assess` treats it as death immediately for `writer: track`. For `writer: perform`, it first requires readable contained output, applies the existing future-mtime rule, and compares output age with `budget_seconds`: age at most the budget returns `running` with `pidVisible: false`; age over it returns `dead`, `stalled`, naming that the pid is outside this namespace. A process visible in `/proc` still must be non-zombie and have the marker's start ticks.

4. Report-mode `runNext` (`next.ts`, extended). A running health with `pidVisible: false` prints `health: running (writer perform, pid <n> is outside this namespace, last output <age>s ago)`. It prints no resume command and exits 0, as every running report does.

Promise queue-rearm: a queue-mode merge perform that polls one identity-stable PR as `CLEAN` and not in the merge queue toggles auto-merge off then on once, with the enabling call pinned to the reviewed head — limit: it does not judge approvals or why GitHub left the PR out, and a perform whose one recovery still leaves the PR out ends in the existing `QUEUE_TIMEOUT`.

Promise fixed-queue-read: every `pr view` used by `gate` carries a boolean `isInMergeQueue`, and a missing or non-boolean value fails the fixed view read closed — limit: `pr list` does not read or promise queue membership, because membership is acted on only after the pinned view.

Promise perform-namespace-health: an absent `/proc` entry cannot by itself call a `writer: perform` marker dead; readable output no older than its budget reports running and output older than its budget reports stalled/dead — limit: during that budget, recent output cannot distinguish a live sandboxed perform from one that died immediately after writing it.

Promise tracked-pid-health: an absent `writer: track` pid remains dead, and a visible zombie or start-tick mismatch remains dead for either writer — limit: tracking a process launched in another pid namespace is not added; `--track` remains an unverified same-namespace attestation.

Limits, stated:

- `MIN_CHECKS`, GHAS, identity, head movement, direct mode, queue setup recheck, poll timing/count and terminal states are unchanged.
- The marker schema and budgets are unchanged; no process is signalled or killed.

## Defaults for the Patron

1. When GitHub says a queue-mode PR is green but not actually queued, one merge perform toggles auto-merge off and back on once. If GitHub still does not enqueue it, that perform times out as it does today; a later perform may try once again. Agree?
2. A perform pid that the next sandbox cannot see is called running while its output remains inside the marker's existing silence budget. This deliberately prefers not to double-run live work; the tradeoff is waiting out the budget after a perform dies just after writing output. Agree?
3. Tracked processes keep the stricter old rule: no proc entry means dead immediately. Cross-namespace tracking is a separate design, not inferred here. Agree?
