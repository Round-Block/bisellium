## Intent

The merge step (`gate` in `packages/cli/src/integrate.ts`) makes three `gh pr merge` calls that can fail on a PR GitHub has already merged. It arms auto-merge (`integrate.ts:826` on master). Its W-347 re-arm then disables auto-merge (`:851`) and enables it again (`:853`) when a PR reads CLEAN and outside the queue. Each non-zero exit returns `state=MERGE_FAILED` at once. GitHub can report a PR as OPEN, CLEAN and outside the queue for a moment after the queue has merged it. The re-arm then calls `gh pr merge --disable-auto` on a merged PR. GitHub refuses that call, and the step holds although the PR landed. This was seen twice on the done land of a records PR (F9, 2026-10-23).

Both the opus `merge` step (`next.ts:3039`, `mergeGate`) and the done land (`next.ts:2471`, `landHead` → `mergeGate`) run `gate`, so one change covers both. After any of the three calls fails, the step waits one poll interval and reads the PR once more with the existing `readView`. The step counts the PR as landed only when that read says MERGED, under the same number, head branch and base branch, on the head it pinned, with a well-formed merge commit. Landed means it goes through the existing `landed`: the merge commit is fetched and checked in master, the step prints `state=MERGED` and one `merge:` line naming the failed call, and the done land then deletes the records head as usual. Any other read keeps the call's own `MERGE_FAILED` lines exactly as they are today. That covers a PR still OPEN, a CLOSED PR, another head, another head branch, no merge commit, and a failed read. The step never parses gh's error text, so a gh failure counts as already merged only when a fresh read shows it.

Sibling paths, checked on master. Every place that arms or re-arms auto-merge is one of these three calls. No other `--auto` or `--disable-auto` appears in `packages/`, `apps/`, `adapters/` or `scripts/`. Two calls are close to the same class and are left unchanged. In direct mode, the direct merge in the poll loop (`:866`) already ignores its exit, and the loop's next read lands a merged PR. `gh pr update-branch` does not arm auto-merge, and a merged PR never reads BEHIND.

Threat model: GitHub's eventual consistency and a confused operator, not a hostile repository administrator (D-045). GitHub's own `pr view` answer is the record of truth here, as it already is for every other MERGED read in `gate`.

## Interfaces

**`mergedAfter(call: string, r: Run, failed: StepResult): Promise<StepResult>`** (a closure in `gate`, over `ctx`, `repo`, `pr`, `pinned` and `sameIdentity`):

1. `await ctx.sleep(ctx.pollMs)`, once.
2. `readView(repo, pr)`, once: `gh pr view <n> -R <slug> --json <PR_VIEW_FIELDS>`, validated by the existing `checkShape` and `toPr`.
3. If the read failed, or `!sameIdentity(view)`, or `view.state !== "MERGED"`, or `view.headRefOid !== pinned`, it returns `failed` unchanged.
4. Otherwise it returns `landed(ctx, view, [line])`, where `line` is `merge: <call> failed (<why(r)>); PR #<n> reads MERGED at its pinned head <pinned 12 hex>`.

The three call sites, with `call` and `failed` as follows (`failed` is today's return, byte for byte):

- the arm (`:826`): `gh pr merge --squash --auto` and `["state=MERGE_FAILED", "why: <why>"]`;
- the re-arm's disable (`:851`): `gh pr merge --disable-auto` and `["state=MERGE_FAILED", "why: disabling auto-merge before re-arming it failed: <why>"]`;
- the re-arm's enable (`:853`): `gh pr merge --squash --auto (re-enabling)` and `["state=MERGE_FAILED", "why: re-enabling auto-merge failed: <why>"]`.

`landed` (unchanged) fetches the trunk to `view.mergeOid` (`fetchTrunk`, with W-141's Patron preflight), checks that master contains it, and ties the merged head to the local branch (`settleMerged`). Its holds (`MERGED_NOT_FETCHED` and the others) are returned as they are. Success prints `local master -> <short>`, `state=MERGED` and the `merge:` line. In the done land, `landHead` then runs `cleanup` as for any merged PR.

Promise landed: when one of the three `gh pr merge` calls in `gate` exits non-zero and the one `pr view` read a poll interval later shows the same PR MERGED on its pinned head with a well-formed merge commit, the merge step and the done land carry it through `landed` and print `state=MERGED` with the `merge:` line. The done land then deletes the records head, pinned by `W-384-b1` "disable: an already-merged records PR is landed, not held", `W-384-b1` "enable: an already-merged records PR is landed, not held" and `W-384-b2` "an already-merged PR is landed: exit 0" — limit: there is one read, with no retry. If GitHub still reports the PR as OPEN a poll interval after the failed call, the step keeps `MERGE_FAILED`, and a rerun of the same perform lands it through the existing MERGED path (`mergeGate`'s first line, unchanged). Whether GitHub's `pr view` reports the merge correctly is GitHub's.

Promise fail-closed: after a failed merge call, every other read keeps the call's own `MERGE_FAILED` lines byte for byte, makes no further call and moves no ref. That covers a read that fails, an OPEN or CLOSED PR, a PR MERGED on another head or from another head branch, and a MERGED PR with no merge commit. A MERGED read whose merge commit cannot be fetched holds through `landed`'s own checks and never prints `state=MERGED`. Pinned by `W-384-b2` "a PR MERGED on another head: the failure is the call's own, unchanged", `W-384-b2` "a failed read: the failure is the call's own, unchanged", `W-384-b2` "and never reads state=MERGED" and `W-384-b1` "the failure is the call's own, unchanged" — limit: a changed base branch or PR number goes through the same `sameIdentity` check and is unpinned (by inspection). `landed`'s fetch, containment and settlement are reused unchanged and stated, not guaranteed here.

Promise siblings: the three calls are every call in the source that arms or re-arms auto-merge, and both the opus merge step and the done land reach them only through `gate`, pinned by `W-384-b2` (the merge step) and `W-384-b1` (the done land, both re-arm calls) — limit: established by search on master 4a0d41d4 (`--auto` and `--disable-auto` appear only at `integrate.ts:826`, `:851`, `:853`), not by a check rule. A new call site added later is not covered.

Limits, stated:

- Unchanged code the promises lean on is stated, not guaranteed (D-076 E): `landed`, `fetchTrunk` and its Patron preflight, `trunkContainsMerge`, `settleMerged`, `readView`, `checkShape`, `toPr`, `identifyPr`, `landHead`, `cleanup` and the W-347 membership read in `integrate.ts`; the gh CLI; and GitHub's merge state and its `pr view` reply.
- One extra `pr view` call and one poll-interval wait (`--poll-ms`, default 20 s) follow every failed merge call, including a failure that has nothing to do with a merge. The result of such a failure is unchanged.
- In direct mode, the direct merge's ignored exit and `gh pr update-branch` are unchanged (see Intent).

### Input domain

A rejection fails closed. The step returns the failed call's `MERGE_FAILED` lines unchanged (`next: <id> <step> held`, exit 1). Nothing is fetched, no ref moves and no branch is deleted. A test row whose own read fails throws, which fails the row.

## Behaviours to test

Both rows use the stub `gh` of `next-world.test.ts` and never run the real `gh` or touch the network. `W-384-b1` uses `next-done.test.ts`'s cleanup-stage world, with the done commit made, and a new `rearmScenario`. The merge queue is on (`QUEUE_RULES`), the records PR reads OPEN, CLEAN and outside the queue, so the step re-arms. The named call exits 1 with `GraphQL: Pull request is already merged (…)`, and when the PR merges, that call raises a flag so that later reads say MERGED on the pinned head. `W-384-b2` uses `next-queue.test.ts`'s `pushed` world and `performMerge` in queue mode. The first `gh pr merge` exits 1 with the same text and raises a flag, and every `pr view` after the flag answers the variant's reply.

1. **The done land counts a records PR as landed when the auto-merge re-arm fails because the PR is already merged on its pinned head, and keeps any other failure.** In `W-384-b1`:
   - The disable fails on a merged PR. The perform prints `next: W-900 done performed` and exits 0. Its output holds `merge: gh pr merge --disable-auto failed (GraphQL: Pull request is already merged (disablePullRequestAutoMerge)); PR #<n> reads MERGED at its pinned head <12 hex>` and `state=MERGED`, and no `MERGE_FAILED`. The merge calls are exactly the arm and the disable. The next gh call after the disable is one `pr view`. Master is at the merge commit, and the records head is deleted locally and on origin.
   - The enable fails on a merged PR. The same holds, with the merge calls the arm, the disable and the enable.
   - The disable fails and the PR still reads OPEN. The perform is held with exactly `state=MERGE_FAILED` and `why: disabling auto-merge before re-arming it failed: GraphQL: Pull request is already merged (disablePullRequestAutoMerge)`. The disable is followed by one `pr view` and no other call of the perform. Master has not moved, and the records head stays, locally and on origin.

   **Genuine red:** `bisellium red W-384 --behaviour 1 --sella builder --studio studio -- node --test-reporter=tap --test-name-pattern='^W-384-b1\s' --import tsx packages/cli/src/next-done.test.ts` prints `not ok 1 - W-384-b1 behaviour 1: the done land counts a records PR as landed when the auto-merge re-arm fails because the PR is already merged on its pinned head, and keeps any other failure`, failing at `disable: an already-merged records PR is landed, not held`. Master holds with `state=MERGE_FAILED` (`red-b1-master.out`, master 4a0d41d4 with the final rows).

2. **The merge step counts a PR as landed when arming auto-merge fails and one fresh read shows it MERGED on its pinned head, and keeps the failure for any other read.** In `W-384-b2`:
   - The read is MERGED on the pinned head. The step exits 0 and prints `merge: gh pr merge --squash --auto failed (GraphQL: Pull request is already merged (enablePullRequestAutoMerge)); PR #<n> reads MERGED at its pinned head <12 hex>` and `state=MERGED`. The mutating calls are exactly `gh pr merge --squash --auto` and `git fetch master:master`, with exactly one `pr view` after the merge call, and master holds the merge commit.
   - Each of six other reads keeps the failure: a PR that still reads OPEN, a PR MERGED on another head, a MERGED PR of another head branch, a CLOSED PR, a MERGED PR with no merge commit, and a failed read (exit 1). In each, the step exits 1 with exactly `state=MERGE_FAILED` and `why: GraphQL: Pull request is already merged (enablePullRequestAutoMerge)`, makes the one merge call and no fetch, makes exactly one `pr view` after it, and leaves master unmoved.
   - A read that is MERGED on the pinned head, but whose merge commit is not on origin, exits 1 and never prints `state=MERGED`.

   **Genuine red:** `bisellium red W-384 --behaviour 2 --sella builder --studio studio -- node --test-reporter=tap --test-name-pattern='^W-384-b2\s' --import tsx packages/cli/src/next-queue.test.ts`, run on the commit implementing behaviour 1 (where only the re-arm's two calls take the re-read), prints `not ok 1 - W-384-b2 behaviour 2: the merge step counts a PR as landed when arming auto-merge fails and one fresh read shows it MERGED on its pinned head, and keeps the failure for any other read`, failing at `an already-merged PR is landed: exit 0` (`red-b2-stage1.out`). On master it fails at the same check (`red-b2-master.out`).

## Out of scope

- Retrying the re-read, or reading queue membership or the merge commit through another API. One read follows each failed call, and a lagging read is handled by a rerun.
- Parsing or matching gh's error text in any form.
- The poll loop's handling of a MERGED read (it lands any MERGED PR whose identity matches, as today), the direct-mode direct merge, `gh pr update-branch`, and `landHead`'s push and PR creation.
- A check rule that keeps every `--auto` call routed through `mergedAfter`.
- Architecture: one closure inside `gate`, with no package edge, seam, lifecycle transition or serve route change; `docs/ARCHITECTURE.md` is unchanged.
