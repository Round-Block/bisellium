## Intent

The cascade has an order (greenlit, spec signed, two-phase build with reds at
a clean tree, review rounds, a PR rebased on the fetched trunk, the merge gate,
cleanup, done, checkpoint). Today that order lives in the producer's memory, in
`docs/SESSION-HANDOFF.md` traps, and in two shell scripts. Every recurring
mistake of the last cascades was a skipped or reordered step: PR 127 closed by a
cleanup chained on the wrong step; PRs opened un-rebased; a green PR left BEHIND
and stalled; `done` run before the merge reached the local trunk; and on
2026-10-02 a dead gate chain reported healthy for four hours.

`bisellium next <opus>` derives, from the record and its evidence alone, the
one legal next step; it **names** the step (with the exact command or dispatch
order) or, with `--perform`, **performs** it, and it refuses to skip. The kept
scripts retire as their steps become verbs (Patron, 2026-10-01).

**One decree family:** the ordering and refusal verb itself, plus the three
standing rules that are properties of that same verb (stale-step health,
dispatch context caps, complete = merged + fetched). Per W-127's rule (not yet
built, honoured here) everything else is a named follow-on, never folded in:
model-tier delegation per munus (W-117), verdict grammar (W-126), recording the
sec-lead input, and recording the declared dispatch budget as an event. See
"Follow-on filings".

## Interfaces

### Grammar and result

```text
bisellium next <opus> [--perform] [--expect <step>] [--budget <tokens>]
    [--title <text> --body-file <path>] [--poll-ms <n>] [--max-polls <n>]
    [--studio <dir>] [--repo <dir>] [--now <iso>]
bisellium next <opus> --track <step> --pid <n> --output <path> [--studio <dir>] [--repo <dir>] [--now <iso>]
```

Flags parse the house way (`parseFlags`, strict allowlist, own argv in
`main.ts`). Exit codes: 0 step named, performed, or a live step reported
running; 1 refused, held, dead, or a performed step failed; 2 usage, unknown
opus, not a studio. Default is report-only; nothing is written without
`--perform` (or `--track`). First stdout line: `next: <opus> <step> <named|performed|held|running|dead|complete>`,
then `key: value` lines (`command:`, `actor:`, `head:`, `why:` naming the
evidence read). Reads use argument arrays only; no shell, no network in report
mode except `gh` read calls for the PR rungs.

`next` runs in the opus's **owning checkout** and relays the D-021 refusal
(`recordOwnerRefusal`) unchanged when it is not. It reads the filesystem of that
checkout plus the local trunk ref; it never fetches in report mode.

### The ladder (the single ordering; exported as `STEPS`)

The next step is the first rung whose evidence is unmet. A rung is also settled
when the opus's PR (head `opus/<id>`) is MERGED, so a merged opus whose branch
is gone does not walk back to `branch`; `done` still re-checks its own gates.

| Step | Met when (read-only evidence) | Mode |
| --- | --- | --- |
| `greenlight` | record state is not `backlog`; a record carrying `declined`, or in state `halted`, holds (no step named) | named; Patron only, never performed, role never set to patron |
| `spec` | local trunk carries `briefs/<id>.md` with the six design-lex sections AND a `ci/<id>-spec-<n>.log` whose header sella is `architect` and outcome starts `passed`; for `kind: ui`, `inspectUiDesignInput` reports no problems | named: architect dispatch order. If the brief exists only on `spec/<id>`, the PR steps below run with head `spec/<id>` |
| `branch` | `refs/heads/opus/<id>` exists | performed: `createOpusBranch` from the local trunk tip (refuses a dirty tree or HEAD not at the trunk tip), then `git worktree add <repo>/.worktrees/<id> opus/<id>` |
| `ready` | state is building, verifying, review or done AND the `spec` gate is passed | performed: `ready --sella architect` in that worktree |
| `reds` | every behaviour `1..N` of the brief has `ci/reds/<id>/NN.log` with `# tree: tree:` (clean), a nonzero `# exit:`, a TAP `ERR_ASSERTION`, not a module-load failure (`isModuleLoadFailure`) | named: builder dispatch order, phase 1 |
| `build` | `admitCurrentRunReceipt` is ok for the current tree | named: builder dispatch order, phase 2 |
| `review` | the `review` gate is passed and its evidence header `# tree:` equals the current SOURCE tree; for `kind: ui` also the ui-lead input check | named: censor dispatch order |
| `pr` | a PR exists for the head | performed (absorbs `scripts/open-pr.sh`) |
| `merge` | the PR is MERGED AND the local trunk ref contains the merge commit | performed (absorbs `scripts/merge-gate.sh`) |
| `cleanup` | local head branch, its worktree and the remote head are gone | performed, only from a re-read MERGED + fetched |
| `done` | record state is `done` on the trunk | performed (`done --sella producer`), only when done-able |
| `checkpoint` | `docs/SESSION-HANDOFF.md` on the trunk, section "Where things stand", names the opus | named |

The `spec` evidence adds one verb call to the architect's close-out
(`verdict <opus> --phase spec --sella architect --outcome passed`); no new writer.
An unmarked (legacy) record past `ready` is outside the ladder: `held`, naming
that it carries no `builder_runtime` marker.

### Step health marker (behaviour 5)

`<repo>/.bisellium/steps/<opus>.json`: `{schema:1, opus, step, pid, started,
output, budget_seconds}`, with `output` a repo-relative log the step appends to
(`<opus>.log` in the same directory for steps `next` performs). `next --perform`
creates the marker exclusively before any long step and removes it on a normal
exit; `--track` writes the same file for a step an orchestrator launched itself.

### Dispatch order (behaviour 6)

Dispatch steps (`spec`, `reds`, `build`, `review`) print an order, not a
command to be guessed: `role:`, `sella:`, `budget_tokens:`, `inputs:` (the brief,
and the opus record's `traditio` handover block; for `review` also the evidence
logs and the ui-lead input path), `command:`.

## Behaviours to test

1. **The ladder names exactly one legal next step from evidence.** Fixture
   officina at each rung boundary (twelve, `greenlight` to `checkpoint`): the
   step before is met and the step itself is not; `next` prints that step, its
   `actor:` and `why:`, and writes nothing (record, `ci/`, `.bisellium/`
   byte-identical, no marker). Rows: backlog; halted and declined hold; greenlit
   without a signed spec; branch absent; branch present with state greenlit;
   reds missing one behaviour (a dirty-tree red, a module-load red and an
   exit-0 red each count as missing); a stale receipt; a review gate passed at
   an older tree; PR absent, OPEN, MERGED but trunk behind, MERGED and fetched
   with branch still present, branch gone; `done`; checkpoint missing. An
   unmarked legacy record past `ready` is held. The same input twice gives the
   same output. **Genuine red:** `main.ts` has no `next` verb and falls through
   to the usage banner (exit 2); the row's first assertion is its own step line.
2. **`next` refuses to skip.** `--expect <step>` exits 1 with `refusing: next
   step for <opus> is <A>, not <B>` and performs nothing whenever `<B>` is not
   the derived step, including when evidence for a *later* rung is present
   (a PR OPEN on a branch with no passing review names `review`, not `merge`;
   a clean tree with a review log but no receipt names `build`); an unknown step
   id is usage (exit 2). `--perform` executes only the derived rung's action and
   re-derives after it, never a second rung in one call, and stops at the first
   named-only rung (dispatch, greenlight, checkpoint) without running anything.
   `branch` refuses a dirty tree and a HEAD not at the trunk tip (no branch
   created); `ready` relays the D-021 refusal from a non-owner checkout; a
   `greenlight` rung is never performed and `BISELLIUM_ROLE` is never set to
   `patron`. **Genuine red:** no verb and no `--expect` surface exist; today
   nothing refuses an out-of-order step, so the row asserts the refusal text.
3. **`pr`, `merge` and `cleanup` do what the scripts do, in order, with the
   refusals the scripts only document.** `pr`: refuses from the trunk and from a
   dirty tree; fetches `origin master:master`, rebases onto it, aborts the rebase
   and reports `state=CONFLICT` without pushing on conflict; when the rebase
   changes the SOURCE tree it stops before push and PR and re-derives (`build`);
   pushes `--force-with-lease`; creates the PR with `--base master --head <head>`
   from `--title` and `--body-file` (without them it only names the command);
   an existing OPEN PR is reused, never duplicated. `merge`: `gh pr
   update-branch` when BEHIND; refuses on any failing check, on fewer than
   `MIN_CHECKS`, and on any open GHAS code-scanning alert (`state=GHAS_STOP`);
   `gh pr merge --squash --auto`, then a direct `--squash` merge when the PR is
   CLEAN or BLOCKED with nothing pending or failing, an update when BEHIND while
   queued, `QUEUE_REJECTED` on CLOSED, `QUEUE_TIMEOUT` after `--max-polls`;
   MERGED is reported only after a read-back, then the trunk is fetched. A
   check is classified by its status field, never by a substring of its name
   (a passed check named `pending-review` is not pending). `cleanup`: refuses
   with the branch, worktree and remote untouched unless a fresh read says the
   PR is MERGED and the trunk contains the merge commit (the PR 127 shape: an
   OPEN PR and a cleanup request deletes nothing). Parity rows run the two
   scripts and the verb against the same stub scenarios that terminate without
   sleeping (CHECKS_FAILED, GHAS_STOP, MERGE_FAILED, MERGED on the first poll,
   QUEUE_REJECTED, CONFLICT, dirty tree, on master) and require the same terminal
   state and the same `gh`/`git` calls. **Genuine red:** the verb does not exist,
   so no scenario reaches a `gh` call; each row asserts its own terminal line.
4. **Complete means MERGED and FETCHED (Patron standing rule 3).** `done` is
   reported done-able, and performed, only when a fresh `gh` read says the PR is
   MERGED and `git merge-base --is-ancestor <mergeCommit> <trunk>` holds on the
   local trunk ref after the fetch. Rows: OPEN, CLOSED unmerged, MERGED with the
   local trunk one commit behind (the step is `merge`, whose postcondition is
   the fetch; `done` is refused with the commit named), and `git fetch origin
   master:master` refused because `master` is checked out in a worktree (reported
   as `held` naming that worktree and the `pull --ff-only` to run there; `-u` is
   never used). The predicate is `trunkContainsMerge`, one implementation. `done`
   itself is unchanged: a control row shows the existing `done` still accepts
   an unmerged opus (W-123 will add its own refusal using the same predicate).
   **Genuine red:** no verb exists to report done-ability, and the existing
   `done` is the only path, which succeeds with the PR unmerged; the row asserts
   the refusal.
5. **Step health comes from evidence, never assumption (Patron standing rule 1).**
   Any state `next` reports about a running step is computed from the marker's
   pid (`process.kill(pid, 0)`; EPERM counts as alive) and the output file's mtime against
   `--now`, and from nothing else. Rows: live pid and output within its
   silence budget is `running` (and no next step is named while it is);
   pid gone is `dead`; pid alive but output older than the budget is `dead`
   (`stalled`, pid named, never killed); output file missing is `dead`; a dead
   step whose rung is now met is reported `finished`, not dead; no marker is
   `health: no step recorded`, never "running" or "healthy"; a started step
   from outside `next` is `--track`-registered or reported unknown. A dead report
   names the step, the last output line and its age, and the resume point: the
   re-derived first unmet rung with its exact command (the resume is
   evidence-driven, not the step that died). `--perform` refuses a live marker
   (`step <s> is running, pid <n>`) and replaces a dead one, saying so. A marker
   age is tested with `utimesSync` and `--now`; no test sleeps. The 2026-10-02
   fixture is a marker whose pid is gone and whose output is four hours old; the
   row asserts `dead`, not `running`. **Genuine red:** nothing reads steps, so
   the same fixture today yields no health report at all; the row asserts `dead`
   and the resume line.
6. **A dispatch is refused over the context cap, and resumes from the handover
   artifact (Patron standing rule 2).** For a dispatch step `next` requires
   `--budget <tokens>`: absent exits 1 (`dispatch budget undeclared`), non-integer
   or non-positive exits 2, above `DISPATCH_TOKEN_CAP` (500000) exits 1 with the
   declared and cap values and prints no order; exactly 500000 is accepted. The
   order carries `budget_tokens:` and lists the record's `traditio` block and
   the brief as its inputs, and nothing taken from conversation. A dispatch is
   a *resume* when its step already has evidence (some reds, a stale receipt, a
   prior review round); a resume is refused when `traditio` is missing or its
   `at` is older than the newest `# at:` among the opus's reds and review logs
   (`stale handover: run bisellium handoff first`). Rows for each of
   `spec`, `reds`, `build`, `review`; `--budget` is irrelevant to non-dispatch
   steps and is ignored there. **Genuine red:** no verb, no cap and no handover
   check exist; the row asserts the over-cap refusal and the stale-handover
   refusal text.

Each behaviour gets its own recorded red via `bisellium red`, at a clean
committed pre-change identity on the owning branch (D-028), and every red is a
completed selected Node TAP `ERR_ASSERTION` (the W-096 `opus.red_assertion`
standard), never a module-load, missing-binary, skipped or environmental
failure. Because the verb is new, the focused test never statically imports it;
each row spawns the CLI, so a red is the row's own failed assertion on the
usage-banner exit and not an import error. Each row's first assertion states
its own behaviour, so no two reds share one output.

## Follow-on filings for the producer

**Title: a review round cites the sec-lead input it consumed.** The ladder's
`review` step enforces the ui-lead input through the existing `--ui-input` /
`opus.ui.design` mechanism, but sec-lead output has no recordable artifact: there

makes the censor's verdict cite it, and teaches `next`'s `review` step to require
it for the opera whose brief declares security-sensitive files. Depends on W-126's
verdict grammar; do not fold into either.

recorded.** `next` validates the 500k cap and names the handover artifact in the
order it prints, but the declaration is not written anywhere durable. File one
opus to record each dispatch order (role, budget, handover digest) as an event
and a retro usage column, which needs a new `workflow.*` attribute and therefore
an architect and Patron ruling on the wire names, and which can feed W-122's
instrument.

**Title (chore, after the live proof): retire `scripts/open-pr.sh` and
