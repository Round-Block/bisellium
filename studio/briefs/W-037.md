# W-037 — shim: polynomial ReDoS in sourceTree path regex (CodeQL high)

## Intent

The repo's first CodeQL run (default setup, enabled 2026-09-20 when the
repo went public) raised exactly one alert at the `master_protection`
ruleset's blocking threshold (`security_alerts_threshold:
high_or_higher`):

```
js/polynomial-redos [warning / security: HIGH]
packages/shim/src/sourceTree.ts:24 — "This regular expression that depends on
library input may run slow on strings with many repetitions of '/'."
```

Line 24 is the whole of `normalizeExclude`:

```ts
function normalizeExclude(dir: string): string {
  return dir.replace(/\\/g, "/").replace(/^\.\//, "").replace(/\/+$/, "");
}
```

The flagged pattern is the third one, `/\/+$/`. On a string whose slashes
are *not* at the end (`"/".repeat(n) + "x"`) the engine restarts `\/+` at
every one of the n slash positions, consumes to the end, and fails the
`$` anchor: O(n²). Measured at HEAD on this machine:

| n slashes | `/\/+$/` |
|---|---|
| 10 000 | 25 ms |
| 40 000 | 400 ms |
| 200 000 | 10 392 ms |

The alert is real and the complexity claim is correct. **It is not
exploitable here**, and the brief says so plainly because it changes the
posture, not the outcome:

- `normalizeExclude` is reached only from `sourceTreeHash` and
  `isDirtyOutside` (`packages/shim/src/sourceTree.ts:41,62`), whose
  `excludeDirs` argument is assembled in exactly three places —
  `packages/cli/src/check.ts:151`, `packages/commands/src/verify.ts:131`
  and `packages/commands/src/lifecycle.ts:494` — always as
  `[<studio dir relative to repo>, ".bisellium", ...manifest.source_excludes]`.
- Every element is repo-owner-authored configuration. `studio/bisellium.yml`
  declares `source_excludes: [examples/]`; the fixture declares
  `[studio/, examples/fixtures/]`. `check.ts:196` validates only that they
  are non-empty strings. Nothing from the network, a receipt, a prompt or
  a harness reaches this function.
- It runs once per *exclude entry*, not once per `ls-tree` line. The blast
  radius is a handful of strings under 64 characters. Costing one second
  needs roughly 60 000 consecutive slashes inside one manifest entry, and
  anyone who can write that into `bisellium.yml` can already hand-edit the
  certificates the hash defends.
- The officina's stated threat model is "Mistakes, not adversaries: the
  threat model is agents that drift, not agents that attack"
  (`docs/design/dossier/body.html`, the five founding decisions).

So: **gate hygiene, not urgent security.** It proceeds anyway, for three
reasons that do not depend on exploitability — the `code_scanning` rule
blocks PR #4's merge today and will block every PR until the alert is
closed; `@bisellium/shim` is a published package whose callers are not all
in this repo; and the linear rewrite is shorter than the regex it replaces.

The alert sits on master's code, not on PR #4's diff. The gate surfaced it
there because CodeQL's baseline landed after the branch.

The one thing this opus must not do is move a hash. `sourceTreeHash` is
the `tree:` in every probatio certificate, read by `verify`, `check`,
`branch`, `merge` and `close`. `normalizeExclude` is the only input
transform on the exclusion set, so a single byte of difference in its
output restates every recorded `tree:` certificate in the repo as stale.
That is behaviour 1, and it is why this is test-first rather than a
one-line commit.

## Interfaces

`packages/shim/src/index.ts` does not change. The exported seam
(`sourceTreeHash`, `isDirtyOutside`) does not change — same signatures,
same return values, same hashes.

`normalizeExclude` gains an `export` from `sourceTree.ts` so the test can
assert on it directly; it is *not* re-exported from `index.ts`. The test
imports it as `../src/sourceTree.js`, the same deep-import shape
`packages/pipeline/test/pipeline.test.ts:18` already uses.

The replacement — no regex left in the function at all, so the alert
cannot be re-raised by a later tweak:

```ts
export function normalizeExclude(dir: string): string {
  let d = dir.replaceAll("\\", "/");
  if (d.startsWith("./")) d = d.slice(2);
  let end = d.length;
  while (end > 0 && d.charCodeAt(end - 1) === 47 /* "/" */) end -= 1;
  return d.slice(0, end);
}
```

Each clause is the exact equivalent of the regex it replaces:
`replaceAll` for the global `/\\/g`; `startsWith`/`slice(2)` for the
anchored, non-global `/^\.\//` (which strips one leading `./`, never two);
the index walk for `/\/+$/` (one maximal trailing run, never an interior
one). Do not substitute `while (d.endsWith("/")) d = d.slice(0, -1)` — it
is linear per step but quadratic in allocation over the same input, which
is the bug again wearing different clothes.

`isUnderExcluded` at line 28 keeps its two regexes (`/^"|"$/g`,
`/\\/g`). Both are single-character, unanchored-alternation patterns with
no nested quantifier; CodeQL did not flag them and they are linear. Leave
them.

## Behaviours to test

1. **`normalizeExclude` is byte-identical to the shipped implementation,
   and the tree hash therefore does not move.** Two layers in one
   behaviour. First, a golden table checked into the test, generated from
   the implementation at HEAD *before* it is edited (record the generating
   command in the section's header comment) and covering both manifests'
   real entries, deep nesting, doubled and trailing slashes, backslash
   paths, `./` prefixes, and the degenerate inputs:

   | input | expected |
   |---|---|
   | `examples/` | `examples` |
   | `studio/` | `studio` |
   | `examples/fixtures/` | `examples/fixtures` |
   | `docs` | `docs` |
   | `./docs/` | `docs` |
   | `vendor//` | `vendor` |
   | `.bisellium` | `.bisellium` |
   | `a/b/c/d/e/f/g/h/i/j/` | `a/b/c/d/e/f/g/h/i/j` |
   | `packages\shim\src\` | `packages/shim/src` |
   | `./` | `` |
   | `/` | `` |
   | `//` | `` |
   | `` | `` |
   | `a//b//c//` | `a//b//c` |
   | `./a/./b/` | `a/./b` |
   | `"x/" × 50` | the same, less the final slash |

   Second, the end-to-end consequence against this repo, which needs no
   frozen literal and so cannot drift with the next commit:
   `sourceTreeHash(repo, ["examples/"])` equals
   `sourceTreeHash(repo, ["examples"])` and differs from
   `sourceTreeHash(repo, [])` — i.e. the trailing slash in the live
   manifest entry still normalizes away, and still actually excludes.

   These are one behaviour, not two, on purpose: the hash is a pure
   function of the normalized excludes, so a split would produce two reds
   from one run with a shared body and trip `opus.red_content`.

2. **A pathological exclude entry completes in linear time.**
   `normalizeExclude("/".repeat(200_000) + "x")` returns
   `"/".repeat(200_000) + "x"` unchanged (no trailing slash to strip) in
   under 500 ms measured with `process.hrtime.bigint()`. Not a flaky
   timing test: the shipped regex takes 10.4 s on that input and the
   replacement takes 0.12 ms, so the bound has four orders of magnitude of
   headroom in both directions — a CI runner ten times slower than this
   machine still lands at ~1 ms.

## Order of work, and where each red comes from

Two behaviours, two tree states, two distinct assertion-level reds:

1. Write the whole test section first. Run it at HEAD, unmodified
   implementation: behaviour 1 passes (it is the old code against its own
   golden table), behaviour 2 fails on the time bound. Record it —
   `bisellium red W-037 --behaviour 2 --repo . -- node --import tsx
   packages/shim/test/shim.test.ts .` — roughly 10 s.
2. Replace `normalizeExclude`'s body with the TDD stub `return dir;` and
   export it. Behaviour 2 now passes, behaviour 1 fails on the golden
   table *and* on the `"examples/"` ≡ `"examples"` hash equality (with the
   stub, `examples/` matches no path and the hash collapses to the
   no-exclusions one). Record it as behaviour 1's red. The two logs differ
   in body, so `opus.red_content` is satisfied.
3. Write the real body. Both green, and the rest of the suite — which
   leans on trailing-slash excludes in `check.test.ts:156` and
   `branch.test.ts:1144` — stays green.

The stub state is never committed.
