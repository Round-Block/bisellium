## Intent

The repeat S1 class `spec×fix-opens-new-surface` (D-076 D, high): a fix or promise adds an input surface, the brief does not name that surface's awkward-but-valid input forms, and the next review finds one. Its live case is W-362 (`ci/W-362-review-1.log` #1, S1): row 1 of its brief ruled the Bash command line's `env -S` words, listed forms (D-085 D) and the four W-336 path forms, and still said nothing of a shell operator inside the split string; the review found `env -S 'bisellium ; merge W-900'` misread. The fix check then found four more forms on the same surface (`\r`, `\v`, `\f` splitting and `while`/`until` as literal words). Its spec round 2 (`ci/W-362-spec-2.log` #2, S1) found the same shape on a second surface: the user settings row named the whole file's type and an absent key, but not a key of the wrong type (`denyWrite` a string). The six older lessons of the class (L-100, L-107, L-111, L-117, L-121, L-137, all 2026-10-09/10) are W-196's, W-319's, W-322's and W-336's ground; L-117's unreadable opus record (#6) is the same shape as the settings case.

The mechanism: W-336's rule, extended (D-042). W-336 makes a row whose Valid domain names a path, a command line or an environment value name a space, a quote, a non-ASCII name and a symlinked parent; those are a path's hostile forms, not a shell lexer's or a record reader's. After this opus `ruledCases` (`brief-admission.ts`) also knows two input surfaces by a fixed vocabulary in the row's Record or Valid domain cell, each with its own hostile forms:

- **shell text** (command line, command-line, shell): a shell operator, a control character and a reserved word;
- **a structured record** (JSON, YAML, front matter, settings): an absent value, a wrong type and an unreadable file.

A row naming a surface names each of its forms by its word, on the row's line or a line its forms clause cites, as a recognised form with its pin or as a stated limit; the lines such a clause cites are pinned as for an any-text row. The design magister's spec signature (`verdict --phase spec`, `promiseLedgerProblems` in `verdict.ts`) is refused otherwise, one problem per row and surface. The rule judges a promise when it is signed and a fix when its brief is signed again, which is when a spec fix adds a row.

Why this and not the other D-076 D forms. A prompt template adds prose, which the reviewer already has; the fix check (`next.ts`, W-309) judges a build fix's paths after the fix, not the brief's forms before the build, and `next.ts` is W-328's lane now. Brief admission re-reads every signed brief, so the rule there would send back the 38 and 7 briefs with a gap on master (`census.out`); the signature check judges new signatures only, as W-322's and W-336's rules do.

What it would have caught (`would-catch.out`, the prototype's reader on the briefs as review read them): W-362's rows 1 and 2 (shell text: all three forms unnamed), so the S1 of review 1 and the fix check's four forms are each a pin or a stated limit before the build; W-362's row 3 (a structured record: no wrong type, no unreadable file), the S1 of spec round 2; W-186's row 3 (front matter: none of the three), where L-117 #6 found the unreadable opus record. It would not have caught L-100 (a write order), L-107 and L-121 (a reader with no row at all), L-111 (an existing containment row a fix broke), L-137 (a matching rule's meaning), L-117 #1 and #5 (rows with no vocabulary word), nor a build fix that departs from a signed brief (W-310's review 2 #3, W-322's review 2 #1).

Threat model: mistakes, not adversaries (D-045).

## Defaults for the Patron

1. When a brief's table of inputs rules shell text (a command line or shell words), it must also say how three awkward-but-valid things are handled: an operator such as `;`, a control character such as a tab or `\r`, and a reserved word such as `while`, each tested or written down as a known limit. The architect's signature is refused otherwise. Agree?
2. The same for a structured record (JSON, YAML, front matter or settings): a missing value, a value of the wrong type and a file that cannot be read. Agree?

4. Be clear on what it does: it checks that the words are there, not that the tests are right, and it would not catch a reader missing from the table or a build fix that strays from its brief; those stay with the reviews and the fix check. Agree?
