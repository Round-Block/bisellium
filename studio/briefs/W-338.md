## Intent

D-088 E files all console work as `kind: ui`, and the UI lane (W-339 to W-342, W-345, W-074) sits behind this opus, but no `kind: ui` opus can reach branch. Four rungs stop it, and none has ever run, since no opus has been `kind: ui`:

1. next holds every spec step of a `kind: ui` opus (`readSpecReviewer`: "a kind: ui opus cannot take a spec review yet").
2. The spec-phase verdict writer refuses every seat but ui-lead on a `kind: ui` opus ("UI spec input must be attributed to ui-lead"), so neither the architect's signature nor the spec review can be recorded, with or without a reviewer.
3. `authoritativeUiInput` reads the highest `ci/<id>-spec-<n>.log` as the UI input, so a signature or a review above the ui-lead's input masks it; and, the other way, `reviewedSpec` holds on any log above the newest signature that is not its review, so a ui-lead input there masks the sequence.
4. When the UI input is missing, next orders the architect, never the ui-lead; it reads the input from the main checkout even after `branch` has moved it to the opus branch; and the ui-lead's verdict and the input reader need `spec:`, which only `ready` writes, so the input cannot be recorded before ready.

The design keeps one log family (D-042). A spec log is the ui-lead's UI input when its header block's first `# sella:` is ui-lead (`isUiLeadLog`), and every other reader of spec logs already tells the signature from the review by the same header (`readSpecSignature`, `readSpecReview`, `readSequence`, `brief-stale`, the retro reader). So each seat's verdict is its own log in the one sequence, each reader reads only its seat's logs, and neither masks the other. A separate log name (the record's candidate 1) would add a family that `specChanges`, `readSequence`, the step tickets and the `ladder.ticket` rule would each learn; a sella mark is what they already read.

After this opus, on a `kind: ui` opus: the verdict writer routes a spec verdict by seat (ui-lead: the UI input path, unchanged; any other seat: the plain spec path, promise ledger and finding tags included, `--dispatch-prompt` refused); the UI input is the newest ui-lead spec log, its digest's brief `briefs/<id>.md` until ready writes `spec:`; next sends the signed spec to the reviewer as on any opus, and once the spec passes orders the ui-lead (role and seat `ui-lead`, the next round, the prompt kept as `ci/<id>-ui-prompt-<n>.md`) where the spec is carried, the main checkout before the branch and the opus worktree after; branch and the spec commit carry the input's log and its prompt.

The Patron's ruling of 2026-10-20 (to be recorded as D-091), relayed while this brief was drafted: for `kind: ui` opera the brief is drafted and signed by Codex `gpt-5.6-sol` as the UI architect, the ui-lead gives its layout input to that drafter, the spec review is Claude `claude-opus-5-5`, and the build review stays a fresh Codex `gpt-5.6-sol` session. This opus does not change who signs or reviews: the ladder keeps one signer (the design magister) and one reviewer (`spec_reviewer`, exactly `gpt-5.6-sol`). It makes the three logs coexist by seat, which the pairing needs; the pairing itself is split out at spec (Out of scope, "W-338 part 2"), with every place it is fixed named there. Until part 2 lands a `kind: ui` opus is signed by the Opus architect and reviewed by Sol.

Revision 2 (round 2): (1) the design digest is read for the caller's opus. `currentDesign(root, record, id)` refuses a record whose `id` is not the CLI opus id (the verdict writer) or the record's file name (next, check, ready), so a record copied with another opus's `id` neither writes nor reads a digest of that opus's brief; every reader takes the id from its caller, never from the record (`inspectUiDesignInput`, `validateUiPolicy`'s candidates and digest, next's `uiProblems` and `uiInput`). (2) A ui-lead log leaves the strict signature-and-review sequence only on a `kind: ui` opus: `reviewedSpec` reads the kind from the record in the source it reads the logs from, and the worktree check from the branch's record, so on any other kind a ui-lead log is judged as a signature or review and holds.

Threat model: mistakes, not adversaries (D-045).

The forms `isUiLeadLog` recognises in a spec log's header block, one per line:

- a first `# sella: ui-lead` line in the header block (its value exactly `ui-lead`) — pinned by `W-338-b2` "a signature and a review above the input" and pinned by `W-338-b3` "an input above the signature holds nothing"
- an unreadable spec log, kept a candidate by `authoritativeUiInput` so its strict read names it — pinned by `W-338-b2` "an unreadable newest spec log"

Every other form is a limit: another seat's log, a log with no first `# sella: ui-lead`, differently cased or spaced values, a later duplicate, or body text; only on a `kind: ui` opus is a ui-lead log skipped by `reviewedSpec` and the worktree signature/review guard, while on every other kind it remains in the strict plain-spec sequence — pinned by `W-338-b6` "a ui-lead log above the signature of a kind: opus holds" and pinned by `W-338-b6` "a new ui-lead log in the worktree of a kind: opus holds".

Promise seat-route: on a `kind: ui` opus the ui-lead's spec verdict is recorded only as the UI input (prompt, substantive transcript, digest) and every other seat's spec verdict only as a plain spec verdict — limit: the seat is the `--sella` the caller gives, as for every verdict; the writer does not check that the seat is declared or that its model is the lex's.

Promise no-mask: the UI input is the newest ui-lead spec log whatever other logs sit above it, and on a `kind: ui` opus a ui-lead log never stands in the signature-and-review sequence, while on any other kind it stays in it — limit: the classification is the first `# sella:` value; a log mis-attributed to ui-lead is read as UI input, not held, and an older valid input is never preferred over a newer bad one.

Promise ui-order: next names the ui-lead, never the architect, when a signed (and reviewed) `kind: ui` spec has no current UI input, in the checkout that carries the spec, and branch and the spec commit carry its log and its prompt — limit: the prompt's name is the order's, not the writer's: a prompt kept under another name is not carried, so after the branch the input's prompt is unreadable and next orders the ui-lead again (fails closed, one more round).

Limits, stated:

- The ui-lead is ordered after the spec passes (after the passed review with a reviewer, after the signature without one), never before the signature: its digest binds the final brief, so an input recorded before the drafting ends goes stale. Its outcome (`revise`, `failed`) sends nothing back mechanically, as today; the build censor dispositions it.
- Without a reviewer, after the branch the ui-lead's uncommitted input in the worktree is not committed by next (the commit-opus step is the reviewer path's); the producer commits it, as any no-reviewer spec round today.
- Unchanged code the promises lean on is a stated limit, not a guarantee (D-076 E): `parseVerdictHeader`, `readContainedRegularFile`, `substantiveUiTranscript`, `designDigest`, `validateUiPolicy`, `readSpecSignature`, `readSpecReview`, `failedSpecReviews`, `specOrder`, `performBranch`, `performOpusSpecCommit`, `dirtyHold`, `requireTicket`, `readSequence`, `promiseLedgerProblems`, `findingTagProblems` and `findingsProblem`.
