## Intent

`scripts/agent-workspace.sh verify` says it only reads (`agent-workspace.sh:6`, `:50` on master). Its first line, "user settings hold every isolation entry" (`:505`), runs `settings_merged` (`:482`): `node --input-type=module -e "$NOOP_JS" "$SELF_DIR/agent-settings-merge.mjs" "$USER_SETTINGS" <patron> <agentGh> <agent>`. Under `node -e` there is no script path, so `process.argv[1]` is the first argument, the merge module's own path. `SELF_DIR` is the script's real directory (`readlink -f`), so that string equals the module's `import.meta.filename`. `NOOP_JS` imports the module (`:473`), and the module's CLI guard, `import.meta.filename === process.argv[1]` (`agent-settings-merge.mjs:66`), holds on that import. The CLI then reads `process.argv.slice(2)`, which is exactly `NOOP_JS`'s settings path and the three merge arguments. When the file differs from the merge, it copies the file to `settings.json.bak-<time>` (`:97`), or makes the folder when the file is absent (`:98`), and writes the merge (`:99`). `NOOP_JS` then reads the merged file and exits 0, so verify prints `ok`. A verify run on a differing `~/.claude/settings.json` therefore rewrites it, leaves a backup, and reports a pass. Reproduced on master 75f826fe on a temp file (`repro-master.out`).

The fix has two parts. First, the merge script gains a read-only mode, `--check`. It reads the file and runs the unchanged `merge()`, then exits 0 when the merge would change nothing. Otherwise it exits 1 and prints one line per entry the merge would add (`missing <path>: <value>`), or why the file cannot be merged: absent, not a JSON object, a wrong type (the sandbox shape `merge()` refuses, a field `merge()` throws on, or one array or string the merge would write into), or a repeated entry. Entries are compared by their key-segment paths, so a literal dot in a key never collides with nesting (spec round 3). This mode never backs up, makes a folder or writes. Verify's settings line runs this mode, `NOOP_JS` is removed, and a FAIL is followed by those lines, indented. Second, the module's CLI runs only when node was started on it (`import.meta.main`). An import, a `node -e` importer whose first argument is the module's path included, runs none of it. `setup` and `guard` run the CLI without `--check`; they write the user settings as they do on master.

Sibling checks, examined on master 75f826fe for the same class, a check labelled as a read that can write. Every other verify line reads:

- `origin_is_https` and `helper_is_set` read git config only (`remote get-url`, `config --get-all`).
- `token_reads_repo` and `token_refused_admin` make three `gh api` GETs.
- `guard_inputs` uses `real` (a `cd` in a subshell), `cgit rev-parse` and `patron_on_master`, whose status already runs with `--no-optional-locks` (`:365`), so git writes no index.
- `guard_linked` uses `readlink -f`.
- `guard_live` runs the installed CLI's `hooks check` (`hooks.ts:201`): it reads the agent clone's `.claude/settings.json` and probes `hook-event guard`, whose handler reads only (`handleGuard`, `guardRefusal`).
- The `--inside` checks: `test -w` for `patron_unwritable`, `guard_unwritable` and `source_unwritable`, and `test -r`/`-s` for `unreadable`. `remote_reachable` runs `git ls-remote`, which fetches no objects.
- `guard-check`, the other subcommand labelled as a read, runs `guard_inputs` alone.

These reads are named as limits, not closed (Promise siblings). `gh` may keep its own state in `AGENT_GH`. `git ls-remote` runs the agent clone's configured transport and credential helper, from a sandboxed session. The probe CLI runs through tsx, which keeps its compile cache in the OS temp directory. `guard` and `sync` are write subcommands by their own labels (W-379, W-369) and are unchanged.

## Interfaces

**`node scripts/agent-settings-merge.mjs --check <settings.json> <patronDir> <agentGh> [<agentDir>]`** (new mode; without `--check` the CLI is unchanged):

1. The argument checks are those of the write mode: a missing argument prints the usage line and exits 2; a relative `agentDir` exits 2.
2. It reads the file once. An absent file reads as `{}`. A file that is not a JSON object, or cannot be read, prints `<file> is not valid JSON (an object); left untouched` and exits 1. When `merge()` throws on the sandbox shape, it prints `<file>: <reason>; left untouched` and exits 1. These are the write mode's own lines.
3. When the file exists and `isDeepStrictEqual(before, merge(before))` holds, it prints nothing and exits 0.
4. When `merge()` has not thrown (item 2) and `before` holds a wrong type it does not refuse, `--check` prints `<file>: <key> is not an object; left untouched` or `<file>: <key> is not an array; left untouched` and exits 1. These types are an array at `permissions` or `env`, and a string at `sandbox.filesystem.denyRead` or `permissions.deny`. On them `merge()` would set a property on the array, where no entry shows it and JSON drops it, or spread the string into its characters. Every other wrong type at these four keys (a string, number or boolean at `permissions` or `env`; a number, boolean or object at `denyRead` or `deny`) makes `merge()` throw, so item 2's `<file>: <Node's message>; left untouched` comes first. The promise covers a file with one wrong type. With several at once, `--check` still exits 1 and writes nothing, but which one line it prints is not promised (W-402).
5. Otherwise it exits 1 after printing, in order: `<file> does not exist` when absent; `missing <line>` for each structurally distinct leaf or array entry that `merge()` adds, comparing unambiguous key-segment paths so literal dots in keys cannot collide with nesting; and, when the file exists and the merge changes only by removing a repeated array entry, `<file> holds every entry, but the merge would rewrite it (a repeated entry)`. An entry (`entries`, new) is its key-segment path, its kind (a leaf or an array element) and its value as JSON, compared as one JSON string; its printed `<line>` is the dotted `path: value` text. With item 2's checks and item 4's passed, the merge changes a file in no way but adding entries and removing a repeated array entry (`union`'s `Set`), so a file that differs with no entry missing differs by a repeated entry alone.
6. No branch of the `--check` mode calls `copyFileSync`, `mkdirSync` or `writeFileSync`.
