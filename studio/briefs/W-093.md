## Intent

Decree family: security-review-every-change

Today the security pieces are disjoint. Master's ruleset holds a CodeQL `code_scanning` rule. `gate` stops every merge on any open default-branch alert (`state=GHAS_STOP open_alerts=<n>`, naming no alert and no opus), the PR that fixes it included. The `sec-lead` seat exists, but nothing orders it and no verdict records it. W-093 joins them, reusing what exists (D-042): the verdict writer, the review packet, `next`'s review order and the merge gate. It adds no workflow, job, scan or dependency.

With `security_reviewer: sec-lead` in the manifest, every current SOURCE tree of an `opus/<id>` branch needs a recorded sec-lead verdict (`ci/<id>-security-<n>.log`). The censor's build verdict cites it. Sec-lead's output is input, not a gate: the censor carries every sec-lead blocker as its own `blocking (security)` finding and stays the only writer of `probationes.review` (D-014).

Promise security-pass: in a configured studio, a censor build verdict is written only when it cites the highest sec-lead security log, that log is at the current SOURCE tree, and every standing sec-lead blocker reappears once as a `blocking (security)` finding — limit: `spec/<id>` and `chore/done-<id>` heads change no SOURCE tree and get no model pass; a studio without `security_reviewer` keeps today's path; the pass reviews the delta and facts the packet holds, not the whole repository.

Promise concurrent-review: while no security log matches the current tree, `next`'s review order names the censor and a sec-lead companion with its own packet, session and verdict command, so both orders name the same tree, and the security verdict is recorded only at its packet's commit (`--packet`); this holds until the censor's verdict at the current tree is recorded — limit: the censor's own packet and verdict are not bound to a commit (today's build-phase path, unchanged); the censor records last, since its verdict must cite the finished security log; after that, `next` does not re-read the security log, and a log removed or broken later is caught only by `gate` at merge (row 3).

Promise alert-fix: on every head, each open alert the repository read returns stops the merge, named by number with the opus, unless the fix pass admits it on this PR. The fix pass admits it only if GitHub's list for this PR's head ref (`refs/pull/<n>/head`) shows the alert `fixed`, and GitHub has analysed the pinned head commit in the alert's category. An unrelated PR's head still shows the alert open, so that PR stops — limit: each read is bounded to 100 records, and a full page stops; the fix pass trusts GitHub's state on the PR's head ref, which was verified for a fixed alert and an open one but not for a commit that brings a fixed alert back. Such a PR could merge while the alert stays open on master, where it already was. Every later merge then stops on it, except a PR the fix pass admits for it. The queue merges the PR onto the current master, which the PR-head analysis has not seen, with the same bound; PR-introduced alerts are withheld by GitHub's ruleset only at or above its thresholds (`readSecuritySetup` requires errors and warnings, and medium-or-higher security alerts, or stricter); a PR-introduced note or low-severity alert is neither withheld nor read by `gate`, and once it is open on master it stops later merges, except a PR the fix pass admits for it.

The threat model is mistakes (D-045). Every security finding is still fixed (D-044); the fix pass dismisses nothing. No test row, CI step or required check is removed.

## Interfaces

```text
bisellium verdict <id> --phase security --round <n> --sella sec-lead --model gpt-5.6-sol --outcome passed|failed --session <s> --packet <dir> --from <file> --studio <dir>
bisellium verdict <id> --round <n> --sella qa-lead --outcome <o> --security-input ci/<id>-security-<k>.log [--ui-input <p>] --session <s> --from <file> --studio <dir>
node --import tsx scripts/review-packet.mjs --phase security --opus <id> --round <n> --sella sec-lead --studio <dir> --repo <dir> --packets <dir>
```

A security log carries the build-phase headers with `phase: security`, and the build-phase body (`## Findings`, as today). A censor log in a configured studio adds `# security_input: ci/<id>-security-<k>.log` and a non-blank `## Security input disposition` section.

`next`'s review order adds `companion_sella`, `companion_round` and `companion_command` (packet, dispatch or resume, verdict) while no security log matches the current tree. This holds until the censor's verdict at the current tree is recorded; after that, `next` does not re-read the security log, and `gate` does (row 3). This is the interface W-169 shares: both reviewers work inside one claimed opus and write disjoint logs, and W-093 adds no lane claim.

`gate`, configured, `opus/<id>` head: it reads the rules once more (`readSecuritySetup`), then the opus's security input (`readSecurityInput`; an unusable input stops before any merge call, with or without open alerts). On every head it then reads the existing `code-scanning/alerts?state=open&per_page=100`. With at least one open alert, `alertsFixedOnHead` makes the fix pass's two reads, both `gh api` with no `--jq`. They run after the checks poll, whose `gh pr checks` reply includes CodeQL's `Analyze (...)` checks whenever GitHub runs them. The poll is unchanged and does not require those checks; the analyses read is the binding:

```text
repos/<slug>/code-scanning/alerts?ref=refs/pull/<n>/head&state=fixed&per_page=100
repos/<slug>/code-scanning/analyses?ref=refs/pull/<n>/head&per_page=100
```

An open alert N passes only if the first read lists N with `state: fixed`, and the second holds an analysis whose `commit_sha` is the pinned head and whose `category` is N's `most_recent_instance.category` from the open-alert read. If any alert does not pass, the gate prints `state=GHAS_STOP open_alerts=<n> opus=<id> alerts=<numbers>`, naming the ones that did not, and nothing is merged. In merge-queue mode (`pr` prints `mode: merge-queue`, W-168), `gate` runs before `gh pr merge --auto` enqueues the PR head, which is never rebased, and the queue's `certify` job is unchanged. In direct mode a BEHIND PR is updated first, and the reads use the updated pinned head; until GitHub has analysed that head, it stops.
