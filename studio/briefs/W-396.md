## Intent

W-370 (a553db3b) gave `scripts/ci-certificate.mjs` the reader the done perform uses (`readCertificate`) and the publisher (`certificatePayload`, `readArtifact`, `publish`, the entry point). No workflow runs the publisher, so no merge commit carries a `certify-certificate` check run and every done falls back to downloading the `certify-<run>` artifact through GitHub's blob host (D-106 C, the stopgap).

This opus adds the job that runs it. `certificate`, appended to `.github/workflows/ci.yml` after `certify`, runs on a merge group once `certify` has succeeded. It checks out master's tooling at the merge group's base commit, downloads certify's artifact on the runner (where the blob host is reachable), and runs master's publisher, which posts one check run on the merge-group commit. The queue fast-forwards master to that commit, so it is the merge commit the done perform reads (W-259's `certifyRun` already relies on this). After it lands, a done for an opus merged through the queue reads the check run with `gh api` and downloads nothing (W-370's Promise check-run-first).

Who can write the check run. Only a GitHub App token can create a check run, and the reader accepts only the `github-actions` app's. So the writers are the workflow jobs holding `checks: write`. On master that is `certificate` alone, and behaviour 1 pins it. Its token holds `contents: read` and `checks: write`, nothing more. Job-level permissions replace the workflow's, so `contents: read` must be named or its checkout fails (W-370 spec round 2, finding 1). Its checkout stores no credential (`persist-credentials: false`). Certify's token gains nothing.

Master's publisher, never the candidate's (W-370 spec round 4, finding 1). `actions/checkout@v5` treats an empty `ref` as the event's own commit (`download-artifact-runtime.out` quotes its `action.yml`). An empty `base_sha` would therefore check out the merge-group candidate and run the candidate's publisher with `checks: write`. Two steps close that, and neither carries an `if` or a `continue-on-error`:
- The job's first step, before any checkout, refuses a `base_sha` that is not 40 lowercase hex. An empty one never reaches the checkout.
- The step right after the checkout refuses a tooling `HEAD` that is not `base_sha`. It runs before the artifact, node and the publisher.

A failed step stops the job, and nothing is posted.

Records-only merge groups. `certify` passes a non-opus head whose diff changes officina records alone, and mints nothing (W-243), so its artifact holds `certify.log` and no receipt. The publish step runs only when the downloaded artifact holds a receipt (`hashFiles('certify/**/receipts/**/*.json')`). A records-only group posts nothing and its run still succeeds. Without that condition, `publish` would refuse with exit 2 (no receipt), and every chore merge's run would conclude `failure`.

What a failure costs. `certificate` is not a required check, so its failure leaves the merge alone. The run then concludes `failure`, though, and `certifyRun` (W-259, unchanged) records a done only from a successful run. So a failed `certificate` job holds that opus's done, and the done names `bisellium verify <id>` instead of falling back to the artifact. This fails closed and is a stated limit (Defaults 2).

How it lands, and what its own merge group proves (the W-323 trap, considered). The trap: certify runs master's tooling, so a change to the runner is judged by the old one at its own merge. W-396 changes neither `scripts/ci-certify.mjs`, the `certify` job, nor the publisher. On a `merge_group` event GitHub runs the workflow file at the merge-group commit, so the new job exists in W-396's own merge group. Its `tooling` is master at `base_sha`, which has carried the publisher since a553db3b. W-396 is an opus, so certify mints its receipt and the job posts the check run on W-396's own merge commit. That first run is the live proof, which no row can give:
- GitHub runs the job with the token, checkout, download and `hashFiles` behaviour assumed here, and both guards pass on a real `base_sha`.
- Master's publisher posts a body GitHub accepts.
- W-396's own done reads it back through `readCertificate`, so GitHub's list reply carries `output.text`, `external_id` and `app.slug` as posted (W-370's Promise round-trip limit).

If any of these fails, that done holds and names verify, and the job's log says which. If GitHub instead read the workflow from master, the job would not run in W-396's own group. W-396's done would then read zero check runs and take W-370's artifact fallback, and the next opus's merge group would be the first proof (a stated limit).

Threat model: mistakes and a confused writer, not a hostile repository administrator (D-045). The trust boundary is the set of workflow jobs that hold `checks: write`, which `.github/` code ownership guards.

## Interfaces

**The `certificate` job** (`.github/workflows/ci.yml`, after line 242, one blank line, then this comment and job; the comment does not contain the word "verify"):

```yaml
  # W-396: certify's certificate (W-370), posted as the one `certify-certificate`
  # check run on the merge-group commit, which the queue makes the merge commit,
  # so the done perform reads it through api.github.com. Runs only after certify
  # succeeded on a merge group. Its token reads contents (the checkout needs it)
  # and writes check runs, nothing more; no other job may write a check run. The
  # publisher is master's (`tooling`, the merge group's base commit), never the
  # candidate's: the first step refuses a base_sha that is not a 40-hex commit id
  # before any checkout (an empty ref would check out the candidate), and the step
  # after the checkout refuses a tooling HEAD that is not base_sha. An artifact
  # with no receipt (a records-only head mints none) publishes nothing. Not a
  # required check: a failure leaves the merge alone and fails the run.
  certificate:
    needs: certify
    if: github.event_name == 'merge_group'
    runs-on: ubuntu-24.04
    timeout-minutes: 10
    permissions:
      contents: read
      checks: write
    steps:
      - name: Refuse a merge-group base that is not a commit id
        shell: bash
        env:
          BASE_SHA: ${{ github.event.merge_group.base_sha }}
        run: |
          if [[ ! "$BASE_SHA" =~ ^[0-9a-f]{40}$ ]]; then
            echo "certificate: refused: base_sha is not a 40-hex commit id"
            exit 1
          fi
      - uses: actions/checkout@v5
        with:
          path: tooling
          ref: ${{ github.event.merge_group.base_sha }}
          persist-credentials: false
      - name: Refuse a tooling checkout that is not the merge-group base
        shell: bash
        env:
          BASE_SHA: ${{ github.event.merge_group.base_sha }}
        run: |
          head="$(git -C tooling rev-parse HEAD)" || { echo "certificate: refused: tooling has no HEAD"; exit 1; }
          if [[ ! "$BASE_SHA" =~ ^[0-9a-f]{40}$ || "$head" != "$BASE_SHA" ]]; then
            echo "certificate: refused: tooling HEAD $head is not base_sha"
            exit 1
          fi
      - uses: actions/download-artifact@v7
        with:
          name: certify-${{ github.run_id }}
          path: certify
      - uses: actions/setup-node@v5
        with:
          node-version: 25
      - if: hashFiles('certify/**/receipts/**/*.json') != ''
        run: node tooling/scripts/ci-certificate.mjs --dir certify
        env:
          GH_TOKEN: ${{ github.token }}
```

`base_sha` reaches both scripts through the environment, never spliced into the script text. The job-level `if` names no status function, so GitHub adds `success()`, and the job runs only when `certify` succeeded. `actions/download-artifact@v7` is that action's first Node 24 major (`download-artifact-runtime.out`), beside `upload-artifact@v6`. With no `github-token` it downloads from the current run. The artifact lands under the workspace, so the `hashFiles` condition can see it: `certify/_temp/certify.log` and `certify/<…>/candidate/studio/receipts/<…>.json`, the layout W-259's artifact walk and W-370-b3's fixture read.

**The check run, `certificatePayload`, `readArtifact`, `publish`, `readCertificate`**: W-370's, unchanged (`studio/briefs/W-370.md`, Interfaces). The job calls the entry point as `node tooling/scripts/ci-certificate.mjs --dir certify` with `GH_TOKEN` and the runner's `GITHUB_EVENT_NAME`, `GITHUB_REPOSITORY`, `GITHUB_SHA` and `GITHUB_RUN_ID`. Exit 0 posted, 1 a failed post, 2 refused input; 1 and 2 fail the job.
