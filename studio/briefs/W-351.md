## Intent

High under D-039. W-347 added `isInMergeQueue` to `PR_VIEW_FIELDS`, the fixed field list used by every `gh pr view --json` read. The installed gh 2.101.0 refuses that name before it reads a PR, so merge perform, done perform and every other fixed PR read now stop at `Unknown JSON field: isInMergeQueue`. Queue membership is available through GitHub's GraphQL schema, not this gh field vocabulary.

After this opus:

- Every fixed `gh pr view --json` call returns to the seven fields gh 2.101.0 accepts: `number,state,mergeStateStatus,headRefName,headRefOid,baseRefName,mergeCommit`. A row compares every requested token with a fixed copy of that version's complete `Available fields` list.
- Queue membership leaves `Pr`, `checkShape`, `toPr` and fixed views. Only a queue-mode poll that sees `CLEAN` and has not already re-armed calls `gh api graphql` for `repository(owner,name){pullRequest(number){isInMergeQueue}}`, with owner, name and number as variables.
- Boolean `false` preserves W-347's one disable/enable recovery; boolean `true` preserves its wait. A failed command or any reply without that exact nested boolean holds the merge, states that membership is unreadable and auto-merge was not re-armed, and makes neither recovery write.

Threat model: mistakes and CLI/schema drift, not adversaries (D-045).

## Interfaces

The prototype is four commits after master 06521a4d, test then feature for each behaviour. `apply-test.py <checkout>` applies both rows; `apply-src.py <checkout> <1|2>` applies source cumulatively; `stages.sh <master|s1|proto>` materialises a fresh local clone under `$TMPDIR` without a network call. The build reproduces it; a hunk that no longer applies after a rebase is redone to the same contract.

1. `PR_VIEW_FIELDS` and `readView` (`integrate.ts`, narrowed). The field string is exactly `number,state,mergeStateStatus,headRefName,headRefOid,baseRefName,mergeCommit`. `Pr` carries no queue-membership property; `checkShape` does not require it; `toPr` does not copy it. Every caller of `readView` therefore uses only fields in gh 2.101.0's fixed accepted set.

2. `readQueueMembership(repo, pr)` (`integrate.ts`, new and private). It splits the already-validated `pr.repo` slug into owner and name and calls:

   `gh api graphql -f query=query($owner:String!,$name:String!,$number:Int!){repository(owner:$owner,name:$name){pullRequest(number:$number){isInMergeQueue}}} -F owner=<owner> -F name=<name> -F number=<PR number>`

   It returns `{ ok: true, queued: <boolean> }` only when the reply has a boolean at `data.repository.pullRequest.isInMergeQueue`. A spawn failure, non-zero exit, over-limit/empty/non-JSON output, top-level GraphQL error shape, null/missing object or non-boolean membership returns `{ ok: false, reason }`.

3. `gate(ctx, pr, "merge-queue")` (`integrate.ts`, corrected W-347 branch). After the initial pinned auto-merge request, only a poll whose fixed view is `OPEN`, `CLEAN` and not already recovered calls `readQueueMembership`. `true` continues the existing poll. `false` disables auto-merge then enables pinned squash auto-merge exactly once. A failed membership read returns the existing held result with `<read reason> (queue membership unreadable after the merge was requested; auto-merge was not re-armed)` before either recovery command. `DIRTY`, non-`CLEAN`, direct mode and an already re-armed poll do not call GraphQL.

4. The fake gh boundary (`next-world.test.ts`, extended). Slot `queue` matches `api graphql` before the catch-all API slot and defaults to the exact nested `true` reply, so existing queued-CLEAN rows continue to wait. W-347-b1 supplies nested `false`; W-351-b2 supplies null, text and a command failure. Fixed `viewOf` replies contain only the seven `PR_VIEW_FIELDS` fields.

Promise fixed-view-fields: every `gh pr view --json` call made through `readView` requests only names in gh 2.101.0's accepted field vocabulary — limit: the vocabulary is a fixed test copy, not a live query, so a future gh that removes or renames a field needs the copy and production list updated together.

Promise one-queue-read: queue membership is read only for W-347's queue-mode `CLEAN`, not-yet-rearmed decision, through `gh api graphql` and not through `gh pr view` or `pr list` — limit: GraphQL availability and GitHub's meaning of `isInMergeQueue` are external and are not guaranteed.

Promise queue-read-closed: a queue-membership command failure or reply without the exact nested boolean holds before disable-auto or the second auto-merge command and states that no re-arm occurred — limit: the initial pinned auto-merge request has already happened, as it did before the poll.

Promise queue-rearm-preserved: nested boolean `false` keeps W-347's disable then pinned-enable recovery once, and `true` keeps the queued-CLEAN wait — limit: approvals, why GitHub left the PR out, and the existing timeout after one recovery are not judged.

Limits, stated:

- Unchanged code the promises lean on is a stated limit, not a guarantee (D-076 E): `ghJson`, `repoSlug` and `SLUG_RE`, fixed-view identity and enum checks, `sameIdentity`, `descends`, `landed`, merge-queue setup reads, checks/GHAS, poll count/timing and `held` rendering.
- The accepted field list is copied from the installed gh 2.101.0 error output because the offline row cannot obtain that output from a real repository call. It proves compatibility with that copy, not with every gh release.
- `PR_LIST_FIELDS` and every `gh pr list` read are unchanged; list fields are a different gh vocabulary and queue membership is not requested there.
- The GraphQL read does not retry separately. A later merge perform may try again under the existing lifecycle.

## Defaults for the Patron

1. The CLI now treats gh 2.101.0's printed field vocabulary as a pinned compatibility boundary. If gh changes that vocabulary later, the fixed copy and production field list must be reviewed together. Agree?
2. A green queue-mode PR gets one GraphQL membership read per poll until it is queued or re-armed. If that answer cannot be read exactly, the merge stops and says no re-arm happened; it does not guess that the PR is outside the queue. Agree?
3. The initial auto-merge request still happens before the membership read. "No re-arm" means neither the disable nor the second pinned enable call ran; it does not undo the initial request. Agree?
