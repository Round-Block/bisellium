## Intent

Every architect already stages a prototype and shows each red failing and passing per stage (W-268's and W-336's spec evidence). The builder then redoes that work by hand, one behaviour at a time, with a step ticket before each red. The audit (`~/.bisellium-evidence/spec-build-1019/compiled.md`, cause 2) found the separate builder costs 2 to 5 minutes an opus plus any idle gap: the dispatch, its brief and the hand replay. The evidence the branch must hold (one red per behaviour on the previous behaviour's commit, D-036; each on its own ticket, D-064 C; the branch's own gate logs, W-312) is necessary; a separate author of it is not (D-014 and D-066 C separate reviewer from author, not signer from builder).

After this opus, `next <id> --perform --expect reds` replays the signed prototype itself, and a builder is dispatched only where the replay cannot run.

**The prototype, named and signed.** The brief carries one line `Prototype: <absolute or ~/ path> sha256:<64 lowercase hex>`. The file is `git format-patch --stdout` of the architect's staged commits: for each behaviour k in order, an optional `test(<id>): row b<k>, red` patch (required for behaviour 1), then one `feat(<id>): behaviour <k>` patch. The spec signature pins the brief's blob (W-206) and the spec review judges that brief, so the digest the replay checks is the signed one. That is how the replay proves it reproduces the signed prototype: it applies only the bytes whose sha256 the signed brief names, each patch by `git am` with no three-way merge, and the reds and the gates judge the result as they judge a builder's.

**The reds perform (design question a).** The reds rung gains a perform, `next <id> --perform --expect reds`, rather than a kept script (D-042: extend the ladder's own mechanism). Its cost is in proportion: one rung reading, one perform, one module of readers. The rung names it when the brief's line is well formed, no replay of the opus was attempted before, the worktree's `ci/reds/<id>/` is read and holds no red, the file is a regular file at that sha256, the series is in the grammar for the brief's behaviours, each behaviour names one red command, and the whole series applies at the worktree's HEAD (`git apply --check --index`, nothing written). The perform first marks its attempt (`.bisellium/prototype-replay/<id>.attempted` in the main checkout, created exclusively), then does, for each behaviour in order: commit its test patch; issue a ticket for that red at that commit; record the red with the brief's command under the design sella (the prototype's author); commit the log alone; commit the implementation. So the reds stay one behaviour at a time on the previous behaviour's commit, each with its own step ticket (design question c), and the red verb's own refusals (a passing command, a dirty tree, a failing earlier behaviour) all still apply.

**Fail closed (design question b).** No Prototype line keeps the old builder order; every other state names the builder and its reason, `prototype: not replayed: <reason>`. That covers a malformed line, an earlier attempt, a recorded red, a reds directory that cannot be read as one (an unreadable level, a symlink or a non-directory), a digest the file does not have, a series out of grammar, a command a shell would read, and a hunk that no longer applies after master moved. A record or git state the replay cannot read is a reason, never "nothing there". The perform writes its attempt marker before its first write and refuses, with nothing written, when it cannot. So a perform that stops anywhere (a first `git am` that fails with HEAD unchanged, a red that passes, a red that is not usable, a HEAD it cannot read, a crash) holds naming the behaviour and the step, keeps the commits it completed, and every later derivation reads the marker and names the builder. The replay runs once per opus. No order loops. The round-2 review proposed a `.failed` marker keyed on HEAD and the signed digest, written before each hold; this one is written before the first write and keyed on the opus alone, so a crash, or a hold the code does not foresee, leaves it too, and no staleness rule is needed.

**The gates and the fixes (design question d).** After a replay with no required fix standing, the build rung names the producer's commands instead of a builder: `bisellium handoff`, then `ci --opus` (the one full suite), then the gate commit. A `ci --opus` that exits non-zero is a builder's. A failed spec review whose blockers all keep the design (D-086 A) still replays the signed prototype. Its required fixes go to a builder at the build rung, as today: the architect cannot fold them into the prototype after the review, because any brief or series edit needs a new signature and review (lex §9 step 2), which is the round D-086 saves. The order names them (`required-fixes`) on the replay and on the builder's build order.

**The lex (design question e).** Lex §9 steps 0 and 3 and §10 are reworded to say who does what, and `studio/prompts/spec-draft.md` tells the architect how to cut and name the series. Both are code-owned: the Patron merges.

**W-310's seam (named, not designed).** W-310's dispatch-role hook decides who may run a perform and a record write. This opus adds one performable rung (`reds`, in `PERFORMABLE`) and records each red under the design sella. If W-310 lists performs, `next <id> --perform --expect reds` is one of them, run by whoever runs the other performs (lex §9 step 0).

Promise replay: when the brief on opus/<id> carries one Prototype line naming a regular file of at most 8 MiB at that sha256, a series of exactly behaviours 1 to n in the grammar, one red command per behaviour in single-quote-only words, no attempt marker for the opus, a `ci/reds/<id>/` read as absent or empty, and the whole series applying at the worktree's HEAD, `next <id> --perform --expect reds` marks its attempt, then commits each behaviour's test patch, records its red with a ticket issued at that commit under the design sella, commits the log alone and commits its implementation, in order, so that afterwards every red is recorded on the commit before its implementation and the branch's source tree is the series applied — limit: `git am` places a hunk at an offset when lines above it moved, so the replayed tree equals the architect's staged tree only on the master the series was cut on, and the reds and the gates judge it either way; the series' paths are not checked against Files owned (the build review and the merge queue judge them); the replay does not run the host's replay classifier (certify does, at merge, and the architect's spec evidence classified each red on the same patch text).

Promise fail-closed: any other brief, series, branch, worktree or marker state, including one that cannot be read, names the builder's reds order with `prototype: not replayed: <reason>` (with no Prototype line, or a brief that cannot be read, the builder's order as before), and a perform that stops at behaviour k holds naming k and the failed step, keeps the commits it completed, and leaves every later derivation the builder's order through its attempt marker — limit: a series that passes `git apply --check` and still fails a `git am` holds without rolling back the patches before it; the marker is never removed, so a replay that held is not retried once its cause is fixed (the builder takes it, as before W-326; deleting the marker by hand allows the replay again); whether the marker can be written is read as `access(W_OK)` on its deepest existing directory, so a write that fails anyway (a full disk) refuses the perform before any write and the order stays the replay, the refusal naming that cause until it is fixed; a red the verb records and the rung cannot use is left uncommitted for the builder to re-record.

Promise gates: after the replay, with no required fix standing and no failed review, the build rung names the producer's `bisellium handoff`, `ci --opus` and gate commit, and a builder only for a `ci --opus` that exits non-zero; with a required fix standing, or a red not recorded under the design sella, it names the builder's phase 2 order as before — limit: "replayed" is read from the reds' `# sella:` header, so a red recorded by hand under the design sella reads as replayed (the gates and the review still judge the code); a failing `ci --opus` records nothing, so the order says in words, not by derivation, that a builder takes it.

Threat model: mistakes, not adversaries (D-045). The series file is a host file the architect writes; its digest in the signed brief catches a file changed after the signature, not a forged brief.
