## Intent

Since advisory GHSA-g3hv-75wg-m249 was published (minimatch below 11.0.1, moderate, denial of service by globparts amplification), `npm run -s audit` (W-236's gate, `npm audit --audit-level=moderate`) exits 1 on master, so the required `gates` check fails on every PR. Its one finding (`audit-master.out`, 10 moderate entries, all the same advisory): minimatch 10.2.6, the lock's only copy, reached only through the dev lint tooling: `eslint` 10.10.0 and its `@eslint/config-array` 0.23.5, and `typescript-eslint` 8.70.0's `@typescript-eslint/typescript-estree`. Their latest releases (eslint 10.14.0, typescript-estree 8.72.1) still ask for `minimatch ^10`, so npm has no fix short of a downgrade to eslint 4. minimatch 11.0.3 is published and is the latest.

**The change (the Patron's option 1).** One top-level entry in the root `package.json`, `"overrides": { "minimatch": "^11.0.1" }`, and `package-lock.json` as `npm install` then writes it (`apply.sh`, `prototype-deps.diff`): `node_modules/minimatch` goes from 10.2.6 to 11.0.3 (its version, resolved, integrity and dependency ranges), and minimatch 11's own new dependency `@isaacs/nonrecursive-glob-match` 1.0.3 (dev, BlueOak-1.0.0) is added; `brace-expansion` stays at 5.0.12. Nothing else in the lock moves, and no `devDependencies` range changes.

**Why a global override, not one nested under eslint and typescript-eslint.** All three dependents share one hoisted copy, so the two shapes resolve the same tree today. The global entry is one line, covers a dependent added later (which would otherwise bring 10.x back, fail the audit and fail the row), and matches the row, which reads every minimatch in the lock. The nested shape (`{ "eslint": { "minimatch": … }, "typescript-eslint": { "minimatch": … } }`) was not prototyped. Its range is `^11.0.1`, the advisory's first fixed version, not an exact pin: the lock pins 11.0.3, and a later 11.x needs a lock change anyway.

**What proves it.** The audit needs the registry, and no test here may reach the network. So, as W-236 and W-346 did, the replayable evidence is an offline node:test row on the lockfile in W-236's file (`scripts/source-map-js.test.mjs`, already in `test:suite`, so `test:suite` is not edited): every `node_modules/minimatch` entry is a plain version at 11.0.1 or above, at least one is listed, and the root `package.json` holds the override. On master's lock it fails by assertion at `node_modules/minimatch is 10.2.6`; on the prototype it passes (`reds.out`).

**eslint on minimatch 11 (a stated limit, D-076 E).** eslint's own behaviour on a minimatch it does not ask for is unchanged code this opus leans on, not a promise. Measured on this tree (`baseline.out`): `npm ci` from the new lock is clean, `npm ls minimatch --all` shows 11.0.3 only, `npm run -s audit` finds 0 vulnerabilities, and `npm run -s lint`'s output is the same on 10.2.6 and on 11.0.3 (0 errors, 8 warnings). A probe through eslint's own API (`eslint-globs.mjs`) gives the same answer for all 14 cases on both versions: `eslint.config.js`'s ignores (`docs/`, `examples/`, `studio/`, `.worktrees/`, `node_modules`, `dist`, `.claude/`) are ignored, source files are linted, and `local/exact-digits` is on for source and off for `*.test.*`, `test/` and `scripts/ci-certify.mjs`.

**Behaviour 2: row W-430-b5 fails on master since 2026-10-30T21:00Z.** Its last part (`packages/cli/src/w430.test.ts`, `next --all, on the real clock`) writes a Codex session line whose time is fixed, `2026-10-28T01:00:00.000Z`, and whose week `resets_at` is the real clock plus 100 h. `weekWindow` (`packages/cli/src/usage-reading.ts`) reads a week only when its reset falls between the line's time and a week after it; once the real clock passed 2026-10-30T21:00Z, the reset is more than a week after the fixed time, the window is not read, `next --all` prints `codex: unread (no session log holds a week rate_limits)` and the row fails at its assertion `the codex line, before the open count` (`red-b2-master.log`).
