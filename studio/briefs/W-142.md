# W-142 — verify's gate timeout fits the suite

Status: **signed spec, revision 1** · architect sella (claude-opus-5-5) · 2026-10-06.
The spec gate is written by `bisellium verdict W-142 --phase spec`, not by this text.

## Intent

Decree family: gate-timeout

The decree: **one gate timeout, with headroom over the measured suite,
bounds both `verify`'s gate commands and `bisellium ci`'s steps.**

Today `localPipeline` kills a gate command after a hard 10 minutes
(`TIMEOUT_MS`, `packages/pipeline/src/index.ts:51`). `bisellium ci` keeps
its own copy of the same 10 minutes (`STEP_TIMEOUT_MS`,
`packages/commands/src/ci.ts:89`). The suite has outgrown both:

- **Local:** `npm test -s` at master `d8bf1fb` took **11 min 09 s** wall
  time and exited 0 (WSL, 24 cores, load average about 1.3).
  `packages/cli/src/next.test.ts` alone took **480 s**, 72% of the run.
  Evidence: `~/.bisellium-evidence/W-142-spec/npm-test.time` and
  `npm-test.out`.
- **CI:** across the last 30 `ci.yml` runs, the `npm test` step took
  318–551 s, with a median of about 480 s. The slowest was W-141's PR,
  run 37365848625, at **551 s**. Script and output:
  `~/.bisellium-evidence/W-142-spec/measure-ci.sh` → `measure-ci.out`.
  The two failed runs in that window are runner cancellations at 15
  minutes, not test failures.
- **Effect:** verify timed out on W-140 once (it passed on rerun) and on
  W-141 twice. Every `done` needs verify's certificates (W-141), so every
  `done` is blocked until the cap fits.

The fix is the laziest one that holds. The cap is raised to 30 minutes,
about 2.7 times the slowest measured run. That still bounds a runaway: a
hung gate costs 30 minutes, not forever. The value lives in one exported
constant, which `bisellium ci` imports in place of its own copy. Nothing is
configurable, and the `PipelineRunOpts` seam does not change.

## Files owned

- `packages/pipeline/src/index.ts` — `TIMEOUT_MS` becomes the exported
  `GATE_TIMEOUT_MS`. `localPipeline`'s doc comment stops saying
  "10-minute".
- `packages/commands/src/ci.ts` — `STEP_TIMEOUT_MS` is deleted. Both of its
  uses (`defaultInstallDeps` and `runStep`) take `GATE_TIMEOUT_MS` from
  `@bisellium/pipeline`. `@bisellium/commands` already depends on that
  package (`verify.ts` imports `localPipeline` from it), so the module graph
  does not move.
- `packages/pipeline/test/gate-timeout.test.ts` — new; row `W-142-b1`.
- `package.json` — `test:suite` runs the new file with
  `node --test-reporter=tap --import tsx`, right after `gate-env.test.ts`.

## Interfaces

```ts
// packages/pipeline/src/index.ts
/** Wall-clock cap on one automated gate command under `verify`, and on one `bisellium ci` step. */
export const GATE_TIMEOUT_MS = 30 * 60_000;
```

The timed-out log line keeps its shape, and so it now reads
`exit code: (timed out after 30m)`. `PipelineRunOpts` and `MergePipeline`
are unchanged.

## Behaviours to test

The row lives in `packages/pipeline/test/gate-timeout.test.ts` (node:test,
TAP). It is named `W-142-b1 behaviour 1: …` and is selected by
`--test-name-pattern=W-142-b1`. The test pins the slowest measured run as
a constant, `SLOWEST_SUITE_MS = 669_000`, with a comment that cites the
local measurement and CI's 551 s.

1. **The gate timeout is one exported constant with at least twice the slowest measured suite run as headroom, and no more than an hour.**
   The test imports the module as a namespace (`import * as pipeline`)
   and reads `GATE_TIMEOUT_MS` from it. It asserts three things:
   - the value is a number;
   - it is at least `2 * SLOWEST_SUITE_MS`;
   - it is at most `60 * 60_000`, so a runaway stays bounded.

   **Genuine red:** the builder first exports the constant at its current
   value (`GATE_TIMEOUT_MS = 10 * 60 * 1000`, nothing else changed) and
   records the red. The row then fails on the headroom assertion
   (`600000 < 1338000`), which is exactly the defect: the cap is below the
   suite. It does not fail on a missing export. Then the value is raised
   and `ci.ts` is switched over.

## Out of scope

- **Speeding up `next.test.ts`** (480 s locally, 72% of the suite). That is
  the real cost, and it is its own decree family. This opus only stops the
  cap from failing a suite that passes. A follow-on is for the producer to
  file.
- **A cap read from the manifest** (a per-probatio `timeout`). That would be
  a schema change and a new check surface for a value no adopter has asked
  to set (Patron question 2).
- **An injectable timeout on `PipelineRunOpts`.** It would change the seam
  for a test alone. The live verify in Acceptance proves the raised cap
  end to end.
- **The host runner's red-replay timeouts** (`scripts/run-builder-host.mjs`,
  10 minutes for the web build and each replay). A replay runs one test
  selection, not the suite.
- **A `timeout-minutes` on `ci.yml`.** None is set, so GitHub's default of
  360 minutes applies. The 15-minute cancellations measured were queue
  cancellations, not the job timing out.

**Open questions for the Patron.** Each default ships as stated and can be
vetoed at the checkpoint.

1. **The cap is 30 minutes.** Default: 30, about 2.7 times the slowest run
   measured (11 min 09 s locally). The alternative is 20 minutes, which
   leaves only 1.8 times the slowest run as headroom.
2. **The cap is not read from the manifest.** Default: no. It is one
   constant, and raising it is a one-line opus. Revisit when an adopter's
   suite needs a different cap from ours.
3. **A follow-on to speed up `next.test.ts`.** Default: yes, the producer
   files it after this lands.
