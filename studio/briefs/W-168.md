## Intent

Decree family: merge-queue-certification

The decree: **when a verb's rules read succeeds and its reply is exactly the queue this brief sets up (squash, one PR per group, one group building, `certify` required, branches not required up to date), `next`'s `pr` step pushes the reviewed head without rebasing, `merge` enqueues it without updating it, and the queue's `certify` job runs the existing mint on the merge result from master's tooling before GitHub merges it. Any other reply, including a gh error or a malformed or truncated one, is direct mode, even when the setup is in fact active. In direct mode, `pr` and `merge` make today's writes and remote calls plus three additions: the rules read (`gh api repos/<slug>/rules/branches/master?per_page=100`), one local `git config --get` of the queue binding, and the `mode: direct` line (a binding read error holds); a PR whose binding is set is held at `merge`, and its `pr` removes the binding after its push.**

Why. Today `openPr` rebases onto master. A moved master changes the SOURCE tree, so the receipt goes stale and the opus needs a second ~15-minute local mint. That is why the production lex holds every PR (§11, "until W-168"). A merge queue tests the PR merged with the latest master. If CI runs the mint there, the rebase, and with it the re-mint, is not needed.

What stays. The first local mint after the passing review stays, and so do `review-receipt.sh` and `record-review.sh`. The receipt and the review are bound to the PR head, which in queue mode is never rewritten. `verify` on master at `done` stays local. A PR that conflicts with master still needs a local rebase. The conflict fix is new source, so today's local re-mint follows (see the Patron call under Defaults).

Parity (lex §11, "CI certifies at least what the local mint does"). The `certify` job runs the same command as the local mint, so every row is the same row:

| Local mint row | On the merge group |
|---|---|
| builder cell (`true`) in bwrap; export check of builder commits (none for `true`) | the same, same cells |
| every red replayed at the commit whose SOURCE tree its log names, with an assertion-level failure; when no commit has that tree, at the commit that introduced its log (W-134), where every recorded `not ok` title must reappear | the same, on the PR head rebased onto the merge group's base inside the job |
| `ci --opus <id>` from master tooling: the six `CI_STEPS` and `verify` | the same; tooling is the merge group's base commit |
| receipt written | written in the runner and uploaded as an artifact |

The `gates`, `officina` and `web-e2e` jobs also run on the merge group, always on the full path: their `scope` step runs only on `pull_request`. That covers live rows, the read guard, both officina checks and the web E2E, which is more than the mint runs. No row is removed. What CI does not reproduce is the host: a fresh GitHub-hosted VM replaces the WSL host. The cells, Git broker and host checks are the same code.

Master pin and its limits. On `merge_group`, GitHub runs the workflow file of the merge-group commit, which includes any edit the PR makes to it. The certifying code is not taken from that commit. The job checks out `merge_group.base_sha` as `tooling` and runs `tooling/scripts/ci-certify.mjs`, which runs the mint through `tooling/packages/cli/src/main.ts`. The code of the mint's host runner and of its gate tooling therefore comes from master. `ci-certify.mjs` refuses a tooling `HEAD` other than `base_sha`, and a base that is not `origin/master`. With build concurrency 1 the base is master's tip. What is pinned to master is bisellium's own code: the script, the CLI, the host runner and the gate tooling. The limits:

- (a) A PR that edits `.github/workflows/ci.yml` changes the YAML that calls the certifier for its own merge group. A PR that adds another Actions job named `certify` adds a check that can satisfy the required context, since the 15368 binding names GitHub Actions, not the job.
- (b) Third-party packages are the PR's. The host runner copies the repository's `node_modules` (`hostModules`, `scripts/run-builder-host.mjs`), here the candidate's, installed from the PR's lockfile, into its master-tooling clone, and relinks only `@bisellium/*` to that clone (`rebaseWorkspaceLinks`). So the master gate code runs on the PR's versions of `tsx`, `yaml`, `typescript` and the rest. The local mint does the same today. A PR that changes a dependency therefore certifies with that change, and a dependency mistake can change what the gate does, in CI exactly as in the local mint.
- (c) The candidate's `npm ci` lifecycle scripts and `npx playwright install` run on the runner outside bwrap before the mint, with write access to its files, `tooling/` included, as the host's `npm ci` in the worktree does before a local mint.
- (d) GitHub-hosted runners and the `actions/*` used are trusted.

Under D-045 (mistakes, not adversaries), review is the guard for workflow and dependency edits. Copying the tooling's own `node_modules` into the tooling clone would close (b). It is a follow-on, not part of W-168, because it changes the host runner for both mints.

Reds after a squash merge. A merge group is one squash commit on the base. It does not contain the PR's commits. `ci-certify.mjs` fetches them from `refs/pull/<N>/head`, which GitHub keeps after the head branch is deleted, pins that commit to the PR's `headRefOid`, and rebases it onto the base inside the job. The mint replays each red there, as a local mint does after a rebase. Those rebased commits live only in the run and are named in the uploaded receipt. The original red commits stay reachable from `refs/pull/<N>/head`, and the red logs ride the squash in `studio/ci/reds/`.

Threat model (D-045): mistakes. The `certify` check is bound by GitHub to the merge-group head SHA, and the queue merges only that commit, so a stale or mismatched certification cannot land. An artifact attestation would add a signed, portable binding. That guards against forgery, or later offline proof, and neither is needed here, so the receipt is a plain artifact (default retention). `verify`, `check` and report-mode `next` make no new network read.

`tooling` is the script's own checkout top level. The CLI wires `gh` and `mint` to real spawns. `certify` logs one `certify:` line per step. It runs in two phases.

Phase A runs no Git command that writes:

1. Checks the event.
2. Checks the candidate, the tooling and the studio.
3. Checks that `repository.full_name` equals the slug of the candidate's `git config --get remote.origin.url`, the configured URL before any `insteadOf` rewrite.
4. Reads the candidate's `<studio>/bisellium.yml` (the `HEAD` check makes it `head_sha`'s) with `readManifest`, requires a mapping, then applies `readSourceExcludes` (tooling's `packages/commands/src/verdict.ts`).
5. Reads the PR (`gh pr view <N> -R <slug> --json number,state,headRefName,headRefOid,baseRefName,isCrossRepository`).

Phase B moves only the job's disposable candidate checkout:

1. Runs `git fetch -q origin refs/pull/<N>/head master` and checks the fetched head and `origin/master`.
2. Runs `git checkout -q -B opus/<id> <headRefOid>`, then `git branch -f master <base_sha>`, then `git rebase -q master` with a fixed committer identity. On a conflict it runs `rebase --abort` and returns 1.
3. Requires `git rev-parse HEAD^{tree}` to equal `<head_sha>^{tree}`. The whole tree, studio included, so the minted officina is exactly the merge group's.
4. Calls `mint([process.execPath, "--import", "tsx", <tooling>/packages/cli/src/main.ts, "run", "--sella", "builder", "--opus", <id>, "--studio", <candidate>/<studio>, "--repo", <candidate>, "--", "true"], <candidate>)`, and returns 0 only if it returns 0.

No refusal in either phase calls `mint`. A refusal in phase A runs no writing Git command. Once the script starts, its `certify:` lines go to the job log and to `certify.log`. The upload step runs `if: always()` with `if-no-files-found: warn`. A job that fails before the script starts (a checkout, `npm ci` or `playwright install` failure) uploads nothing and leaves only the job log.

The `certify` job runs only `if: github.event_name == 'merge_group'`. On `pull_request` it is skipped, which a required check counts as passing. It has `timeout-minutes: 100`, `permissions: { contents: read, pull-requests: read }` and no `continue-on-error`. Its steps, in order:

1. `actions/checkout@v5` with `path: candidate` and `fetch-depth: 0`.
2. `actions/checkout@v5` with `path: tooling` and `ref: ${{ github.event.merge_group.base_sha }}`.
3. `actions/setup-node@v5` with `node-version: 25`.
4. `sudo apt-get update && sudo apt-get install -y bubblewrap` (as in `gates`).
5. `sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=0` (as in `gates`).
6. `npm ci` in `tooling`.
7. `npm ci` in `candidate`.
8. `npx playwright install --with-deps chromium` in `candidate`.
9. `node --import tsx scripts/ci-certify.mjs --candidate ../candidate --studio studio 2>&1 | tee "${{ runner.temp }}/certify.log"` in `tooling`, with `shell: bash` (GitHub's `-eo pipefail`, so the script's exit is the step's) and `GH_TOKEN: ${{ github.token }}`.
10. `actions/upload-artifact@v4`, `if: always()`, `if-no-files-found: warn`, named `certify-${{ github.run_id }}`, holding `candidate/studio/receipts/` and that log, whichever exist.

`openPr`, in queue mode: after its existing on-branch, dirty and `fetchTrunk` checks pass, it reads the mode and does not rebase. It reads the worktree's full `HEAD` with `readRef(wt, "HEAD")` and sets the queue binding `git config branch.opus/<id>.bisellium-queue <HEAD>` (a failed read or write holds before any remote change), pushes `--force-with-lease`, then reuses or creates the PR. In direct mode `openPr` reads the key with `git config --get` at the mode read: absent (exit 1) is the direct path with no other binding call; present (exit 0), it runs today's rebase and push and then `git config --unset-all` on the key (a non-zero exit holds, key kept); any other exit holds before the rebase. `mergeGate`, in direct mode, reads the key right after the mode read: absent (exit 1) is the direct path; present, or any other exit, holds with `why: PR #<n> was pushed for the merge queue without a rebase, and master no longer enforces the queue; rebase opus/<id> onto master, which changes the SOURCE tree and needs the local mint again`, before any `gh` write. `mergeGate`, in queue mode: it never calls `gh pr update-branch` or the CLEAN direct-merge fallback, and makes the one `gh pr merge --squash --auto --match-head-commit <pin>` call. Immediately before that call it reads the rules again; any result but `merge-queue` holds with `why: master's merge-queue setup changed while the merge step ran; nothing was enqueued` and makes no `gh` write, and the binding stays. Limit: the recheck and `gh pr merge --auto` are separate calls, so the queue removed between them is not caught. That is outside D-045's mistake model, and Patron setup 4 says to empty the queue first. In direct mode no recheck is needed: a queue that appears mid-step only turns `--auto` into an enqueue. Steps of one opus never overlap, because `next`'s step marker serializes them, so no binding changes between its read and a write. A PR read `DIRTY`, before or after that call, holds with `state=CONFLICT` and `why: PR #<n> conflicts with master; rebase opus/<id> and resolve it there: that changes the SOURCE tree and needs the local mint again`. Checks, GHAS, the poll, `landed`, `QUEUE_REJECTED`, `HEAD_MOVED` and `QUEUE_TIMEOUT` are as today.

The mode line (`mode: merge-queue` or `mode: direct`) is printed only by a verb that reaches the mode read, and then it is the first line of that verb's result:

- `openPr` reads the mode where it would rebase today, after the on-branch, dirty and `fetchTrunk` checks. A refusal before that prints today's lines and no mode.
- `mergeGate` reads it right after its existing MERGED and not-OPEN returns, so for an OPEN PR only. A MERGED PR goes to `landed` with today's lines and no mode.

So for an OPEN PR at the merge step, `next --perform --expect merge` prints `mode: merge-queue` followed by the checks polls and then `state=MERGED`, `state=CONFLICT`, `QUEUE_TIMEOUT` and so on. Without the queue it prints `mode: direct` followed by today's lines, after the rules read and the binding read. Report-mode `next` is unchanged.

### Input domain

Every rejection fails closed. `certify` exits 2 for a refused input and 1 for a failed certification; neither mints, and a non-zero exit fails the required check, so GitHub removes the PR from the queue (it is not re-queued on its own) and nothing merges. `readMergeQueue` turns any reply outside its domain into `direct`, the direct path. The reads were enumerated mechanically, not by inspection: `~/.bisellium-evidence/W-168-spec/enumerate-reads.mjs` parses every non-test source, closes the call graph by name from `runNext` (through `gather`, `deriveNext`, `gateDispatch`, `openPr` and `mergeGate`; the other steps' performers excluded), the mint (`runCommand`, `runBuilderCommand`, the host runner's top level, `runCi`, `runVerify`, the local pipeline's `run`, `checkStudio`, `classifyReplay`) and `readSourceExcludes`. It also follows each process boundary: a reached function that names a repo script or the CLI entry starts that process, so the probe, the Git cell client and broker, `served-e2e.mjs` and the CLI's `ci` and `check` are traced too. It lists every fs, Git, gh, env, `/proc`, parse and subprocess read (`reads.txt` beside it: 458 functions, 145 with reads, then the processes it followed and every subprocess call). Each read falls in one row below. Rows marked (reused) are W-168-unchanged code; each names the existing function that rejects, or a limit. Matching by name over-approximates, so every reached function with a read was re-checked by its `<-` call chain in `reads.txt`. Not on these paths: `firstFreeSlot` and `gitStatus` (`runCommand`'s non-builder branch, after its `return runBuilderCommand`; the `acquire` that chain names is the Git cell client's, which is live and has its own row), `mutate` in `scripts/w030-usage-guard-mutation.mjs` (only the name of `editOpusFrontMatter`'s callback), and the `git` wrappers of `branch.ts` and `prune.ts` (a name match). Every other entry is live and is in a row.

## Defaults for the Patron to veto

1. The queue takes one PR at a time and builds one at a time, so bisellium's certifying code is master's (third-party packages are the PR's; see limit (b)). Each merge waits for a full mint in CI, roughly 20 to 30 minutes.
2. In queue mode an opus PR is no longer rebased before it opens; the queue tests it merged with the latest master.
3. A PR that conflicts with master still needs a local rebase and a local re-mint, because the conflict fix is new code. **Patron call:** 13 of the last 20 feature merges edited the one-line `test:suite` in `package.json`, so two such opera in flight will conflict. Recommend filing a follow-on that makes the test list conflict-free; until then, parallel lanes still re-mint about that often.
4. The first local mint after the passing review stays, and so does the local `verify` at done.
5. Spec, done and chore PRs need no mint in CI; their other required checks still run on the merge result.
6. Anything short of the full setup means today's writes and remote calls at `pr` and `merge`, plus the rules read (`gh api repos/<slug>/rules/branches/master?per_page=100`), one local `git config --get` of the queue binding, and the `mode: direct` line. A PR pushed for the queue is held at `merge` until it is rebased and minted again.
