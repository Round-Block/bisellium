## Intent

After W-362 the only code that runs outside the sandbox is the Patron's install: `~/.local/bin/bisellium` linked into `~/projects/bisellium-guard`, a worktree of the Patron's clone, which every hook runs. A session can write the agent clone's `.git` but not the Patron's clone, the guard worktree or the agent clone's source folders. So the main checkout's code moves only when the Patron types a command, and `next` stalls behind every code merge. Moving the install into the Patron's clone at master is W-379; this opus leaves W-362's guard worktree and installer as they are.

After this opus:

1. **One sync step, judged before it runs git in the agent clone.** `scripts/agent-workspace.sh sync` refuses, changing nothing, when its paths are wrong, when it runs from the agent clone's copy, when the Patron's clone is off master or has an uncommitted tracked change, or when the agent clone's `.git` holds anything a session could have planted for git to run or to misjudge: a config key outside setup's set, a value of a core key git consults other than its clone's, a hook, or `info/attributes`. Then it prunes dead worktree entries (git's own rule: the entry's folder or its `.git` file is gone, W-227's busy case among them), fetches origin's master into the Patron's clone and fast-forwards the agent clone's master to that commit, never to a ref the session wrote, when HEAD is master and clean and master is behind it; a tracked change is refused also when master is already current. Git in the agent clone runs with a clean environment, no global or system config, no hooks and no fsmonitor, and the merge keeps ignored files.
2. **The installed guard runs it, at SessionStart and after a requested Bash call.** `bisellium hook-event sync` runs the `scripts/agent-workspace.sh` beside its own real file (the installed guard's copy: a session cannot point it at agent-clone code) and hands its `sync:` lines to the model as the event's additional context, and exits 0 whatever the sync finds. `.claude/settings.json` runs it at SessionStart, and at PostToolUse on Bash when `<the project>/.git/bisellium/sync` exists; every other Bash call costs one `test -e`, no node start.
3. **The merge rung requests it.** When the merge rung holds because an incoming path lies in a folder the session may not write (W-362's stop, reached by the merge perform and by the done perform's land), it writes the request file and prints a `sync:` line after the Patron's command. The PostToolUse hook then syncs as the perform's Bash call returns, and `next`, which derives the rung from local master, names cleanup on its next read. A refused sync is reported in the same turn; the next perform holds again and requests again; the Patron's command stays the fallback.

Why this trigger. Hooks are the only unsandboxed actor, and `.claude/settings.json` holds no agent-clone path: the hook runs the `bisellium` on PATH, and that CLI finds the script by its own real path. The session's only input is a file's existence. The commit comes from the Patron's clone after the sync's own fetch, so a forged request at worst triggers a correct sync. A PostToolUse hook with no precheck would start node on every Bash call (0.4 s measured); a ref comparison in the hook would run git in the agent clone before its config is judged. The PreToolUse guard's 2 s bound cannot hold a fetch.

Why `next` reads nothing new. `next` derives the merge rung from whether local master contains the merge commit (`settleMerged`), and the merge perform is idempotent on a MERGED PR (`landed`). Once the sync moves master, `next` moves on with no new state. A result file written by unsandboxed code into a session-writable folder would be a second source of truth and a symlink-follow hazard. No `next.ts` line changes.

Why the sync judges the Patron's clone. The sync fetches into that clone and fast-forwards to what it fetched, so it acts only while the clone is on a clean master, never in the middle of the Patron's own work there; W-379's guard step reuses the same check.

Promise sync-inputs: `agent-workspace.sh sync` runs no git in the agent clone, and changes nothing, unless `sync_inputs` accepts Input domain rows 1 to 3 and 10; a refusal prints one `sync: refused: <why>; master was not moved` line and exits 1 — limit: the inputs are judged once, before the steps, so a change made between the judgement and a step is not seen; `real`, `within` and `top_is` are reused unchanged (D-076 E).

Promise sync-git: every git command the sync runs in the agent clone runs under `env -i` with `HOME`, `PATH`, `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_CONFIG_NOSYSTEM=1`, `GIT_TERMINAL_PROMPT=0` and `GIT_PAGER=cat`, and with `core.hooksPath=/dev/null`, `core.fsmonitor=false` and `submodule.recurse=false` — limit: git itself, its reading of the judged `.git/config`, and a `.gitattributes` in the incoming tree naming a filter that no read config defines (git then passes the file through) are trusted; the Patron clone's fetch and status run with the Patron's own environment and config.

Promise sync-forward: after the inputs, the sync removes the request file, prunes, fetches origin's master into the Patron's clone, and then refuses, leaving master unmoved, when HEAD is not `refs/heads/master` or a tracked file is changed (`status --porcelain --untracked-files=no` not empty), whether master is behind or already current; else it prints `sync: master is current (<commit>)` when master is the target, or fast-forwards with `merge --ff-only --no-overwrite-ignore` when master is an ancestor of the target and prints `sync: master <old> -> <new>`, and exits 0; each other case is a refusal that leaves master unmoved — limit: a git process the session runs in the main checkout at the same time (its `index.lock`) or a process writing the tree during the merge is git's to refuse or race; `node_modules` is not refreshed after a lockfile change.

Promise sync-sweep: the prune removes exactly the entries git's `worktree prune` removes (its gitdir file missing or pointing at a missing location; locked entries kept) and prints `sync: pruned <n> dead worktree entries` when there were any — limit: an entry whose folder still exists, even empty, is never removed; while a session lives, its sandbox may re-create a pruned entry's mounted files (an entry with no gitdir, which git neither lists nor counts against a branch), swept again at the next SessionStart.

Promise hook-sync: `bisellium hook-event sync` runs `bash <its own real directory>/../../../scripts/agent-workspace.sh sync` with a 55 s bound and prints its output as `{"hookSpecificOutput":{"hookEventName":<event>,"additionalContext":<lines>}}` for SessionStart and PostToolUse, as plain lines for any other event, and exits 0 — limit: `runHookEvent`'s payload read and its catch are reused unchanged (D-076 E), so an unreadable payload runs no sync; Claude Code's handling of `additionalContext` and of the hook's `timeout` is Claude Code's.

Promise wiring: `.claude/settings.json` adds `bisellium hook-event sync --studio studio` to the SessionStart group and a PostToolUse group on `Bash` running `test ! -e "$CLAUDE_PROJECT_DIR/.git/bisellium/sync" || bisellium hook-event sync --studio studio`, each with timeout 60; nothing else in the file changes — limit: which `bisellium` the hooks run is the Patron's install (W-362's `guard` step and probe, reused unchanged); a session opened in the Patron's own clone also syncs the agent clone at its start.

Promise request: when `patronStop` holds on a path this session may not write (W-362), it writes the reviewed commit to `<git common dir>/bisellium/sync` and appends `sync: requested; the installed guard fast-forwards master to origin/master when this call returns and prints a sync: line; then rerun (W-369)` after the `patron:` line, or `sync: not requested (<why>)` when the file cannot be written; no other hold writes it — limit: `writableAt`, the Patron-path rule, `fetchTrunk`'s other holds and `landed` are reused unchanged; the pr rung's `git pull` advice is unchanged (Out of scope).

Promise patron-master: `patron_on_master` accepts `PATRON_DIR` only with HEAD `refs/heads/master` and no uncommitted tracked change, and otherwise prints `PATRON_DIR <dir> is on <ref>, not master; the sync runs only while it is on master` or `PATRON_DIR <dir> has uncommitted tracked changes (<first line>); the sync runs only while it is on a clean master`; `sync_inputs` refuses on it before any change — limit: it reads the clone with the Patron's own git and config, so untracked files and a mode-only change hidden by the Patron's own `core.filemode` are not seen; the sync does not compare its own path with `PATRON_DIR` (the installed guard is W-362's worktree until W-379).

Threat model: mistakes, not adversaries (D-045). Decree F makes the planted-config case a row, not a limit: the hook is the one unsandboxed actor, so what it lets git run is judged before git runs. A planted object, an `objects/info/alternates` entry or a race against the check are limits. The Patron's clone and its config are the Patron's: no session can write them (W-362's deny).
