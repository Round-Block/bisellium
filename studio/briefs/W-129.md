## Intent

D-034 (with its 2026-10-03 addendum) records three Patron rulings from live use of the
console board, plus one wording fix in the same theme. This opus implements all four
and nothing else. The Patron ruled each; the architect only chose the mechanism.

1. **Backlog opera render as cards in the Planned column** (ruling 1). Today
   `apps/web/src/lib/board.ts:13` `EXCLUDED_PHASES` hides them behind a `N backlogged`
   count. The count and its footer go; the cards come, using the card component the
   board already has (no new visual design; the card already shows the native state
   inline, so a backlog card reads `backlog`).
2. **serve reads branch-owned records** (ruling 2). D-021: while `opus/<id>` exists the
   branch owns the record and the trunk copy is frozen at the fork point. serve reads
   only the trunk checkout's `opera/`, so in-flight work shows as `greenlit` in Planned.
   serve now overlays the branch's record, read by **snapshot-on-poll**: one bounded,
   read-only, asynchronous git refresh per poll, never a spawn per request (below).
3. **The verbs write the verifying and review stages as those stages run** (ruling 3).
   Today `verify` "writes gate records and never touches `state`" and nothing sets
   `verifying` or `review` (`docs/ARCHITECTURE.md:94-103`), so two board columns are
   structurally empty. Only verbs write state ids ("Never by hand"): `verify` writes
   `verifying` before its pipeline runs and `review` or `building` when it ends;
   `review --fail` gains one source state. The full cycle is in Interfaces.
4. **The dossier backlog page** (`scripts/backlog-page.mjs:29,161`) groups `greenlit`
   under "In flight". Greenlit is planned. It gets its own "Planned" table.

Three parts of this are one mechanism seen from three sides: the verbs write the truth
on the branch, serve reads the branch, the board draws every state. If any item grows
past what is written here, the builder stops and escalates (Stop conditions).

## Interfaces

### The state cycle (ruling 3)

Only these verbs write a state id. `Active` is `{building, verifying, review}`.

| Verb and moment | From | To | Condition |
| --- | --- | --- | --- |
| `ready` (unchanged) | greenlit, halted | building | existing |
| `verify`, start (after every refusal, immediately before `pipeline.run`) | building, review | verifying | always |
| `verify`, start | verifying | verifying | no write |
| `verify`, start | greenlit, backlog, halted, done | unchanged | `verify` on a non-active record never moves state (keeps every existing fixture and the trunk-side officinas as they are) |
| `verify`, end (same write as the gate results) | verifying | **building** | at least one automated gate has `failed` |
| `verify`, end | verifying | **review** | every effective automated gate is `passed` with a `tree:` or `dirty:` certificate, every agent gate other than the review probatio is `passed`, `kind` is not `ui`, and the review gate is not `failed` at the tree just certified (the predicate `reviewFailedAtCertifiedTree`, below); gates come from `effectiveProbationes(kind, manifest.probationes)` and a `since:` exemption is **not** honoured here (a conservative miss: it keeps `verifying`, it can never write a state `check` blocks) |
| `verify`, end | verifying | verifying | otherwise (a gate without a command is still `pending`; a UI opus; a current failed review) |
| `review --fail` | **verifying**, review, done | building | verifying is the one new source; review and done are existing; `end` cleared as today |
| `review --pass` (unchanged) | any | no change | state moves forward only by `verify` or `done` |
| `done`, `halt`, `waive`, `handoff`, `amend` (unchanged) | active | per verb | all already accept the three active states |

The cycle for one opus on its branch: `ready` -> building -> `verify` (pass) ->
verifying -> review -> censor round -> `review --fail` -> building -> fix -> `verify`
(pass) -> verifying -> review -> `review --pass` (state stays review) -> `done` -> done
-> merge. A failed `verify` returns building; a killed `verify` leaves verifying, and the
next `verify` simply continues (nothing reads verifying as "a process is alive").
`kind: ui` opera stay in verifying after a green verify: UI review state carries the
served-evidence policy (`opus-model.ts:748`) the Patron's UI path owns; this opus does not
touch it. Each state change emits `workflow.state_changed` (`WF.ITEM_ID`, `WF.STATE_FROM`,
`WF.STATE_TO`, no `WF.ACTOR_ROLE`: `verify` has no `--sella`) in the same shape as `done`;
no state change, no event. Exit codes, stdout and the gate write are unchanged; `verify`
adds no flag.

`reviewFailedAtCertifiedTree(root, record)` (new, exported from
`packages/commands/src/opus-model.ts`, used by `verify` and by `check`): true when the
review gate's `status` is `failed` and either its `evidence` log is unreadable, or the log
text contains the hash of a `certifies` value (`tree:<hash>` or `dirty:<hash>`) held by an
automated gate. A failed review of an older tree is stale and answers false. One
predicate, so the verb never writes a state its own checker blocks.

### The check rules this makes necessary (`packages/cli/src/check.ts`)

1. `state.review.failed`: blocks only when `reviewFailedAtCertifiedTree` is true (today:
   whenever the gate is `failed`). A `review` whose failed review is of an older tree is
   the honest "awaiting a new round", not a defect. Everything else about the rule, its id
   and its message, is unchanged. This loosens a block; no record becomes newly invalid.
2. `traditio.stage` (advise): no finding when the handoff `stage` and the `state` are both
   in `ACTIVE`. The handoff records the stage it was written at; the verbs now move the state
   past it without touching a field they do not own. `stage` against a non-active state
   (the cascade-23 sweep case) still advises.

### serve reads branch-owned records (ruling 2)

New `apps/server/src/branchRecords.ts` (the reader) and a small seam in `store.ts`.
`adapters/native` `snapshotDir(root, projectId, now?, recordText?)` and
`createBiselliumAdapter(..., { recordText })` take an optional
`recordText: (opusId: string) => string | undefined`; when it returns text that
`parseFrontMatter` accepts and whose `id` equals the opus id, that record replaces the
disk file for the opus, else the disk file is used. Nothing else in the adapter changes.

`Store` holds one in-memory `Map<opusId, rawRecordText>` (the **overlay**) and rebuilds it
at the top of `ingestOnce()`, which is already called at start and on every poll; every
route that builds a snapshot (`opera`, `needsYou`, `acta`, `aerarium`, `opus` and the
ingest diff) reads it through a single private `snap()`. Requests only read the map.
**No git runs on a request path.** Because the overlay feeds the ingest diff, a branch
changing an opus's state produces a `workflow.state_changed` event and an SSE nudge exactly
as a trunk edit does today, with no new route and no client change.

The refresh (`refreshBranchRecords`), once per poll, is read-only git through
`execFile` (asynchronous; the event loop and the HTTP server are never blocked), each call
with `cwd` = the repo top, `timeout` = `branchGitTimeoutMs` (new `StartServerOptions`
field, default 5000), `maxBuffer` 256 KiB, `GIT_OPTIONAL_LOCKS=0`, `GIT_TERMINAL_PROMPT=0`,
`LC_ALL=C`:

1. First refresh only: `git rev-parse --show-toplevel` from the studio dir. Not a repo
   (every temp studio, `examples/`): the overlay is **disabled for the life of the server**
   with no output and no further git call. `studioRel` is the studio dir's path relative
   to the realpath of the top.
2. In parallel: `git for-each-ref --format=%(objectname)%00%(refname) refs/heads/opus/`
   and `git worktree list --porcelain -z`. Either failing or timing out clears the whole
   overlay (the board falls back to the trunk copy, the safe baseline) and writes one
   `bisellium serve: branch records unavailable: <why>` line to stderr; the poll goes on.
3. Per branch `opus/<id>`, at most 32 (the rest are ignored), considered only if `<id>`
   matches `^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$` **and** the trunk checkout has
   `opera/<id>.md` (the overlay can replace a record, never create one):
   - If a worktree has `branch refs/heads/opus/<id>` checked out, read
     `<worktree>/<studioRel>/opera/<id>.md` from the filesystem: this is the **live**
     record, including edits no commit holds yet (which is the only way `verifying`, set
     before a commit exists, is ever visible). The read opens with `O_NOFOLLOW`, requires a
     regular file of at most 256 KiB, and requires the realpath of the file to lie under
     the realpath of the worktree.
   - If no worktree holds the branch, or that read fails, or its text does not parse or
     its `id` differs (a half-written file), read the **committed** record with
     `git cat-file blob <objectname>:<studioRel>/opera/<id>.md` using the object name
     captured in step 2 (never the ref name), concurrently across branches.
   - Any failure of that too (unreadable, over 256 KiB, no front matter, a different `id`)
     drops that one opus's entry (trunk copy shown); other entries survive.
4. The new map replaces the old one atomically after all reads settle. A refresh is bounded
   by about two timeouts; `doPoll` already refuses to start a second poll while one runs.

Consequences, stated: a branch mid-rebase has a detached worktree, so it is not matched
to its branch and its committed record at the (unmoved) ref tip is read; a branch deleted
between list and read leaves a vanished worktree or object and the entry is dropped or
served from the object name that was captured, never an error; a hung git costs one
timeout per poll and the HTTP server keeps answering. serve never fetches, checks out,
writes, or takes an index lock. Precedence is the Patron's: while the branch exists its
record wins, the whole record (state, gates, tokens, handoff, body).

is not a column. Opera whose phase is `backlog` become cards in the column whose id is

CSS rule is left in place (dead styling is not this opus's to delete). The needs-you
column is unchanged (a backlog opus with a pending human gate appears there and in

## Stated residuals (accepted, with reason)

1. **The Verifying column is short-lived.** `verify` sets `verifying` for the duration of the
   pipeline (minutes for `npm test`), then `review` or `building`. An opus waiting for a re-review
   after a failed round whose review gate is current-failed (an unchanged tree) sits in
   `verifying`, not `review`. Both follow the check rules; a longer-lived `verifying` would
   need a verb the Patron has not ruled on.
2. **Live reads are the worktree file, uncommitted.** A half-written file (`editOpusFrontMatter`
   uses `writeFileSync`, not rename) fails to parse and falls back to the committed tip for
   that poll, so the board may show the older committed state for one cycle and then the live
   one again; at most one extra `state_changed` pair.
3. **Branch wins while it exists, even if it is stale or merged but not yet cleaned up.** After a
   merge the trunk record equals the branch's `done`, so the two agree; an abandoned branch
   keeps showing its last state until it is deleted. Showing that is the Patron's ruling.
4. **Remote-only branches are not read.** serve reads local `refs/heads/opus/*` of the
   checkout it serves; work pushed from another machine and not fetched is not in flight here.
5. **A `kind: ui` opus does not reach `review` through `verify`.** It stays `verifying` until the
   UI path writes `review`; this opus does not change that path.
6. **No browser e2e covers the overlay.** The served-dist harness runs on non-git temp
   studios; the overlay is covered at the HTTP boundary by behaviours 3-7 and the unedited
   client by the existing fetch/SSE e2e.
7. **`events.jsonl` is per checkout.** The `state_changed` events the overlay causes are
   derived (`workflow.time.derived`) and live in the serving checkout's log only, as every
   derived event already does.
8. **The checkout serving must have the same studio-relative path** on every opus branch; the
   reader uses the trunk's `studioRel`. A branch that moved the studio directory is not read.
