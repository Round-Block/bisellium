## Intent

D-034 (with its 2026-10-03 addendum) records three Patron rulings from live use of the
console board, plus one wording fix in the same theme. This opus implements all four
and nothing else. The Patron ruled each; the architect only chose the mechanism.

1. **Backlog opera render as cards in the Planned column** (ruling 1). Today
   `apps/web/src/lib/board.ts:13` `EXCLUDED_PHASES` hides them behind a `N backlogged`
   count. The count and its footer go; the cards come, using the card component the
   board already has (no new visual design; the card already shows the native state
   inline, so a backlog card reads `backlog`).
2. **serve reads branch-owned records** (ruling 2). D-021: while `opus/<id>` exists the
   branch owns the record and the trunk copy is frozen at the fork point. serve reads
   only the trunk checkout's `opera/`, so in-flight work shows as `greenlit` in Planned.
   serve now overlays the branch's record, read by **snapshot-on-poll**: one bounded,
   read-only, asynchronous git refresh per poll, never a spawn per request (below).
3. **The verbs write the verifying and review stages as those stages run** (ruling 3).
   Today `verify` "writes gate records and never touches `state`" and nothing sets
   `verifying` or `review` (`docs/ARCHITECTURE.md:94-103`), so two board columns are
   structurally empty. Only verbs write state ids ("Never by hand"): `verify` writes
   `verifying` before its pipeline runs and `review` or `building` when it ends;
   `review --fail` gains one source state. The full cycle is in Interfaces.
4. **The dossier backlog page** (`scripts/backlog-page.mjs:29,161`) groups `greenlit`
   under "In flight". Greenlit is planned. It gets its own "Planned" table.

**What the board now shows, said plainly.** Reading the branch means the Patron's board
renders **unreviewed, uncommitted builder content**: a builder's working-tree edit to its own
record, seen before any commit, check, CI run or review. D-034 ruled "the branch's live
state"; the architect chose the worktree file because a committed-only read would leave
`verifying` (written before any commit exists) invisible. The exposure is bounded by rule,
not by trust: a live read can change only `state` (and only to `building`, `verifying` or
`review`), `traditio` and `heartbeat`; every other field, including `probationes` (the gate
row and the Needs-you card), `tokens`, `title`, `kind` and `collegium`, and the body, come
from the **committed tip**, which is itself shown only after it parses and validates
(Interfaces). The gate row therefore lags the state: a card in Verifying or Awaiting review
shows the committed gates until the verb's gate write is committed. That is the price of
making a forged live gate unable to show green or to hide a Needs-you card. Text reaches the page only through
React children and attributes (no `dangerouslySetInnerHTML`, no markdown sink; behaviour 2
proves a hostile title is escaped in the board HTML). The `href` of a gate's evidence in the
drawer is unchanged by this opus and filed as a follow-on.

Three parts of this are one mechanism seen from three sides: the verbs write the truth
on the branch, serve reads the branch, the board draws every state. If any item grows
past what is written here, the builder stops and escalates (Stop conditions).

## Interfaces

### The state cycle (ruling 3)

Only these verbs write a state id. `Active` is `{building, verifying, review}`.

| Verb and moment | From | To | Condition |
| --- | --- | --- | --- |
| `ready` (unchanged) | greenlit, halted | building | existing |
| `verify`, start (after every refusal, immediately before `pipeline.run`) | building, review | verifying | only under the **own-tree rule** (below): a run aimed at another tree never writes state. Compare-and-set: the fresh record's state must still be the one read (tested inside the `editOpusFrontMatter` callback) |
| `verify`, start | verifying | verifying | no write |
| `verify`, start | greenlit, backlog, halted, done | unchanged | `verify` on a non-active record never moves state (keeps every existing fixture and the trunk-side officinas as they are) |
| `verify`, end (same write as the gate results, same own-tree rule) | verifying | **building** | own-tree rule, and at least one of **this run's** automated results has `failed`. Compare-and-set: if the fresh record's state is no longer `verifying` (a `halt`, `done` or `review --fail` ran meanwhile) the gates are written, **no state, no event** |
| `verify`, end | verifying | **review** | own-tree rule; evaluated **inside the compare-and-set callback, on the document as it will be written** (the fresh record with this run's gate results already merged in), never on the pre-write record read at the start, whose `certifies` belong to the previous run. Computed over **this run's results**: every effective automated id (from `effectiveProbationes(kind, manifest.probationes)`) is present in the results with `status: passed` and a `certifies` equal to `tree:<hash>` (or `dirty:<hash>` for an `--allow-dirty` run) for the tree hash **this run** computed (a gate whose command was removed keeps an old pass but is not in the results, so it cannot count); every agent gate other than the review probatio is `passed` in the record; `kind` is not `ui`; and `reviewFailedAtCertifiedTree` over that merged document is false. A `since:` exemption is **not** honoured (a conservative miss: it keeps `verifying`, it can never write a state `check` blocks) |
| `verify`, end | verifying | verifying | otherwise, and always outside the own-tree rule (a gate without a command is still `pending`; a UI opus; a current failed review) |
| `review --fail` | **verifying**, review, done | building | verifying is the one new source; review and done are existing; `end` cleared as today. **New:** when the state moves, it also emits `workflow.state_changed` (`WF.ITEM_ID`, from, to, `WF.ACTOR_ROLE` the review sella) beside its existing `gate_evaluated`; `building` + `--fail` moves nothing and emits no `state_changed` |
| `review --pass` (unchanged) | any | no change | state moves forward only by `verify` or `done` |
| `done`, `halt`, `waive`, `handoff`, `amend` (unchanged) | active | per verb | all already accept the three active states |

**Own-tree rule.** `verify` writes a state only when all three hold: the run certifies this
checkout's `HEAD` (`--commit` absent or `HEAD`), there is no `studioRepoRelative` (`ci --ref`),
and `realpath(git -C <repo> rev-parse --show-toplevel)` equals `realpath(git -C <studioDir>
rev-parse --show-toplevel)`, where `<repo>` is the `--repo` the run uses (so `verify W-X --studio
studio --repo <another checkout or clone>`, and `ci --repo`, which certify and run in a different
tree while the owner refusal on the studio's own branch still passes, never write state). If either
`rev-parse` fails, no state is written (fail closed). Outside the rule the gates are written exactly
as today, state untouched, no event.

The cycle for one opus on its branch: `ready` -> building -> `verify` (pass) ->
verifying -> review -> censor round -> `review --fail` -> building -> fix -> `verify`
(pass) -> verifying -> review -> `review --pass` (state stays review) -> `done` -> done
-> merge. A failed `verify` returns building; a killed `verify` leaves verifying, and the
next `verify` simply continues (nothing reads verifying as "a process is alive").
`kind: ui` opera stay in verifying after a green verify: UI review state carries the
served-evidence policy (`opus-model.ts:748`) the Patron's UI path owns; this opus does not
touch it. Each state change emits `workflow.state_changed` (`WF.ITEM_ID`, `WF.STATE_FROM`,
`WF.STATE_TO`, no `WF.ACTOR_ROLE`: `verify` has no `--sella`) in the same shape as `done`;
no state change, no event. Exit codes, stdout and the gate write are unchanged; `verify`
adds no flag.

`reviewFailedAtCertifiedTree(root, record, ctx)` (new, exported from
`packages/commands/src/opus-model.ts`, used by `verify` and by `check`), where `record` is the
raw front-matter dictionary **as it is on disk** (`check`) or **as it will be after this run's
write** (`verify`, called inside its compare-and-set callback on the fresh record with this run's
gate results merged in; never the pre-write record) and `ctx` is `{ reviewId: string;
automatedIds: readonly string[] }` (the manifest's `review_probatio`, default `review`, and the
effective automated probatio ids for the record's kind; `check` and `verify` each compute them
from the manifest they already hold). It **fails closed**: it returns `true` (the failure is
current, so it blocks) whenever the review gate's `status` is `failed`, **unless it can prove
the failure is of an older tree**. The proof needs **all** of: `ctx.automatedIds` is non-empty
(an empty list would make "every id differs" vacuously true); the gate's `evidence` log is read
through `readContainedRegularFile`; `parseVerdictHeader` reports no duplicate `tree` and no
duplicate `opus` key (it keeps the first and lists the rest in `duplicates`); the header `opus`
equals the record's `id` (a verdict log of another opus, or one with no `opus` line, proves
nothing: the gate's `evidence` path is hand-editable); the header `tree` value matches
`^tree:[0-9a-f]{40}$` (a source-tree hash is a 40-hex SHA-1, `packages/shim/src/sourceTree.ts`;
`tree:`, `tree:x`, upper case and `dirty:` prove nothing); every id in `ctx.automatedIds` has a
recorded `certifies` matching the same pattern; and none of those equals the header value.
Anything else (no `certifies`, a `dirty:` certificate, an unreadable or missing log, a log with
no or a malformed tree header, a different record shape) answers `true`. It answers `false` for a
gate that is not `failed`. One predicate, so the verb never writes a state its own checker
blocks, and it reads the same header value the ladder reads (`next.ts` `reviewGate`).

### The check rules this makes necessary (`packages/cli/src/check.ts`)

1. `state.review.failed`: blocks only when `reviewFailedAtCertifiedTree` is true (today:
   whenever the gate is `failed`). A `review` whose failed review is of an older tree is
   the honest "awaiting a new round", not a defect. Everything else about the rule, its id
   and its message, is unchanged. This loosens a block; no record becomes newly invalid.
2. `traditio.stage` (advise): no finding when `stage` and `state` are both in the order
   `building < verifying < review` and the stage's rank is **at most** the state's rank. The
   handoff records the stage it was written at; the verbs move the state forward past it without
   touching a field they do not own. A stage **ahead** of the state (`review` after `review
   --fail` put the opus back in `building`) is the misdirecting baton and still advises, as does
   a stage against a non-active state (the cascade-23 sweep case) and any unknown stage.

### serve reads branch-owned records (ruling 2)

New `apps/server/src/branchRecords.ts` (the reader) and a small seam in `store.ts`.
`adapters/native` gains two exports and one optional parameter:
`validateOpusFront(data: unknown): string | undefined` (a reason, or `undefined` when valid:
`id` a string, `state` a string naming a declared `STATES` id, `probationes` absent or a plain
object whose every value is a plain object with a `status` that is one of `PROBATIO_STATUSES`
(`@bisellium/schema`, already an adapter dependency; `check` already blocks any other status, so no
valid record is dropped), `tokens` absent or a finite
number, `traditio` absent or a plain object, `title` absent or a string), and
`snapshotDir(root, projectId, now?, overlay?)` /
`createBiselliumAdapter(..., { overlay })` where `overlay: (opusId: string) => { data: object;
body: string } | undefined` supplies an **already parsed and validated** record that replaces
the disk file for that opus. Inside `snapshotDir` the overlay record is mapped in its own
`try/catch`; if the mapping throws, the disk file is used. Disk records are mapped exactly as
today.

`Store` holds one in-memory `Map<opusId, { data, body }>` (the **overlay**, a `Map`, so an id
such as `constructor` is harmless) plus a `branchRecords` status object, and rebuilds both at
the top of `ingestOnce()`, which is already called at start and on every poll. Every route that
builds a snapshot (`opera`, `needsYou`, `acta`, `aerarium`, the ingest diff) goes through one
private `snap()`; `api.opus()` returns `frontMatter`/`body` from the overlay entry when there is
one, and `api.opera()` takes `body` from the overlay entry (with the same 64 KiB cap and
truncation marker as `readOpusBody`) instead of `readOpusBody`. Requests only read the map; the
YAML is parsed **once per poll**, not per request. **No git runs on a request path.** Because
the overlay feeds the ingest diff, a branch changing an opus's state produces a
`workflow.state_changed` event and an SSE nudge as a trunk edit does today.

The refresh (`refreshBranchRecords`), once per poll, is read-only git through `execFile`
(asynchronous; the event loop and the HTTP server are never blocked). Every git call has
`cwd` = the repo top, `timeout` = `branchGitTimeoutMs` (new `StartServerOptions` field, default
5000), `killSignal: "SIGKILL"`, `maxBuffer` 4 MiB for the two listings and 128 KiB for a blob,
and an environment that **scrubs** `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`,
`GIT_COMMON_DIR` and every `GIT_CONFIG*` variable, then sets `GIT_OPTIONAL_LOCKS=0`,
`GIT_TERMINAL_PROMPT=0`, `LC_ALL=C`:

1. First refresh (and every refresh while it has not succeeded): `git rev-parse
   --show-toplevel --git-common-dir` from the studio dir. Exit 128 with "not a git
   repository": the overlay is **off for the life of the server**, status `off`, no output and
   no further git call (every temp studio, `examples/`). Any other failure (a timeout, `ENOENT`
   on git, another exit): status `unavailable`, retried on the next poll, never disabled.
   `studioRel` is the studio dir's path relative to the realpath of the top.
2. In parallel: `git for-each-ref --sort=-committerdate
   --format=%(objectname)%00%(refname) refs/heads/opus/` and `git worktree list --porcelain
   -z`. If either fails or times out, the **last good overlay is kept** and the status is
   `stale` (with the failure count and reason); after 6 consecutive failures the overlay is
   cleared and the status is `unavailable`. A recovery poll returns to `ok`.
3. Candidates are branches `opus/<id>` where `<id>` matches `^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$`
   **and** the trunk checkout has `opera/<id>.md` (the overlay can replace a record, never
   create one). They are ordered worktree-backed first, then newest commit first, and **the
   first 32 after that filter** are read (the cap counts only real candidates, so junk branches
   cannot crowd out an in-flight opus); each omitted candidate is counted in the status
   (`capped`). Reads run with a concurrency of 8.
4. For each candidate the **base** is the committed record: `git cat-file blob
   <objectname>:<studioRel>/opera/<id>.md` using the object name captured in step 2 (never the
   ref name), at most 64 KiB, parsed with `parseFrontMatter`, with `id` equal to `<id>` and
   `validateOpusFront` clean. If the base fails any of that, the opus's entry is **dropped**
   (trunk copy shown) and recorded in the status as `{ id, reason }`; other entries survive.
5. If a worktree has `branch refs/heads/opus/<id>` checked out, its file is also read as the
   **live** record, and only if it passes every one of: the worktree's `.git`, read through the
   **shared opener** below (at most 4 KiB + 1 bytes), is a regular file whose `gitdir:` target
   resolves inside `<git-common-dir>/worktrees/`, **and** that admin directory's own `gitdir` file
   (the same opener) names `<worktree>/.git` back (so `.git` pointed at some other worktree's admin
   directory is not trusted); the record `<worktree>/<studioRel>/opera/<id>.md` is read through the
   shared opener (at most 64 KiB + 1 bytes); the text parses, `id` matches and
   `validateOpusFront` is clean; and the live `state` is one of `building`, `verifying`, `review`.
   When it passes, the entry is the base with **only** `state`, `traditio` and `heartbeat` taken
   from the live record. **`probationes` is never taken from a live read** (chosen over taking only
   the manifest's `automated` gates: that would need the manifest in apps/server and would still let
   a builder forge a green tick; with no live gate field a forged `probationes` can neither show
   gates passed nor hide a Needs-you card, at the cost named in Intent). When the live read fails for any reason the committed
   base stands (no error, no drop) and `liveRejected` is incremented.
6. The new overlay and its status replace the old atomically after all reads settle. A refresh
   is bounded by about three timeouts; `doPoll` already refuses a second poll while one runs.

**The shared opener** (`readBoundedRegular(path, root, maxBytes, opts?)`, exported from
`branchRecords.ts`; the only way the reader opens a file the builder controls, the record, the
worktree's `.git` and the admin `gitdir` alike): `lstat` must say a regular file; `open` with
`O_RDONLY | O_NOFOLLOW | O_NONBLOCK` (so a FIFO or a device cannot block it); `fstat` on the open
fd must say a regular file with the `lstat`'s `dev`/`ino`; the realpath of `/proc/self/fd/<n>` lies
under the realpath of `root`; at most `maxBytes` + 1 bytes are read (the `fstat` size is not
trusted; more than `maxBytes` is a refusal); the whole sequence races a wall-clock timer of
`branchGitTimeoutMs`; and the fd is closed in a `finally` on every path, including a lost race.
It resolves `{ text }` or `{ refused: code }` with `code` one of `not-regular`, `changed`,
`escapes`, `too-large`, `timeout`, `unreadable`. `opts` carries two test-only injections, never
set by `store.ts`: `afterLstat?: () => void | Promise<void>`, called between the `lstat` and the
`open` (so a row can swap the file for a FIFO exactly there), and `timeoutMs?` (overrides the
timer). Without `O_NONBLOCK` an `open` of a FIFO parks a pool thread, loses the race and answers
`timeout`: that is what behaviour 5(j) catches.

The status is served in `GET /api/officina` as `branchRecords: { status: "ok" | "partial" |
"stale" | "unavailable" | "off", failures?: number, reason?: StatusReason, capped?: number,
liveRejected?: number, dropped: { id: string, reason: DropReason }[] }` (`partial` when anything
was dropped or capped; `liveRejected` counts live reads refused by step 5, a hostile or
half-written worktree file, and never makes the status `partial`). **Every `reason` is a fixed
code chosen from the kind of failure, never an error message, a YAML message or a path** (those
quote record text and absolute paths and may carry newlines or escape codes): `DropReason` is one
of `no-front-matter`, `id-mismatch`, `invalid-shape`, `too-large`, `unreadable`, `parse-error`;
`StatusReason` is one of `git-timeout`, `git-error`, `git-missing`. `dropped` holds at most the 32
candidates, each id regex-bound. One line is written to stderr when the status or reason
**changes**, not on every poll: the fixed prefix `bisellium serve: branch records ` followed by
`JSON.stringify({ status, reason, failures, capped, liveRejected, dropped })`, so nothing
record-derived reaches a terminal unescaped and the line cannot be split. (The per-request access
log, `http.ts` `${method} ${url} ...`, shares stderr and is not this line; tests filter on the
prefix.) The web board shows one line when the status is `partial`, `stale` or `unavailable`
(below).

Consequences, stated: a branch mid-rebase has a detached worktree, so it is not matched to its
branch and its committed record at the (unmoved) ref tip is read; a branch deleted between
list and read leaves a vanished worktree or object and the entry is dropped or served from the
captured object name, never an error; a hung git costs one timeout per poll and the HTTP
server keeps answering. serve never fetches, checks out, writes, or takes an index lock.
Precedence is the Patron's: while the branch exists its record wins.

## Stated residuals (accepted, with reason)

1. **The Verifying column is short-lived.** `verify` sets `verifying` for the duration of the
   pipeline (minutes for `npm test`), then `review` or `building`. An opus waiting for a re-review
   after a failed round whose review gate is current-failed (an unchanged tree) sits in
   `verifying`, not `review`. Both follow the check rules; a longer-lived `verifying` would
   need a verb the Patron has not ruled on.
2. **Live reads are the worktree file, uncommitted, and the builder writes it.** A builder can put
   any allowlisted value in its own record and the board shows it before review: `state` among the
   three active states (so a builder can claim Awaiting review for work no one has checked),
   `traditio`, `heartbeat`. `probationes` is not allowlisted, so no gate tick or Needs-you card can
   be forged or hidden through a live read. This is the cost of showing `verifying`; the bounds are
   the allowlist, the active-state restriction and the committed base (Intent). Nothing here reaches
   `done` or a merge: `state.done.probationes` and the merge's own `done`-on-branch check still
   stand. A half-written file falls back to the committed tip for that poll (at most one extra
   `state_changed` pair); a builder who flaps the file mints derived events in the serving
   checkout's local log, the same exposure a trunk-file editor has today.
3. **Branch wins while it exists, even if it is stale or merged but not yet cleaned up.** After a
   merge the trunk record equals the branch's `done`, so the two agree; an abandoned branch
   keeps showing its last state until it is deleted. Showing that is the Patron's ruling.
4. **Remote-only branches are not read.** serve reads local `refs/heads/opus/*` of the
   checkout it serves; work pushed from another machine and not fetched is not in flight here.
5. **A `kind: ui` opus does not reach `review` through `verify`.** It stays `verifying` until the
   UI path writes `review`; this opus does not change that path.
6. **No browser e2e covers the overlay.** The served-dist harness runs on non-git temp
   studios; the overlay is covered at the HTTP boundary by behaviours 3-9 and the client by
   behaviour 2 plus the existing fetch/SSE e2e.
7. **`events.jsonl` is per checkout.** The `state_changed` events the overlay causes are
   derived (`workflow.time.derived`) and live in the serving checkout's log only, as every
   derived event already does.
8. **The checkout serving must have the same studio-relative path** on every opus branch; the
   reader uses the trunk's `studioRel`. A branch that moved the studio directory is not read.
9. **`verify` has no actor.** Anyone on the branch can run it and flip `review` back to
   `verifying`, hiding "awaiting review" until the next `verify`; the event has no
   `WF.ACTOR_ROLE`. Accepted: `verify` has no `--sella` and adding one is out of scope.
10. **The live read is Linux-specific** (`/proc/self/fd`, `O_NONBLOCK` on a FIFO). The repo runs in
    WSL and CI is Linux only; elsewhere the live read fails closed to the committed tip.
11. **The 6-poll staleness limit is a constant,** not an option. A failure that lasts longer than
    about thirty seconds at the default poll interval shows the trunk copy and `unavailable`.
12. **The drawer's evidence `href`** (`BoardDrawer.tsx:59`) accepts `data:` and `https:` targets
    that a builder-written record can name; React blocks `javascript:`. Pre-existing for trunk
    records and now reachable from a live record; filed below, not fixed here.
13. **Clearing and dropping mint reversal events.** After six failed refreshes (the overlay
    cleared), or when one opus's entry is dropped, the ingest diff sees `building` -> `greenlit`, and
    the reverse on recovery: two derived `state_changed` events in the serving checkout's local
    log. The display is honest (`stale`/`unavailable`/`partial` is reported); the events are
    derived noise, the same class as residual 2's flapping.
14. **An `--allow-dirty` run can reach `review`** on a `dirty:` certificate (behaviour 11(g)); the
    board then shows Awaiting review for uncommitted code. Intended: the certificate says so.
15. **The branch-note line is provisional.** It awaits the Patron's ratification (Interfaces) and
    appears at the next `/api/officina` refetch, not when the status flips.
