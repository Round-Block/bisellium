## Intent

The merge queue's `certify` refused W-178's PR #578 (`~/.bisellium-evidence/W-178-build/certify-fail.log:749`: `test.rows git merge-base no refs/heads/master or refs/remotes/origin/master`). `certify` runs master's host runner (`.github/workflows/ci.yml:177`, tooling at the merge group's `base_sha`), and its producer gate clones the candidate with `git clone --single-branch --branch <opus branch>` (`scripts/run-builder-host.mjs:798-807`), so the clone holds no master and W-178's new rule finds no base. W-178 carries the fix (its behaviour 5, commit 9d7588f0), but only master's runner mints its receipt. The Patron split the fix out (2026-10-19, option A): W-323 lands the one fetch first, then W-178 is re-queued.

**The design question: after W-323 lands, does W-178 certify unchanged?** No, under either shape the orchestrator's brief offered, and the prototype shows why (`rebase-sim.out`, `w178b5-replay-accept.out`):

1. `certify` rebases the PR head onto the merge group's base (`scripts/ci-certify.mjs:197-205`). W-178 unchanged conflicts there at 0c97539d (its row b5 and the census pin, `run.test.ts`), whatever W-323's row is named: both append a live row and both move the census pin 26→27. With that commit and its red log dropped, its fix commit 9d7588f0 conflicts too (the fetch is already on master, under another comment).
2. Even resolved, the replay refuses W-178's red 5. After a rebase the host re-identifies each red at the commit that introduced its log (W-134, `run-builder-host.mjs:692-717`) and runs its command there (`:764-778`). That commit now sits on a master holding the fetch, so `W-178-b5` passes: on the prototype with W-178's row added it exits 0, and the host classifier rejects it (`{"accepted":false,"reason":"the command exited 0"}`), which is `red 5 did not reproduce its assertion failure` (`:772`). No fetch W-323 could land avoids this, short of fetching master under a ref W-178's gate does not read (rejected: two fetches of one master, to keep a red alive).
3. W-178's brief counts five behaviours (`w178-behaviours.out`), and the host needs a red for each (`:684`), so dropping the red log alone is refused too.

So W-178 needs a brief amendment and a re-signed spec dropping behaviour 5 whichever way W-323 is shaped, and W-323 takes W-178-b5's row as its own (`W-323-b1`, the same gate and assertions, renamed) with the census pin. W-178 is then rebased with its three behaviour-5 commits dropped (0c97539d the row, 10dfb8f0 its red log, 9d7588f0 the fetch): the other 51 apply cleanly, the source diff left is W-178's other five files, each of reds 01–04 is introduced by exactly one commit carrying no source, and each replays at that commit with an assertion failure printing every recorded title (`rebase-sim.out`, `replay-w178.out`). No record is edited by hand: the red log leaves with the commit that added it, the amendment is the architect's signed revision, and the opus record and receipts are untouched.

Threat model: mistakes, not adversaries (D-045). The fetch runs in the host, in a clone no candidate code has run in yet, through the runner's locked-down `git` (`run-builder-host.mjs:96-115`: hooks off, no global config); the gate cell's bwrap arguments are unchanged.

## Interfaces

None new. In `runBuilderHost`'s producer phase the order becomes: clone the opus branch single-branch (`:798-807`, unchanged), refuse a failed clone (`:808`), fetch the host repository's `refs/heads/master` into the clone's `refs/remotes/origin/master` (new), refuse a failed fetch (new), check `HEAD` is the exported tip (unchanged), then the tooling clone and the gate cell as before.

Promise master-in-clone: when the host mint's producer gate runs, its candidate clone holds `refs/remotes/origin/master` at the host repository's `refs/heads/master` as fetched, or no receipt is minted — limit: master is read by name when the gate starts, so a master that moved during the build gives a newer one (in `certify` it is the merge group's base, set by `ci-certify.mjs:200`); a repository with no `master` is already refused at `run-builder-host.mjs:466` before any build, so the fetch adds no refusal there; the failure branch is read in review, not exercised by a row (mutant m3 in `mutants.out` passes `W-323-b1`).

Promise host-unchanged: apart from the fetch, the producer phase is byte-unchanged: the clone, the tooling checkout, the gate command and its cell, the red replays and the receipt — limit: unchanged code the promise leans on is a stated limit, not a guarantee (D-076 E): the clone at `run-builder-host.mjs:798-808`, the `git` helper and `GIT_LOCKDOWN` at `:96-115`, the gate at `:812-855` and the replay at `:666-790`; `run-test-proto.out` (all 41 rows of `run.test.ts`, none skipped) is the evidence they still hold.

Limits, stated:
