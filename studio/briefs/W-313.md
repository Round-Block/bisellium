## Intent

A `verify` gate runs its command under `spawnSync` with its output captured (`packages/pipeline/src/index.ts`, `localPipeline`), so nothing is printed until the gate ends, up to 30 minutes later (`GATE_TIMEOUT_MS`). `bisellium ci` runs its steps with their output on the terminal, but prints nothing of its own between them. On W-292 a local `verify` sat silent until it hit the 30-minute cap twice, and nobody watching could tell a slow healthy suite from a hung one (W-259's brief, Out of scope, part 3).

After this opus every `bisellium ci` step and every `verify` gate (so every gate of `ci --opus` too) runs through one helper, `runWatched`, which prints to stderr a start line with the UTC time, then every 60 s while the command runs a progress line with the elapsed time, the time, the bytes of output so far and its last line, then an end line with the time, the elapsed time and the outcome. A gate's pass or fail, its log and its timeout are as on master; a step's output still reaches the terminal, now passed through by `ci` itself so it can count it.

Re-scope (D-071 E, D-082 B): no host mint runs before review any more, and the merge queue's `certify` is the one mint. `scripts/run-builder-host.mjs` is dropped from scope: certify's runner needs no change, because its producer cell runs `ci --offline --opus` from master's tooling with stdout and stderr inherited (`run-builder-host.mjs:856`), and certify tees the whole run into `certify.log`, so the lines reach the log and the job's console once this lands on master. `scripts/ci-certify.mjs` and `.github/workflows/ci.yml` are unchanged.

Threat model: mistakes, not adversaries (D-045). The progress line repeats untrusted command output, so its last line is redacted as a gate log is.

## Interfaces

```ts
export const PROGRESS_INTERVAL_MS = 60_000;
export interface WatchOptions {
  label: string;            // "bisellium verify: gate <probatio id>" or "bisellium ci: step <CI_STEPS entry>"
  cwd: string;
  env?: NodeJS.ProcessEnv;
  shell?: boolean;
  timeoutMs: number;
  tee?: boolean;            // pass output through to this process's stdout and stderr, keep none (ci)
  everyMs?: number;         // default PROGRESS_INTERVAL_MS; tests shorten it
  write?: (line: string) => void; // default: process.stderr.write(line + "\n")
}
export interface WatchResult { status: number | null; signal: NodeJS.Signals | null; timedOut: boolean; error?: NodeJS.ErrnoException; stdout: string; stderr: string }
export function progressLine(text: string): string | undefined;
export function runWatched(command: string, args: readonly string[], opts: WatchOptions): Promise<WatchResult>;
```

`runWatched` writes `<label>: start <ISO time>`, then spawns the command (async `spawn`, stdio `[tee ? "inherit" : "ignore", "pipe", "pipe"]`). Each chunk of stdout or stderr adds its bytes to a count and, decoded by a per-stream `StringDecoder`, joins that stream's last 4096 characters, from which `progressLine` takes the last line. With `tee` the chunk is written as received to `process.stdout` or `process.stderr`; otherwise it is kept, each stream up to `CAPTURE_MAX` (64 MiB, spawnSync's `maxBuffer` in master's `localPipeline`): the chunk that would pass it sets `error` `ENOBUFS` and kills the child, as spawnSync did. Every `everyMs` it writes `<label>: running <m>m<ss>s at <ISO time>, <bytes> bytes of output, last line: <line or "(none yet)">`. At `timeoutMs` it sets `timedOut` and kills the child with SIGTERM (spawnSync's `timeout`). When the child closes, or fails to spawn, it clears both timers and writes `<label>: end <ISO time> after <m>m<ss>s, <outcome>`, the outcome being `timed out after <minutes>m`, `failed to start: <message>`, `exited <status>` or `killed by <signal>`, and resolves. No line holds the text `exit code:`, which gate logs and W-279-b3 use.

`progressLine(text)` recognises these forms (each a grammar line of Input domain row 1):

- `\n` and `\r` each end a line, and the result is the last line that is not blank, trimmed — pinned by `W-313-b1` "a carriage return ends a line, as a progress bar redraws it" and pinned by `W-313-b1` "blank output has no last line"
- a CSI escape sequence (`ESC [`, parameter bytes `0-9;?`, intermediate bytes, one final byte `@` to `~`) is dropped — pinned by `W-313-b1` "escapes dropped"
- every other C0 control character and DEL reads `?`, after `redact` (`@bisellium/shim`) has masked the secret shapes it knows — pinned by `W-313-b1` "a bell read as ?, a secret redacted"
- a line over 200 characters is cut to its first 200 and `…` — pinned by `W-313-b1` "a long last line is cut to 200 characters"

Every other form is a limit: an OSC or other non-CSI escape, a C1 control, bidirectional and zero-width characters pass through; a line longer than the stream's last 4096 characters shows only its end; the last line is the one from the stream that wrote last, so a step writing to both interleaves them by chunk.

`localPipeline.run` calls `runWatched(command, [], { cwd: repo, shell: true, timeoutMs: GATE_TIMEOUT_MS, env, label: "bisellium verify: gate <id>" })` and builds the log from `stdout + stderr`, `timedOut`, `status` and `signal` exactly as it did from spawnSync's result. `runStep` calls `runWatched(bin, rest, { cwd, tee: true, timeoutMs: GATE_TIMEOUT_MS, label: "bisellium ci: step <command>" })`, returns 1 on `timedOut`, prints its existing `failed to start` line on `error`, and otherwise returns `status ?? 1` as before.

Promise timed: every `bisellium ci` step and every `verify` gate, including each gate of `ci --opus` and of certify's mint, prints a start line and an end line on stderr, each with the UTC time, the end line with the elapsed time and the outcome — limit: `ci --ref`'s `npm ci` install, `verify`'s reads before its gates and `next`'s own steps print none; certify shows the lines only once this is on master, since its mint runs master's tooling; a gate of a pipeline other than `localPipeline` prints none (`selectPipeline` returns only `localPipeline` today).

Promise heartbeat: while a step or gate runs, a progress line is written every 60 s naming the elapsed time, the time, the bytes of stdout and stderr so far and the last line as `progressLine` reads it, and none is written after its end line — limit: the line comes on a Node timer, so a busy event loop delays it; the byte count is of the output this process received, not of a file; a gate of `ci --opus` writes its lines inside `verify`'s, whose own work before and after the gates prints none.

Promise outcome-kept: a gate's status, its log's bytes and its 30-minute timeout, and a step's exit status, its 30-minute timeout and the bytes of its output, are as on master — limit: a step's command now writes to a pipe, not to `ci`'s terminal, so a tool that colours or animates only on a TTY (eslint, npm) prints plain text when `ci` runs in a terminal; a gate's stdin is `/dev/null` rather than an empty pipe; a gate killed by its 64 MiB cap is not exercised by a row; a step's output that `ci`'s own stdout does not take at once waits in this process's memory, where the terminal or pipe used to apply back-pressure to the step.

Limits, stated:

- Unchanged code the promises lean on is a stated limit, not a guarantee (D-076 E): `redact` and `filterEnv` (`@bisellium/shim`), `GATE_TIMEOUT_MS`, `runVerify`'s plan and result printing, W-279's hand-off of steps to `verify`, `CI_STEPS`, and certify's runner (`run-builder-host.mjs`'s inherited stdio, the workflow's `tee`), all unedited.
- A timeout or a kill sends SIGTERM to the direct child, as spawnSync did: a gate run through `sh -c` whose shell does not pass the signal on leaves grandchildren running, as on master.
- `next --track`'s silence check reads the newest line of a step's output file; a tracked step that runs `ci` now writes at least once a minute while a gate runs, so a long healthy gate stops reading stalled. That is a side effect, not a promise: no row pins it.

### Input domain

A rejection fails closed: a malformed or hostile output line is cleaned, cut or masked before it is written, never refused; a command that cannot start, overflows, times out or is killed ends with its end line and a failing gate or step. A test row whose own setup write fails throws, which fails the row.

| Record | Valid domain | Rejected by |
|---|---|---|
| 1. A running command's stdout and stderr, as `progressLine` reads them (new reader) | any text, decoded as UTF-8; recognises the forms on brief:55-58; every other form is a limit (brief:60) | `progressLine` (specified): a control or escape is dropped or read as `?`, a secret shape masked by `redact`, a long line cut; pinned by `W-313-b1` "a progress line names the output so far and its last line" |
| 2. The same output, as a gate's log keeps it | stdout then stderr, each at most 64 MiB, the last 200 lines redacted, as master's spawnSync kept them | `runWatched` (specified): a stream passing 64 MiB sets `ENOBUFS` and kills the child, and the gate fails; pinned by `W-313-b1` "stdout is captured" and pinned by `W-279-b3 behaviour 3` "long tail is" |
| 3. The same output, as a `ci` step passes it on | any bytes, written unchanged and in arrival order to `ci`'s own stdout or stderr | `runWatched` (specified): nothing is refused; with `tee` no byte is kept; pinned by `W-313-b2` "a step's output passes through between its start and end" |
| 4. The command's end | an exit status, a signal, a spawn error or the timeout | `runWatched` (specified): each gives its end line's outcome, and `localPipeline.run` a failed gate or `runStep` exit 1 unless the status is 0; pinned by `W-313-b1` "a run past its timeout is killed" and pinned by `W-313-b1` "the end line names the signal" and pinned by `W-313-b1` "a spawn failure is returned" |
| 5. The label | `bisellium ci: step ` and a `CI_STEPS` entry, or `bisellium verify: gate ` and a probatio id from the manifest | limit: written as given, unredacted; `CI_STEPS` is fixed and a probatio id is the manifest's own; pinned by `W-313-b2` "a gate prints its start" |
| 6. The new rows' fixture writes (the child script, the fixture repository and studio) | files and commits the rows make under their own temporary directories | `writeFileSync` and the file's `git` helper throw on failure, which fails the row; unpinned: the rows' own setup |

## Behaviours to test

1. **A watched run prints its start, a progress line each interval naming its output size and last line, and its end, with the time.** In `W-313-b1` (`gate-timeout.test.ts`): `PROGRESS_INTERVAL_MS` is 60 000. A child prints `alpha <pid>` on stdout and waits; run with `everyMs` 50 and a collecting `write`, the test signals it (SIGUSR1) on the first progress line naming that line, and the child then prints a line with a CSI colour, a bell and `token=s3cr3t` on stderr; on the first progress line naming it the test signals again (SIGUSR2) and the child exits 3. No wall-clock wait: the progress lines drive the child. The result has status 3 and both streams captured; the first line is the start and the last the end (`exited 3`), each with an ISO time; every line between is a progress line; one names stdout's byte count and `alpha <pid>`, a later one both streams' bytes and `beta red? token=***`. `progressLine` cuts a long line to 200 characters and `…`, reads `50%\r60%\r` as `60%`, and finds no line in blank output. The same child, left waiting, is killed at a 300 ms timeout and its end line says `timed out`, and the first run wrote no line during it; a child killed by SIGKILL ends `killed by SIGKILL`; a missing binary returns `ENOENT` and ends `failed to start`.

   **Genuine red:** `bisellium red W-313 --behaviour 1 --sella builder --studio studio -- node --test-reporter=tap --test-name-pattern='^W-313-b1\s' --import tsx packages/pipeline/test/gate-timeout.test.ts` prints `not ok 1 - W-313-b1 behaviour 1: a watched run prints its start, a progress line each interval naming its output size and last line, and its end, with the time`, failing at `the progress line comes every minute`: master has no `PROGRESS_INTERVAL_MS` (`row-b1-master.out`, accepted by the replay classifier, `red-accept.out`). It passes on the prototype (`row-b1-proto.out`).

2. **`ci --opus` prints each step's and each gate's start and end with the time, a step's output between them.** In `W-313-b2` (`w279.test.ts`): a fixture repository whose npm scripts each print `marker <name>`, and a studio whose opus has W-279's three automated gates. With `process.stdout.write` and `process.stderr.write` recorded and passed on, `runCi --opus` exits 0; for each step left in the loop (audit, format:check and both checks), in order, stderr has `bisellium ci: step <command>: start <ISO time>`, then stdout has its `marker` line, then stderr has its end line (`exited 0`); then for each gate (`tests`, `lint`, `types`) stderr has `bisellium verify: gate <id>: start <ISO time>` and its end line; no gate's `marker` line reaches stdout.

   **Genuine red:** `bisellium red W-313 --behaviour 2 --sella builder --studio studio -- node --test-reporter=tap --test-name-pattern='^W-313-b2\s' --import tsx packages/cli/src/w279.test.ts` prints `not ok 1 - W-313-b2 behaviour 2: ci --opus prints each step's and each gate's start and end with the time, a step's output between them`, failing at `a step prints its start: no err line matching /^bisellium ci: step npm run -s audit: start`, on master and on behaviour 1's code, where the gates print their lines and the steps do not (`row-b2-master.out`, `row-b2-s1.out`, accepted, `red-accept.out`). It passes on the prototype (`row-b2-proto.out`).

## Defaults for the Patron

1. While `bisellium ci` or `verify` runs a step or a check, it prints when that step started and ended, and once a minute how long it has been running, how much output it has produced and its latest line. A silent half hour is no longer mistaken for a hang. Agree?
2. To count `ci`'s output, `ci` now passes each step's output on itself rather than handing the step the terminal directly. Run by hand in a terminal, tools that colour their output only on a terminal (the linter, npm) print plain text. Agree?

4. The pre-review host mint is gone, so `scripts/run-builder-host.mjs` is not touched: the merge queue's certify run already passes `ci`'s output into its log, where the new lines appear once this is merged. Agree?
