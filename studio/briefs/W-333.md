## Intent

The ranked queues live as hand-kept prose in `docs/SESSION-HANDOFF.md`'s Queue section (two engineering lanes and two UI lanes, D-089, D-137; ranked entries each with a one-line description, folded ids and a `next.ts` marker; halted, cut and deferred lists), and which lane holds which opus lives in `~/.bisellium-evidence/current-state.md` (D-109). Nothing checks either, and the Patron's queue rules (a lane takes the highest entry not blocked by another lane's opus; a skipped entry keeps its place; one `next.ts` opus in flight at a time) are applied by the orchestrator from memory. An idle lane goes unnoticed until someone reads both files (W-478).

**The design, a narrow first cut.** One new officina file, one reader, one check rule, and lane lines in `next --all`:

1. **`studio/queue.yml` and `queue.shape` (behaviour 1).** The file holds a `queues` mapping (one queue per key, `engineering` and `ui` in the real officina), each queue with its `lanes` (lane id to the opus it holds, or `~`: Now) and its ranked `next` list (Next); each entry is `{ opus, says, folded?, next_ts? }`: the opus id, a plain one-line description (the Patron reads no bare id), the ids folded into it, and whether it touches `packages/cli/src/next.ts`. Top-level `halted`, `cut` and `deferred` lists take the same entries. Later is every other opus record and is not listed, as the handoff says today. One reader, `readQueue` (new `packages/cli/src/queue.ts`), judges the shape and, across the file, that an opus is listed once (its folded ids included), a lane is named once, two lanes never hold one opus, a lane's opus is an entry of its own queue's `next`, at most one lane holds an entry marked `next_ts` (one `next.ts` opus in flight at a time), and every opus named has a record in `opera/`. The new check rule `queue.shape` (block) reports each problem as one finding; it is inert while the file is absent, as `milestones.shape` is.
2. **Lane lines in `next --all` (behaviour 2, W-478).** With a well-formed `queue.yml`, `next --all` prints, after the opus lines and before the milestones line, one line per lane by queue in file order. A lane holding an opus whose record is not done or halted is busy and prints the opus and its state. Any other lane is idle and names the entry it would take: the highest entry of its own queue's `next` that no lane holds or takes before it, whose record is greenlit up to review, and that is not marked `next_ts` while another lane holds or takes a `next_ts` opus. Every entry passed over above the take is named with its reason, so a skipped entry keeps its place and the reason it waits is visible. Busy lanes are read first, then idle lanes in file order, each take holding its entry for the lanes after it. A malformed file prints one held line and the run exits 1, as a held milestones line does; an idle lane does not fail the run. A file in which more than one lane already holds a `next_ts` entry is malformed (behaviour 1), so the one-at-a-time rule holds for the lanes held as well as for an idle lane's take.

The one reader serves both the rule and `next --all`, so the two cannot disagree (the class `design×indirection-duplicates-source-of-truth`). The lane lines are derived, never written: nothing claims a lane, reorders an entry or writes the file.

**Overlap.** This opus touches `packages/cli/src/next.ts` (one import and one block in `runAll`); it is the only `next.ts` opus in flight. W-364 (in spec review) touches `guard.ts`, `main.ts`, `scripts/run-builder-host.mjs` and `package.json`'s `test:suite`; the one shared file is `package.json`, where W-364 adds its file after `w496.test.ts` and this opus adds its file after `milestones.test.ts`, two separate hunks.

Threat model: mistakes, not adversaries (D-045). The file is the officina's own record, written by a dispatched clerk.
