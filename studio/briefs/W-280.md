## Intent

W-280 was filed as two fail-opens. The master re-check (3d4eb563, unchanged at b407139f for these paths) cuts it to what is still open, as D-208 item 3 ruled:

- **`newItem` and `validateRecordReferences`: closed by construction, out of scope.** `validateRecordReferences` has one rule, the record's `spec` pointer (`packages/commands/src/opus-model.ts:678`: no `spec`, no problem). `newItem` takes no `spec` and writes no `spec:` line (`packages/cli/src/new.ts:93`, `:101`-`:108`), so the record it proposes and the record it writes have nothing for that check to refuse. Calling it from `newItem` would change no outcome and could not be shown red. `newitem-probe.out` shows this: the check answers `[]` for a record with no `spec`; `newItem` given a `spec` it does not declare writes a record with no `spec`; the check on that written record answers `[]`. (`runNew` needs it: `--spec` and `--brief` write `spec:`.)
- **A failed `/api/inbox` read shows no demo petitions: closed on master, for the plain Inbox.** `Inbox.tsx`'s read failure clears to `EMPTY` (W-341; `W-341-b2` in `apps/web/test/w341.test.ts:124`-`:125`, and `W-345-b4` in the served `inbox.spec.ts`).
- **Still open: `?demo`.** The served console (the production build `bisellium serve` serves from `apps/web/dist`) still honours `?demo` on the Inbox: `/?demo#/inbox` shows the invented P-008, P-009 and P-010 in place of the studio's petitions, and never reads, so a failed read there still "shows" the demo petitions. The fixtures `DEV_DATA`, `DEV_OFFICINA` and `DEV_OPERA` sit in `Inbox.tsx` and so in the production bundle (`s18/red-b2-before.out`: all six markers in `assets/index-*.js`).

After this opus:

1. The served console's Inbox ignores `?demo`: `/?demo#/inbox` reads and shows the studio's own petitions, exactly as `/#/inbox` does, and a failed read there is the error state with no petition. `?demo` stays a vite-dev aid (`npm run dev`; `apps/web/tests/smoke.spec.ts`, unchanged).
2. The Inbox's demo fixtures move, unchanged, to `apps/web/src/screens/inboxDemo.ts`, loaded by a dynamic import inside the dev-only branch, so a production build drops the branch and never emits them.

Served specs that read the demo petitions through `?demo` (`W-345-b1` to `b3`, `W-407-b3`'s overlay and storage rows, `W-407-b4`, `W-407-b5`'s groups) get the same records from a route fixture (`tests-serve/inbox-demo.ts`, which reads `inboxDemo.ts`), signed in: the named flips.

Cause fix: the demo switch was a runtime read of the URL in every build; it is now gated on vite's build-time `import.meta.env.DEV`, which a production build folds to `false`, so the branch and the fixtures it alone loads are dropped from the bundle.

Threat model: mistakes, not adversaries (D-045). `?demo` is a URL anyone at the console can type; the harm was invented petitions read as the studio's, not an attack.
