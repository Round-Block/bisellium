## Intent

The build-review perform (`next <id> --perform --expect review`, `reviewSteps`) starts and resumes the reviewer's Codex session with the opus worktree as its working directory (`const call = { cwd: wt.dir, ... }`). Codex loads `AGENTS.md` from its working directory's repository, so the reviewer reads the opus branch's `AGENTS.md` as standing instructions; `AGENTS.md` is generated, not code-owned, so an opus can rewrite its own reviewer's instructions. Measured on codex-cli 0.153.4 through the shipped shim (`probe.out`): a session started in a linked worktree loads that worktree's `AGENTS.md` and not the main checkout's; started in the main checkout it loads the main checkout's and not the worktree's; and a resume reloads `AGENTS.md` from the working directory it is resumed in.

After this opus the perform runs Codex with the main checkout (`f.repo`, the `--repo` that `runNext` has already proven is not a linked worktree) as its working directory, for a fresh round and a resumed one, so the reviewer loads master's `AGENTS.md` as the main checkout carries it. Because the reviewer's relative paths would now resolve in the main checkout, the round-1 prompt names the opus's own files by absolute path under the worktree: the two computed focus lines name `<worktree>/studio/briefs/<id>.md` and `<worktree>/studio/ci/reds/<id>/`, and the shipped template names the spec, its spec verdicts, the gate logs and the reds under `<WORKTREE>` and tells the reviewer its working directory is the main checkout.

Design. Two candidates were weighed; this opus takes (a), another working directory, with the main checkout as that directory:

- (a) moves one value in `reviewSteps`, a caller the shim already lets choose its working directory (`HarnessStartOpts.cwd`), keeps the reviewer reading the project's standing instructions (master's, which is the intended reading), and leaves every other Codex caller unchanged.
- (b) `-c project_doc_max_bytes=0` works (`probe-b.out`: no `AGENTS.md` loads in the worktree), but it goes in `CODEX_POLICY_FLAGS`, the one fixed policy every Codex caller shares and no caller may configure (W-044, W-049): `talk`'s Codex sellae would lose the project's instructions too, and the reviewer would lose master's. Rejected.
- The packet directory as the working directory was weighed and set aside: it lies under the main checkout, so Codex walks up to the same repository root and loads the same `AGENTS.md`, plus any `AGENTS.md` in the directories between, for no gain.

Cause fix: this closes W-315's stated `AGENTS.md` limit for the build-review perform. Every other path that runs a reviewer's Codex was checked (Limits): the spec-review and handoff-review paths already run outside the opus checkout, and one advisory kept script does not.

Threat model: mistakes, not adversaries (D-045). The main checkout is the orchestrator's; its working copy is read as it stands.

Bootstrap: this opus is reviewed under master's ladder, never its own (Patron 2026-10-18). Its build rounds run master's `reviewSteps` from the main checkout, which runs Codex in this opus's worktree, so its reviewer loads this branch's `AGENTS.md`; this opus does not edit `AGENTS.md`, and its edits leave the generated `AGENTS.md` unchanged (`instructions-proto.out`, revision 1's and revision 2's), so that file is master's at the branch point. Its round 1 is filled from master's `prompts/build-review.md` read from the main checkout (W-314), whose relative paths name files in the checkout master's code runs Codex in, so its sentences hold for it; its later rounds take master's `prompts/later-round.md`. Its spec rounds run from the kept scripts in the main checkout. The new working directory, text and stall line govern from the next opus; this opus's own health lines are master's.

**The stall (behaviours 3 and 4).** Today a dispatch order with no step marker prints `health: no step recorded` however long the agent has been silent: the step-health machinery (W-124, D-042) proves liveness only for a marker `next --perform` or `--track` wrote, and nobody tracks a dispatched agent (an architect, a spec reviewer, a builder, a censor dispatched rather than performed). After this opus, report-mode `next` on a dispatch order with no marker reads the files the agent writes, and when none has changed for more than `DISPATCH_SILENCE_SECONDS` (900, fifteen minutes) its health line reads `stalled (no step recorded; newest file <path> changed <n>s ago, past 900s)`. The first line, the order and the exit status stay as they are: the line is a notice for the orchestrator, never a claim about the agent and never a reason to perform or hold.

Decisions, each with its reason:

- **What dispatched means.** The ungated derivation carries a dispatch order (`deriveNext(f).order`, which `dispatch()` sets for the spec signature, a spec review, the reds, the build and a review), and the marker read is `none`. The ungated derivation, not the printed one, so an order held for its budget or its handover is checked too: the agent may still be at work while the orchestrator's re-run lacks `--budget`. A marker's own states (running, dead, stalled, unknown, finished, stale) are unchanged, and a rung that is not an order (the producer's and the Patron's) is never checked.
- **Which files count.** Every regular file, by its mtime, under `<repo>/.worktrees/<id>` and `<repo>/.worktrees/<id>-*` (the opus worktree, and the architect's scratch worktrees such as `.worktrees/W-316-amend`) and under `~/.bisellium-evidence/<id>` and `~/.bisellium-evidence/<id>-*` (the kept evidence: `<id>-spec`, `<id>-specreview`, `<id>-review/r<n>`, `<id>-build`), directories only, `node_modules` and `.git` skipped at every depth and no symlink followed. These are where the dispatches' own briefs tell agents to write (the dispatch model's item 3, `.claude/agents/builder.md`'s `cmd > X.log 2>&1`). The evidence root is outside the repository: a new read, its own Input domain row.
- **Heavy runs are not stalls.** A long test run redirected to a file writes its rows as they finish (`stream-probe.out`: a single-file `node --test` wrote its first row at 2 seconds of a 6-second run), and the longest row of `next.test.ts` takes 137 seconds of its 20-minute run (revision 1's `next-full-proto.out`), so a run whose output lands under a counted directory is never silent for fifteen minutes. A `bisellium run` (the isolated build) works in a disposable clone nobody can see; it holds the opus's producer lease `<repo>/.bisellium/leases/<id>/pid` for its whole length, and the host runner's own timeout (`HOST_RUN_TIMEOUT_MS`, 60 minutes, now exported from `builder-run.ts` and used by both) bounds that, so a lease no older than 3600 seconds is a run in flight (behaviour 4) and an older one is a killed run's residue.
- **Why not a pid.** Each sandboxed command has its own PID namespace on this host (measured: `/proc/1` is the sandbox's init and four pids are visible), so the pid in the vendor-sentinel lock or the lease, written by another command, proves nothing from `next`'s namespace. The vendor-sentinel lock is not read: its mtime is its start, a killed run leaves it, and the full `npm test` it guards streams its output like any run.
- **The threshold.** A constant, not a setting: fifteen minutes catches the 20-minute idle that prompted this fix by its fifteenth minute and sits above the measured longest silent row by a factor of six. A setting can follow when a studio needs another value (Defaults 6).
- **No counted file** (a spec order before the architect writes anything) keeps `no step recorded`: there is no time to measure from.
- **Cost.** One directory walk per report-mode `next` on a dispatch order: 14,759 files under W-316's eight roots in 112 ms (`walk-cost.out`).
