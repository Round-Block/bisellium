## Intent

Decree family: review-loop

The decree: **after a third counted failed build-review round, `next` holds for the Patron and recommends one more fix round or a re-spec. Each valid Patron ruling permits one more round; a re-spec never restarts the count. A round whose every standing blocker is marked `blocking (security)` is pre-approved and does not count (D-044). When the failed current round has any standing class blocker, the fix order says to fix the class with one check at the input boundary (L-069).**

This implements D-046 §2–3. W-162's measurement is reused, not repeated: 93 verb-written build-review logs, 55 failed; W-137, W-153, W-096 and W-163 would have stopped.

A failed round counts only from a strictly parsed verdict log whose outcome agrees with its standing findings. Converted blockers are advisory, as in retro. A mixed security/plain round counts. Every failed log stays in the count after a brief edit or a new spec signature.

At the cap `next` prints, through the existing renderer (`head:` sits after `why:` when a tip exists):

```text
next: <id> review held
actor: patron
why: <k> counted failed build-review rounds (<n>, <n>, <n>); a further round needs the Patron's OK (D-046)
recommendation: re-spec: ci/<id>-review-<n>.log finding <f> is a class, so the brief's boundary or promise is the problem
grant: Grant: one more build-review round for <id>.
attach: bisellium amend <id> --round-ruling <decision-id> --reason <text> --studio .worktrees/<id>/<studio>
```

With no class blocker in the newest counted failure the recommendation is `one more fix round: round <n>'s blockers are single instances`. The hold applies before any build (phase 2 or fix) or review dispatch, unless the recorded gate is passed at the current tree. Class detection, here and below, scans every standing blocker of the log and names the lowest-numbered one that matches.

A ruling is a decision by the manifest's `patron`, in the worktree studio's `decisions/`, dated strictly after the third counted failure's `# at`, whose body holds the exact standalone line `Grant: one more build-review round for <id>.`. Attached with `amend --round-ruling`, each distinct ruling adds one round.

When the current gate failed at the current tree and any standing blocker of its log contains the whole word `class` or `classes`, the fix order carries (`<f>` the lowest-numbered such blocker):

```text
boundary: ci/<id>-review-<n>.log finding <f> is a class: fix it with one check at the input boundary named by the brief's Input domain, which every path reads, not a patch at the cited site (L-069)
```

Threat model (D-045): mistakes, not adversaries. The tool cannot judge whether a finding is truly a class or truly security-only; those words are the censor's claim. It enforces their shape, counts conservatively and fails closed on malformed records. Timestamps order records; they do not prove external clocks.


`readBuildRounds` lists `<root>/ci` with `readdirSync` (any error, absence included, is an error: reds precede the build rung, so `ci/` exists there), keeps entries starting `<id>-review-`, requires each to be `<id>-review-<n>.log` with `n` positive and no leading zero, reads each through `readContainedRegularFile` with retro's 4 MB cap, and sorts by `n`. `parseBuildReviewLog` runs `parseVerdictLog`, then requires exactly one each of `phase`, `round`, `sella`, `outcome`, `at`, `tree`; `phase: build`; `round` equal to the filename's; `sella` equal to the censor; `at` passing `utcTimestampProblem`; an outcome matching `/^(?:verdict:\s*)?(pass(?:ed)?|fail(?:ed)?)\b/i` (the `reconcileFindings` spelling); no standing blocker when passed, at least one when failed. `securityOnly` tests each standing blocker's text against `/^\**blocking \(security\)/i`. The class test is `/\bclass(?:es)?\b/i`, applied to every standing blocker's text; the first match by finding number is named.

The current source tree is `f.curTree()`: `tree:<hex>` from `sourceTreeHash` over `refs/heads/opus/<id>` minus the officina and `source_excludes`. Today an uncomputable tree (`undefined`) silently reads as "not current" and re-dispatches review; under this opus `deriveNext` holds instead, before the cap or any build, review or PR order.

`readRoundRulings`: an absent `round_rulings` is no rulings. Otherwise, with fewer than three counted failures it is an error (nothing to postdate); else every id passes `patronDecisionProblem` with `by` the manifest patron, `grantLine` the exact line, and `after` the third counted failure's `at`.

## Out of scope

- W-162's signed-spec and spec-review gate.
- Performing a re-spec, resetting branches, a decision verb, a petitio or a new state.
- The other `review_probatio` readers (`check.ts`, `verify.ts`, `runReview`, `opus-model.ts`) keep their `"review"` default; only `next` and `amend` validate strictly here.

## Defaults for the Patron to veto

1. Three means three failed rounds that count, not three review attempts.
2. A round is exempt only if every standing blocker is marked `blocking (security)`; a forgotten marker stops the loop earlier, never later.
3. Each ruling grants one more round, not a lifted cap. Two rulings filed together grant two.
4. The grant is one exact sentence, so a decision that only mentions the opus grants nothing.
5. Rulings must postdate the third counted failure; none can be filed in advance of it.
6. The ruling's decision file must be in the opus worktree's studio (commit it on the branch, or rebase the branch after it lands on master), because `amend` and `next` both read the worktree.
7. A pass already recorded at the current tree proceeds even past the cap; the stop governs further fixes and reviews.
8. A branch-side change to a review key holds the opus until master carries the same value (land it there first, then rebase); this is what keeps the orders `next` prints and the evidence the verbs write naming the same censor and tree.
9. Class detection is the whole word `class` or `classes` in any standing blocker of the round, naming the lowest-numbered match; a false match only adds advice.
10. A UI build-review log without a strict `## Findings` section holds rather than counting as anything.
