## Intent

The console has four screens and a nav rail that reaches them, and **nothing walks
them**. `apps/web/test/*.test.ts` render components to static markup; `tests-serve/`
drives the built bundle but only for the write path (`answer`, `auth`, `seats`), the
board's own keyboard/SSE behaviour and computed layout. No test clicks the rail from
end to end, and no test asserts that a screen shows the officina it is serving. The
consequence, measured below: the **Officina screen fetches no acta at all**, so its
fasti strip has been permanently blank in every served console since W-025 shipped,
and nobody noticed because nothing looks.

This opus implements exactly three things.

1. **The rail is walked.** One served-dist spec clicks every rail entry in order and
   asserts the hash, the mounted screen, the active mark, Back/Forward, a reload on
   each route, no uncaught page error and no 4xx/5xx from the served origin. The rail's
   entry list stops being hand-copied in three places (`Sidebar.tsx`, `route.ts`,
   `test/sidebar.test.ts`) and becomes one `NAV_ENTRIES` table in `apps/web/src/lib/nav.ts`
   that the router derives its map from — so "every screen the rail lists" is a value the
   walk can read, not a list a test re-types. The active entry gains `aria-current="page"`
   (it has none today: an accessibility defect, not a visual change).
2. **Each screen is checked for content.** The same spec asserts, per screen, anchors
   that can only come from the served officina: the fixture's petitio and its opus id on
   Inbox; the seven lifecycle columns and the card-id set from `GET /api/opera` on Board;
   a model select per declared seat, valued from the manifest, on Seats; the three panel
   headings, a posture card per collegium with an allowance in the current period, the
   integrity table's own count from `GET /api/health`, and a **filled fasti tick** on
   Officina. The last of those is red today and is the one product defect this opus fixes:
   `Officina.tsx` never calls `fetchActa`.
3. **A `kind: ui` opus cannot reach review without screenshots.** The reserved
   `served-e2e` gate already carries a log, a timestamp and a SOURCE certificate
   (W-096). It now also carries a **screenshot manifest**: the walk writes one PNG per
   rail entry into the officina's own bookkeeping at `<studio>/ci/shots/<opus>/`,
   `scripts/served-e2e.mjs` writes `manifest.txt` beside them in that same per-run
   cleared directory, and `validateServed` reads the manifest file and re-reads every
   named PNG, refusing the gate unless the files on disk agree with it. The manifest is
   a **file, not a log line**: `localPipeline` records only the last 200 lines of
   `stdout ++ stderr` (stderr last), so anything that depended on where a gate command
   printed would be one noisy subprocess away from unprovable. The gate command learns
   which opus and which officina it is running for from two environment variables that
   `verify` scopes to this one gate — the one seam this opus changes, for the documented
   reason that a gate command otherwise has no way to name the opus its artifacts
   belong to.

**A fourth thing is closed because it makes the other three vacuous.** Nothing in the
served path ever builds: `apps/web/package.json:11` is bare `playwright test
--config=playwright.serve.config.ts`, and the config declares no `globalSetup`, so a
served run drives whatever `apps/web/dist` happens to hold — a bundle from any earlier
commit, or none at all (retrospectio 35, L-047; `apps/server/src/http.ts:510-512` falls
back to a plain API index when `dist/index.html` is absent). The build moves into the
served config's `globalSetup`, so **every** entry point into
`playwright.serve.config.ts` builds first — a bare `playwright test --config=…` as much
as the gate — and `served-e2e.mjs` stops building separately. (The dist on any given
checkout is as old as the last build anyone happened to run, which is why the defect is
stated as the missing step and not as a date: a probe that builds repairs the symptom
and leaves the cause.)

Nothing else. W-115 and later queue items are out of scope; so is every visual design
decision (the Patron's).

### The gate command learns who it runs for — for one gate only

`PipelineRunOpts` gains one optional field:

```ts
/** Extra environment per probatio id, merged over the filtered env for that
 *  command only. A gate that is not named here sees exactly today's env. */
commandEnv?: Readonly<Record<string, Readonly<Record<string, string>>>>;
```

`localPipeline` keeps computing `filterEnv(process.env)` once, and **inside** the loop
spreads `opts.commandEnv?.[probatioId]` over a copy for that command alone:

```ts
const base = filterEnv(process.env);
// … per command:
const extra = opts.commandEnv?.[probatioId];
const env = extra === undefined ? base : { ...base, ...extra };
```

`verify` populates it with exactly one entry, keyed by the reserved gate id it already
owns (`SERVED_E2E_PROBATIO`, a new `const` export beside `effectiveProbationes`, which
holds the `"served-e2e"` literal at `opus-model.ts:298` today):

```ts
commandEnv: { [SERVED_E2E_PROBATIO]: { BISELLIUM_OPUS: opus.id, BISELLIUM_STUDIO_DIR: resolve(studioDir) } }
```

**Why scoped rather than global.** Revision 1 put the two names in the one env object
`localPipeline` builds above its loop, which would have handed them to **every**
automated probatio a manifest declares — `tests`, `lint`, `types` and anything an
adopter adds — and `--studio <dir>` accepts a path outside the repo (the codebase
supports that shape; `packages/commands/src/lifecycle.ts:838-841` branches on
`rootInside` precisely for it), so for such an adopter an out-of-repo absolute path
would be disclosed to every gate command. The keyed field costs one optional parameter
and three lines and discloses nothing to any command that does not need it. It also
keeps the dependency graph still: `@bisellium/pipeline` learns no gate id and gains no
import; `@bisellium/commands`, which already owns the reserved id, supplies it.

Values are set **after** the filter, so a parent value can never win, and the studio
path is absolute. Neither name is credential-shaped, so `filterEnv` would not have
dropped them; setting them after is the guarantee, not a workaround. The parent's
`process.env` is never mutated. Everything else about `localPipeline` — the log text,
`certifies`, the evidence path, the `status` mapping, the timeout, `maxBuffer`,
`redact`, `filterEnv` — is byte-for-byte unchanged, and a `MergePipeline`
implementation that ignores `commandEnv` stays valid.

**This is the one seam this opus changes** (beside the additive `maxBytes` option
below). The documented reason: a gate command runs with `cwd` = the repo and no argument
of its own, so it cannot name the opus whose evidence it is producing. Without that it
cannot write per-opus artifacts, and per-opus artifacts are the whole requirement.
`docs/ADOPTION.md:62-76` (the allowlist paragraph) and `docs/ARCHITECTURE.md:117-126`
(the `opus-model.ts` policy seam paragraph) record it in the same cascade.

### The gate command produces the shots (`scripts/served-e2e.mjs`)

Still exactly `node scripts/served-e2e.mjs`, the reserved command string
(`effectiveProbationes`, `opus.ui.e2e`): **unchanged**, so nothing about the manifest
contract moves. Its internals become:

1. `opus = process.env.BISELLIUM_OPUS`, `studio = process.env.BISELLIUM_STUDIO_DIR`.
   When both are set, `opus` matches `^[A-Za-z0-9][A-Za-z0-9._-]{0,21}$` (22 characters;
   see the cap below) and `studio` is absolute: `shotsRel = "ci/shots/" + opus`,
   `shotsDir = join(studio, shotsRel)`. Otherwise `shotsRel` is `undefined` and
   `shotsDir = <repo>/apps/web/test-results/shots` (gitignored — a bare manual run makes
   no evidence claim).
2. `rmSync(shotsDir, { recursive: true, force: true })` then `mkdirSync(shotsDir, {
   recursive: true })`. A PNG or a manifest from a previous run can never be passed off
   as this run's.
3. One `npm --workspace @bisellium/web run test:serve`, `shell: false`, `stdio:
   "inherit"` (unchanged: the walk's own diagnostics keep streaming), `env: {
   ...process.env, BISELLIUM_SHOTS_DIR: shotsDir }`. **No separate build** — the served
   config's `globalSetup` owns that now.
4. After the child settles, the `*.png` entries of `shotsDir` are listed, sorted by
   name (`manifest.txt` is not a `*.png` and is never listed); each one's byte length
   and its IHDR width and height are read (PNG signature `89 50 4e 47 0d 0a 1a 0a`,
   then `readUInt32BE(16)` and `readUInt32BE(20)`). A name that does not match
   `^[a-z][a-z0-9-]{0,21}\.png$`, or a count over 64, is a failure (exit nonzero, no
   manifest written).
5. With `shotsRel` undefined: print the one line `shots: none`, write no file, exit
   with the child's code. With `shotsRel` set and the list empty: exit with the child's
   code if nonzero, else `1` — a green walk that produced no screenshot is a failure.
   Otherwise build the manifest text

   ```
   shots: <n> <shotsRel>
   shot: <name>.png <width>x<height> <bytes>
   ```

   one `shot:` line per file in name order, **write it to `<shotsDir>/manifest.txt`**,
   echo the same text to stdout, and exit with the child's code.

**The manifest is a file, and the file is what the rule reads.** Revision 1 made the
gate log the manifest's home and claimed "the last lines of the run … so the pipeline's
200-line tail always keeps it whole". That claim was false about the mechanism:
`packages/pipeline/src/index.ts:89,97` tails `${r.stdout}${r.stderr}` — the two streams
concatenated with **stderr last** — so a gate command's stdout is never the log's tail,
and 200 lines of stderr from anywhere in the subtree (npm, vite, playwright, a warning)
evict it entirely. Today's headroom happens to be comfortable, which is exactly why it
is the wrong thing to build an evidence chain on: it degrades silently as specs are
added. `ci/shots/<opus>/manifest.txt` has no such property to lose. It is read through
the containment helper like every other piece of `ci/` evidence, it lives in the
directory step 2 clears on every run, and the gate's own `certifies`, `at` and
`exit code: 0` — all already validated against the log — are what bind it to the run.
The stdout echo is kept for a human reading the gate log and for behaviour 5; **nothing
in the rule depends on it.**

**The 22-character cap is the measured `redact` boundary**, and it applies to the
stdout echo rather than to the file (`redact` never touches the file). Measured:
`ci/shots/` is 9 characters, every one of them inside `redact`'s
`[A-Za-z0-9+/_-]{32,}` class, so an opus id of 23 makes the header `shots: 2 ********`,
and a shot name of 32 makes the line `shot: ********.png …`. Capping both the name and
the id at 22 makes the longest run a legal line can contain **31** — one short of the
threshold — structurally rather than incidentally. For the same reason the per-shot
lines carry a **bare file name**, not a path, and no hash at all: a 64-hex digest would
be masked to `********`. Integrity is established by re-reading the file (below), which
is stronger than a digest the same process printed.

### The check rule (`packages/commands/src/opus-model.ts`, `validateServed`)

No new rule id and no new wire name: the screenshot manifest is part of the
`served-e2e` gate's evidence contract, so every problem is reported under the existing
**`opus.ui.e2e`**, through the existing `addPolicyProblem`, under the existing
`needsServed` trigger (`phase`/`state` `review` or `done`). A `kind: ui` opus in
`building` is unaffected; a non-`ui` opus is unaffected; no existing record changes
validity (no record anywhere is `kind: ui`).

`readContainedRegularFile` gains one **optional, additive** parameter,
`maxBytes?: number`, checked against the `fstat` it already performs on the open fd
(`opus-model.ts:228`) before `readFileSync(fd)`: over the cap it answers
`{ error: "target exceeds <maxBytes> bytes" }`. Post-open, so it cannot be raced; every
existing caller passes nothing and is untouched. `validateServed` runs inside
`checkStudio` — on every `check`, `tick`, `verify` and `/api/health` — so it is the one
caller that must not read an unbounded file, and nothing else in the repo currently
bounds it. For the same reason `validateServed`'s **own existing gate-log read**
(`opus-model.ts:675`) takes `LOG_MAX_BYTES` (1 MiB): it sits in the same function on the
same always-on path, existing fixtures are a few hundred bytes, and a 2 GiB
`ci/served.log` is the hazard this opus just closed for PNGs. The other eight uncapped
call sites (`:583`, `:598`, `:621`, `:637`, `:696`, `:727`, `:890`, `:939`) are filed as
a follow-on, not widened into here.

Five named constants beside the existing ones: `SHOT_MIN_WIDTH` 800,
`SHOT_MIN_HEIGHT` 600, **`SHOT_MAX_ENTRIES` 64**, **`SHOT_MAX_BYTES` 4 MiB** (per PNG),
**`MANIFEST_MAX_BYTES` 8 KiB** (which 64 legal entries cannot exceed — about 2.6 KiB at
the 22-character caps), plus `LOG_MAX_BYTES` 1 MiB above.

**No finding message interpolates the helper's error string.** `readContainedRegularFile`
answers two distinguishable kinds of failure, measured on the real helper:

| Failure | `code` | `error` |
| --- | --- | --- |
| the file is absent | `"ENOENT"` | `ENOENT: no such file or directory, lstat '/tmp/claude-1000/w110-err-uQrwpl/ci/shots/W-110/board.png'` — **an absolute path** |
| the helper's own refusal (symlink, escape, not a regular file, over `maxBytes`) | `undefined` | today, one of seven fixed strings with no path in any of them: `path must be a nonempty officina-relative string`, `path must remain under ci/`, `path reaches its target through a symlink`, `real parent escapes ci/`, `real target escapes ci/`, `target is not a regular file`, `target exceeds <n> bytes`. Passed through under a shape guard, not because the set is assumed closed (below). |
| any other fs error | `"EACCES"`, `"ELOOP"`, `"EISDIR"`, … | the thrown exception's message, which may carry a path |

So the two new sites switch on `code`, never on `error`: `code === "ENOENT"` gives a
fixed "missing" wording; `code === undefined` passes the `error` through **only if it
matches `^[\x20-\x7e]{1,80}$` and does not match `/\/[\w.-]+\//`, and otherwise reports
the bare word `refused`**; any other `code` reports **the bare code** and nothing else.
That shape guard rather than an enumerated allowlist of the seven strings: the set is
fixed *today* but it lives in another function, and a future refusal that embedded a
path would leak through a list that was merely inferred to be closed. Validating the
shape cannot drift, and it is the same move as the `redact` cap — make the property
structural instead of incidental. Revision 2 wrote `is unsafe or unreadable: ${error}` at both sites "exactly
as the existing log path does" — and that precedent (`opus-model.ts:583, 598, 621, 637,
675, 696, 727, 890, 939`, nine sites) is itself leaky, so these two are a deliberate
improvement on it rather than a deviation. Closing the other nine is the follow-on; this
opus does not change `:675`'s message even though it caps its read, because an
assertion somewhere may pin that wording and the cap is additive on its own.

**Clause ladder — this is the ordering every finding count in behaviours 6 and 7 is
counted against.** The steps run in this order and **each step stops the whole manifest
clause as soon as it yields a problem**, except step 4, which visits every entry:

1. `readContainedRegularFile(root, "ci/shots/" + record.id + "/manifest.txt", "ci",
   MANIFEST_MAX_BYTES)`. An id longer than 22 characters →
   `served-e2e screenshot manifest needs an opus id of at most 22 characters` (checked
   first, so no path is built from an over-long id). Then, **switching on `code`, never
   on `error`**: `code === "ENOENT"` →
   `served-e2e evidence carries no screenshot manifest`; `code === undefined` (one of
   the helper's own refusals) →
   `served-e2e screenshot manifest is unsafe or unreadable: <that refusal, under the
   shape guard above>`; any other
   `code` → `served-e2e screenshot manifest is unsafe or unreadable: <the bare code>`.
   The latter two match `/unsafe|unreadable|symlink|regular file/i`, so
   `addPolicyProblem` raises `opus.reference` beside `opus.ui.e2e` for them — two
   findings, deliberately, because a containment refusal is a reference problem as well
   as a gate problem. **One problem, stop.**
2. the header, `^shots: (\d+) (ci\/shots\/[A-Za-z0-9][A-Za-z0-9._-]{0,21})$`
   (multiline). Absent → `served-e2e screenshot manifest has no header`. Present but
   its directory is not `ci/shots/<record.id>` →
   `served-e2e screenshot manifest names another opus's directory`. **One problem,
   stop** — a manifest that points elsewhere is not evidence about this opus, so no
   entry is read.
3. the entries, `^shot: ([a-z][a-z0-9-]{0,21}\.png) (\d+)x(\d+) (\d+)$` (multiline,
   global), checked in exactly this sub-order, the **first** failure yielding its one
   problem and stopping:
   (i) the count of lines merely **starting** `^shot: ` differs from the number of
   strict matches → `served-e2e screenshot manifest has a malformed entry`;
   (ii) the strict count is 0, or differs from the header's `\d+` →
   `served-e2e screenshot manifest count disagrees with its entries`;
   (iii) the strict count exceeds `SHOT_MAX_ENTRIES` →
   `served-e2e screenshot manifest declares more than 64 screenshots`;
   (iv) a file name appears twice →
   `served-e2e screenshot manifest repeats a file name`.
   The sub-order is what makes a malformed entry report *only* "malformed entry": a
   mangled name is also one strict match short, so (ii) would otherwise fire on the
   same mutation.
4. per entry, in name order, `readContainedRegularFile(root, `${dir}/${name}`, "ci",
   SHOT_MAX_BYTES)`. **Each entry contributes at most one problem** — the first of
   these clauses that fails for it — and the loop visits every entry. On the same
   `code` switch as step 1: `code === "ENOENT"` →
   `served-e2e screenshot <name> is missing` (one finding: the wording deliberately
   carries none of `/unsafe|unreadable|symlink|regular file/i`, because a deleted file
   is a gate problem and not a containment event);
   `code === undefined` → `served-e2e screenshot <name> is unsafe or unreadable: <that
   refusal, under the same shape guard>`, which is where an over-cap file lands, with the helper's own
   `target exceeds <n> bytes`; any other `code` →
   `served-e2e screenshot <name> is unsafe or unreadable: <the bare code>`. Then, for a
   file that was read: no PNG signature →
   `served-e2e screenshot <name> is not a PNG`; `readUInt32BE(16)`,
   `readUInt32BE(20)` or `bytes.length` not equal to the line's three numbers →
   `served-e2e screenshot <name> does not match its recorded size`;
   `width < SHOT_MIN_WIDTH || height < SHOT_MIN_HEIGHT` →
   `served-e2e screenshot <name> is smaller than 800x600`.

So a manifest with one broken entry out of four yields one problem; a manifest that
names another opus yields one, not one per entry; and a count mismatch yields one, not
one per entry plus the mismatch. The gate log's own existing clauses (`certifies`,
`command`, `exit code: 0`, `status`, `at`) are evaluated as today, before step 1, and
are **not** short-circuited by it.

Every message the two new sites produce is ASCII, at most **160** characters, and
carries nothing but a regex-bound file name, a decimal number, one of the helper's seven
fixed refusal strings, or a bare `errno` code: **no absolute path, no screenshot byte and
no raw manifest text ever reaches a finding** — which revision 2's
`is unsafe or unreadable: ${error}` did not achieve, since a real `ENOENT` message is
159 characters of `/tmp/claude-1000/…` and would have been produced by behaviour 7's own
Genuine red. The rule never trusts the manifest's own numbers — it re-derives all three
from the file on disk — which is why the script may write them without a digest.

## Stated residuals (accepted, with reason)

1. **Completeness of the screenshot set is enforced by the walk, not by the rule.**
   `check` cannot know what screens exist; it verifies that every file the manifest
   names is a real, large-enough PNG at the right path, and that there is at least one.
   The "one per rail entry" guarantee comes from behaviour 3(f) and from the gate being
   `passed` — exactly how the `tests` gate guarantees the suite ran.
2. **The PNG header is read in two places.** `scripts/served-e2e.mjs` is plain `.mjs`
   run by bare `node` and cannot import the TypeScript rule. The duplication is
   deliberate rather than DRY debt: the rule does not trust the script's numbers, it
   re-derives them, so the second copy is an independent check. Bridging it would mean
   a new JS package or a tsx dependency on the gate command.
3. **A `kind: ui` record is required to be at `review`/`done` before shots are
   demanded.** A ui opus in `building` can have none. That is W-096's existing
   `needsServed` trigger, not a new choice.
4. **All the bounds are constants**, not options: 800×600 so a 1×1
   placeholder cannot satisfy the gate (the walk's viewport is 1280×900), 64 entries and
   4 MiB per PNG so the one always-on read loop this opus adds to `checkStudio` is
   bounded, 8 KiB for the manifest and 1 MiB for `validateServed`'s own gate log. A
   console with more than 64 screens, or a screenshot over 4 MiB, needs the constants
   raised deliberately; the refusal says which bound it hit.
5. **The manifest carries no digest** because `redact` masks any 32-character run in the
   stdout echo. Integrity rests on the rule re-reading each file, which a digest written
   by the same process would not have added to.
6. **The manifest file carries no certificate of its own.** It is bound to the run by
   living in the directory the run clears on every invocation, and by the gate's
   `certifies`, `at` and `exit code: 0`, which are validated against the log as today.
   A hand-written `manifest.txt` with hand-made PNGs would pass — exactly as a
   hand-written `ci/*.log` would, which is the trust level every gate's evidence already
   has. No new hole; adding one would mean a third environment variable carrying the
   certificate into the script.
   **And: `ci/shots/<opus>/` is the only `ci/` artifact that is not tree-keyed.** Every
   gate log is `<opus>-<probatio>-<tree8>.log` (`packages/pipeline/src/index.ts:99`), so
   two verifies on two trees leave two files and the record's `evidence:` points at the
   right one. The shots directory is a fixed path that step 2 clears, so a re-verify or
   a rebase **silently replaces committed evidence** and nothing on disk says which tree
   a PNG belongs to. That matters because residual 16 has the operator committing the
   directory: the screenshots in a merge commit are the last run's, not necessarily the
   run whose log sits beside them. Keying the directory by `tree8` would fix it and is
   not done here — the gate's `certifies` already names the tree the *run* covered, and
   accumulating a directory per tree needs a retention rule this opus does not want to
   invent.
7. **The two environment variables reach the reserved `served-e2e` gate only**, through
   `PipelineRunOpts.commandEnv`. For that one command the studio's absolute path is
   disclosed — including when `--studio` points outside the repo, the shape
   `lifecycle.ts:838-841` supports — which is the minimum the requirement needs, and no
   other probatio command (an adopter's `tests`, `lint` or anything else) sees either
   name. Revision 1's global env would have disclosed it to all of them.
8. **An opus id longer than 22 characters cannot carry screenshots.** The cap is the
   measured `redact` boundary (`ci/shots/` is 9 characters, so 23 reaches 32). Every id
   in either officina today is 5 characters; a longer one is refused at review with a
   message naming the limit rather than silently producing a masked manifest.
9. **The gate log no longer needs to hold the manifest**, which means the log's own tail
   behaviour (last 200 lines of `stdout ++ stderr`, stderr last) remains exactly as
   quirky as it is today. This opus does not fix that; it stops depending on it.
   `scripts/served-e2e.mjs` still echoes the manifest to stdout, so a human reading a
   gate log usually sees it — *usually* being the honest word, and the reason nothing in
   the rule reads it.
10. **`/api/aerarium` still answers `[]` for a period with no allowance file**, so the
    System status panel is empty until someone writes it (and `/api/health` says so).
    Behaviour 3 seeds the period rather than changing the route: the empty panel is the
    officina's honest answer, and changing it is a Patron call.
11. **The fasti assertion tolerates a UTC midnight straddle.** The spec seeds an actum
    at "now" and the browser computes "today" a moment later; the row asserts exactly one
    filled tick at column index ≥ 12 rather than exactly 13, so a sub-second day flip
    cannot flake it.
12. **The console still loads Google Fonts from a third party.** Measured 407 behind a
    proxy. The walk ignores non-served-origin traffic for that reason; removing the
    dependency is typography and is filed below.
13. **`apps/web/test/`, `apps/web/tests-serve/` and `playwright.serve.config.ts` are
    still not typechecked, and `packages/`/`apps/` are not format-checked.** `eslint .`
    covers all of them; `.prettierignore` excludes `packages/`, `apps/`, `adapters/` and
    `studio/`, so among the new files only `scripts/served-e2e.test.mjs` is
    format-checked. Widening either would surface churn across the whole tree; filed below.
14. **The `web-e2e` job builds twice.** Redundant after `globalSetup`, kept so the
    workflow file and `scripts/ci-workflow.test.mjs` do not churn.
15. **The Officina screen still discards `GET /api/officina`.** Fixing it needs new
    visible copy; filed below.
16. **The walk's shots are evidence only once committed.** `verify` writes them under
    `<studio>/ci/shots/<opus>/`; the operator commits them with the gate record, as
    `ci/*.log` already are. An uncommitted shot is a local artifact, and the SOURCE
    certificate is unaffected either way (the studio dir is excluded from the hash).
