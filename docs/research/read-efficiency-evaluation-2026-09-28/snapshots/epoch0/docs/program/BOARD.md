# Epoch 0 — Program Board

The unified task board. Every task, backlog item, review finding, and
design follow-up the program is tracking lives here, in ONE table, with
ONE state vocabulary — not scattered across `tasks.md`, `PROGRAM.md`'s
"Absorbed Backlog", and `DECISIONS.md` prose. Process authority for how
this board is used: `docs/program/WORKFLOW.md` ("Controller — board
grooming"). Milestones/gates/strategy: `docs/program/PROGRAM.md`.

## States

BOARD.md stores DURABLE states only: `reported` (raised, not yet
triaged) → `validated` (confirmed real, reproduced or verified —
includes "note for the record" rows with no action needed) →
`backlogged` (real, scheduled for a future milestone/train, not in
flight) → `scheduled` (next up, explicitly queued — including a row a
train has actually picked up and is actively working) → `done`
(shipped, verified — true on master because the merge that made it true
already landed) or `rejected` (investigated, not real / not worth
doing, reason on the row).

**"in-train" is NEVER a stored state.** It is DERIVED live from
`git worktree list` + `gh pr list` — `scripts/train_status.sh` computes
it on demand (falling back to "worktrees only" when `gh` is
unavailable), and `.claude/hooks/journal-context.sh` surfaces it the
same way at session start. A row a train has picked up stays
`scheduled` in storage; `start_train.sh --board-id <ID>` annotates it
("started `<date>`, see worktree") rather than changing its state —
the annotation is a hint for humans/tools, not the source of truth for
whether work is live (a stale annotation naming a dead worktree is a
grooming finding, not evidence of anything). This design exists because
a STORED in-train state and a git worktree can silently diverge (sol's
2026-08-29 task review of this exact train, D3/D6/D7, caught exactly
that: a stored `in-train` row can claim liveness a worktree no longer
backs, or claim `done` before a merge has actually happened) — deriving
it removes the divergence by construction.

## Priority

`P0` launch-blocking · `P1` current-milestone-blocking · `P2` real,
scheduled, not urgent · `P3` deferred / nice-to-have / post-launch.

## Grooming

The Controller grooms this board after every QA triage and at milestone
planning (`WORKFLOW.md` §Controller). Grooming = re-state rows whose
evidence has changed (a "backlogged" row a later train actually fixed
moves to `done`; a stale row gets a note, not silent deletion), fold new
QA/tester findings in, and check `scheduled` rows' "started..."
annotations against `scripts/train_status.sh`'s live view — a
stale annotation naming a dead worktree gets a note, not a silent
demotion (see WORKFLOW.md §5 Escalation, crash recovery).
`scripts/check_process.py` enforces the mechanical half: no row EVER
stores `in-train` (fails the gate if one does), and a `done` row must
be reachable on master or the current branch.

**PB-number allocation (owner-verified Controller convention, 2026-09-11):**
new rows take their `PB-*` number from Controller allocation, not from a
builder's own scan of "the highest number I can see" — a three-collision
day (`feature/pre-review-check-v2`, `feature/char-spike-2`,
`feature/portrait-rep-1` each independently scanning open branches and
landing on overlapping numbers) is the citation. Ask the Controller for
the next number before filing a new row from inside a train's own worktree.

**P-milestone tags (2026-09-11 groom, `docs/program/PRODUCT.md`):** every
`Scheduled`/`Backlogged` row's Title now carries a `[P1]`-`[P5]` / `[PROC]`
/ `[PARK]` bracket tag naming the P-milestone it advances (`PROC` = process/
tooling debt with a stated product-velocity justification; `PARK` =
genuinely untraceable to the current ladder, e.g. explicitly owner-deferred
work or store/payments scope this program's finish line excludes). Applied
mechanically in one pass — treat a `PARK` or a tag that reads wrong on a
specific row as a grooming finding, not settled law; re-tag as understanding
of a row improves. New rows should carry their own tag at filing time going
forward, same as the state/priority columns.
